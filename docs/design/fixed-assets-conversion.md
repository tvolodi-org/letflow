### 1.3 Commissioning, version 2 (`assets_commission_v2`; change, handover, write-off have the same shape)

```
start -> check (module_call assets.check_posting) -> ok_gate
ok_gate --[variables.postable == true]--> post (HUMAN_TASK, role TENANT_ADMIN, required_permission AssetsApprove,
                                                form assets.document_review readonly)
ok_gate --(default)--> end_refused
post -> commit (module_call assets.post_document) -> end
```

- The human task keeps the node id `post`, so the read side (`posting.ex:58`, `:572-613`) needs only the new names.
- `module_call` runs in the transaction that completes `post` (T-2843 section 3.2), so the approver keeps today's
  immediate 409/422 and nothing is half posted.
- What stays code: posting rules, card moves (`documents/card_moves.ex`), numbering, the 96-hour/period rules,
  print forms (`form_da1..4.ex`), the issue and reverse routes as the only start paths.

### 1.4 Opening, version 2 (`assets_opening_v2`): four eyes as a gateway on the tenant parameter

```
start -> submit (HUMAN_TASK, role ASSETS_OPENING_SUBMIT, completed by the issuer at issue, posting.ex:189-213)
      -> check (module_call assets.check_posting) -> ok_gate (default -> end_refused)
      -> eyes (module_call approval.four_eyes_required, rule const "assets_opening/approve")
      -> eyes_gate
eyes_gate --[variables.four_eyes == true]--> approve (HUMAN_TASK, AssetsApprove, distinct_from ["submit"])
                                             -> commit (module_call assets.post_document) -> end
eyes_gate --(default)--> self (module_call approval.record_self_approval) -> commit -> end
```

- The parameter is read at the gateway, in the transaction that completes `submit` (= the issue request), with the
  caller's credential; non-`:oidc` callers always take the ON branch; read failures answer `true` (T-2843 2.3).
- `approve` keeps `distinct_from`, so `SeparationOfDuties` keeps its live read for an approval that waits when the
  setting changes (owner rule "live", `four-eyes-switch.md:38`).
- **Setting key.** The rule row is keyed by `(definition_name, node_id)` and read through the instance's own snapshot
  name (`approval_rule_setting.ex:159-171`). A new name `assets_opening_v2` would start from the tenant default. So
  the switch-ON action (section 2.4) copies the tenant's `(assets_opening, approve)` row to
  `(assets_opening_v2, approve)` with an `approval_rule.changed` audit and the reason "assets process v2 switch",
  and the function reads the same row through its const `rule`. Activation fence and its run-time twin as T-2843 2.3:
  a version whose `assets.post_document` is reachable without an AssetsApprove task or the gateway is refused.

### 1.5 Composite: acquisition with commissioning (`assets_acquisition`, new, ships in the assets pack)

The T-2843 section 9 shape, applied to the PM's 13:55 decision:

```
start -> request (HUMAN_TASK, AssetsPost: what, why, cost centre)
      -> decide (HUMAN_TASK, AssetsApprove, distinct_from ["request"])
      -> receive (HUMAN_TASK, storekeeper with AssetsPost: supplier, invoice, inventory number, org unit,
                  material responsible; completer_inputs = exactly these fields)
      -> make_doc (module_call assets.prepare_commission: outputs document_id, version_no)
      -> commission (SUB_PROCESS definition_name assets_commission_v2,
                     interface inputs document_id, version_no (required), outputs [])
      -> end
```

- `:420` passes (same `owner_module`). `:448` does not apply (no platform call in either).
- The T-2846 gaps apply here unchanged and are prerequisites: **G-SUB-1** (module-only start transitive; the parent's
  own graph has a `module_call`, so with T-2843 P3 it is module-only by itself, belt and braces), **G-SUB-2** (refused
  keys include the children's write-read keys: the `receive` completer must not be able to send `document_id`),
  **G-SUB-5** (lazy activation of parent and child together, the name list of `ensure_active`), **G-SUB-6** (a
  document cancel cancels from the top parent). G-SUB-3 (rename) does not arise: one child. G-SUB-4's assets twin is
  `assets.prepare_commission`: the document's content comes from a person (the receiver), which is acceptable
  because the same person may create that draft on the document screen with AssetsPost; the TARGET (the document id)
  is created by the body and bound to this instance, never taken from a variable.
- **Start.** Who starts an acquisition is open: there is no assets route for a "request" today (owner question Q6).
  The design assumes a new assets route `POST /modules/assets/acquisitions` (AssetsPost) that starts it with
  `module_start: true`; it must be added to the `[sensitive]` list in the same task.
- Four eyes do not cross the instance boundary (`distinct_from` is per instance): `decide` in the parent and `post`
  in the child are never compared. Q7.

### 2.4 The tenant switch (deviation from T-2843 section 4, with the reason)

T-2843 ships `2.0.0` of the SAME process key and deprecates `1.0.0`. For assets that cannot be a switch:
`EnsureSeeds` step 5 (`ensure_seeds.ex:15-24`) activates a new pristine draft of an unmodified module definition by
the system actor at upgrade, which deprecates `1.0.0` on every tenant the moment it is upgraded; and switching back
by version rollback produces an UNSTAMPED copy whose handler lines are refused (`module_writes.ex:17-34`). So:

- v2 ships under **new names**, `<key>_v2` (`assets_commission_v2`, ... `assets_opening_v2`, plus
  `assets_acquisition`). v1 rows stay active and stamped. `EnsureSeeds` may activate the v2 rows (no row of the name
  was ever activated): harmless, because only the start code chooses a name, and the public start is refused for both.
- The switch is a module setting `process_v2` (boolean, default `false`) in the assets settings record
  (`lib/letflow/modules/assets/settings.ex`, beside `count_enabled?` `:76-77`), written by a TENANT_ADMIN with
  `ModulesManage` and audited. New feature flag, default off (domain rule).
- `Kinds` gains `definition_v2` per kind; `start_post/4` and `start_reversal/5` pick the name from the setting at
  start; `definition_names/0` and `pending/2` read both names; `ensure_active/3` handles both.
- Switch ON copies the four-eyes row (1.4). Switch OFF is safe at any time: only new starts change; v2 instances
  in flight finish on v2.

## 3. Running instances of the old shape

T-2843 section 4 ("drain, do not rewrite") holds, with the separate names making it simpler:

- An instance runs its own snapshot (`InstanceDefinitionSnapshot`); a v1 instance finishes on v1 whatever the switch
  says. The v1 handlers (`handlers.ex`, with T-2432's `check_instance`) and the `module_writes` runtime stay until a
  count of open v1 assets instances reads zero on every tenant AND every tenant is ON (Q3).
- A document issued under OFF and not yet posted stays on its v1 instance after ON; the post-retry/new attempt of
  the same version id continues v1 (`instance_count/3` is per name, `posting.ex:346-356`; the start chooses the name
  of the document's EXISTING instance if one is open, else the switch). A cancel withdraws either.
- No open document is lost: the mark is unique per kind, so a document can never be posted once by v1 and once by v2.
- QA: `project/scripts/qa_tenant_upgrade.py` (team repo) gains "open v1 assets instances per tenant" (operator
  check after the deploy that ships A1).
