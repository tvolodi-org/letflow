## 0. Plain summary

- Today a module process is a wrapper. Its definition is `START -> one HUMAN_TASK -> END`. The human task has a
  `module_writes` line, and that line calls the module's handler when the task is completed. Everything the
  user thinks of as "the process" is in code: the order of steps, the posting, the binding checks and the
  four-eyes switch. A tenant cannot change any of it. If a tenant edits the definition, the copy loses its
  module stamp and the handler lines are refused.
- The pilot shows the target. The definition is a chain of steps, each one a function from a compiled
  catalogue. The function declares its inputs, outputs, permission, idempotency key and side effects. The
  definition decides the order. A runner scenario proves that a reordered, removed or added step runs exactly
  as the definition says.
- For modules this means: (1) a **module family** in the catalogue, derived from the `WriteHandlerSpec`s that
  modules already compile; (2) a new step kind `module_call` that runs **inside the engine transaction**, so the
  approver still gets the same immediate 409/422 as today; (3) authority from the catalogue permission and the
  signed activator, not from the module stamp, so a tenant may edit the definition; (4) four eyes as an
  exclusive gateway on a catalogue read of the tenant setting; (5) old instances finish on their pinned
  snapshot.
- Cost: about 7 platform tasks (about 45 points), then 18 conversions (about 70 points), then about 8 new
  processes (about 85 points). The first two conversions are asset opening and stock opening.

### 1.2 Decision: one catalogue, a module family derived from `WriteHandlerSpec`

A module function becomes an `Entry` with `family: "<module id>"`. Modules do not get a second, hand-written
list. The entry is derived at compile time from the module's existing `write_handlers` (`stock.ex:596`), plus four new
spec fields: `permission`, `outputs`, `idempotency_inputs` and `side_effect_class`. The catalogue reads the module
families from `Letflow.Modules.Catalog`, so `catalog.ex:42` needs no new config. Two gaps in the pilot's types
must close first:

- `Entry.SideEffect` classes are closed to `:read | :write_tenant_registry | :ddl | :outbound`
  (`entry.ex:73-87`). Add `:write_module_record` and `:ledger_post`.
- `platform_tenant_only` is the only tenant rule (`entry.ex:27-28`; `Guard.check_tenant/2`, `guard.ex:91-98`,
  refuses every company tenant). A module entry is `platform_tenant_only: false` and has a new rule: the module
  must be installed in the instance's tenant, and its compiled manifest hash must be accepted. This is the check
  `ModuleWrites` does today (`module_writes.ex:21-27`), moved from the stamp to the entry.

## 2. The human task, the form and the approval in the definition

### 2.1 The form

The HUMAN_TASK keeps its role label and `required_permission` (`generate_pack.exs:207-208`: the permission
decides who may claim and complete the task; decision 0093 F1/F2). The form of the approval is a read of the
document, not an input: the approver must see the whole document (owner checklist item 26). The node gets a
`form` attribute that names a module form key (`stock.document_review`) with
`readonly: true`. The output schema is empty, except an optional `comment`. Nothing the completer writes is an
input of a write-like entry: source class `:person` is refused for write-like inputs (`entry.ex:37-39`), and
`WriteTargets` refuses trusted keys in a completion body (`entry.ex:126-134`).

### 2.2 The receive-goods definition, version 2

```
start -> check (module_call stock.check_posting) -> ok_gate
ok_gate --[variables.postable == true]--> post_task (HUMAN_TASK, StockApprove, form stock.document_review)
ok_gate --(default)--> end_refused
post_task -> post (module_call stock.post_document) -> end
```

The receipt has no four-eyes pair today: its single task is completed by the approver, and the storekeeper's
issue is not a task (BP-STOCK-01, `docs/bp/stock.json` row 1). The two-person kinds (opening, quick count) use
the gateway of 2.3.

### 2.3 Four eyes as a gateway on a process parameter (PM 11:30)

**Today, verified.** The pair is IN the definition: `distinct_from ["submit"]` on `approve`
(`priv/modules/stock/pack.json:482`, stock opening; `:560`, quick count; `priv/modules/assets/pack.json:443`,
asset opening). The engine enforces it in `SeparationOfDuties.check` (`separation_of_duties.ex:3-19`, called
from the completion guards, `engine.ex:8912`). The SWITCH is not in the definition. It is engine code at
completion: the setting `ApprovalRuleSetting` is read only on a would-be refusal (`separation_of_duties.ex:28-33`)
through `off_for_instance_step` (`approval_rule_setting.ex:159-171`), with the new-tenant default OFF (D-165,
`approval_rule_setting.ex:68-76`, `:94-106`; `approval_rules.ex:8-11`). `ApprovalRules.four_eyes_off?/3`
(`approval_rules.ex:68-74`) is the same read for the old-app path. A self-approval is audited `task.self_approved`
with "self-approved, four-eyes off" (`engine.ex:10173-10204`). Service users are never let through: only an
interactive `:oidc` credential may self-approve, plus two named exceptions (`:shared_access` and
`:system_self_approval` on `stock_quick_count/approve`, `separation_of_duties.ex:30-49`). The owner decision on
waiting approvals is "the setting at the moment the approval is completed (live)"
(`docs/design/four-eyes-switch.md:38`, owner table row 6).

**Design.** The stock opening, version 2:

```
start -> submit (HUMAN_TASK, completed by the issuer at issue, posting.ex:224-225, 238-262)
      -> eyes (module_call approval.four_eyes_required, node_id const "approve")
      -> eyes_gate (EXCLUSIVE_GATEWAY)
eyes_gate --[variables.four_eyes == true]--> approve (HUMAN_TASK, StockApprove, distinct_from ["submit"])
                                              -> post (module_call stock.post_document) -> end
eyes_gate --(default)--> self (module_call approval.record_self_approval)
                                              -> post (module_call stock.post_document) -> end
```

- **When the parameter is read.** At the gateway, in the transaction that completes `submit`, not at instance
  start. For the opening and the quick count, start and submit are one request (`posting.ex:224-225`), so in
  practice this is "at start", as the PM wrote. Reading at the gateway keeps the owner's "live" rule for a
  `submit` that waits.
- **What the function reads.** `ApprovalRuleSetting.effective(prefix, definition_name, "approve")`, the stored
  row or else the tenant default, plus the CREDENTIAL of the completing caller from the engine context (never
  from a variable). It answers `four_eyes: true` whenever the credential is not `:oidc`, so API tokens, service
  principals, scripts and timers always take the ON branch, even on a tenant that switched OFF (the rule of
  `separation_of_duties.ex:30-33`). Every read failure answers `true` (fails closed, as `approval_rules.ex:63-67`).
- **OFF branch.** No human click. `approval.record_self_approval` writes the same `task.self_approved` audit
  row with the same note and `four_eyes: "off"`, and `setting_changed_at` from the row. Then the posting runs.
  Owner question Q3: keep one confirm click instead.
- **Waiting approvals when the setting changes.** The `approve` node KEEPS `distinct_from`, and
  `SeparationOfDuties.check` keeps its live read at completion. So:
  - an instance already waiting on `approve` when the tenant switches OFF: the submitter may complete it
    themself, audited as today. This is the owner's "live" rule, unchanged;
  - switched ON while an instance is on the OFF branch: nothing waits there, because `self` and `post` run in
    the transaction that completed `submit`. No instance is caught half way.

  The gateway therefore adds the routing to the definition without moving the authority out of the engine.
- **Kept as is.** The admin screen and routes (`GET /approval-rules`, `PUT /approval-rules/:definition_name/:node_id`,
  `approval_rules.ex:3-4`), the reason and the audit `approval_rule.changed`, and the setting key
  `(definition_name, node_id)`. A tenant-edited version keeps its node id `approve`, so the setting still applies;
  the designer must warn when that id is renamed.
- **The two old-app exceptions** (`:shared_access`, `:system_self_approval`) stay engine code on
  `stock_quick_count/approve` (owner question Q11).
- **First two conversion candidates:** asset opening (`assets_opening`, `priv/modules/assets/pack.json:443-484`)
  and stock opening (`stock_opening`, `priv/modules/stock/pack.json:470-524`). They are the only plain four-eyes
  pairs, both already proven OFF end to end (`four-eyes-switch.md:216-217`, slices 2 and 3). The quick count
  comes after them, because of its two old-app exceptions.

**Activation fence (new).** A tenant edit must not be able to delete the four eyes silently. A version whose
`stock.post_document` step is reachable from START by a path that passes neither a HUMAN_TASK with
`required_permission` `StockApprove` nor an `approval.four_eyes_required` gateway is refused at activation. The
body of `post_document` checks it again at run time from engine-owned data: a completed task of this instance
with `StockApprove` by a person other than the `submit` completer, OR a `task.self_approved` row of this
instance. This is the SF-03 pattern (`handlers.ex:279-302`). Whether a tenant may ever remove the approval is owner
question Q2.

## 3. What the definition does and what stays code

### 3.1 The split

| The definition decides | Code keeps (on purpose) |
|---|---|
| order of steps; extra steps (a notice to the responsible person, a second check task, a timer) | the posting rules and the ledger (`HandlerWrites.post`, ledger policy) |
| who approves (role label, `required_permission` per task) | the binding of a posting to the issued version and to the instance start (`handlers.ex:214-302`) |
| four-eyes routing (the gateway of 2.3) | the four-eyes enforcement (`SeparationOfDuties`) and the switch storage |
| whether a refusal ends the process or goes back to a task (gateway on `postable`) | document numbering, the 96-hour window, master checks, print forms |
| notifications (the pilot's notify step, `definition_v2.ex:159-169`) | the start function per document kind (the only start path, `posting.ex:199-233`), cancel and withdraw (`posting.ex:608-653`) |
| | the old-app (Qoimeks) address and its two four-eyes exceptions; the Excel workbook apply |

### 3.2 Run time: in the transaction (deviation from the pilot's dispatcher)

The pilot runs platform steps outside every transaction, because `tenant.provision` runs DDL
(`dispatcher.ex:13-34`). The runner works in the platform tenant only (`engine/platform_step_runner.ex:30-33`).
A refusal puts the instance in ERROR plus the DLQ (`platform_step_runner.ex:17-20`). Module functions run no
DDL. Their bodies are already Multi composers. Today a refusal is an immediate 409/422 to the approver, and the
task stays open (`engine.ex:4222-4300`). So a `module_call` runs in the transaction of the step that ENTERS its
node: the task completion, or the start. The SERVICE_TASK runtime of R5 already plans `module_writes` on a
service node in the apply transaction (`engine.ex:7216-7231`, `:7303-7312`). `module_call` reuses that plan,
without an HTTP or script outcome.

- A refusal rolls back the whole completion. The approver sees today's answer, and nothing is half posted.
- A `:ledger_post` on a SERVICE_TASK today needs `ledger_post_consent: true` (`module_writes.ex:40-46`,
  REQ-688). For `module_call`, the entry's side-effect class carries that consent. The activator signs it.
- Owner question Q8: a durable, asynchronous posting with retry instead.

### 3.3 The start stays one function per kind

The pilot's step 5 (`docs/bp/process-template.md:36-39`) maps onto the existing `Posting.start_post/5`. The issue
route and the retry route `post/4` (`posting.ex:475-497`) start the ACTIVE version by name (`attempt/9`,
`definition_name`, `posting.ex:318-346`). A callers test limits the module's catalogue bodies to the step runner,
the "no bypass" rule of the template.

## 4. Running instances of the old shape

**Facts.** An instance runs its own snapshot of the definition, taken at start (`InstanceDefinitionSnapshot`;
`engine.ex:235-251`). BP-PLATFORM-24 step 5 proves that an instance of A stays on A after B is activated
(`test/uat/processes/BP-PLATFORM-24-definition-drives-execution.json`, description). `PinRebind` rebinds
SERVICE and catalogue pins only (`engine/pin_rebind.ex:16-22`), never a definition version. The completion of an
old `post` task re-checks the stamp and the manifest hash against the pinned snapshot. If the installed module's
hash is not accepted, that completion is refused 409 `module_upgrade_required` (`engine.ex:4335-4347`).

**Decision: drain, do not rewrite.**

1. The module's pack gains version `2.0.0` of each `process_key`. The `1.0.0` rows stay `deprecated`, never
   archived or deleted, so open snapshots keep their definition row (`Definitions.get_by_id` in
   `engine.ex:4238`).
2. Every new start takes the active `2.0.0` (start by name, `posting.ex:318-346`). The retry route therefore
   restarts a stuck document on the new shape.
3. The `module_writes` runtime, the stamp check and the old handler arities stay in code until a per-tenant
   count of open `1.0.0` instances reads zero on every tenant. The module version that ships `2.0.0` lists the
   old manifest hash in `accepted_manifest_hashes` (REQ-769, `module_writes.ex:24-25`). Without that, every open
   old approval in the field answers 409 after the upgrade. That would be the one way to "lose" an open
   document.
4. No open document is lost. The document stays `issued`, the mark is unique per kind (`handlers.ex:23-24`), and
   cancel withdraws any instance of either shape (`posting.ex:608-653`, through `Engine.cancel_instance`).
5. Optional, owner question Q4: an operator action "restart on the new version" cancels the old instance and
   starts `2.0.0` with a new idempotency attempt number (`posting.ex:318-327`). It is safe for the same reason as
   point 4. It is not done by default.
6. Auto-CD already deployed `1.0.0` to QA. The QA tenants follow points 1 to 4. The upgrade runner check
   (`project/scripts/qa_tenant_upgrade.py`, team repo) gains a line "open 1.0.0 instances per tenant".

## 9. Second worked example: fixed asset acquisition with commissioning as a SUB_PROCESS (PM 12:00)

### 9.1 The shape

```
assets_acquisition (module assets)
start -> request (HUMAN_TASK, requester) -> decide (HUMAN_TASK, AssetsApprove, distinct_from ["request"])
      -> receive (HUMAN_TASK, storekeeper: supplier, invoice, acceptance)
      -> make_doc (module_call assets.create_commission_document: outputs document_id, version_no)
      -> commission (SUB_PROCESS definition_name "assets_commission", interface inputs document_id, version_no;
                     outputs entry_id)
      -> end
```

Verified facts: the engine node exists (`lib/letflow/engine/sub_process.ex`). No shipped pack uses it
(`grep -rn SUB_PROCESS priv/modules` is empty). No UAT scenario runs one. BP-STOCK-38 only proves the refusal
(a tenant parent cannot start a module child, `docs/bp/stock.json` BP-STOCK-38, `sub_process.ex:415-436`).

### 9.2 Answers

**(a) Child version rule.** Late binding. The child is resolved by `definition_name` with
`Definitions.get_active_by_name/2` WHEN THE PARENT'S TOKEN ENTERS THE NODE (`sub_process.ex:40-55`,
`resolve_child_definition/2` at `:521-535`), not when the parent starts. The child's own snapshot is created at
child start (`create_child_snapshot`, `sub_process.ex:540-545`; called at `:373`), and the child is pinned to it
from then on. The child's service and script pins are resolved fresh for the child, never inherited
(`sub_process.ex:501-516`). `PinRebind` does not touch definition versions (`pin_rebind.ex:16-22`). So a new
commissioning version activated mid-run is used by every parent that has not reached `commission` yet. A child
that is already running keeps its version. (Q9.)

**(b) Variable mapping and output merge.** With an `interface` on the node, the inputs named in it are copied,
with a schema check, and missing required ones fail. Without an interface the whole parent map is copied, minus
reserved engine keys (`build_child_initial_variables/2`, `sub_process.ex:133-161`). On completion only the declared
`outputs` merge into the parent. Without an interface everything merges, minus reserved keys
(`build_parent_merge_variables/2`, `:163-191`). The design REQUIRES an interface on every module child. A child
output must never feed a write-like input of a later parent step unless it is the `:step` output of a catalogue
call in the child. This is the module analogue of the pilot's foreign-source rule, which refuses a SUB_PROCESS
beside a write-like platform call (`guard.ex:25-28`; `definition_v2.ex:17-19`).

**(c) Failure, cancel and compensation.** A failed input filter or child resolution writes no child and puts
the PARENT in ERROR (`to_error_args/6`, `sub_process.ex:249-291`, codes `SUB_PROCESS_MISSING_REQUIRED_INPUT`,
`..._DEFINITION_NOT_FOUND`). A bad child output puts the parent in ERROR without the merge
(`lib/letflow/design/req062-sub-process-runtime.md:575-576`). A child that lands in ERROR never completes, so the
parent waits: the ERROR landing only takes a key-share lock on the waiting parent (`engine/execution_error.ex:171-182`).
A parent cancel does NOT cancel the child (EE-08, `req062-sub-process-runtime.md:49-56`, `:655-669`). A direct
child cancel leaves the parent waiting forever (OQ-4, `:790-797`). There is no compensation in the engine. The
undo of a posting is a separate reversal process. **Needed (P7):** a parent cancel cancels its open children; a
child cancel or ERROR moves the parent to ERROR with a code, so the DLQ and retry of the pilot apply.

**(d) Permissions and four eyes inside the child.** Each child HUMAN_TASK keeps its own `required_permission`
as usual. The child's start requirements (derived and declared) are joined into the parent's start
(`start_permission.ex:37-43`; used by `gate_start_permission/2`, `engine.ex:946-982`, through
`SubProcess.child_definitions/2`, `sub_process.ex:456-500`). The PM's cite `definitions.ex:2007` is the comment of
`check_start_permission_name/1` (`definitions.ex:2005-2040`): the definition's OWN declared start atom, not the
children. A module child needs a parent stamped by the SAME module (`refuse_module_only_child`,
`sub_process.ex:415-436`). A child that calls a platform function is refused (`:448-454`). **Four eyes do not
cross the instance boundary.** `distinct_from` compares completions "in the SAME instance"
(`separation_of_duties.ex:3-5`), so a `decide` in the parent and an `approve` in the child are never compared.
The switch row of a child step is keyed by the CHILD's definition name (`off_for_instance_step` joins the
instance's own snapshot, `approval_rule_setting.ex:159-171`). Design rule: a four-eyes pair lives inside one
instance. With P3, the same-module rule is replaced by "the parent's activator holds every entry permission of
the child" (Q13).

**(e) Designer.** The child is a free-text field `definition_name` (`web/src/components/diagram/NodeEditPanel.tsx:313-315`,
`diagramConfig.ts:38`). There is no picker and no display of the child's inputs or outputs. The old canvas edits
`interface` as raw JSON (`web/src/components/canvas/PropertyPanel.tsx:173-238`). Its node label reads
`attributes.sub_definition_name` (`web/src/components/canvas/nodes/SubProcessNode.tsx:5`), a key the engine never
reads (the engine reads `definition_name`, `sub_process.ex:522`), so the old canvas shows an empty child name:
**defect for the operator to file**. The G16 test cases refuse a SUB_PROCESS (`:sub_process_not_supported`,
`lib/letflow/definitions/test_cases.ex:25-26`, `:497`), so a parent cannot be tested before activation. Needed
(P5/P7): a picker of active definitions with their interface, and G16 cases that fake a child's outputs like
`step_outputs`.

**(f) Limits.** Each graph has a hop limit (`length(nodes) * 4 + 10`, `sub_process.ex:391`). The start fence's
walk of children removes duplicates by definition id, so a cycle does not loop there (`sub_process.ex:466-500`).
Cross-definition recursion depth at run time has no bound: it is out of REQ-062's scope (`sub_process.ex:60-69`;
`req062-sub-process-runtime.md`, around `:786-789`). A grandchild that the child's first activation reaches is
not activated in that pass (OQ-3, `sub_process.ex:60-69`), although later grandchildren cascade on completion
(`test/letflow/engine/service_task_subprocess_cascade_test.exs:400`). **Needed (P7):** a depth cap (proposal 3)
and a refusal at activation of a cycle in the child graph.

**(g) Reports and step log.** The step log belongs to one instance (`lib/letflow/instances/step_log.ex:3`). The
parent shows only `SUB_PROCESS_COMPLETED` on its node (`:54`, `:67-68`). The child's steps are in the child's
log. The link is the parent token's `waiting_child_instance_id` (`engine.ex:476-478`). There is no combined view.
Needed (P7 or a web task): the parent's step log links to the child's log and shows its rows indented.

### 9.3 What P7 contains

Child cancel and ERROR propagate to the parent. A parent cancel cascades down. A depth cap and a cycle refusal.
An interface is required on module children, with the foreign-source rule of (b). The same-module rule is
replaced by the permission rule of (d), behind Q13. Designer picker and G16 child fakes go with P5. The old
canvas label defect is a separate bug.
