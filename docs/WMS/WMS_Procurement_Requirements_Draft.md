# Procurement and Warehouse Management Application Requirements — Review Draft

This draft turns `WMS.docx` into testable customer requirements. **[S]** means explicitly stated in the source; **[C]** means clarified by the Customer; **[P]** means proposed from common practice or needed to make a source requirement workable. Proposed behavior and unresolved decisions require customer validation before contract baseline. The accompanying `WMS_English_Translation.md` preserves the source wording and sequence.

## 1. Scope and system boundaries

The solution shall be implemented over the Customer's in-house [Letflow BPM platform](https://github.com/tvolodi-org/letflow) and support internal purchase requests for materials, works and services plus warehouse execution across multiple warehouses. The application module shall provide operational inventory accounting, stock and document operations, validation, algorithms, permissions and audit. Letflow shall configure document routes, tasks, performers, approvals and exception paths using its process, task, role and document configuration. **1C and SAP mainly hold general-ledger accounting**; the module shall own the historical operational stock ledger and physical balances. The destinations and mappings of financial events to 1C/SAP, and ownership of purchase orders and legal documents, remain to be mapped. [C/P]

**Process boundaries.** A *purchase request* is an internal demand and approval record. A *purchase order* is the supplier-facing procurement commitment, where used; its source system is to be decided. An *expected receipt* is the warehouse instruction to receive goods. A *warehouse receipt* is the actual physical receipt. A *service acceptance* confirms work or service delivery. A *payment request* initiates payment approval. These records shall have separate identifiers and statuses, with line-level links between them. Letflow routes their tasks; the module or connected system holds the business record according to the ownership map. [C/P]

**Implementation boundary [C/P].** BPM controls *when* an operation is offered, *which role or user* receives a task, *which document version* is routed, and *which approval or exception path* follows. The module controls *whether* the requested stock operation is valid and posts it atomically to the physical stock ledger. BPM may configure thresholds and invoke an override path, but it cannot bypass module invariants such as unique serials, nonnegative available stock, traceable movements and idempotent posting. The module returns a typed outcome and domain event to BPM. All BPM, module and ERP references shall be correlated.

**Proposed release split.** Release 1: BPM integration contract, purchase-request data/actions, master data, receiving, putaway, stock, picking and route optimization, shipping, counts, handhelds, 1C/SAP adapters as required by the ownership map, core security and reports. Release 2 candidate: resource forecasting, advanced waves, yard management, truck scales, no-code report builder, full BI mart, ABC/XYZ automation. Voice picking remains a separately priced option. This split is a proposal, not a reduction of the source scope.

## 2. Roles and core data

| Role | Main permissions (subject to access policy) |
|---|---|
| Requester | Create and revise own purchase requests; view status and fulfillment. |
| Approver | Act on BPM tasks assigned by the configured process. |
| Procurement officer | Handle BPM procurement tasks; record supplier and procurement references through authorized module actions. |
| Warehouse operator | Execute assigned receiving, moving, picking, shipping, and counting tasks. |
| Warehouse supervisor | Perform only the work and exception actions granted by BPM and module permissions. |
| Quality inspector | Record inspection outcome and perform configured quality tasks. |
| 1C/SAP integration services | Exchange general-ledger events and any masters or documents assigned to each system by the ownership map. |
| System administrator | Configure module reference data, algorithms, permissions, devices and integrations; BPM administrators configure process routes and tasks. |

**BPM and module contract [C/P].** BPM shall call documented module operations such as `validate`, `reserve`, `receive`, `putaway`, `move`, `pick`, `pack`, `dispatch`, `count`, `adjust`, `hold` and `release`. Each command shall include document and line IDs, document version, performer, role/context, idempotency key and correlation ID. The module shall return a stable operation ID, validation errors or posted result, and publish completion/exception events. BPM shall route those results; the module shall not embed a fixed approval sequence or supervisor privilege. Long-running BPM tasks shall not hold a database transaction open. Offline assignments shall carry a bounded, versioned work scope.

| Concern | BPM configuration | Module hard feature |
|---|---|---|
| Approval, return, escalation, delegation | Task and document route; role/user assignment; thresholds | Validate and record authorized operation requested by BPM; publish result. |
| Stock movement | Trigger point and exception path | Atomic stock ledger posting, balances, reservations, lot/serial/status checks. |
| Picking and putaway | When task is released, performer, policy choice | Feasible allocation, location selection, route optimization, scan validation. |
| Permissions | Map roles to tasks and document actions | Enforce role, warehouse, zone, operation and field checks in API and UI. |
| Audit | Process/task history | Immutable business-operation log and correlation to process history. |

**Core identifiers [P].** Every item, warehouse, location, lot, serial number, license plate/shipping unit, owner, custodian, purchase request, request line, source document and line, task, physical stock movement, and integration message shall have a stable unique identifier. Letflow, 1C and SAP identifiers shall be retained alongside module identifiers when applicable. A barcode may identify an item, pack, location, or handling unit; its meaning shall be unambiguous at scan time.

**Stock dimensions [S/P].** Quantity shall be distinguishable by item, warehouse, location, unit of measure, lot, serial, inventory status, owner, and custodian, as applicable. The system shall distinguish physical on-hand, allocated/reserved, available-to-pick, and blocked/quarantine quantities. Available-to-pick shall exclude blocked, quarantined, expired, and allocated stock under configured rules. A stock transaction shall contain its source document, cause, actor, timestamp, and before/after quantity. Negative stock shall be prevented except through an explicitly authorized exception policy. [P]

### 10a. Letflow fit and implementation gap

Letflow is an in-house, multi-tenant BPM platform with a definition-driven process engine and a Flutter mobile tier. Its mobile documentation records cached definitions and pinned task form versions, which are useful for presenting assigned work offline. The same current scope explicitly **excludes offline writes in v1** and states that no optimistic write queue exists. Therefore the WMS offline requirement is a new deliverable: either extend Letflow mobile under a separately approved scope or build a WMS handheld client that shares Letflow identity/task context and calls module operations. The design shall include versioned assignments, local encrypted event storage, idempotent replay, stock-scope partitions and BPM merge-resolution tasks. Do not claim that Letflow's existing definition cache already executes warehouse documents offline. Sources: [Letflow README](https://github.com/tvolodi-org/letflow), [mobile architecture scope](https://github.com/tvolodi-org/letflow/blob/main/docs/mobile/architecture.md), [MOB-8 requirement](https://github.com/tvolodi-org/letflow/blob/main/docs/mobile/requirements.md).

### 10b. Preliminary Kazakhstan document matrix (research as of 14 October 2026)

This matrix identifies likely document families; applicability depends on the legal entity, transaction, goods category and transport. External-party dispatch is in scope; goods categories are still unknown. The module shall store item classification attributes and evaluate a configurable pre-dispatch document checklist. BPM shall route document preparation/approval; 1C, SAP or a connected legal-document service shall issue and register the legal document according to the ownership map. Accounting and legal owners should approve the final matrix before templates or integrations are built.

| Transaction | Document or system to assess | Proposed application responsibility |
|---|---|
| Supplier goods arrive at warehouse | Stock receipt order, form **З-1**, under Ministry of Finance Order 562; supplier documents and any applicable СНТ/ЭСФ | Module records physical receipt and evidence; Letflow routes discrepancies; designated document owner issues the primary form and any 1C/SAP general-ledger event. |
| Internal movement between stores or departments | Internal inventory movement note, form **З-5**; accounting rules allow defined electronic movement/СНТ alternatives in some cases | Module records both handover sides; Letflow routes the document; designated system issues the form and any financial event. |
| Goods released to an external party | Outward inventory release note, form **З-2**, or applicable electronic СНТ alternative under accounting rules | Module supplies actual picked/shipped quantity and recipient evidence; Letflow routes preparation/signature; designated system issues the legal form. |
| Regulated goods movement, relevant imports/exports or other cases in the current list | **СНТ** (goods accompanying note) in the IS ЭСФ/Virtual Warehouse under Ministry of Finance Order 657 effective 1 January 2026 | Classify goods and transaction before dispatch; designated tax/document integration creates, signs and registers СНТ; module checks required acknowledgment before physical release. |
| Road freight | **ТТН** (goods transport note) and waybill where applicable; from 1 June 2026, the Transport Ministry says registration in **ЕСУТД** is mandatory for road freight vehicles over 3.5 tonnes | BPM routes transport preparation; transport/ERP integration issues/registers; module captures vehicle, driver, load, departure and release check. |
| Accepted works/services | Acceptance act, commonly form **Р-1** under Order 562 for non-construction works/services | Letflow routes acceptance and payment; designated document system holds the act; module records no physical stock event. |
| Tax invoice | **ЭСФ** under the current tax rules, where applicable | Designated tax/document system issues/corrects; module supplies receipt/dispatch evidence only. |

The 2026 СНТ rules are in [Ministry of Finance Order 657](https://www.gov.kz/org/minfin/documents/details/929609). The primary forms are in [Order 562](https://www.gov.kz/org/kostanai-bilim/documents/details/531620?lang=ru), and the [accounting rules](https://old.adilet.zan.kz/rus/docs/V1500010954) discuss when internal and outward notes are used or replaced by an electronic form. The [Ministry of Transport notice](https://www.gov.kz/org/transport/press/news/details/1205794?lang=ru) states the ЕСУТД registration threshold and start date. [Ministry of Finance guidance on service acts](https://www.gov.kz/org/minfin/press/article/details/208387) addresses form Р-1. These sources do not establish that every listed document is needed for every shipment.

## 11. Suggested customer workshop and sign-off order

1. Confirm Letflow integration capabilities and map each legal entity, warehouse, master and document to the module, Letflow, 1C, SAP or a legal-document service. Physical stock accounting belongs to the module; map general-ledger event destinations.
2. Map representative document and item flows, including returns, quality, cross-dock and special inventory.
3. Approve item/location/status model, allocation strategies and tolerances; encode exception authorities in BPM task/role/document configuration.
4. Approve BPM command/event contract, 1C/SAP integration mapping, offline rules, module permissions, legal-document classification and measurable nonfunctional targets.
5. Prioritize releases and run an end-to-end pilot in one warehouse before multi-warehouse rollout.

## 12. Basis for proposed additions

The source requirements come from `WMS.docx`. Proposed practices draw on the following official product and standards documentation as examples of established patterns, not as a requirement to use those products:

- [Microsoft: purchase requisition workflow](https://learn.microsoft.com/en-us/dynamics365/supply-chain/procurement/purchase-requisitions-workflow) — separate approval and purchase-order stages.
- [Microsoft: product receipt against purchase orders](https://learn.microsoft.com/en-us/dynamics365/supply-chain/procurement/product-receipt-against-purchase-orders) — receipt, discrepancies and later invoicing.
- [Microsoft: cycle counting](https://learn.microsoft.com/en-us/dynamics365/supply-chain/warehousing/cycle-counting) — count work, mobile entry and variance review.
- [Microsoft: inventory blocking](https://learn.microsoft.com/en-us/dynamics365/supply-chain/inventory/inventory-blocking) — blocking stock from use.
- [GS1: application identifiers](https://ref.gs1.org/guidelines/2d-in-retail/1.0.0/GS1-2DRetailPOS-Guideline-i1.0-r-2024-05-28) — standard fields for item, lot, expiry and serial barcodes.
- [Oracle: mobile WMS guide](https://docs.oracle.com/en/cloud/saas/warehouse-management/25b/owmma/redwood-mobile-wms-guide.pdf) — illustrates that offline support is product-specific and needs explicit acceptance criteria.
