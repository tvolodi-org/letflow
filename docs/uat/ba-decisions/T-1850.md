# T-1850 — Does a STOREKEEPER-only user see every task of the company? (security ruling, decision for UAT)

No issue number was given in the task text, so this file is named after the task id. The full ruling with its evidence
is `docs/design/storekeeper-task-visibility-ruling.md` (the path the task names).

## Question

Finding 4 of `docs/design/roles-architect-verdict.md` (T-1848): `is_task_worker_only?/1` filters the task list only
for a TASK_WORKER who holds none of five named roles. STOREKEEPER is not one of the five and holds `TasksRead`. Is a
STOREKEEPER-only user seeing every task of the tenant a defect, how severe is it, and what permission-only rule fixes it
while every other role keeps its answer?

## Decision

1. Defect: yes, re-verified by reading the code path and by running a temporary test against today's code
   (`Result: 1 passed`: a STOREKEEPER-only user gets other users', other groups' and TENANT_ADMIN-role tasks from
   `GET /tasks`, `GET /tasks/inbox` and `GET /tasks/:id`; a TASK_WORKER, and a STOREKEEPER + TASK_WORKER, do not).
2. Severity: medium. One company only (tenant isolation holds); task metadata (name, assignee, status, dates, business
   key, form layout) leaks inside the company; no form data or process variables; no completion of others' tasks.
3. STOREKEEPER is the only role affected today.
4. Recommended fix: a new tenant-scope permission `TasksReadAll` held by PLATFORM_ADMIN, TENANT_ADMIN,
   PROCESS_DESIGNER, PROCESS_OPERATOR and TENANT_AUDITOR; the three task read routes filter to own, group and role tasks
   for any caller without it. Every existing golden row stays identical; only STOREKEEPER's task list narrows.
5. For UAT: no current scenario changes (the roster has no storekeeper actor; stock counts are module documents, and
   stock posting tasks are routed to TENANT_ADMIN). After the fix, a storekeeper UAT scenario, once an account exists,
   expects "My Tasks" to show only tasks addressed to the storekeeper, their groups or their roles.

## Reasons

- `docs/roles.md` says the storekeeper does "its own tasks" and the task worker "read and complete their tasks"; the
  code comment on the STOREKEEPER core list says "own tasks (count and approval tasks)". Today's behaviour contradicts
  both.
- Decision 0081 grants `TasksRead` and `TasksComplete` and records only a node-scope limit; it never decides that a
  storekeeper reads the whole queue.
- The add-only permission changes one answer (the defect) and nothing else, so it is the smallest safe change and fits
  the owner's permission-only principle D-129 (as stated in the T-1848 verdict).

## Assumptions

- UAT assumption, to be confirmed by the process owner: tasks meant for storekeepers (if any process routes count or
  approval steps to them) are addressed to the storekeeper's user, group or the `STOREKEEPER` role, not left unassigned.
- The fix itself changes production access and is not decided here: it needs a requirement, the owner's or PM's go,
  and a security review of the change.

Decision for UAT only; the process owner configures production.
