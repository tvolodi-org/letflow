# BA decision for UAT: how EO-005 (page-size limit) is checked in vortex-entity-list-filter-and-page (GH #3120)

Business analyst: Vortex UAT. This file changes no code, seed, definition, test or scenario file; the scenario rewording below is stated here and applied by a later task.

## Question

The scenario `test/fixtures/uat/scenarios/vortex/entity-list-filter-and-page.yaml` has step 4 (Karl asks for more results on one page than the platform permits, `via: gui`) and expected outcome EO-005 (the request is refused with a readable message stating the limit, and no partial list is shown as complete). The screen offers only 25/50/100 per page, so an oversize page cannot be requested from it. Over the API, `page_size=201` returns 400 `page_size out of range` without naming the limit. Is EO-005 checked over the API (and the message must then state the limit), or dropped as unreachable in the GUI?

## Sources opened

- Issue #3120 (body; no comments): the observation and the two options.
- `test/fixtures/uat/scenarios/vortex/entity-list-filter-and-page.yaml`: step 4 (`via: gui`, input "more rows per page than the platform permits") and EO-005 (verification method `gui_screen`, "refused with a readable message stating the limit").
- `lib/letflow/api/pagination.ex`: `@max_page_size 200`, `max_page_size/0`, `validate_page_size/1` (returns `{:error, :page_size_too_large}` above 200 and for 0).
- `lib/letflow/routers/entities.ex` (lines ~1100 and ~2031): maps that error to `Response.bad_request(conn, "page_size out of range")`; the text carries no number.
- `lib/letflow/design/req393-entity-list-query-ui.md`, sections 6.1 and 6.2: the design already says the dropdown prevents accidental oversize requests, that the E2E spec injects an oversized value by a direct API call, not through the dropdown, and that the page shows "Page size is too large. Choose a smaller value." (also without the number).
- `web/src/components/ui/PaginationControls.tsx` (`PAGE_SIZE_OPTIONS = [25, 50, 100]`) and `web/src/pages/entities/EntityListBrowserPage.tsx` (`[25, 50, 100, 250]`): the options offered by the screens.

## Decision (UAT only)

**EO-005 is kept and checked over the API, not dropped. The 400 message must state the limit of 200.**

Reasons:

1. The business rule behind EO-005 is real and sourced: the platform has one maximum page size (200, `Pagination.max_page_size/0`), and a request above it must be refused, not silently truncated. That rule is a property of the platform, not of the screen; the screen merely makes it hard to trigger. Dropping the check would leave the "no silent truncation" rule unverified in UAT.
2. The design record for the list UI (req393, section 6.1) already settled that the oversize case is exercised by a direct API call, so checking it over the API follows an existing decision and contradicts none.
3. The scenario's own wording requires "a readable message stating the limit". A message that says only "out of range" does not meet that. The requirement is in the scenario; the product falls short of it. So the product should change, not the criterion.
4. A caller who sees "out of range" cannot tell the right size to ask for. Naming the limit costs nothing and discloses nothing sensitive (it is a platform constant, not tenant data).

Consequence for the UI: the web screen offers 250 in `EntityListBrowserPage.tsx`, which is above the server limit of 200, so that choice would produce the very refusal EO-005 describes. This is a possible product defect (not decided here; the req393 OQ-2 asked for this value to be confirmed). Reported in `findings` for the operator.

## How step 4 and EO-005 are reworded (to be applied to the scenario file in a later task)

- Step 4: `via: api` (was `gui`). Action: "Karl's list request asks for one more result per page than the platform permits (201 where the limit is 200), and he reads the answer he gets." Input: `requested_page_size: 201`.
- EO-005 description stays: refused with a clear message, not quietly cut short. Verification method changes from `gui_screen` to `api_response`. Detail: "The request at step 4 is refused (HTTP 400) with a message that states the limit of 200, and the answer contains no list of records." Evidence: "The recorded answer to the step 4 request: status and message text."
- A second, GUI-side observation stays optional and is not a criterion: the page-size choices offered on screen are at or below 200.
- Until the message change below lands, EO-005 fails with the existing `on_fail` severity; it is not to be reworded to pass on "out of range".

## Backend change needed: YES

A small backend change is needed so the 400 message for an oversize page states the limit (for example "page_size out of range (maximum 200)"). The planner should queue it as one change:

- Scope: the entity list and entity query routes in `lib/letflow/routers/entities.ex`; the same text is shared by other routers (`audit.ex`, `definitions.ex`, `admin_services.ex`, `exam/router.ex`, `record_attachments.ex`), so the planner decides whether to change them together via `Pagination.max_page_size/0` (preferred: one source of the number, no hard-coded 200).
- Check before editing: tests that pin the exact text `page_size out of range` (`grep -rn "page_size out of range" test/`) and the req393 web handling of that text.
- Web: confirm the dropdown option 250 against the server limit (separate small change or the same task).
- Not in this decision: the Playwright spec for the vortex actors, which #3120 also asks for (FRONTEND-DEV).
