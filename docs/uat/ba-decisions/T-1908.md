# BA decision for UAT: maintenance inside the platform (task T-1908)

Business analyst (UAT). Topic confirmed by the owner through the PM, 2026-11-13 (D-144, from the task text). No issue
number was given, so the file is named after the task. The full design note is `docs/design/platform-maintenance.md`.

## Question

How should Letflow handle maintenance inside the platform: a "Report a problem" button with automatic context, automatic
error capture with grouping and alerts, the support work run as a Letflow process in the platform company, four request
classes, a routing switch from the owner to AI per class, AI work day and night inside the budget, safety rules, user
status, the list of what infra must provide, and the open/closed split?

## Decision

1. The answer is the design note `docs/design/platform-maintenance.md`. It is a recommendation; nothing is built before
   the owner confirms it (task text).
2. For UAT only, I decide:
   * Default routing is "owner reviews everything" for all four classes (task text, requirement 5).
   * UAT scenarios for this feature use only actors of `test/fixtures/uat/actors.yaml`; no new actor is invented. The
     scenarios are written after slices 1 to 4 are on main (a `uat_design` task), not now.
   * UAT never sends a real report to the AI provider until the owner answers owner-table line 5 of the note.
3. Everything that touches production, access across companies, money or the AI provider is in the owner table of the
   note (lines 4 to 10), not decided here.

## Reasons

1. Letflow has no report feature today (grep in the note, section 13), but it has the parts: help by screen, trace ids on
   every call and error, redacted JSON logs, operator alerts, the bell and mail log, audit, the BPM engine and a pinned
   platform tenant (note section 1.1, each with its file).
2. Qoimeks shows a small working shape to copy: append-only report row, redaction on device and server, throttled
   failure rows (note section 1.2, quoted from its files).
3. A report copies one company's facts into the platform company, and `docs/roles.md` says PLATFORM_ADMIN "must not act
   inside a customer tenant or read a customer's business data". Only consent plus "no field values" keeps that rule, and
   it is an access decision: the owner's (note owner table line 4).
4. The repository is public (`docs/design/open-core-closed-candidates.md`, candidate 3), so customer text must never
   reach a GitHub issue (note section 7 point 7).
