# T-1885: one pattern for list + detail screens (master-detail design verdict)

Design verdict of the web designer/architect, delegated by the owner (PM D-136). It is not a production access, data or
permission rule. No issue number was given in the task, so this file is named after the task id. The full audit
and verdict are in `docs/design-system/master-detail-verdict.md`, which sits beside this record as the task asked.

## Question

On the gate walk the owner found list + detail screens inconsistent: some have no divider, some have a divider with
no collapse button, some have both. Which one pattern should the web app use? Answer with a component API, a
design-system entry, a guard that blocks new hand-made layouts, and a migration order.

## Decision

1. Every screen with a list and one selected record uses one new shell, `ListDetail`. It is built on the existing
   registry markup (`lf-reg`) and the existing splitter engine. It always has a divider with a collapsible list, the
   always-visible restore control, a layout saved per user and screen, and "the record replaces the list" at
   <= 900 px of work area. It replaces `MasterDetail` on 12 screens and the hand-wired balances splitters on 2.
2. `DocLayout` (documents with lines) and `Journal` (movements) stay as their own shells. They follow the same divider
   rule: the divider between list and record collapses the list. That change is new for the journal (slice 1b).
3. A source-scan guard (three patterns in `web/tests/guards/forbidlist.ts`, with a ratchet list that shrinks slice by
   slice) fails `npm run guards` in CI when a screen writes a shell class, calls the splitter itself or imports
   `MasterDetail`.
4. Migration in 7 slices, gate C-E screens first (balances, movements, asset cards, counts, codes, lots, locations,
   org), each with browser checks at 1920/1440/1280/1024/390 px and no data, permission or route change. All slices
   start after T-1884 has merged.

## Reasons

- The audit (verdict section 3.1) counts 19 list + detail screens on 6 shells. 12 of them have no divider, which
  breaks the design repo's own rule 13. Two have a divider without collapse.
- `lf-reg` already has the splitter, collapsible list, tree variant, layouts and container-query breakpoints, so it
  needs no new CSS. `lf-md` has none of these, and it uses a viewport breakpoint where the others use the work area.
- The restore, reset, clamp and in-viewport behaviour already exists in the splitter engine (T-1873, T-1875, T-1884).
  A shared shell gives it to every screen and nothing is redone.
- The repo's UI guards already live in the forbid-list harness with two-sided fixtures, so a new pattern there is
  the smallest enforcement that CI already runs.
