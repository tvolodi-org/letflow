# T-1519 — Design note: updates at runtime, a new module/application version delivered and tenants upgraded WITHOUT stopping the server

Source request: PM item D-114(3) ("design note first, docs only, plain words, recommendation + options").
Written by the business analyst, 2026-11-09. Docs only: no code, route or requirement is changed by this note.
The operator copies it to the portfolio proposals folder.

**Decision for UAT only; the process owner configures production.**
Everything below that touches production behaviour, money, access or other tenants' data is a *recommendation*
or an *open owner question*, not a settled rule. Rules not found in a source are marked
"UAT assumption, to be confirmed by the process owner".

## 0. Short answer

1. **A tenant upgrade needs no server restart. A new build does.** The upgrade of a tenant (new entity definitions,
   new process drafts, new version and hash) is an ordinary database transaction on a running server. What the running
   server cannot do is *get new code*: Elixir code, the module manifests (compiled into the build), the permission
   matrix and the web bundle all arrive with a new build.
2. **Recommendation: do not hot-load code on the BEAM.** Use *rolling* deploys of the backend (two nodes, one
   Postgres) plus the existing per-tenant upgrade, and keep every database change in expand/contract form so the old
   and the new build can both run against the same schema for the window of the deploy.
3. **Already built (all four pieces named in the task):** plan route, apply route, the clear 409 `upgrade_required`
   during the gap, upgrade on deploy behind a default-off flag, and the demo script that drives the chain. **Not built:**
   a rollback route, the data-step runner (so any plan with a data step is refused), a fleet driver over many tenants,
   the `min_data_version` gate, and anything for on-site delivery (no package format, no signature).
4. **On-site installs** need a signed, versioned *application package* and an offline installer. Nothing exists; the
   recommendation is in section 6 and the key-holder question is open owner question O1.

## 2. (a) What still needs a restart

| Kind of change | Restart of the server needed? | Why / how it arrives |
|---|---|---|
| **Elixir code** (routers, engine, handlers) | **Yes — a new build is started.** | Code is compiled into the release. |
| **Module manifest** (entities, process pack, permissions, ledgers, routes) | **Yes for the manifest itself; no for the tenant.** | The manifest and pack file are compiled into the build (`Catalog`, plan compares "tenant state" with "the module compiled into the running build", REQ-768). After the new build is up, each tenant's *data side* moves by the upgrade (no restart). |
| **Permissions / role grants** | Yes (code). | Grants are compiled code evaluated without a tenant (0055 D7). They are **live for every tenant at deploy**; the upgrade cannot gate them. Widening is refused by rule until per-tenant grants exist (0055 D7, ruling of 2026-10-15). |
| **Database migration, tenant schema** (tenant tables, columns) | Not by itself; runs at boot / on the replay. | `TenantProvisioning.MigrationReplayBoot` replays pending tenant migrations at boot; the upgrade boot child is placed after it so the new columns exist (`boot.ex` moduledoc). |
| **Database migration, shared/public schema** | Run once by the deploy step *before* the new build takes traffic. | UAT assumption, to be confirmed by infra: how the public-schema migration is invoked in the release was not found in this repository. |
| **Tenant data change (data step)** | No restart, but not yet possible (runner not built). | REQ-773 / 0055 D3, D5. |
| **Web bundle (`web/`)** | **No server restart**, but users must reload; an old open tab runs the old bundle against the new API. | UAT assumption: the SPA is static files; how it is served was not verified. Rule: the API stays compatible with the previous bundle for one release (same expand/contract idea). |
| **Mobile app** | Store release; cannot be forced. | Old apps call the new API: same one-release compatibility rule. |

**What the BEAM can hot-load, and what we should not.** The BEAM can load a new version of a module into a running
node (code upgrade by `code:load` or a release upgrade "appup/relup"). **Recommendation: do not.** Reasons: (1) our
state lives in Postgres, not in long-lived processes (REQ-045: no process per workflow instance), so hot loading buys
almost nothing; (2) a relup must be hand-written and tested for every release, and a mistake corrupts a running node
rather than failing at start; (3) the compiled manifest, the permission matrix and `Application.compile_env` values
(0055 D7 S3-3) are read at compile time and do not change by loading a module; (4) with two nodes behind a balancer a
plain restart of one node at a time gives the same "no downtime" with a far simpler failure mode. What is safe to
change without a release is *data and settings* (feature flags, tenant settings) — those already change at run time.

## 3. (b) Rolling and blue-green deploys with one Postgres

**Constraint:** during a deploy, build N and build N+1 both run against one database, and tenants are at version N
until upgraded. The design record already states the skew: code at N+1 while a tenant is at N (0055 D5 "Deploy skew").

| Option | How | For | Against |
|---|---|---|---|
| **R1 Rolling (recommended)** | Two or more nodes; stop, replace, start one at a time; health check between. | No extra environment; the BEAM boots fast; matches current single-compose practice scaled to 2 nodes. | Old and new build serve at once: every DB change must be expand/contract. |
| **B1 Blue-green** | A second full environment (green) on the same Postgres; switch the balancer; keep blue for rollback. | Instant switch back for *code*. | Double hardware; same Postgres, so it does **not** remove the compatibility need; two boots run the boot children (see risk below). |
| **S1 Stop-the-world** (today's fallback) | Stop, migrate, start. | Simplest. | Downtime — what this task wants to avoid. |

**Expand / contract rule (recommended, already in 0055 D5 for module data):**
1. *Expand* release: add the new column/table/definition; old code ignores it. Both builds work.
2. Upgrade every tenant (data side).
3. *Contract* release (later): remove the old thing, and only now raise `min_data_version`. 0055 D5 says a release
   may raise it "only after every tenant that has the module installed has been upgraded at the previous release".
4. Never in one release: drop or rename a column, change a column type, make a nullable column NOT NULL without
   default, tighten a constraint the old build can violate. Dropping a column is *not allowed at all* by 0055 D8.1.
5. Every module version ships a compatibility test that runs its code over fixtures at the previous data version
   (0055 D5 ruling, open point 8).

**Risks to design for:**
- *Boot child on two nodes.* The upgrade boot child (REQ-772) runs on every node that boots. This is safe because the
  apply takes a per-tenant-and-module transaction-level advisory lock with `pg_try_advisory_xact_lock` and refuses the
  second caller with `upgrade_running` (`apply.ex`, around the `SET LOCAL lock_timeout` block). Second node: no double
  upgrade. Idempotency is pinned by REQ-772 criterion 5.
- *Old node, new tenant version.* When a tenant is at N+1 and an old node still serves, old code sees newer data. This
  is why the version-ahead refusal (`module_version_ahead`, 0055 D5) is wanted; it is **not built** (see section 8).
- *Migration replay on a rolling start.* UAT assumption: migration replay is idempotent; confirm before relying on it
  with two nodes starting within seconds.

**Recommendation:** R1 for the demo and QA first (slice S2 below), B1 only if a customer demands instant code rollback.

## 4. (c) Per-tenant upgrade windows and who triggers them

| Trigger | Who | Good for | Status |
|---|---|---|---|
| **Admin action** | The tenant's TENANT_ADMIN (permission `ModulesManage`): plan, read it, apply with the hash and a rationale. | Class B changes, any plan with a decision; a customer who wants to choose the time. | **Built** (REQ-768, 770). |
| **On boot** | System actor, flag `LETFLOW_MODULE_UPGRADE_ON_BOOT=true`. | Plans that are all Class A with no step: nothing for a human to decide. | **Built**, default off (REQ-772). |
| **Scripted by operator** | Operator runs `demo_upgrade_chain.sh` per tenant with a tenant admin token. | Demo/QA fleet. | **Built** for the demo only. |
| **Scheduler (a window)** | A platform job applies Class-A plans inside a tenant's configured window (e.g. 02:00–04:00 local). | Production tenants who want "never during working hours". | **Not built.** |
| **Fleet driver** | Platform operator rolls through tenants, halts after N failures. | Many tenants. | **Not built**; 0055 D5 names it a prerequisite of the first release that raises `min_data_version`, and it needs its own platform-scope permission (INV-10). |

**Recommendation:** default = *Class A upgrades itself shortly after deploy (flag on in QA first); everything else waits
for the tenant admin, who sees the plan in the application; production tenants may later be given a window setting.*
The window setting is a tenant setting, not a rule; its default is an open owner question (O3). A tenant that has not
upgraded stays *working* on its old definitions (stamps accepted, REQ-769); only the module's **write handlers** are
refused with 409 until the upgrade (REQ-771). So an unupgraded tenant degrades, it does not go down.

## 5. (d) Locks while a tenant upgrades; what is refused; for how long

From `apply.ex` and the records (0055 D5, REQ-770):
- The apply is **one transaction** with `SET LOCAL lock_timeout = '10s'` and a transaction-level advisory lock keyed
  on (tenant schema, module). A second apply for the same tenant and module is refused immediately (`upgrade_running`);
  other tenants and other modules are not affected.
- Inside the transaction the tenant's `tenant_modules` row is locked `FOR UPDATE`. Readers are never blocked by Postgres
  row locks; ordinary record **reads** and writes of other modules continue.
- What is refused for the module being upgraded: a second upgrade (`upgrade_running`), and — in the gap before the
  upgrade — module write-handler completions (409 `upgrade_required`, task stays pending, nothing committed, REQ-771).
  After the transaction commits, the new version is live at once.
- **How long:** a Class-A-only plan is definition inserts and activations, normally well under a second (UAT
  assumption: not measured; the demo chain run on `showroom` is the place to measure and write the number down). If the
  lock cannot be taken within 10 s the transaction fails with code `lock_timeout`, the journal row is `failed`, the
  tenant stays on the old version, and nothing is half-done.
- **Long upgrades (data steps) are not possible yet.** 0055 D5 designs three phases: stage (one transaction), migrate
  (batches, old definitions still active, each batch commits and advances a cursor, resumable, fenced by an epoch so
  two runners can never both write), cutover (short; `lock_timeout`, record writes briefly blocked on the affected
  tables, a catch-up pass). Writes are therefore refused only for the cutover moment, not for the whole migration.
  Until that runner exists, `apply.ex` refuses a plan with a step (`upgrade_needs_runner`) — so today the long case is
  *unreachable by construction*, which is the safe state.
- The 409 shape: the existing problem of `Error.module_upgrade_required/0`, fixed text, no module id/hash/version in
  the body (REQ-771 criterion 4). Open point: whether the web screen should show "your administrator must upgrade
  module X" using a separate permitted read (O4).
- Column promotion with `ALTER TABLE`/`CREATE UNIQUE INDEX` takes an exclusive lock and is the exception, post-cutover by
  default above a row threshold (0055 D5). That threshold is an open point of 0055 (point 2), not decided here.

## 6. (e) Rollback

| Layer | Can it be rolled back? | How |
|---|---|---|
| **Code (the build)** | Yes. | Redeploy the previous build (rolling again, or the blue node). Safe only while the data is still readable by the old build: i.e. only if no tenant was upgraded to a version the old build rejects. Rule: never contract before the previous release is out of rollback range. |
| **Manifest (compiled)** | Same as code; it is code. | |
| **Tenant data, before cutover / failed apply** | Yes, automatically. | The apply is one transaction; a failure leaves the old version (REQ-770). `abandon` for staged runs (0055 D9, designed). |
| **Tenant module version, after a done upgrade** | **Designed, not built.** | 0055 D9: a new journal row `kind: rollback` to the *previous* version only, with `down` for every step, `ModulesManage` and a rationale; entity definitions roll back by re-activating the previous row (reversible, `activate_definition/4`). No rollback route exists in `tenant_modules.ex` (grep shows none). |
| **Public-schema DB migration** | Only if written as expand-only. | Never roll back by dropping; roll *forward* with a corrective release. |
| **Web bundle / mobile** | Bundle yes (redeploy files); mobile no (store). | |

**Not reversible (by design, 0055 D9, D8):** a step without a tested `down` (default is irreversible, fail closed);
`irreversible` steps; copy-field onto a column that already mixes old and new rows (reversible only for journal-marked
rows); process-definition drafts a tenant has activated since; promoted columns and constraints (never dropped, a
rollback only *reports* a constraint the old version lacks); permission widening already live at deploy; anything a
user did on the new version (new records in new fields stay in the stored blob). Lossy steps are forbidden in an
upgrade altogether (D8.1). A rollback below `min_data_version` is refused (`rollback_below_min_data_version`).
**Recommendation:** point-of-no-return text appears in the plan before the admin applies (designed in 0055 D9).

## 7. (f) On-site (customer-delivered) installs

**Finding:** nothing for this exists. I searched `docs/` for on-site/on-prem delivery and for a signed package format
and found none (the only "pack" documents are *solution pack* decisions 0026/0027/0029/0052, which are definitions
installed into a running tenant, not a delivery artifact). So this section is a recommendation from scratch.

**What an application package is (recommended):** one archive per *application version*, containing: the release
build (or container image reference), the module manifests and pack files, the public- and tenant-schema migrations,
the web bundle, a `package.json`-style *manifest of the package* (name, version, previous versions it can upgrade from,
required platform version, `min_data_version` per module, list of files with SHA-256), and the plain-language release
notes.

| Question | Option A (recommended) | Option B | Option C |
|---|---|---|---|
| Integrity | SHA-256 per file inside a signed package manifest; installer refuses on any mismatch. | Checksums file only, published on a website. | None (trust the medium). |
| Authenticity | **Detached signature** over the package manifest (modern public-key signature such as Ed25519, or Sigstore/minisign-style tooling); the installer ships with the **public** key and refuses unsigned or wrongly signed packages. | Per-customer HMAC key (shared secret). | none |
| Why | The private key never leaves the vendor; a stolen customer machine cannot forge a package. | Shared secrets leak with the customer's backup. | Unacceptable for tenant data. |
| Offline | Everything inside the archive; installer needs no internet; verification and install are local. | | |

**Who holds the signing key:** this is the owner's decision (O1). Recommendation: the vendor (ai-dala) holds the
private key in a hardware token or offline vault, signs only in the release pipeline after the gates are green, with a
second person for key use; the public key is fixed in the first installer and a **key rotation** path exists (the new
public key is itself signed by the old one). A key compromise needs a revocation list shipped with the next package.
INV-4 applies: no key material in git, logs or responses.

**Offline install flow (recommended):**
1. Customer administrator receives the package and puts it on the server (or media).
2. Installer verifies signature and every checksum *before* it touches anything; prints what it will change.
3. Checks the "can upgrade from" list against the installed version; refuses a skip it does not support.
4. Takes a database backup (a hard step, not optional) and records its location.
5. Runs the public-schema migration, swaps the build (rolling if two nodes, else a short restart), starts.
6. Tenant upgrades follow exactly the same plan/apply as in the cloud (admin action, or boot flag for Class A). The
   installer does not invent a second upgrade path.
7. Prints a report; writes the installed package id and signature fingerprint to the audit.

**Differences from cloud:** no fleet driver (a handful of tenants), no demo promote worker, the customer decides the
window, and **rollback = restore the backup** plus the previous package (because the customer may not be able to run
a corrective release quickly). Licensing/entitlement of an on-site customer is out of scope here (O5).

## 9. Open owner questions

- **O1 Signing key:** who holds the private key, where, and who may use it? Is a vendor-held key acceptable to on-site
  customers, or do some need their own trust root? (Blocks S7.)
- **O2 Downtime promise:** is "no downtime" a promise for production customers, or only for the demo/QA? This decides
  whether R1 is a nice-to-have or a requirement and whether blue-green is ever worth the cost.
- **O3 Upgrade window default:** may Class-A plans be applied automatically in production at deploy (flag on), or only
  inside a tenant-chosen window, or only by the tenant admin? Starting value is a setting, not a rule.
- **O4 Tenant-user message:** what should an end user see while their module is awaiting the upgrade (the 409 today
  carries a fixed technical text)? Who is told to act — the tenant admin only?
- **O5 On-site entitlement:** licence checks, expiry and support rights for delivered packages — in scope or not?
- **O6 Support window:** how many previous versions must an on-site package be able to upgrade from (this fixes the
  length of every expand/contract overlap and the compatibility-test burden)?
- **O7 Backup duty:** is a verified backup before an on-site upgrade a hard stop the installer enforces, and who is
  responsible for it?
- **O8 Rollback promise:** after a tenant has worked on the new version for days, is "go back" a promise? (0055 D9 says
  only to the previous version and only if every step has `down`; most real upgrades will not qualify.)
