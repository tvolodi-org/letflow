# T-1848 — Architect verdict on permission-only access with tenant-defined roles (decision for UAT)

No issue number was given in the task text, so this file is named after the task id. The verdict itself is
`docs/design/roles-architect-verdict.md` (the path the task names).

## Question

Owner principle D-129 (as given in the task text): access is checked against permissions only, never role names; no
built-in business roles; only the platform admin is preinstalled; the owner side creates the tenant admin; the tenant
admin creates all other roles. Is the principle right for Letflow, what is the target model, what happens to each
role-name site, is a "task worker" shortcut needed, what are the risks, how to migrate with no behaviour change, what is
superseded in the open-core note, and what must the owner decide?

## Decision

1. The principle is right, with four conditions: a role name may identify a row but never decide access; the platform
   admin and tenant admin are protected rows whose permission set is a computed rule (`all`, `all_tenant_scope`), not a
   name; some permissions are not assignable to custom roles (platform scope, role management, admin-only switches and
   asset actions); routing a task to a role is addressing, not access.
2. No task-worker shortcut: the task-worker sites become two permissions (see all tasks; work tasks in a granted scope).
3. Every role-name site in the T-1846 inventory becomes a permission, a scope rule on permissions, a row flag, or
   identification only; none must stay a role-name check.
4. Migration starts with stage 0: replace the role-name sites by permissions while the nine roles are still compiled in;
   the first PR is the import site. Tables, backfill, live switch, management routes, tokens/IdP, web and removal follow.
5. Disagreements with T-1846: stage order; TENANT_ADMIN guards must key on the protected row, not the name; module
   `role_grants` are global today, not per installed module; the "594 test files" count does not reproduce.
6. Finding: a user who holds only STOREKEEPER sees every task of the tenant in the task list, while a task worker sees
   only their own (`is_task_worker_only?/1` names five roles and not STOREKEEPER). This cannot be kept exactly with
   permissions; it is flagged as a probable defect for a security ruling, not decided here.
7. Open core: custom roles belong to the open build; no socket should sit on the access decision; T-1842 section 1.6
   option A and the `custom_roles_enabled?/1` callback are superseded.
8. Owner choices O1 to O6 (verdict table): existing starter roles, starter roles for new tenants, automatic grants on
   module updates, delegated role management, free or paid custom roles, limits.

## Reasons

- The code already decides every route by permission (`evaluate_access/2`, `role_allows?/2`); the names live in the
  compiled table and about twenty other sites, all of which have a permission form.
- Decision 0084 D2 already loads a per-tenant input at the request edge and passes it to the pure decision; the target
  model generalises that precedent.
- The storekeeper task-list case shows the risk of name checks: adding a ninth role silently changed who sees all tasks.
