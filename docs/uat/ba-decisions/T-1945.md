# T-1945: the four-eyes switch in the pilot and first-customer notes

No issue number was given in the task text, so this file is named after the task id. Docs only: no code, nothing on
QA. The design this rests on is `docs/design/four-eyes-switch.md` (task T-1944, merged as #4459) and its UAT record
`docs/uat/ba-decisions/T-1944.md`.

## Question

Task text (operator, PM 2026-11-14): "Qoimeks Client 1 (stock-only pilot, small company) may need the four-eyes rule
switched to two eyes. DOCS ONLY: add a short section to docs/status/qoimeks-migration-readiness.md (fit/gap table and
readiness conditions: the four-eyes switch, which approvals exist in the stock module, the new permission, the audit
line 'self-approved, four-eyes off') and one line to docs/runbooks/pilot-rollout.md (decide per customer whether to
switch it off, who does it, audit check)."

## Decision (for UAT)

1. **Stock approvals.** The stock module has one four-eyes approval: `stock_opening / approve`, kept apart from
   `submit` by `distinct_from` (`priv/modules/stock/generate_pack.exs`, `two_step_definition`, used only for
   `stock_opening`). Every other stock process (receipt, issue, write-off, transfer, handover, return, reversal, count
   posting) is one step. This matches the design, section 2 rows 3 and 14, and section 6.
2. **When Client 1 needs the switch.** Only if one person both issues and approves, which count 5 of the readiness
   note (how many operator names) will show. With two people who may post stock, nothing changes (default ON).
3. **Who switches it.** The company administrator (TENANT_ADMIN) through the new tenant-scope permission (working name
   `ApprovalRulesManage`, design section 1), with a reason. The open owner rows of the design (name, platform admin
   exclusion, non-assignable, service users) are not decided here.
4. **Audit check.** One `approval_rule.changed` entry for the switch and one `task.self_approved` entry with the note
   "self-approved, four-eyes off" per self-approved opening (design, section 3.3).
5. **Readiness condition C17** in the readiness note: if needed, slices 1 and 3 of the design built and merged, the
   switch turned off with a reason, and the audit check passing in a QA rehearsal. Added as fit/gap row G22, section
   1.4, condition C17 and one row of the owner table.
6. **Pilot runbook.** One Onboarding step (step 6) in `docs/runbooks/pilot-rollout.md`: decide per company, the
   administrator switches it, the audit check. No new heading (the runbook's headings are pinned by
   `test/letflow/pilot_rollout_runbook_test.exs`, test T1).

## Reasons

- The owner decided the rule, default ON, "by permission" and the audit text (design, section 0); this task only places
  that in the two pilot documents.
- The switch is not on main (`git grep -n "FourEyes\|four_eyes\|ApprovalRules" origin/main -- lib web/src priv` prints
  nothing), so both documents say "planned, not on main" and make it a readiness condition, not a step that can be done
  today.
- Making it conditional on count 5 avoids asking for a build that a two-person client does not need.

## UAT assumptions, to be confirmed by the process owner

- The switch is turned off before the opening lines are loaded, so the first opening can be posted by the one person.
- The QA rehearsal check (switch off, one self-approved opening, then switch on and the next self-approval is refused)
  is enough evidence for condition C17.
