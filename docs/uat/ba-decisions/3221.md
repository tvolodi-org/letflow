# BA decision for UAT: which account advances timers in the swiftroute scenarios (issue #3221)

Business analyst: swiftroute (UAT).

## Question

Four swiftroute scenarios advance a timer as test control: `shipment-ops-timeout-escalation` (step 2), `shipment-ceo-stall-fails-closed` (step 3), `driver-incident-ops-assessment-lapses` and `driver-incident-finance-estimate-lapses` (steps 3-4). They and BA decision T-0321 point 5 call for "a swiftroute tooling account holding the Process Operator responsibility". The QA account list has no such account; the only swiftroute tooling account is `swiftroute-admin-user` (TENANT_ADMIN), which runs T-0295 and T-0521 used for advance-timer only.

Option (a): ask infra to create a new tooling user `swiftroute-timer-user` with PROCESS_OPERATOR only. Option (b): accept `swiftroute-admin-user` for timer advances.

## Decision (UAT only)

**Option (b).** In the swiftroute UAT scenarios, the timer is advanced by the existing tooling account `swiftroute-admin-user` (TENANT_ADMIN), under these limits:

1. It is used for the advance-timer action and for nothing else in a scenario. It never performs a persona's business step and never serves as the actor of a refusal check.
2. It is a tooling account, not a persona: it is not added to the actor roster as a scenario actor (the roster header already treats the per-realm `<slug>-admin-user` accounts that way).
3. The run report names the account used for each timer advance, so a reader can see that a TENANT_ADMIN, not a persona, moved the clock.
4. No infra request is made now. Nothing is provisioned, and no role is assigned or widened by this decision.
5. This replaces the account named in T-0321 point 5 (a tooling account with PROCESS_OPERATOR). The other parts of T-0321 stand. The four scenarios (and their "BLOCKED until infra provides the account" wording) are changed in a separate UAT-design task; I did not edit them here.

If the owner later wants the narrower account, option (a) remains open and replaces this decision with no scenario logic change other than the account name.

## Reasons

- **The permission is held.** The matrix row `InstancesAdvanceTimer` is "yes" for PLATFORM_ADMIN, PROCESS_OPERATOR and TENANT_ADMIN, "no" for the other roles (`docs/roles.md`). TENANT_ADMIN is therefore a legitimate holder; the step is not made to pass by widening a role.
- **No access change is needed.** Option (a) creates a user, a credential and a role assignment in the QA realm: an access change that the infra owner and the process owner must approve, and which has already blocked four scenarios. Option (b) uses an account that exists and is already used for this purpose.
- **The risk of the wider role is contained.** PROCESS_OPERATOR is narrower than TENANT_ADMIN, but the difference matters only if the account is used for more than the clock. Limits 1-3 keep it to the clock, and the refusal checks of these scenarios are done by personas, not by this account. PLATFORM_ADMIN is still never used (tenant-side tests do not use platform authority).
- **Not a false PASS.** Timer steps run for real with an account that holds the permission; the scenarios no longer sit in BLOCKED for a missing account.
