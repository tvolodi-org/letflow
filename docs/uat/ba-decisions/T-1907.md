# T-1907 — Is Letflow ready to take the Qoimeks pilot client (Client 1)?

Recommendation to the owner, not a decision. Written by the business analyst, 2026-11-13. Docs only. The task text gives no issue number, so this file is named after the task id.

**Decision for UAT only; the process owner configures production.**

## Question

Owner statement D-143 (PM, 2026-11-13, quoted from the task text): "the first production action is migrating the Qoimeks pilot client (Client 1) onto Letflow; it moves when the Letflow applications are ready (D-115)". The PM update of the same day adds: "STOCK-ONLY pilot: assets and fixed asset count NOT needed for the first migration; needed: stock module, codes/barcodes, import, voice, a way to keep the old token working". The questions are:
- what fits and what is missing;
- how the data moves and how the move is rehearsed;
- which conditions and owner items stand in the way.

## Answer

The full note is `docs/status/qoimeks-migration-readiness.md`. It is built on the Qoimeks inventory of Client 1 (`Qoimeks-team/project/client1-inventory.md`, 2026-11-13, read-only; copy in `state/tasks/T-1907/sources/client1-inventory.md`). In short:
1. **Stock only.** Client 1's confirmed use is the Excel import and reading the stock. It has 666 items, 134 places, 600 balances and 3 imports, with no money and no printing.
2. **Not ready.** The stock module may not be enabled for a customer tenant until ledger slices L6 and L7 are done (decision 0073, PILOT GATE row). Neither is on main: `Letflow.Ledger.authorize/3` accepts `:read | :reconcile` only, and `lib/letflow/modules/stock/access.ex` says "not built (L6)". No open issue builds them.
3. **Three conflicts that need the owner:**
   - **The old token.** It cannot keep working in Letflow, because stock accepts only a signed-in person; an API token gets 404 (`lib/letflow/modules/stock/router.ex`).
   - **Negative balances.** They are refused (`insufficient_stock`).
   - **A count that replaces the balance.** Letflow posts a difference. Only the D-094 freeze mode makes the formal count replace the balance (`docs/runbooks/stock-counts.md`, "The freeze locations mode").
4. **No new production access.** The ten read-only counts the PM holds (inventory §4) settle the open rows. The note maps each count to its rows. The inventory's eleven client questions stay with the owner.
5. **Owner items:**
   - the token vs accounts, minus balances, counts, history and Android or PWA;
   - the production go, including the D-050 rule for the real extract;
   - the VPS money and the data location, the DNS token and the backup key;
   - production sign-in, voice keys, whether Client 1 pays, and the window.

## What I decided for UAT (the rehearsal on QA), with reasons

All of these are UAT assumptions, to be confirmed by the process owner. They govern the QA rehearsal only. For production they are recommendations.
- **The rehearsal uses same-shape test data, not Client 1's data.** Reason: the inventory's move rules say "no real data leaves production (D-050)" (§8.10). The test set copies the shape of the data from the inventory: 666 items, 134 places in the `RI2` scheme, unit `шт`, 3 decimals, and a few minus and zero rows.
- **Opening balance, not history (R-1).** Reason: Letflow posts opening documents at posting time, with no backdating (decision 0079 D1), and the T-1616 runbook leaves history out.
- **Negative or zero balances are not loaded (R-2).** Each dropped row is listed in `report.txt`. Reason: the ledger refuses a balance below zero (`lib/letflow/modules/stock/stock.ex`), and the converter drops rows ≤ 0 (`quantity_not_positive`).
- **The rehearsal proves the formal count with `freeze_locations` (R-4).** Reason: it is the only Letflow path in which a count sets the balance (`docs/runbooks/stock-counts.md`).
- **A rehearsal passes only on equal quantities per item and place**, plus one hash of the sorted (item, place, quantity) list. Equal record counts alone are not enough. Reason: inventory §8.10 asks for "counts and md5 per table plus current balances equal". A per-table md5 cannot compare two different schemas, so the hash of the business list takes its place.
- **Two clean rehearsals before any production step.** Reason: one run shows the tool works; a second run on a fresh tenant shows the result is stable.
