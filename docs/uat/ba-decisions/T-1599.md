# T-1599 — D-115 design: the public repo holds source code only

Task: T-1599 (workflow `ba_question`), owner decision D-115 of 2026-11-10 (portfolio, all projects).
Status: DESIGN ONLY. Nothing is moved, deleted, rewritten or pushed by this document.
Copy for the portfolio: the operator copies this file to portfolio `proposals/`.

## 1. Question

D-115: the public repo `tvolodi-org/letflow` must hold source code only. Requirements, project documentation and
agent instructions leave it. What leaves, where it goes, what reads those paths today, how the engine, agents, CI and
merge flow keep working, what happens to git history, and in what order, without ever breaking CI?

## 2. Decision (summary for the owner)

1. **Classification**: SOURCE stays (lib/, web/, apps/mobile/, priv/, config/, test/, deploy/, build and CI scripts,
   `mix.exs`, `.github/`, README, licence files). Everything under section 4 "NOT source" moves, about 30 MB of the
   working tree plus `handoffs/` (41 MB, 3,864 files) and `lib/letflow/design/` (21 MB, 564 files).
2. **Companion repo**: a private repo `tvolodi-org/letflow-project` whose tree mirrors the original paths
   (`docs/...`, `handoffs/...`, `.claude/...`, `CLAUDE.md`). Readable by the owner, the lab's machine user and the
   named agents' deploy key only.
3. **Readers keep working through one rule**: a "companion root" that every reader resolves in the same way
   (`LETFLOW_COMPANION_DIR`, default `<repo root>/.companion`, and the files are overlaid at their old paths in a
   worktree or CI checkout). Tests that need the docs are split in two groups: **source tests** (run for everybody,
   including forks) and **companion tests** (tagged, run only where the companion is present). Not a submodule.
4. **History**: do NOT rewrite in place. Recommended: the lab keeps working in a **private** repository that holds the
   whole history and the issue tracker; a **new public repo** gets a squashed, source-only first commit and is fed by a
   one-way export. In-place `git filter-repo` plus force push is described as the alternative; it is the owner's
   separate decision either way.
5. **Order that never breaks CI**: companion repo first, copy, switch readers (dual-read), prove CI green with the
   tree still full, delete from the tree, then history. Every stage is its own PR and can be undone by reverting it.
6. **OSS-1 (T-1597)**: its scanner and report are not on `origin/main` yet (`git ls-tree origin/main docs/open-source`
   prints nothing; only the design exists, in the task folder). **Scope of this decision:** it decides
   stages 0 to 6 (nothing here depends on OSS-1) and the comparison of the two history options from sourced facts only
   (git keeps deleted files; a rewrite changes SHAs). It does **not** decide stage 7 (the history action): that needs a
   separate, later decision record that cites the delivered OSS-1 report. Section 9 lists how each possible finding
   would change the plan; it is conditional text, not a claim about findings.

## 5. The private companion repo (question 2)

- **Name**: `tvolodi-org/letflow-project` (private). Reason: it holds the project's non-code, not only "docs".
- **Layout**: mirrors paths exactly: `CLAUDE.md`, `.claude/agents/*.md`, `docs/**`, `handoffs/**`,
  `lib/letflow/design/**`, `test/fixtures/uat/**`, `scripts/gh_work.sh`. A reader changes only the root, never the
  relative path. A top-level `COMPANION.md` states "mirrors <public repo> paths; do not add code".
- **Who may read it**: owner (admin), the lab machine user `tvolodi` (write), CI of the public repo through a
  **read-only deploy key** stored as an Actions secret (see 6.3). No external collaborators. The public repo's README
  does not link to it.
- **History**: start with a fresh `git init`, then import the moved paths **with** their history by
  `git filter-repo --path ...` run on a *mirror clone* (needs the tool, which is absent on this host; installing it is
  an install from a not-yet-enabled source, so it is the owner's call and listed in section 12). If the tool is not
  installed: first commit is a plain copy and the full-history copy is the offline bundle (section 8.1).
- **Merge flow in the companion**: no merge queue and no heavy CI (a YAML/Markdown lint only). Lab tasks of kind
  `requirement`, `ba_question`, `uat_design` push a short-lived branch and fast-forward `main` after a rebase; the
  existing keep-both conflict resolver for `docs/requirements.yaml` in `publish.sh` is reused unchanged on this path.
  Side benefit: today a docs-only PR still runs the full product CI shard 1 (`ci_docs_only.sh files`); these changes
  stop costing product CI at all.

## 6. What reads these paths today and how each keeps working (question 3)

### 6.1 The mechanism: one companion root, overlay in worktrees

- `LETFLOW_COMPANION_DIR` names a checkout of the companion. Default in the lab: `$TEAM_ROOT/companion` (one shared
  clone, updated by `lf.sh setup` with `git fetch` + fast-forward).
- `lf.sh setup` creates, in each task worktree, **symlinks** from the old paths (`docs`, `handoffs`, `.claude`,
  `CLAUDE.md`, `test/fixtures/uat`, `lib/letflow/design`) to the companion checkout, and the product repo's
  `.gitignore` lists those paths so the tracked tree can never take them back by accident. Rejected: a git submodule
  (pins a SHA in the public tree, shows the private repo's name publicly, and every companion edit would need a
  product commit), and copying (two copies drift).
- A worktree with writes to a symlinked path would write into the one shared companion checkout and mix tasks. So the
  overlay is a **copy** for tasks that edit companion paths (requirement, uat_design, ba_question) into the task's own
  companion worktree (`git worktree add companion-T-NNNN`), and a read-only symlink for implement tasks. The engine
  commits companion edits as a second commit stream (section 6.5, change E1).

### 6.3 CI and the merge queue (public repo)

- `ci_changed_paths.sh`: `BACKEND_PATHS_RE` currently lists about 15 doc paths as gate inputs. Those entries are
  removed in stage 5 together with the files; the guard test `ci_backend_path_filter_test.exs` is edited in the same
  PR (its table and its layer 3 literal scan). `ci_docs_only.sh` and its job in `ci.yml` become dead (no `docs/`
  left except README and `docs/design-notes/`): stage 5 keeps the script but its `files` mode now selects nothing.
- Two CI modes: **full mode** (push to the private working repo or to a branch of the main repo, and the merge queue):
  the job checks out the companion with the read-only deploy key (`actions/checkout` with `repository` and `ssh-key`)
  into `.companion` and exports `LETFLOW_COMPANION_DIR`. **Source mode** (pull requests from forks, which receive no
  secrets): no checkout, `:companion` tests excluded, a visible job summary "companion tests skipped".
- Required checks `Backend gate (mix letflow.check)` and `Frontend gate (npm run check)` keep their names. The
  backend gate in full mode must run the companion tests, otherwise a merge could break a doc-reading test unseen. Rule:
  the merge queue always runs full mode.
- A deploy key is read-only and per repository; rotation is one secret edit. Failure mode: key missing or revoked -> full
  mode fails loudly ("companion not reachable"), never silently falls back to source mode on the queue.
- `cd.yml` and `cd-pwa-web.yml` do not read `docs/` apart from comments (checked: the `docs` hits in `.github/` are
  comments and the path filter); no change except the comment pointing to `docs/runbooks/qa-lag.md` and
  `docs/merge-queue.md`, which become companion paths.

2. Record the SHA of every branch tip and of `main` in a file in the companion (`HISTORY-MAP.md`).

### 8.2 Option A — rewrite in place (`git filter-repo` + force push)

- Needs `git-filter-repo` (absent on this host; installing it is the owner's decision) and a **fresh mirror clone**
  (filter-repo refuses a used clone).
- Consequences: every commit SHA changes (all 5,719); all 415 branches and every open PR are rewritten or must be
  recreated; closed PRs on GitHub keep their old merge SHAs in the web UI and old objects stay reachable at
  `refs/pull/*` and through cached views until GitHub support purges them (GitHub keeps unreferenced commits fetchable
  by SHA; only a support request or deleting the repository removes them). Forks keep the old history for ever.
  Engine state (`state/team.db`) stores SHAs and branch names: tasks in flight break. CI caches key on SHAs and are
  rebuilt. Issue links to commits `#N` stay textually but point to dead SHAs. The merge queue must be empty.
- Risk: **the secrets and the content remain readable** at the old SHAs for anyone who has them or any fork; so for a
  true removal this option is weaker than it looks. It also needs a force push over `main`, covered by the lab's rule
  "Force-pushing ... is reserved" in spirit and by the owner's decision.

### 8.3 Option B — a new public repo with one squashed source-only commit

- The source-only tree (after stage 5 deletions) is committed once into a **new** repo; the old repository is renamed
  and made private (history, branches, PRs, issues stay intact there).
- Consequences: no force push, no history rewrite, SHAs of the working repo do not change, engine state stays valid; the
  new public repo starts at 1 commit (no contributor history; the squash commit can credit the project). Stars, watchers
  and old links of `tvolodi-org/letflow` are lost or must be redirected by README; GitHub redirects are lost when a new
  repo takes the old name. Fork network is cut (good for D-115).
- The slug `tvolodi-org/letflow` is hard-coded in `project/team.toml` (`issue_url`), `scripts/gh_work.sh`, `gh` calls in
  lab scripts, workflows and docs; the number of occurrences must be counted in stage 0 (`git grep -c tvolodi-org/letflow`
  in product, lab and template; not measured in this task).
- Two sub-variants, the owner picks the name layout (Q4): (B1) the **private repo keeps working** as the product
  (renamed `letflow-dev`, with all history, issues and the merge queue) and the public `letflow` is a one-way export of
  its source-only tree on each release or merge (a script run by the lab; contributions arrive as patches that the team
  re-applies). (B2) the public one becomes the working repo and the old one is only an archive; this loses the issue
  tracker and breaks the engine slug, so it is **not recommended**.

### 8.4 Comparison

| | A: rewrite + force push | B1: private working repo + new public squashed repo |
|---|---|---|
| Old content still reachable | Yes (old SHAs, forks, refs/pull, caches) | No, the public repo never had it |
| Engine state and SHAs | Break (all rewritten) | Unchanged |
| Open PRs, 415 branches | Rewritten or lost | Untouched in the private repo |
| Issues and PR text (also public today) | Still public | Private with the old repo |
| Force push over main | Required | Not needed |
| Tool needed | git-filter-repo (not installed) | none (git only) |
| Cost | about 2 days incl. dry runs and fixing branches | about 1 day incl. export script |
| Public history value | Kept (but with rewritten SHAs) | Lost (one commit) |
| Rollback | Restore the mirror bundle, force push back | Rename the repos back |

**Recommendation: B1.** It is the only option that actually removes the content from public view, and it breaks nothing
in the engine. The loss of public history is the price; the owner's wording ("source code only") accepts it.
Option A is only worth it if public stars, forks or contributor history are valuable. Both need the owner's explicit
decision before anything irreversible happens (the rename and visibility change are the irreversible-in-practice step:
once public content was cloned it cannot be recalled; making private now stops new exposure only).
