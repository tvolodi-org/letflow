## 1. Off-site copy: allowed for Letflow production only, pull-based
Source: infra discovery section 1 (VERIFIED unless noted).
- **Scope:** the off-site rule applies to **Letflow production only**. It is not a general permission for other systems.
- **Pull, not push.** The Hetzner hosts cannot dial the agent host (it is behind the owner PC's NAT); the agent host can dial out to them. Pull also means a broken-into production server cannot delete or overwrite the copies. The source side uses a restricted read-only key (rsync sender only).
- **Two copies recommended** (infra option D): (1) the **agent host** pulls **twice a day** (home disk 735 GB free; best independence from the provider; its uplink was down about 55 h on 11-05..11-07, so the job must tolerate retries); (2) the **QA host** (113 GB free of 150 GB, Hetzner Nuremberg) or a **later second VPS**. The QA host is the same Hetzner account, so it protects against disk or host loss, not against loss of the account; that dependency is an open owner choice.
- **Worse targets:** the owner's PC (reachable only over the cable from the agent host, single point shared with the NAT, off part of the time); hetzner-prod (crowded, 66 GB free, 38 containers, production for other clients).
- **Bandwidth** (one sample, includes ssh handshake): about 76 Mbit/s up and 27 Mbit/s down for the agent host. A 1.5 MB daily set takes under a second; a 1 GB base about 5 minutes. Not a constraint.
- **Alert on an off-site copy older than about 30 hours** (infra's figure; T-1600 used 26 h for the push status file, the pull job runs twice a day so 30 h tolerates one missed run).
- Extra restore time from off-site: about 10–20 minutes on top of the RTO **[E]**, UAT assumption of infra, not drilled; a new VPS dominates (tens of minutes plus DNS and certificate).

## 2. Encryption
Source: infra discovery section 1; scripts above.
- Production holds **only the public gpg key**. The key pair is generated on the **agent host**, not on production. The private key stays on the agent host (file mode 600) with **one offline copy kept by the owner**. Loss of the private key means loss of every backup, so the offline copy is mandatory. No key pair exists yet (the agent host keyring is empty).
- **Restore tests run on the agent host** (the side that holds the private key), never on production: `restore_test.sh` decrypts with `RESTORE_GPG_HOME`, which would otherwise put the private key on production. Whether Docker is available on the agent host for the throwaway database is UNKNOWN (not probed).
- **Product gap (a requirement to write, not written here):** `scripts/backup/wal_archive.sh` has no encryption step, so WAL segments would leave the server in clear text. It must be fixed **before WAL mode is switched on**. Per D-116 no WAL is used now, so dump and base backups (already gpg-capable) are enough for stage 1 and the gap blocks nothing today.

## 3. Alerts, with D-116 applied

- T-1600 section 4 (AI agent on call) is **narrowed**: while there are no paying clients, nobody is on call and nobody works nights. An alert is read when the agent or the owner next looks.
