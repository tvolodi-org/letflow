# T-2014: photos for items, lots, locations, asset cards and document lines (design for the PM)

No issue number in the task text, so this file is named after the task. The full design is `docs/design/photos.md`.
Design decisions for the UAT build and a recommendation to the owner; production limits, grants and retention are
configured by the process owner.

## Question

The owner (PM 2026-11-16) wants photos on records: several per record, a main photo as thumbnail in lists and cards,
the phone camera, desktop upload by file, drag and drop and paste, caption, order, delete by permission, and an
optional photo as evidence at count lines and at receipt and issue lines. Decide which records, storage, permission
atoms, limits, offline upload, audit, export, the open/closed split, and how this relates to the problem-report
screenshots and the future assets store (one attachment service, not three). End with slices.

## Decision

1. **One attachment service** (`Letflow.Attachments`, planned) with two tables per tenant schema, a blob table that
   can delete bytes and a link table with owner, purpose (`photo`, `evidence`, `file`, `screenshot`), position, main
   flag, caption, thumbnail and lock. Record photos, evidence photos, the future assets-store files and the
   problem-report screenshots all use it. Design section 3, 6.
2. **Not a reuse of the record attachments table**: its bytes live in `repository_artifacts`, which refuses every
   update and delete by trigger, and its routes refuse module-managed types, which every target record is. Design 2.1.
3. **Records**: gallery photos (10, one main) on `catalog_item`, `catalog_lot`, `location_node`, `assets_card`;
   evidence photos (3 per line) on stock and asset count lines, stock receipt, issue and write-off lines, asset
   write-off lines. Design section 4.
4. **Bytes in PostgreSQL** in the tenant schema for v1 (backed up by the existing dump, purged with the tenant),
   behind a store seam for a later object-store adapter.
5. **Checks**: JPEG, PNG, WebP by first bytes only; structure walked once; EXIF, XMP, IPTC and GPS removed on the
   server; scanner; 5 MiB and 4096 px for the original, 100 KiB and 400 px for the client-made thumbnail; counted in
   the company's storage allowance.
6. **Atoms**: read follows the owner record's read; new `PhotosAdd` and `PhotosDelete`; a user may delete their own
   unlocked photo. Evidence photos lock when the sheet closes or the document is issued or posted.
7. **Audit** per change without bytes or caption text; **retention** as the owner, screenshots 30 days; **export**
   as a `photos` dataset of the data export.
8. **Offline**: online in v1 with retry in the form; the offline queue is left to the owner (open question below).
9. **Open build**: everything needed to use photos. Closed candidates: object store, server-side recognition and
   re-encoding, long retention and legal hold.
10. **Slices** P1 to P11 with sizes and order in design section 8; first P1 to P3 (the asset card gallery).

## Reasons

- Deletion must really remove bytes (a wrong shot, a person in the picture, 30-day screenshots), and the existing
  byte store cannot (`lib/letflow/repository/artifact.ex`: "both `BEFORE UPDATE` and `BEFORE DELETE` triggers reject
  any mutation"; `lib/letflow/repository/entity_attachments.ex` `delete/2` is metadata-only).
- Five places keep uploaded bytes today with five rule sets (design section 2); a sixth for screenshots would repeat
  that. One service gives one set of checks, one strip, one audit shape and one quota.
- PostgreSQL storage adds no server, credential or dependency, and is in the backup today.
- The first-bytes check and the scanner already exist (`lib/letflow/identity/tenant_logo.ex`,
  `Letflow.Repository.AttachmentScanner`); the 5 MiB and 6-image values are the owner's for the review thread
  (`lib/letflow/problem_reports/review.ex` `@max_image`, `@max_images`).
- Read follows the owner so no new read rule can leak a photo of a record the user cannot see (INV-5 404).

## UAT assumptions, to be confirmed by the process owner

- The caps: 10 gallery photos per record, 3 evidence photos per line, 2048 px client scaling, 5 MiB / 4096 px
  original, 100 KiB / 400 px thumbnail, 60 uploads per user per hour.
- Write-off lines get evidence photos; transfer, hand-over, return, opening and commission lines do not.
- STOREKEEPER gets `PhotosAdd` (through the stock manifest grants), not `PhotosDelete`; a user may delete a photo
  they added while it is not locked.
- "The future assets store" is read as files of the assets application (purpose `file`); no file on main describes
  it.
- The client-made thumbnail is accepted in v1 (it may not match the original); server re-encoding is optional
  slice P10.
- The storage estimate (risk 2 in the design) is arithmetic, not a measurement.
