# T-1944: configurable four-eyes rule (approval by a different person)

Recommendation to the owner, not a decision, for every point the owner has not decided (marked O below). No issue
number was given in the task text, so this file is named after the task id. The full design is in
`docs/design/four-eyes-switch.md` (plain summary and owner table on top).

## Question

The PM relayed an owner decision on 2026-11-14 (quoted from the task text): "the four-eyes rule must be configurable in
the process; one-person companies (our small clients; Qoimeks Client 1 may need it off) reduce it to two eyes: the same
person issues and approves. Decided details: setting PER TENANT and per document type or process step where the
approval exists (asset opening first, then every other approval step that has the same rule); default stays ON (four
eyes); the tenant admin switches it off BY PERMISSION (a new permission atom, never a role name: D-129/D-131/D-132
roles-as-data model); when one person approves their own document the audit log records 'self-approved, four-eyes off'.
Open build: the switch is part of the open base, not a closed feature."

Asked: does it touch the roles and permission model; where does a "different person must approve" rule exist today;
where is the setting stored and read; slices; risks; a pilot note for Qoimeks Client 1.

## Decision (for UAT)

1. **One mechanism.** The only real four-eyes rule in the product's processes is the engine's `distinct_from` check
   (`lib/letflow/engine/separation_of_duties.ex`). It is used by two shipped steps: `assets_opening / approve` and
   `stock_opening / approve`, each kept apart from `submit`, which the issuer completes at issue (decision 0083 D5;
   `priv/modules/assets/generate_pack.exs`, `priv/modules/stock/generate_pack.exs`). The switch acts there and nowhere
   else; tenant-authored processes with `distinct_from` (QA fixtures of Vortex, Meridian, Swiftroute) get it too.
2. **Not four-eyes, not switched:** count commission signatures and the signer role, "only the chair may" checks, the
   chair-not-member rule, definition-promotion self-approval, the script publisher rule (it has its own `scripts.sod`
   switch, decision 0053 D6). Procurement's self-decision ban is four-eyes but on its own code path and procurement is
   held; it gets a later slice.
3. **Permission model:** one new tenant-scope atom (working name `ApprovalRulesManage`), held by the tenant admin through
   the computed tenant-scope rule, tenant-wide only, non-assignable (decision 0088 D4). No role name is read; the check
   still compares user ids, never roles.
4. **Setting:** a new core tenant table keyed by process key and step; no row means ON, so the migration changes no
   data and no module version bump is needed for the core and asset-opening slices (no process definition changes).
5. **Read:** only when the same person would be refused (zero extra queries otherwise); a read failure means ON.
   **UAT decision:** the setting in force when the approval is completed counts, not the one in force when the document
   was issued. Reason: switching back to ON must stop pending self-approvals at once (fails safe).
6. **Audit:** one `task.self_approved` entry with the note text "self-approved, four-eyes off" in the same transaction
   as the completion; the switch change itself is audited with who, when and the reason.
7. **Slices:** core (M) -> asset opening (S, first) -> stock opening (S) -> admin screen (M) -> procurement (S, later)
   -> corpus scan test (S).
8. **Qoimeks Client 1 (stock only):** the stock opening approval is the only four-eyes step in the stock module; every
   other stock process is one step. Switching it off for `stock_opening / approve` covers the need.

## Reasons

- The owner decided the rule, the granularity, the default, the "by permission" and the audit text; this note only maps
  them onto the code. Putting the switch in the one engine check keeps one place to test and one place to review.
- Default ON plus "no row means ON" plus fail-closed reads means no tenant changes behaviour until its admin acts.
- Non-assignable and tenant-wide follow 0088 D4 (a permission that lowers a control is held only by the admin rows) and
  the stage 0 switches `TenantSecurityManage` and `TasksReassignRouted` (`lib/letflow/api/authorization.ex`).
- The live-setting choice (point 5) is a UAT-only business call, made here because it only concerns which value a
  waiting approval sees; it does not widen access.

## Open for the owner (recommendations, not decided)

- O-1 the atom's name; O-2 keep the platform admin in the platform tenant out (explicit `false`, as ruling 2 of
  `docs/design/roles-stage0-security-rulings.md`); O-3 non-assignable in the corporate role editor.
- O-7 **service principals:** recommended that four eyes stays ON for a service-principal actor even when the tenant
  switched it off (touches access, so not decided here).
- O-8 a reason is required when switching off (as `scripts.sod`); O-9 no refusal when the tenant has two or more
  possible approvers (a hint on the screen only); O-10 promotion self-approval and the script rule keep their own rules.

## UAT assumptions, to be confirmed by the process owner

- The approver of an opening is not the user who issued it, unless the tenant switched four eyes off for that step
  (extends the UAT assumption of 0083 D5 and 0079 opening Q2).
- In a UAT tenant with one administrator, that administrator may switch four eyes off and then issue and approve an
  opening alone; the audit log must show one "self-approved, four-eyes off" entry per such approval.
