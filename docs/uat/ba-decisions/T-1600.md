## 3. Off-site backup
Why: with local disk only, losing the server or its disk loses the data **and** its backups together (`docs/runbooks/backup-restore.md` section 1). What must travel off-site: the dump sets and WAL of `dump/`, `base/`, `wal/` (section 4 of the runbook), including the Keycloak database. **Never** off-site together with the database: `LETFLOW_SECRETS_MASTER_KEY` (decision 0016 A and B; REQ-785 criterion 4). The copy must be encrypted before it leaves the server (`BACKUP_ENCRYPT=gpg` already exists in `scripts/backup/`), so a stolen off-site disk shows no tenant data.

| | Option 1: second small server or storage box (different Hetzner location) | Option 2: the owner's PC over a tunnel |
|---|---|---|
| Cost **[E]** | EUR 4–6 per month for tens of GB; current data is tiny (demo set 1.5 MB, Qoimeks 110 KB, T-1569 section 2) | EUR 0 in money; the owner's electricity and time; a tunnel tool is free (which one: infra) |
| Availability | always on; a failed nightly push is visible in the same hour | PC is off, asleep, moved or behind a home NAT part of the time (the agent host, also behind a PC NAT, was down about 55 h on 11-05..11-07 [V]); a nightly copy will sometimes be missed |
| Encryption at rest | copy is gpg-encrypted before sending; the private key is **not** on the production server nor on the target | same gpg step; plus the owner's disk encryption is the owner's (UAT assumption: not verified) |
| Bandwidth | datacentre to datacentre; no issue at these sizes | home upload speed limits the first full base copy and any large restore; a restore of a few GB over a home link can take hours |
| Who can write / delete | recommended: **the target pulls** (or the key on the server may only append), so a broken-into production server cannot erase the off-site copy | a tunnel from production into a private PC widens the attack surface of the owner's PC; the PC would have to pull, which means the PC must be on at the pull time |
| Who restores | the AI agent on call, from the target to a new VPS (section 4), using the private key held by the owner or the agent's secret store (to agree with infra) | the agent cannot restore while the PC is off; the owner must be reachable. A human is a bottleneck, against owner answer (e) |
| Main risk | provider-level incident affects both only if the same account and location are used: choose another location and keep the credentials separate | silent gaps (missed days) and a restore that depends on one person |

**Recommendation (UAT assumption, to be confirmed by the process owner and infra):** Option 1 as the off-site copy; **in addition**, the owner's PC may hold a monthly copy of the encrypted set and of the gpg private key backup, as a last resort, not as the only copy. Retention at the target: not shorter than the local one (14 days, `scripts/backup/retention.conf`) and **not longer than the purge rule allows**: a purged tenant's data survives in off-site copies as long as the target's retention (`docs/runbooks/tenant-provisioner-credential.md`, "Delete"); the privacy notice must say so.
Not built yet: the push/pull step and its status file. It would add a status file for infra to poll like the four existing ones (runbook section 4); it belongs in a separate implementation requirement (section 7).

## 4. What the AI on-call needs
The on-call is an agent, so every alert has to be machine-readable, and every response has to be written down. No human is paged.
1. **Health endpoints (exist).** `GET /health` returns `{"status":"ok","sha":...}` with no authentication and no database access (`lib/letflow/router.ex`), so it shows "the application process answers", **not** "the database works". `GET /metrics` is public Prometheus text (`lib/letflow/routers/metrics_exposition.ex`). **Gap:** no check that goes through to the database; to be decided as a separate requirement (section 7). Until then the agent also needs a login-page check and the backup status files.
2. **Alert log.** One append-only file or feed on the production server (and copied off the server) that the agent reads: one line per alert with UTC time, alert id, severity, source and a runbook name. Reason: the agent has no phone. It must also include "no alert for N hours" heartbeat lines, so silence from a dead monitor is itself visible (UAT assumption).
3. **Alert list, each with a runbook** (a runbook = what to check, what to do, when to stop and wake the owner): site down (login page and `/health` from outside); backup status file `"ok":false` or older than its schedule (`status/dump.json`, `base.json`, `prune.json`, `restore_test.json`; 8 days for the restore test, runbook section 4); off-site push failed or older than 26 hours; disk above 80%; certificate expires in 14 days; Keycloak down; memory pressure or a container restarting; failed restore drill. Existing: only the backup/restore parts (runbook sections 6–8). Missing: the rest, to write in stage 1 preparation.
4. **Restore drill schedule.** Weekly automatic (`restore_test.sh`, Sunday 03:30 UTC, runbook section 4). Quarterly manual drill (runbook section 10), now also **from the off-site copy onto a different host**, done by the agent, timed against the RTO. The first drill must have passed before the first paying customer.
5. **Limits of the agent (what it must not do alone)** (UAT assumption): no dropping databases or the old database after a restore (the "point of no return", runbook section 6), no deleting off-site copies, no change of DNS or billing. These steps wait for the owner, and the alert text says so.
6. **Credentials the agent holds** are listed by infra (SSH key to production, read key to the off-site target, the gpg private key or a way to ask for it); the production server must not hold the key that can decrypt its own backups. To agree with infra (ai-dala-infra-18).

## 5. RPO and RTO
Still open owner questions (REQ-785 criterion 8): no number is approved. Proposal stays: RPO 15 minutes (WAL archive + daily dump) on the same server, **host-loss RPO = the age of the last off-site copy (up to 24 hours with a nightly push; with off-site WAL shipping, minutes, a later requirement)**; RTO 1–2 hours same host, **half a day** for a new VPS from the off-site copy (UAT assumption; the quarterly drill measures the real number).

## 6. Stage 1 preparation checklist (no purchase, nothing switched on)
Each line can be built and checked on the QA host or on this repository, without a new server.
- [ ] **Sizing dry run on the QA host:** start the production compose shape (application, Postgres, production Keycloak on Postgres) with memory limits matching the smallest candidate type; record peak memory and disk; decide the server type from it.
- [ ] **Production Keycloak on Postgres** compose file and realm import from `priv/keycloak/provisioner/v2/tenant-realm.json`; a login test on QA.
- [ ] **Wildcard certificate procedure** tested on a QA name with Let's Encrypt DNS-01 and the restricted token (pattern already works for `*.letflow.qa.bizdala.com`, T-1569 section 3); renewal and its alert.
- [ ] **Backup units** from runbook section 4 installed on the QA host for a trial, WAL mode on, the weekly drill run once and its seconds recorded.
- [ ] **Off-site step prototype:** encrypted push or pull of one dump set from the QA host to a **free local directory or an existing non-production host** (not a new purchase); check that the copy decrypts, that the production-side key cannot decrypt it, and that a deleted source file does not remove the copy. Add the status file and its poll rule.
- [ ] **Restore from the off-site copy** onto a throwaway container, with the real master key stored apart; time it.
- [ ] **Alert log and heartbeat** on QA, plus one runbook per alert in section 4 item 3; the agent runs a dry exercise of each (stop a container, age a status file, fill a small tmpfs for the disk alert; no load tools).
- [ ] **Hardening list** for the new server written as a script/runbook (firewall, ssh keys only, automatic security updates, no password login), tested on a throwaway container or the QA host without changing it permanently.
- [ ] **Terms and privacy notice draft** naming Hetzner, Cloudflare and the off-site target; retention of backups after a company is deleted.
- [ ] **Not in this list, wait for the PM's money confirmation:** ordering the VPS and the off-site target, switching DNS, any real customer data.
