# T-1859 — Roles stage 0: may a scoped tenant-admin grant count for task work, and is a platform admin in the platform tenant allowed at the admin-only switches and at taking a routed task away? (security rulings, decision for UAT)

The task text gives no issue number, so this file is named after the task id. The full rulings, with their evidence, are in
`docs/design/roles-stage0-security-rulings.md` (the path the task names).

This is a recommendation to the owner, not a decision on production access. The task asks for security-review rulings.
Neither ruling changes any behaviour, in stage 0 or today.

## Question

`docs/design/roles-stage0-slices.md` section 5 leaves two rulings open:
(1) Should a scoped TENANT_ADMIN grant count for scoped task work (see, claim, complete), as a TASK_WORKER grant does?
(2) Should a PLATFORM_ADMIN in the platform tenant pass the two interactive tenant-admin switches (scope enforcement, the
service-principal flag) and the "take a routed task away" check, which refuse it today?

## Decision

1. Scoped TENANT_ADMIN grant: it does **not** count. Today's rule stays: under scope enforcement, task work needs a TASK_WORKER
   grant that covers the task's unit. Stage 0 (S0-2) is built in form (b). Stage 2 is the earliest stage where this may change,
   and there it becomes an explicit exclusion of the task-work permission from the tenant-admin row. From stage 3 a company may
   give that permission to a role of its own, on purpose.
2. Platform admin in the platform tenant: it stays **refused** at both switches and at taking a routed task away. Stage 0 (S0-3,
   S0-4) is built in form (b), with explicit `false` clauses for PLATFORM_ADMIN. In stage 2 these become explicit exclusions from
   the platform-admin row. Any later change is its own requirement and security review.

## Reasons

- Ruling 1: decision 0051 Q3 (ruled) names a TASK_WORKER grant as the approver condition, and `docs/roles.md` ("Known limitation:
  scoped approvers") says that a TENANT_ADMIN grant never substitutes for it. Counting it would silently give approval authority
  to every scoped tenant admin in every enforced company. Tenant isolation (INV-1) is not affected, because the change stays
  inside one company.
- Ruling 2: the switch refusal is a reviewed security fix (REQ-519 2f-b, SEC S-3), and the test
  `test/letflow/routers/tenant_scope_enforcement_test.exs` ("a platform-tenant PLATFORM_ADMIN without TENANT_ADMIN is refused
  the PUT") pins it. The last-admin gate counts only interactive tenant-wide TENANT_ADMINs as people able to flip. The reassign
  guard (GH #2931, `lib/letflow/tasks.ex` `authorize_reassign/3`) stops a holder of the reassign permission from taking a routed
  task for itself, and the platform admin holds that permission.

## Effect on UAT

None. No answer changes, so no scenario changes. The roster's platform admin (`actor-platform-admin`) and the tenant admins
keep their current outcomes. UAT assumption, to be confirmed by the process owner: no UAT scenario relies on a scoped tenant
admin working tasks without a TASK_WORKER grant.
