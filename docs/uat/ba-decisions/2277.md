# BA decision for UAT: is GH #2277 met, or does "declared value is a required start field" need a requirement?

Business analyst: swiftroute (UAT).

## Question

GH #2277 (SwiftRoute Shipment Approval, audit finding PA-SWIFTROUTE-002) lists four acceptance criteria:

1. `ops-review` and `ceo-approval` each have a form with a required decision field matching the variable the outgoing edges test.
2. The declared value is a required start field.
3. Completing either task without a decision is rejected (test).
4. The process validator reports status OK.

PR #2334 delivered criterion 1 and part of 3. REQ-462 (PR #2358, GH #2340) later added `required_outputs`. Is the issue now met by AC3 plus the documented declared value, or does the start-field item (criterion 2) need a requirement?

## Decision (UAT only)

**The issue is not fully met. Criteria 1, 3 and 4 are met. Criterion 2, the required start field, needs a requirement.**

1. **Criterion 1 is met.** Both tasks have decision forms. The required enumerated fields `ops_decision` and `ceo_decision` are exactly the variables the outgoing edges read.
2. **Criterion 3 is met.** The 2026-10-07 comment said it was not, because an omitted decision key was accepted. REQ-462 then declared `required_outputs` on both tasks, so a completion without the decision is refused with a retryable 422 and the task stays open. This is also stated in the fixture description (v1.6), and PR #2358 replaced the "KNOWN LIMITATION" tests with real assertions. The old comment is out of date on this point.
3. **Criterion 4:** the issue's own comment and the v1.5 to v1.7 history show the definition passing validation. I did not re-run the validator. That is a check for the confirm step, not for me.
4. **Criterion 2 is not met, and documenting the value does not meet it.**
   - A requirement is "required" when the product refuses a start without it. Today the only thing that makes `declared_value` required is a sentence in the description and a number type that applies only if the value is submitted.
   - The repository's own records say the same: REQ-462's open question says the line "stays unmet", and #2335 deferred it to a future start-form mechanism.
   - The business risk is the one the audit named. A shipment above 500 whose request leaves out the value must not skip the CEO co-signature by accident.
   - The gap cannot be closed by editing the SwiftRoute definition, because the node model has no start-form node. It needs an engine or definition-model capability: required start variables checked when an instance is created. That is a product requirement with design and security review (it touches the instance-start path, `POST /instances`), not a UAT-environment choice.
5. **What this means for the team:**
   - A requirement is to be written for "required instance-start variables, validated at instance creation, declared by the definition", with SwiftRoute's `declared_value` as the first adopter.
   - The requirement writer must keep its criteria checkable, for example "a start without `declared_value` is refused and no instance is created". It must not presume how the gateway behaves today.
   - This task does not write that requirement. Its workflow has no requirement step and its criteria forbid changes to anything but this file.
   - GH #2277 therefore must NOT be closed on this decision. Its remaining scope is only criterion 2, and it should wait for that requirement. No confirm-and-close task should follow.
6. **For UAT meanwhile:** scenarios start SwiftRoute shipments with an explicit declared value. A scenario must not rely on the system refusing a start without it. If one is needed, it stays BLOCKED until the requirement is delivered.
