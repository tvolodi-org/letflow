# T-1970: tenants behind the deployed module version after a QA deploy

Recommendation to the owner, not a decision, for everything outside QA. The full design check (why, options, risks,
slices) is `docs/design/module-upgrade-after-deploy.md`. The task text names no issue number, so this file is named after
the task id.

**Decision for UAT only; the process owner configures production.**

## Question

After a deploy that bumps a module version, QA tenants answer 409 `upgrade_required` on task completion until someone runs
the plan and apply by hand, although the plans say `applicable_on_boot: true` (class A, no data step). What should QA do,
and what is recommended for production?

## Decision (QA / UAT only)

1. QA runs the upgrade on deploy that is already built: `LETFLOW_MODULE_UPGRADE_ON_BOOT=true` in the QA host's environment
   file. Every plan that is class A with no data step is then applied to every QA tenant at application start.
2. After every QA deploy the operator checks that no QA tenant is left behind: the log line `module upgrade on boot: summary`
   (its `failed_count` and `left_count`), and, for any module left for the administrator, the fleet rollout ("Module
   rollouts", platform tenant's PLATFORM_ADMIN) or `scripts/demo_upgrade_chain.sh` per tenant.
3. Plans that are not class A, or have a data step, or need `ack_destructive`, stay manual on QA too.

## Reasons

- Decision 0080 Q3 already rules the flag "is set to `true` on QA only" and keeps production for the owner; this decision
  only applies that ruling. The code applies exactly the plans that are class A with no step and never fails the boot
  (`lib/letflow/module_upgrade/boot.ex`).
- Class A with no data step cannot lose or reshape data (decision 0055 D2 as quoted in 0080 Q3); QA tenants are test data.
- Nothing in this repository sets the flag: `grep -rn MODULE_UPGRADE_ON_BOOT deploy/ scripts/ .github/` finds nothing;
  `git grep -l` finds only the reader (`config/runtime.exs`, `boot.ex`), tests and docs. The QA environment file is local to the host (`deploy/docker-compose.qa.yml`, `env_file: .env`). The finding is
  consistent with the flag being unset (not verified, see the assumptions below): with the flag unset (default `false`), the boot child reads and writes nothing.

## Recommendation for production (owner decides)

Flag off. After the owner agrees to a deploy, the operator upgrades with the fleet rollout (halt after N failed tenants,
per-tenant window, per-tenant outcomes). Later, one slice for a banner and an "Upgrade now" screen for the tenant
administrator (needs a read-only "upgrade pending" signal first). Details and effort: the design file, sections 2 and 5.

## UAT assumptions, to be confirmed by the process owner

- The QA host's environment file currently does not set the flag to `true` (I could not read it; the design file section 1
  names the two checks that confirm it).
- QA tenants each have their own realm, so `demo_upgrade_chain.sh` runs once per tenant with that tenant's admin token.
- After a module upgrade, an image rollback is done only after the tenant rollback route has taken the tenant back.
- The first QA start with the flag on stays under the ~30 s health-check wait of `deploy/redeploy-qa.sh` (not measured).
