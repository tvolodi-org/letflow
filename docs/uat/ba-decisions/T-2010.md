# T-2010: maintenance hub as a separate Letflow instance (recommendation to the owner, not a decision)

No issue number in the task text, so this file is named after the task. The full design is
`docs/design/maintenance-hub.md`.

## Question

The owner's picture (PM 2026-11-15): problem reporting runs on a separate Letflow instance, the maintenance hub, on the
team host; other instances are registered in it; a remote instance connects to the hub; the hub hands work to the task
engine. Check the picture against what is built, the rule "the host calls out, nothing calls in", security, customer
data, the hub's own shape, the engine link, instance registration, and give slices.

## Answer (recommendation)

1. The picture fits what is built (each instance's platform-company report list, read-only cursor export, owner inbox,
   owner list of class `review`). New: a write-back of the status into the reporter's instance, and a
   registered-instances list.
2. A hub on the home host breaks the "calls out only" rule if instances connect to it, and the owner's phone could not
   reach it (no overlay network, PM 2026-11-14). Recommended option C: the hub on a small public server in Germany; the
   hub pulls from each instance with a per-instance read-only token and writes status back with a narrow per-instance
   status token; the team host pulls from the hub. Until that server exists, QA's platform company stays the hub of one.
3. Customer text: kept cut-down, 90 days after close in both places, owner only; the delete job is not on main yet and
   must exist before a production or customer instance is registered; a customer's own production instance needs an
   owner decision and an agreement with that customer first.
4. The PM and operator get service tokens, never user accounts. The owner list moves to the hub with the existing import.
5. The engine link is a work-item contract plus an adapter on the team host (`team.py add`, state back), so moving the
   engine onto Letflow later replaces only the adapter.
6. Slices H0 to H9 with sizes are in the design, section 7.

## Reasons

* Every credential on main is held by the side that calls out, with only a hash on the server
  (`Letflow.Plugs.ReportExportAuth`); option C keeps that and adds no route that accepts customer text from the internet.
* The export has no status field (`export_map/1` in `lib/letflow/problem_reports.ex`), and the bell is written in the
  reporter's own company (`Letflow.ProblemReports.Status`), so a decision taken in the hub needs a way back.
* The lab engine listens on 127.0.0.1 only (`engine/ui.py`), so only the team host can queue work in it.

## UAT assumptions, to be confirmed by the process owner

* The hub keeps its copy no longer than the source copy (90 days after close).
* A registration is "silent" after 12 hours without a successful poll (default, a setting).
* The setting name `LETFLOW_MAINTENANCE_HUB_ENABLED` and the table `registered_instances` are proposals (planned, not on main).
