# BA decision: where does MES live on the platform, three options (task T-1822, MES-5)

Business analyst. Owner request 2026-11-12. No issue number was known; the file is named after the task, as `T-1818.md` and `T-1820.md` are. DRAFT design only: no code, no client contact, nothing on production, money, DNS, secrets, demo or a public repository.

## Question

Where does a MES (Manufacturing Execution System) live on Letflow? A) new modules on the module manifest and upgrade chain; B) a separate service talking through API and events; C) integrate an existing open MES or historian and add only Letflow documents. For each: core changes, data model, plant data, real-time limits, offline/edge, tenant isolation, security and audit, effort by phase, risks, first prototype.

## Decision (short)

Full text: `docs/design/mes/05-platform-options.md`.

| Option | Core change | Effort to first batch (assumption) | Main risk |
|---|---|---|---|
| A in-platform modules | Ledger causes and lot status in stock (manifest hash changes, U1/U2 run, security review); posting-kernel decision | 4 to 5 months incl. 1-month prototype | Shared ledger policy; small team |
| B separate service | Same ledger and hold change **plus** a service credential and identity link | 7 to 11 months | Two sources of truth, doubled security work |
| C integrate | Small | 1 to 3 months per client | Fit, licence, selling a third-party product |

Recommendation (a proposal, not an owner decision): **A**, phased (prototype, `mes_core` + `mes_batch`, `mes_stream`, discrete, machine feed). B only for a client that needs long offline work on site; C as fallback for a client that already runs a MES.

## Reasons

* The ledger change (consume/produce causes, lot status) is needed in every option, because booking into stock stays in Letflow (part 1 row 4, part 3). B and C do not remove it.
* A manifest change alters the hash and forces an upgrade run on installed tenants (`docs/design/core-extraction-design.md` section 3). That is the main unknown of A, so the first prototype tests it.
* A inherits schema-per-tenant isolation, the audit chain and roles; B rebuilds them; C leaves them outside.
* The platform has no time-series store and no inbound device route (`lib/letflow/integration_mappings.ex` is a mapping only; part 2). Raw machine data stays outside the core; this is where B is strongest.
* The open/closed split allows closed MES modules over a community core (`T-1521.md` sections 1 and 4).
