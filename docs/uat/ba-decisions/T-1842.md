# T-1842 — Open core with closed sockets: design note (decision for UAT)

No issue number was given in the task text, so this file is named after the task id.

## Question

PM D-126: how should Letflow be an open core with a few closed features behind sockets, starting with a role-management socket? Deliverable: `docs/design/open-core-sockets.md`.

## Decision

The design note is written (`docs/design/open-core-sockets.md`). The decisions taken for the note:

1. **Role socket shape:** a behaviour with a default implementation in the open repo (today's code moved behind it); a closed package replaces it by build-time configuration. The open repository never names the private one (no submodule, no ignored folder).
2. **Two roles versus nine:** the code has nine built-in roles, not two. The note assumes the open build keeps the nine and only permission-bearing custom roles come from the closed package (option A, size M guess). This is a UAT assumption, to be confirmed by the PM.
3. **Isolation and audit:** unchanged, because sockets sit above data access and take no repository or audit writer.
4. **Licence:** facts only (MIT chosen; no LICENSE file on this branch). The LICENSE action stays with the PM.

## Reasons

- `lib/letflow/api/authorization.ex` closes the role set (`@roles`, `roles_from_strings/1`) and docs/roles.md says a module cannot create a role (0046 D10). A custom role cannot be an atom, which is the main cost.
- Existing "custom roles" (`POST /roles`) are process-routing names, not permission sets.
- T-1521 section 4 already set the principle "corporate adds, does not patch" and left the per-edition pins as an open item; the note makes it concrete.

- When a licence ends, custom roles grant nothing and data stays readable (proposal only; production behaviour is the owner's decision).
- All size labels (S/M/L) are guesses.
