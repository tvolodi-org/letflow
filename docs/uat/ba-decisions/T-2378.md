# T-2378 (K4): a count from the old Qoimeks app at the old address

Recommendation to the owner, not a decision, for production. For UAT on the QA tenants, the business
analyst decides the rule in section 9. The task text gives no issue number, so this file is named after
the task (T-2378). This is task K4 of `docs/status/qoimeks-old-client-compat.md` section 5.3.

## Plain words first

- **What the old app does.** A storekeeper picks an item and a place, chooses the operation
  «Инвентаризация» and types the number they counted (0 allowed). The old server **replaced** the
  balance with that number at once. It answered with the movement, and the phone showed «Проведено ·
  <place>: <new balance> <unit>».
- **What Letflow does.** A count is a quick count document. The person who counts issues it. Then an
  administrator approves it in My Tasks, and only then does the balance change. The tenant's four-eyes
  switch for counts (Approval rules, step `stock_quick_count / approve`) is ON unless an administrator
  turns it OFF. While it is ON, the approver must be a different person from the one who counted.
- **Today the old address cannot count at all.** It answers 400 `invalid kind`. Even with the switch
  OFF, the shared code could not approve its own count: the OFF switch lets only a person who signed in
  interactively approve their own document (section 2, fact F3).
- **The old app can show only two kinds of answer.** (a) A movement, which it always shows as a green
  «Проведено». (b) An error text, which it shows as a red «Ошибка: <text>». It has nothing like
  "waiting". So a count that waits for an administrator can only be shown as a red «Ошибка: …»
  that says in words that the count was accepted and is waiting.
- **Option 1: follow the switch.** With the switch OFF, the count changes the balance at once, as on
  the old server. With it ON, the count waits for an administrator, and the phone shows the red waiting
  text.
- **Option 2: always at once.** Every count from the phones changes the balance at once, whatever the
  switch says. No second person ever looks at a phone count.
- **Recommendation: option 1** (section 6). The switch must mean the same thing for the phones as for
  the web. With one administrator and the switch ON, that administrator can approve the phone counts
  alone, because the counter is the shared code, not the administrator. So ON works even in a
  one-person company.
- **The owner's question, in one sentence (section 7):** may the shared phone code ever approve its own
  count (option 1: only when the company has switched four eyes for counts OFF; option 2: always), and
  is that switch ON or OFF for Client 1 (O-006)?

## 1. The question (task text, PM GO 2026-11-20)

The old app's count (kind `adjustment`, `qty` = the counted quantity, 0 allowed) replaces the balance
at once, and the app expects a movement answer with `balances[]`. Letflow's quick count goes through
issue and an administrator's approval when the tenant's four-eyes switch for counts is ON. The PM asked
for the options and what they mean for the staff, in each state of the switch:

1. The count at the old address is a quick count document. It posts at once when the switch is OFF.
   When the switch is ON, the answer is a clear "waiting for approval" shape that the old app can show.
2. The count is always at once under the shared-access actor, with the audit trail. This amends
   decision 0091 section 9 and A12, and four eyes is not applied.

The PM also asked about: the 0 count, the negative book (decision 0090), the freeze guard, the 422
`balance_in_other_rows` case (T-2286), and idempotency by the body `id`. The note must recommend one
option and size K5 and K6.

## 3. Option 1: the count follows the tenant's switch

The old address creates a quick count through `Documents.quick_count/4` with the shared access as the
counter. The counter completes `submit` at issue, as today. Then:

### 3.1 Switch OFF (`stock_quick_count / approve` four eyes OFF)

- **The storekeeper sees:** the same as on the old server. «Проведено · A-01: 7 шт» (green), the
  form clears, and the count is in the history.
- **The administrator does:** nothing for the count. They read the audit if they want to.
- **What is built:** in the same call, the shared access also completes `approve` on its own count.
  This happens only because the tenant's switch row says OFF. Fact F3 must be widened for exactly this
  case: credential `:shared_access`, process `stock_quick_count`, step `approve`, switch OFF. The
  existing `task.self_approved` audit entry ("self-approved, four-eyes off") is written for each count,
  with the credential's actor. With the switch ON, or with no switch row, the widening does not apply
  (it fails closed, like F3 today).
- **Control and audit "by whom":** the same control the tenant administrator chose for the web. The
  administrator turned four eyes OFF on purpose, with a reason, and that change is audited
  (`approval_rule.changed`). Each count carries the audit entries `task.complete` (submit and approve)
  and `task.self_approved`. All of them name the shared access's one synthetic actor. The person who
  counted is known only by the typed operator name, which is free text and not checked (decision 0091
  section 5).

### 3.2 Switch ON (the default; on the QA tenant today, F11)

- **The storekeeper sees:** a red «Ошибка: Подсчёт принят и ждёт подтверждения администратора»
  (the text is a proposal, see section 9 A3). The form stays filled. Pressing again with the same
  numbers repeats the same answer and does not create a second count (section 5, idempotency). The
  balance on the screen does not change, and the count is not in the history until it is approved.
  - Why not a green answer: anything below 400 must be a movement, and the app always shows it as
    «Проведено» with the balance (F7). That would tell the storekeeper the balance changed when it did
    not.
  - Why not 409: the app would show «Эта операция уже была проведена» and clear the form.
  - Why not 422: the app would show «Ничего не слышно. Повторите».
  - Why not 404, 401, 408, 429 or 5xx: the 0.1.3 offline queue would retry forever (F7).
  - **So the only honest shape is 400 `{"error": "<waiting text>"}`.** This matches the PM's rule
    "400, not 409" for the old address.
- **The administrator does:** opens My Tasks, takes the count's `approve` task, checks the item, the
  place, the book, the counted quantity and the typed operator name, and approves or cancels it with a
  reason. **One administrator is enough.** The counter is the shared access, not the administrator,
  so `distinct_from` passes (F2, F3). This is real four eyes: the phone person counts and a named
  administrator confirms.
- **If stock moves before the approval** (for example the same phone posts an issue at that place),
  the approval is refused `quick_count_stale`. The administrator cancels the count, and the storekeeper
  counts again. At a busy place, a count that waits for hours will often go stale. That is a real cost
  of ON.
- **Control and audit "by whom":** the approval is by a named person (the administrator's own
  account). The count is by the shared access, with the typed name.
- **What is built:** the call issues the count and stops. The client `id` is bound to the issued
  document, so a repeat answers from the document's state (section 5). The typed operator name is
  kept on the `submit` task, so the administrator sees who counted.

## 4. Option 2: always at once under the shared access

The old address creates the quick count and, in the same call, the shared access completes `approve`,
whatever the switch says.

- **The storekeeper sees:** always the old behaviour. «Проведено · A-01: 7 шт», the form clears, and
  the count is in the history.
- **The administrator does:** nothing for phone counts, ever. Counts made on the web still follow the
  switch. So on a tenant with the switch ON, the Approval rules screen says "four eyes" for counts, but
  phone counts skip it. The web cannot show this exception (the batch rule is "the web SPA does not
  change"), so it can only be written in the runbook.
- **What is built:** F3 is widened for credential `:shared_access` on `stock_quick_count / approve`
  without any condition. Decision 0091 section 9 ("cannot initiate or record a count") and A12 are
  amended. Recommended: one audit entry per count saying "approved by the shared stock access, four
  eyes not applied", so that the exception shows in the audit.
- **What it means for control:**
  - Anyone who has the shared code can set any balance of any item at any place to any number,
    including 0, at once.
  - No second person ever sees a phone count before it changes the book.
  - The audit "by whom" for both steps is one synthetic actor shared by every phone. The person is
    only the typed operator name, which is not verified.
  - The shared code can already post receipts and issues at once today (single-step processes, no four
    eyes: `docs/design/four-eyes-switch.md` section 2 row 14). What option 2 adds is the "set to"
    power of a count, plus a way round a control the tenant may have turned ON.
  - It goes against the rule as built: only an interactive sign-in may approve its own document (F3),
    which `docs/design/four-eyes-switch.md` owner row 7 left to the owner.

## 6. Recommendation: option 1

1. **One meaning for the switch.** The administrator's Approval rules choice then holds for every
   count, from the web or from a phone. Option 2 makes a hidden exception exactly where most counts are
   made (the phones), and the screen cannot show it.
2. **Smallest change to settled rules.** Option 1 widens F3 only when the tenant has switched four eyes
   OFF, which is the owner's own rule for one-person companies (`docs/design/four-eyes-switch.md`
   section 0). Option 2 widens it always, against owner row 7 of that design and A12 of decision 0091.
3. **ON is workable with one administrator.** The counter is the shared access, so a single
   administrator can approve phone counts (section 3.2). A one-person company is not forced to switch
   OFF.
4. **OFF gives the old behaviour exactly.** If the owner decides OFF for Client 1 (O-006), the staff see
   no difference from the old server.
5. **The price.** With ON, a count that differs from the book shows a red «Ошибка: …», and a waiting
   count can go stale. The PM must accept that, or the owner chooses OFF. The runbook must tell the
   storekeepers what the waiting text means.

## 9. UAT decision (QA tenants only)

For UAT, the rule to build and test is **option 1**, once the owner's answer in section 7 allows it.
Until then K5 may be written, but K6 waits. On `qoimeks-qa2` the switch for counts is ON (F11, as the
PM stated it; to be read live before the walk). So the re-run (K15) checks:

1. A count that differs from the book answers the 400 waiting text. `actor-qoimeks-qa2-admin`
   approves it in My Tasks, the balance becomes the counted number, and a repeat of the same `id` then
   answers 200 with the movement.
2. A count equal to the book answers at once.
3. With the switch OFF (the administrator switches it with a reason on the Approval rules screen, and
   switches it back ON after the step), a count answers at once, and the audit shows
   "self-approved, four-eyes off".
4. The refusal texts of section 5 (negative, freeze, other rows).

UAT assumptions, to be confirmed by the process owner:

- A1: The waiting answer is 400 `{"error": text}`, because the old app has no other honest shape
  (F7).
- A2: The reason code of an old-address count is `recount`.
- A3: The new texts (waiting, cancelled, freeze, other rows, stale) are in Russian, because the
  storekeepers read Russian or Kazakh and the server cannot tell which language the phone uses. K5
  fixes the exact words. The old server's existing English texts stay as they are (PM rule).
- A4: A count equal to the book is answered at once and does not appear in the history list (F2 against
  F1).
- A5: Cancelling a count from the history reverses the difference and does not restore the old number.
