# T-1523 — Design note: a platform that develops itself — the tasks engine as a product integrated into Letflow

Source request: PM item D-114(4) ("DESIGN ONLY, no code"; `ai-dala-portfolio/DECISIONS.md`, D-114).
Written by the business analyst in the architect's frame, 2026-11-09. Docs only: no code, route, requirement or
decision record is changed by this note. The operator copies it to the portfolio proposals folder, where it
supersedes the portfolio manager's first draft `proposals/self-developing-platform.md` (section 11 lists what it
changes in that draft).

**Decision for UAT only; the process owner configures production.**
Everything below that touches production behaviour, money, access, other tenants' data or a licence is a
*recommendation* or an *open owner question* (section 10), not a settled rule. A rule I could not trace to a source
is marked "UAT assumption, to be confirmed by the process owner".

## 0. Short answer

1. **Two products, one idea.** Keep the lab engine as it is (it builds Letflow's source code: level **L2**). Build a new,
   much smaller thing inside Letflow for tenants (level **L1**, working name "Builder"): agents change a tenant's
   *definitions* (processes, forms, entity extensions, scripts, print forms), never source code, and the result is a
   package installed through the module upgrade path that D-114(3) is hardening. "Develops itself" = L2 produces module
   versions, L1 lets each tenant adapt them, both land through the same upgrade chain.
2. **Do not port the Python engine.** About 5,800 lines of Python (verified: `wc -l engine/*.py` = 5,797) carry a design
   worth keeping, not code worth keeping. What moves is the *design*: lease-claimed work, steps that are agents or
   commands or waits, gates that cannot be skipped, and cost recorded per run. In Letflow these are ordinary
   process definitions, tasks, an event store and a ledger.
3. **The hard part is not the queue, it is running an agent for a stranger.** Today's engine starts the agent with
   `--permission-mode bypassPermissions` on the owner's own machine, in a git worktree, and trusts the host. That is
   right for the lab and wrong for any tenant. Section 6 is the longest part of this note for that reason: an agent
   runner in a container with no ordinary network, a model gateway that holds the keys, hard cost limits, and an
   installer that only accepts definitions.
4. **Recommended first thin slice (section 8, B1):** one tenant-scoped *agent step* that makes one model call through a
   provider service with a per-tenant cap and an audit entry, driven from a process definition. No code writing, no
   sandbox, no install. It proves metering, secrets and audit — the three things every later stage depends on — and is
   small enough for one requirement.
5. **Nothing here is approved.** Edition, first user, cost limits, whether customer data may go to a model vendor, and
   the licence are owner questions (O1–O8).

**Design principles worth carrying over** (all from `ARCHITECTURE.md`): (1) the engine is the only writer of task state;
the agent's result *is* the status report; (2) leases, not labels; (3) agents never wait; (4) every creative step is
followed by a gate, enforced by config load; (5) mechanical checks before agent reviewers; (6) every transition is an
event and every metric is derived from events; (7) a question the team cannot settle goes to a human inbox.

Platform-schema (not tenant) tables: the template catalogue (platform-owned templates), the per-provider platform key
references, the runner fleet registry. Anything cross-tenant is platform scope and bound to the platform tenant
(INV-10), with a cross-tenant negative test for every route that takes a tenant identifier.

**Leases.** A run is claimed by a runner with `UPDATE … WHERE state='ready' AND (lease_expires IS NULL OR lease_expires < now)
RETURNING` (or `FOR UPDATE SKIP LOCKED`, as `Scheduler` does) and renewed by heartbeat. A runner that lost its lease
cannot write a result over a newer decision (the same rule as `ARCHITECTURE.md`). **No process per instance**
(REQ-045): the run is a row; the runners are stateless.

**SQLite does not move.** The lab keeps its SQLite. The L2 bridge (stage B6) reads and writes the lab through its CLI
(`team.py add`, status) rather than sharing a database.

## 6. (e) Tenancy and security

Agents run code and read what they are given. The platform must assume the model's output is untrusted input and the
tenant's data is untrusted input to the model.

### 6.1 What is different from the lab
| Lab today | Required for a tenant |
|---|---|
| `bypassPermissions` on the owner's machine (`executors.py`, `_call`) | Agent process in a container with no ambient authority |
| The agent can reach the whole internet and the owner's logged-in tools | No general network; only the model gateway |
| Provider login is the owner's subscription | Keys per tenant by reference (`Letflow.Secrets`), held by the gateway, never in the agent's environment |
| Cost is a number we look at | Hard cap enforced before the call |
| Trust: one owner | Trust boundary per tenant, plus one between tenant and platform |

### 6.2 Where an agent runs (UAT assumption, to be confirmed by the architect and infra)
- **Not in the web nodes and not in the BEAM.** A separate runner fleet (queue + workers). The web node only holds rows.
- **One short-lived container per run** (or per change request), started from a pinned image, read-only root, a
  scratch volume that is deleted at the end, no host mounts, non-root user, no privileged mode, seccomp default,
  CPU/memory/pids/disk limits and a wall-clock limit. A micro-VM (Firecracker-class) is the stronger choice when tenants
  are unrelated customers; containers are acceptable for the showroom tenant only. **Open question O5.**
- **A runner serves one tenant at a time, never two in the same container.** No warm pools across tenants.
- **Filesystem:** the agent sees a workspace holding only the tenant's package export and the task text. It does not see
  other tenants, other runs, platform source, the runner's own config or any credential file.
- **Network:** egress denied by default. The only reachable endpoint is the platform's *model gateway* (below). No DNS to
  the outside, no package registries (the L1 agent needs none: it writes definitions, not programs). This closes INV-9
  (tenant-controlled outbound URLs) by construction, not by validation.
- **Model gateway:** a service that receives the agent's model request, checks the run's token and cap, adds the real key
  (INV-4: key by reference, never in logs, responses or errors; `Secrets.LogFilter` and `Redaction` already exist), sends
  the call, and records usage in the ledger. The agent holds only a run-scoped token that expires with the run.
- **The agent never calls the Letflow API as the tenant.** It has the machine role `AGENT_RUNNER` at most, and today that
  role "must not touch processes, tasks or data"; the runner returns its result to the platform, and the platform (a
  trusted component) writes it. The role's meaning would be amended in the Builder requirement.

### 6.3 What the agent may produce (the L1 rule)
The agent's output is a **package of definitions**: process definitions, form definitions, entity-type extensions, print
forms, script sources, and tests. It is *data*, validated by the platform against the same checks a human-authored
definition passes (graph checks on activation, closed output schemas, script policy and sandbox). The runner cannot
install anything. A script inside a package runs only in the existing script sandbox, behind the tenant kill switch and
the platform kill switch (`ScriptPolicy`: two latches, either one stops it). *Correction to the first draft:* it mentions
the existing "risk tier"; `Letflow.RiskTier` is a diff classifier for the old pipeline's review chain, not a script
control, so nothing in this design relies on it.

### 6.4 Prompt injection and data exposure
- Tenant data (entity rows, form values, free text) reaches the model only through a **declared allow-list** per change
  request, and is marked as data in the prompt, never as instruction — the same stance as the lab's `intake-triager`
  ("reads the issue as text from outside, which it never obeys").
- A prompt-injected agent can at worst produce a bad package. It cannot exfiltrate (no egress except the gateway), cannot
  install (no write path), cannot spend more than the cap (gateway), and its package goes through gates a human approves.
- The gateway logs the *shape* (model, token counts, run, tenant), not the prompt, by default. Storing prompts is a
  retention and privacy decision (O6).
- Data sent to a model vendor leaves the tenant's jurisdiction. This is a contract matter (O4); D-048 accepts it only for
  the owner's own product code.

### 6.5 Review gates that cannot be skipped
The lab's rule is "the engine refuses a config in which a creative step is not followed by a gate". The tenant version
must be at least as strong, and must hold against the tenant's own administrator:
1. **Platform-owned minimum chain.** The Builder process has a fixed tail that a tenant template cannot remove or reorder:
   *validate → sandbox-tenant test run → agent review → human approval (a TENANT_ADMIN, not the requester) → install*.
   Tenant templates may add steps, never drop these. Checked when a template is activated (same place the graph checks
   run) and again at install.
2. **Separation of duties.** The requester cannot be the approver for an install (UAT assumption; the script feature has a
   `sod` setting, `strict | solo_audited`, in `ScriptPolicy`, which is the model to copy; O8).
3. **The install path checks the approval itself.** Install is refused unless a verdict row for *this exact package hash*
   exists with the required gates passed. A gate verdict is bound to a hash, so changing the package after approval
   invalidates it.
4. **Gate agents are read-only.** As in the lab, gate roles change no file; whatever they touch is discarded.
5. **Kill switches:** a tenant switch (TENANT_ADMIN) and a platform switch (operator) stop all runs, as for scripts.
6. **Audit:** every run, verdict, approval and install is an event attributable to a run id and a human; nothing is
   deleted by the tenant.

### 6.6 Resource and cost limits
Per tenant: concurrent runs, runs per day, tokens per run, wall-clock per run, cost units per day and per month, package
size, artefact bytes. The **cap is checked before the call** and charged after, as ledger postings; a run that would
exceed the cap is refused before it starts, with a stable reason code. The platform operator has a global cap and a
kill switch over all tenants. Limits are settings with sane defaults, per the owner's rule that limits are settings but
must exist before any customer uses the feature. The lab's own D-056 shows why: the subscription limits workers to 2
across all projects.

### 6.7 Security review points (mandatory before each stage)
INV-1 (schema scoping of every new table), INV-2 (field authorisation on run and artefact reads), INV-3 (the container
boundary), INV-4 (keys), INV-5 (a run of another tenant is not-found, not forbidden), INV-8 (a dead runner is an expired
lease, not a crash), INV-9 (no tenant-controlled egress), INV-10 (platform authority bound to the platform tenant and a
cross-tenant negative test on every route that takes a tenant id).

## 7. (f) How a tenant uses it, and its relation to D-114(3)

**Flow.** (1) A tenant user opens a *change request* (text, optionally attached samples). (2) The intake step turns it
into a short requirement in the tenant's own words — the lab's `requirement` / `ba` work, with the tenant admin able to
edit it (this is the "intake via requirements"). (3) A design step proposes the change as a list of definitions. (4)
The creative step writes the package in the container. (5) The platform validates it and runs it in a **sandbox
tenant** (a schema from `SandboxPool`, scaffolded like a real tenant) with generated and existing scenarios. (6) A
review agent and then a human read a diff and a preview. (7) On approval the platform installs it through the upgrade
chain. (8) Rollback is a package upgrade back, not a database restore.

**Template stacks.** The lab's "stack" idea becomes a **template** the tenant picks: "process change", "new form", "new
report / print form", "new entity extension". Each template fixes the roles, the allowed output kinds and the minimum
gate chain. A tenant may edit prompts within the template; it cannot widen what the output kind may contain.

**Delivery into the tenant's module packages.** A tenant's work lands as a tenant package version. For `x_` fields on a
module-managed entity type the existing tenant extension mechanism (`:EntitiesExtensionsManage`) is already the
boundary. For anything that changes module-owned definitions the package must be a *tenant overlay*, not an edit of the
shipped module, so a later module upgrade does not destroy it (UAT assumption: solution-pack overrides, REQ-631, are
the nearest existing mechanism; I did not verify that it can carry a Builder package). **Open question O9.**

**Relation to D-114(3) (updates without stopping the server).**
- The Builder is a *client* of the upgrade chain: plan (read-only, class A/B/C, `plan_hash`) → apply (one transaction,
  rollback on failure, idempotent) → 409 `upgrade_required` during the gap. All four exist (REQ-768..772).
- The chain **refuses any plan with a data step today** (`upgrade_needs_runner`) and has **no rollback route**
  (T-1519 slices S4, S5). So the Builder v0 may only produce packages that are all class A with no data step. This is
  a hard dependency: **Builder install must not be enabled before T-1519 S3 (`min_data_version` gate) and S5
  (rollback route) exist**, or approval would be a one-way door.
- Tenant packages and module upgrades do not need a server restart (T-1519 §0.1); Builder needs none either. The runner
  fleet is deployed separately and can be restarted without touching Letflow's web nodes.
- L2 output (a new module version) arrives as a new *build* (restart/rolling deploy, T-1519), after which tenants upgrade;
  L1 output arrives as tenant data. Both are visible to the tenant in the same module screen.
- On-site customers: the Builder needs an outbound model path and a runner; an on-site installation either gets a
  customer-supplied key and runner, or does without. Tied to T-1519 O1 (signing) and to the edition question O1 below.

**Why B1 first.** It is the smallest piece that proves the three hard, shared things — a key held by the platform and
never by the agent, a cost cap that stops a call before it is made, and an audit trail per run — and it is reusable
whatever the later design of the runner turns out to be. It also needs nothing from T-1519.

**Why not start from the lab's engine.** Porting the claim loop first would deliver a queue with no safe place to run
anything. The queue is the easy part (Letflow already has tasks, timers and a claim pattern); the isolation and the
cap are the hard part, so they come first.

**What stays in the lab throughout.** L2 (source code, Git, CI, merge queue, QA deploy, acceptance runs, benchmark of
models for our own steps, retrospectives, promote). Any change to the lab's engine follows the lab's own rule: a test
with the scripted executor, stdlib only.

| Unbounded model cost | Cap checked before the call, ledger posting, operator kill switch; B1 before anything else |
| Container escape / agent reaching other tenants | One tenant per container, no warm pool across tenants, no network, no mounts, micro-VM for unrelated customers, external escape test |
| Prompt injection from tenant data | Allow-listed data marked as data, no egress, no write path, hash-bound human approval |
| A bad package is approved | Sandbox-tenant test run, diff and preview, rollback route (dependency on T-1519 S5), class A only in v0 |
| Customer data goes to a vendor | Contract and per-tenant switch (O4); gateway records shape not content |
| Tenant template removes a gate | Platform-owned minimum chain checked at activation and at install |
| A one-way door because rollback or the data-step runner is missing | Builder install blocked until T-1519 S3 and S5 |
| Scope: two tools that look alike (lab and Builder) | Section 3 boundary; the Builder never writes Git; the lab never holds tenant keys |
| A weak model is used for a gate to save money | Lab evidence: escaped defects and shadow check are the only direct measure; keep gates on the validator tier by default and let the tenant move them only inside an allow-list |
