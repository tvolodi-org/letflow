# BA decision: MES, liquid fertilizer streams, three design options (task T-1819, MES-2)

Business analyst. Owner request 2026-11-12. No issue number was known; the file is named after the task, as `T-1818.md` is. DRAFT design only: no code, no client contact, nothing on production, money, DNS, secrets, demo or a public repository.

## Question

How would continuous (stream) production of liquid fertilizers be modelled on Letflow, and how should machine data (PLC, SCADA, historian) come in?

## Decision (short)

Three options are written in `docs/design/mes/02-liquid-streams-options.md`: **A** manual entry and file imports, **B** periodic historian import, **C** live OPC UA / MQTT connector. Proposal for the owner: start with **A**, give every reading a `source` field from day one, add **B** when the client shows a real export file, and do **C** only after that and only if the client pays for it. The 20 client questions are in section 7 of the design file.

## Reasons

* The production layer (recipes, runs, consume/produce booking, samples, release, shift log) is missing (fit/gap rows 2, 3, 4, 7, 8 in part 1) and is the same in all three options. Machine data only improves it.
* A and B need no inbound connection to the plant network; C does, and adds a time-series store the platform does not have.
* Tank = location plus equipment card; tank content = stock ledger balance with the lot in its key (part 1, section 4).

## UAT assumptions, to be confirmed by the process owner

* Lot of a stream = tank fill, with a "mixed" flag. Open question for the client.
* The ledger is the book of record for tank content; readings are checks.
* Most historians can export CSV on a schedule.
* Effort sizes are rough comparisons, not measurements.
* Letflow only receives data pushed from the plant side; it never connects into the plant network.
