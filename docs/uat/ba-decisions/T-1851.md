   tenant's role set stays fixed (as data, not code), and the storekeeper asset switch of 0084 stays; only the corporate build lets a
   tenant change its roles and retires the switch.
2. **Open-core note:** section 1 is now "the role editor socket": what each edition offers (1.2), the socket's three callbacks with
   the open default "no editor" (1.3), where the open build calls it (one mount point, one display field of the access answer, never

   the golden per edition (the editor reuses `UsersGroupsRolesManage`, held only by PLATFORM_ADMIN and TENANT_ADMIN, so the golden is
   the same in both editions). Every sentence saying custom roles are open is gone.
3. **Closed candidates note:** 1 role editor (decided), 2 audit export and retention, 3 several sign-in realms, 4 print template
   designer, 5 advanced reports, each with what it is, why closed, the small open socket, a size guess, and what the open build keeps

   document retention, the realm-per-tenant provisioner (QA only), per-tenant print overrides with a JSON layout editor, and saved
   views with aggregates).
4. **Names (decided by me, as the task says):** the template rows keep today's names (storekeeper, candidate, task worker, auditor and
   the rest). Reason: the principle forbids a name **deciding** access, not a name **labelling** a row. Checked: `roleLabels.ts` only
   maps an id to a display name and description; `docs/roles.md` describes what each role holds; the one web use of a name,
   `isCandidate` (`web/src/auth/access/access.ts`), chooses a link on the "no access" page and is display only (stage 5 of the slice
   list); the exam module's candidate grant is template content from its manifest; the ledger check on auditor and candidate keys is a
   registration lint, not a request-time decision. No neutral names are needed; the rows are shipped and documented as templates.

## Reasons

D-132 says in plain words that the open build's tenant admin cannot create roles; D-126 puts closed features behind sockets; the
architect's model (permission-only checks, roles as data, protected admins by rule) is kept for the code, so stages 0 to 2 stay. A
read-only template row with today's permissions is the only open-build form that is no behaviour change for existing tenants. Reusing
`UsersGroupsRolesManage` for the editor keeps the golden identical in both editions and the escalation rules in the core.
