# BA decision for UAT: the three REQ-499 deferrals (GH #2690), addendum to decision 0054

Business analyst: platform / WMS UAT. This file is the recorded decision the issue asks for ("a short addendum to decision 0054 or this issue's closing comment"). It changes no code, seed, test or decision record.

## Question

Decision 0054 (option A, the at-most-once rule for stock posting) left three items of the service-task entity-write work (REQ-499, PR C) deferred and unfiled. For each: build (with its own requirement), defer (with a trigger), or drop?

1. A pre-call activator check at dispatch time, before the external call.
2. A `{"response": key}` source kind for a declared line value, and a declared-output-keys check for script-bound nodes at activation.
3. Persisting the service response body so an operator can re-apply from the DLQ.

## Sources opened

- `docs/migration/decisions/0054-process-step-writes-entity.md`: D4a.4 (a deactivated activator keeps running with recorded authority, a known weakness); open point 9 (`needs_reactivation`); the open point 6 ruling (atomicity with the RESULT apply is enough for stock posting; a lost response is an incident; stock posting is keyed by `(instance, node, attempt)` and never depends on the HTTP call); the "Amendment (GH #2587 PR C1)" paragraph (a refused entity step lands the instance in ERROR + DLQ).
- `lib/letflow/design/gh2587-req499-pr-c-service-task-writes.md`: section 15, OQ-C5 ("CLOSED: defer", with the reasons); D-C.7 (field sources are `{"var": name}` and `{"const": value}`; `var` reads the variables after the apply's merge, so response body keys are already reachable; "`{"response": key}` is deferred"); D-C.8 (landing and residual); section 16 (the deferred list, including the three items and the stuck-`"advanced"` sweeper).
- `docs/runbooks/service-task-entity-write-refusal.md`, "Recovery" (the result of the service call is not stored; recovery is cancel and restart or reactivate; the external effect is not compensated) and "Known residual".
- Issue #2690 body (no comments).

## Decisions (UAT only)

### 1. Pre-call activator check: DROP

- The check is advisory. 0054 D4a.4 and OQ-C5 already say a deactivation can happen between the check and the call, so the doomed write is reduced, not removed.
- The write itself is already safe: the apply refuses with `entity_write_needs_reactivation`, nothing commits, and the instance lands in ERROR + DLQ (PR C1 amendment). The cost is the accepted incident of the open point 6 ruling, which the runbook names.
- The structural cost (OQ-C5): the check would run in the dispatcher, which the architecture boundary forbids from calling the engine.
- The real remedy for deactivated activators is the `needs_reactivation` handling (open point 9), which is already a separate follow-up in section 16 and is not touched here.
- Reopen only by a new owner decision, not by a trigger.

### 2. `{"response": key}` source kind and declared-output-keys check: split ruling

- `{"response": key}` source kind: DROP. D-C.7 shows `{"var": name}` already reads the merged body keys (HTTP) and the declared output (script), so the new kind gives no new capability, only a second way to say the same thing and a larger surface to secure and test.
- Declared-output-keys check for script-bound nodes at activation: DEFER. Trigger: the first real or UAT definition whose script-bound node ends in ERROR + DLQ because a declared output key is missing (a data-dependent `validation_failed` that an activation check would have caught). Until then the run-time refusal is correct and visible. When the trigger fires, it is built as its own requirement (see "Build outcomes" below); the 0054 design for module handlers already refuses undeclared output keys at the handler, so check that overlap first.

### 3. Persisting the response body for operator re-apply: DEFER

- Not dropped: a lost or refused response after an irreversible external effect is the one real operational gap, and today the only recovery is cancel and restart with no compensation.
- Not built now: it stores external-system data, which may be sensitive, inside tenant storage (INV-1 scope, INV-2 field authorisation, INV-4 no secrets in logs or payloads, a size cap) and it needs a re-apply path that is itself a privileged write. That is a production design question (money, access, other tenants' data), not a UAT rule.
- It pairs with the stuck-`"advanced"` sweeper (section 16); they should be designed together.
- Trigger: any of (a) a first real incident where a refused entity step needs a re-apply that cancel and restart cannot give; (b) WMS stock posting through a service task (the `(instance, node, attempt)` business key, WMS slice 5) is being switched on for a customer; (c) the process owner asks for it. When it fires, it goes through a security review and updates the runbook "Recovery" section in the same change.

## Reasons

- 0054's rule is at-most-once with an accepted incident class; two of the three items would not change that rule (1 is advisory, 2 adds no capability). Only item 3 changes what an operator can do, so only it is kept alive.
- Nothing here is needed for a UAT scenario: no scenario in the roster depends on any of the three.

## Build outcomes

None now. No requirement is created by this decision. The two deferred items (2b, 3) each become a requirement when its trigger fires; the requirement is written then, by a requirement task, with acceptance criteria. Until one is built, the runbook "Recovery" section stays correct as written ("the result of the service call is not stored").

## UAT assumptions, to be confirmed by the process owner

- UAT assumption, to be confirmed by the process owner: dropping item 1 and the `response` source kind of item 2 is acceptable for production. The sources record them as deferred by the supervisor (OQ-C5, D-C.7), not rejected; "drop" here is this team's UAT backlog stance, not a production rule.
- UAT assumption, to be confirmed by the process owner: the triggers listed for items 2b and 3 are the right ones for production.

Decision for UAT only; the process owner configures production.
