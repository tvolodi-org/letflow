## Context

Procurement needs "the exact version submitted" to be inspectable and an old approval must not authorize a changed version (PR-02, PR-06). Kazakhstan legal forms need numbered, signed documents: З-1 receipt, З-2 release, З-5 movement, Р-1 act, СНТ data set, ТТН (10b table). The customer draft assigns issuing and registration of СНТ/ЭСФ/ЕСУТД to a designated external system (`:165-175`); the module "supplies evidence". Today the platform has none of: a numbered document, a version chain, an approval that binds a content hash.

What exists on main (cited):

- Attachments: `instance_attachments` rows reference a content-addressed byte store by `content_hash = sha256(raw_bytes)` (`lib/letflow/repository/attachments.ex:197,245`; `lib/letflow/repository/attachment.ex:16-19`). The row is NOT immutable and has a normal delete path (`lib/letflow/repository/attachment.ex:23-25`); delete removes the metadata row only and never the bytes (`lib/letflow/repository/attachments.ex:85-96`). A "changed" attachment is a new row (`lib/letflow/repository/attachment.ex:25-28`). Upload goes through a content-type allow-list (`lib/letflow/repository/attachments.ex:138-140`) and a scanner (`lib/letflow/repository/attachment_scanner.ex`). There is no number, version, status, or signature concept.
- Byte store: `repository_artifacts` is per-tenant (in the tenant schema) and immutable at the database by row triggers `BEFORE UPDATE` / `BEFORE DELETE` calling `repository_artifacts_immutable()` (`priv/repo/migrations/20260830030001_create_repository_artifacts.exs:142-171`, verified on main). That migration defines NO `TRUNCATE` trigger, so the precedent leaves TRUNCATE open; this record's trigger adds it (D4). A content hash therefore cannot address bytes across tenants by construction.
- Signed links: `AttachmentLinks.issue/3` mints a stateless, per-tenant HMAC-SHA256 token over attachment id and expiry (`lib/letflow/repository/attachment_links.ex:15-45,95,232`); `verify/3` collapses six failures into one `:expired_or_invalid` (`lib/letflow/repository/attachment_links.ex:48-56,133-155`). Route `POST /:id/attachments/:attachment_id/link` is guarded by `:AttachmentLinksIssue` (`lib/letflow/api/routers/instances.ex:412`, policy key `lib/letflow/api/authorization.ex:933`). This is download-access signing, NOT document signing; it proves nothing about content or signer.
- Entity records: event-sourced; envelope requires `entity_type`, `entity_def_version`, `record_id`, `field_values` (`lib/letflow/entities/event_types.ex:56`). Create/update/delete are routed (`lib/letflow/api/routers/entities.ex:51`). Records are mutable in the business sense; there is no "issued, frozen" state.
- Audit: tenant-scoped hash chain, `chain_hash` = sha256 over a canonical string including `prev_chain_hash` (`lib/letflow/audit.ex:48-97`), appended under `SELECT ... ## Options

A. Extend attachments (add number/version/status columns to `instance_attachments`). Rejected: attachments are deletable, tied to instance or entity record, free-form, and upload-oriented (`lib/letflow/repository/attachment.ex:23-25`); mixing immutable legal documents into that table weakens both.

B. Modules each build their own document tables. Rejected: numbering, hashing and signature semantics would diverge per module; the roadmap lists this as a core need for every domain (`docs/migration/core-roadmap-20261014.md:62`).

C. (Recommended) A core `documents` service: its own tenant-schema tables, a thin module-facing API, reusing the content-addressed byte store for rendered artefacts and the audit chain for events. Attachments are unchanged.

Recommendation: C.

## Decision (proposed)

### D1. Document model (BINDING)

Tenant-scoped tables in the tenant schema, like attachments (`lib/letflow/repository/attachment.ex:8-14`). `tenant_id` is never a request or content field: it is the `:prefix` of the call (0003 addendum). Every access path takes the prefix; no path reads tables outside it.

- `document_types`: `key` (e.g. `purchase_request`, `kz.z1`), `owner_module`, `numbering_scope` (D2), `template_ref` (D5), `signature_policy` (D6), `retention_class` (D7), `legal_entity_required` (bool), `restricted_fields_allowed` (bool, default false; see D8), `declared_fields` (the entity/content fields the template prints, D8). Registered as described under "Document-type registration" below; core ships none. A type row is frozen once a document of that type exists (D4 trigger); a changed policy is a NEW type key.
- `documents`: stable `document_id` (uuid) = the logical document across versions; `type_key`, `legal_entity_id` (0050 org reference, id only), `issuing_org_unit_id` (an `org_unit` id, NOT NULL, the document's resource scope; set once at draft creation, never changes, D8), `period` (D2; null until version 1 is issued, then write-once together with `number`), `number` (nullable until issued, write-once), `source_ref` (optional `{entity_type, record_id}` or `instance_id`; may be set or changed only while no version has left `draft`, frozen after the first issue), `current_version` (must reference an `issued` version of the same document, D4), `hold` (D7 direction).
- `document_versions`: `(document_id, version_no)` unique; `status` an `Ecto.Enum` in `draft | issued | cancelled | superseded | discarded`; `content` (structured JSON snapshot, D3); `content_hash` (D3); `artefact_hash` (sha256 of the rendered PDF bytes, null while draft); `issued_at` (server clock), `issued_by`, `cancelled_at`, `cancelled_by`, `cancel_reason`, `superseded_by_version`, `discarded_at`, `discarded_by`. Allowed transitions are a closed list of function heads in the context module AND of the database trigger (D4), so an invalid state is unrepresentable in both layers.
- `document_sequences`: one row per scope (D2), counter only upward.
- `document_external_registrations` (append-only side table, D4): `document_id`, `version_no`, `system`, `registration_id`, `registered_at`, `recorded_by`. This holds what the customer calls the external registration number (D10); it is NOT a column of the immutable version row.
- `document_signature_nonces` and `document_signatures` (D6, direction).

Status machine: `draft -> issued`; `draft -> discarded`; `issued -> superseded` (only by issuing the next version, D4); `issued -> cancelled` (reason mandatory). `draft` may be edited in place. A draft is DISCARDED by the `draft -> discarded` status transition (sets `discarded_at`, `discarded_by`, audited `document.draft_discarded`), NEVER by DELETE: the D4 trigger refuses DELETE on every row including drafts, so there is no draft-only delete exception. A draft carries no number (D2), so discarding creates no gap. `issued`, `superseded`, `cancelled` and `discarded` are never edited. No other transition exists. `cancelled` and `superseded` remain readable forever (subject to D7).

#### Document-type registration

Document types are NOT a new SolutionPack section. The pack section set is a closed, exhaustively enumerated struct (0029 section 4: a closed set forces each new section's install policy to be decided by name), and every tenant-content section needs its own install policy (0026, 0027). Registering types through the pack would therefore require a separate amending record ("Record P-like": a `document_types` pack section with its own install policy, the way 0053 reserved 'Record P' for the `scripts` section). This record does NOT take that route.

Chosen path: a module registers its document types from its reviewed `on_install/3` `(prefix, settings, ctx)` (decision 0052 D3 prefers /3 over /2; registration is audited and needs `ctx.actor_id`, which /2 does not receive). On the branch `lib/letflow/modules/installs.ex` runs pack install, the `tenant_modules` insert and the `on_install` call in ONE transaction (`install/3` at :84, `Repo.transaction` at :89, `maybe_run_on_install` called at :100, dispatching /3 before /2 at :284-288; line numbers read on the branch, nothing run), so a failed registration rolls back the install. `on_install` is reviewed code, not pack content (0039). Consequences: registration is by code review, not tenant content; type registration is audited (`document.type_registered`); the declared rendering fields are checked at registration AND re-checked at every issue (D8), and a type that violates the rule fails the install. If a later need makes the pack section preferable, that is a separate record amending 0026/0027/0029; this record does not decide it.

### D2. Number sequences (BINDING)

- Scope key: `(type_key, legal_entity_id, period)`, period = calendar year by default (type-configurable: `year | none`). A number is `<prefix>-<year>-<n>` with `n` starting at 1; the prefix and zero-padding are type config. The period is computed ONLY from the server clock, in the tenant's local timezone (open point 11: Asia/Almaty assumed, UTC the alternative); no caller supplies a period, a number or an `issued_at`. Back-dating `issued_at` is never allowed.
- Allocated at ISSUE of version 1, not at draft creation. Versions of one document keep its number; the version is shown as a suffix (`-v2`) so the legal number never changes.
- Allocation protocol, inside the SAME transaction (`Ecto.Multi` / `Repo.transact`, a plain transactional context per the REQ-045 shape, no process per document) that flips the version to `issued`:
  1. insert-if-absent: `INSERT ... ON CONFLICT DO NOTHING` of the `document_sequences` row for the scope (first issue in a period, or for a new legal entity);
  2. `SELECT ... FOR UPDATE` of that row, increment, use. This is the two-step protocol the audit tail documents (`lib/letflow/audit.ex:212`, mirroring `EventStore.assign_sequence/3`); without step 1 the first issuer of a scope has no row to lock.
- Fixed lock order, always: the sequence row FIRST, the audit chain lock SECOND. The audit event is written in the same transaction (D9), so both are held together; a path that took the audit lock first and then a sequence row would deadlock. The lock is taken as late as possible: validation first, number allocation after.
  **Ruling. Ruled by the advisor (letflow-ec) under the user's delegation, recorded by the supervisor, 2026-10-15.** (open point 1, resolved.) Numbers are GAP-FREE per scope with a row lock (the protocol above), and the numbering transaction holds NO rendering and NO file or byte-store I/O. The PDF (slice 2, D5) prints the number, so it cannot be rendered before allocation: it is rendered AFTER the numbering transaction commits and attached in a second transaction (D5); a render never runs while the sequence row or the audit lock is held. The earlier wording that put the render inside the issue transaction is deleted here and in D3 and D5.
- Rollback releases the number, so numbers are GAP-FREE for issued documents by construction.
- Backstop, NULL-safe: unique index on `documents (type_key, legal_entity_id, period, number)` declared `NULLS NOT DISTINCT` (Postgres 15+; the project runs `postgres:16`, `docker-compose.yml:3`, `.github/workflows/ci.yml:388` and `:516`, verified). **Ruling. Ruled by the advisor (letflow-ec) under the user's delegation, recorded by the supervisor, 2026-10-15.** All compose and CI configurations use `postgres:16`; PostgreSQL 15 or newer (`server_version_num >= 150000`) is a boot-time DEPLOY PRECONDITION: the application checks it at boot and REFUSES TO START below it. In addition `legal_entity_id` is NOT NULL for any type with `legal_entity_required = true`, and the sequence row key uses a fixed sentinel when a type has no legal entity, so the key never contains a bare NULL. Plain `UNIQUE` would let duplicates through, since NULLs are distinct.
- Gap-free is chosen because Р-1/З-forms are accounting primary documents and auditors look for gaps. Cost accepted. The serialization bottleneck is NOT the sequence row: the audit chain lock already serializes all audit writes of a tenant, so the total issue rate of a tenant is bounded by the audit tail, and the per-scope lock adds no tenant-wide limit (open point 3 is reframed accordingly). Statement and lock timeouts apply to the issue transaction so a slow statement cannot hold the locks indefinitely (T11).
- Cancelled numbers are NOT reused: a cancelled document keeps its number with status `cancelled` (so "gap-free" means no unexplained gaps).
- Reset: never automatic except the period rollover. Set-next is performed through a tenant-scope sequence route (D8; there is NO separate `DocumentSequenceAdmin` permission or role, see the ruling below), allowed only to a value strictly greater than the current counter, with a MANDATORY reason, always audited (`document.sequence_adjusted` with before and after values and the reason; both are counters, so D9's payload rule holds). The "upward only" rule is enforced by the database trigger on `document_sequences` (D4), not only by module code. Lowering is refused. 
  **Ruling. Ruled by the advisor (letflow-ec) under the user's delegation, recorded by the supervisor, 2026-10-15.** (open point 10, resolved: the split is REJECTED, a two-principal rule is adopted.) A `DocumentSequenceAdmin` split is rejected: under 0046 D5/D10 TENANT_ADMIN holds every tenant permission and no other role does, so a separate permission has no separate holder. Instead every sequence change (reset in the sense of starting a new series, prefix change, gap declaration, period change, set-next) requires (a) a MANDATORY reason and an audit entry, AND (b) a second, non-proposing tenant-wide admin who approves it, WHEN the tenant has two or more such admins. "Admins" are counted as distinct ACTIVE owning users who hold a tenant-wide TENANT_ADMIN grant, using the helper of #2547 (the same count as the 0051 N1 guard); with fewer than two, the single admin acts with reason and audit alone. The proposer can never approve their own change. The counter is still never lowered (the D4 trigger). Audited as `document.sequence_change_proposed` and `document.sequence_adjusted` (before, after, reason, proposer, approver).

### D3. Content, canonical form, hash (BINDING)

- `content` is a JSON snapshot taken at issue: header fields, lines, and the reference snapshot required by 0050 D3.4 (name, UoM, BIN copied by value, ids kept). It never holds a live reference that can change the meaning later.
- Canonical form: REUSE `Letflow.Repository.Canonicaliser` (`lib/letflow/repository/canonicaliser.ex`) for the canonical bytes of `content`; no third canonical JSON form is introduced. `Letflow.Definitions.PromotionDigest` is NOT used and the two existing canonicalisers are never merged (the Canonicaliser moduledoc forbids it). The rules this record relies on, and adds as service-level pre-checks before canonicalising, are:
  - object keys sorted, compact output, array order significant (Canonicaliser);
  - monetary and quantity values are carried as decimal STRINGS in `content` (never JSON numbers), so the Canonicaliser's number rules, including its Jason-default fractional float form, are never exercised for business values; a float anywhere in a document `content` is refused by the service pre-check;
  - Unicode: strings are normalised to NFC before hashing, by the service; the Canonicaliser does not do this (verified: it has no normalisation step), so this is a service pre-check, not a Canonicaliser change;
  - duplicate object keys and non-finite numbers are rejected by the pre-check (the Canonicaliser decodes with Jason and does not itself reject duplicate keys: NOT VERIFIED beyond a read of the moduledoc and function heads; the pre-check must decode in a way that surfaces duplicates).
- Hash input: `content_hash = sha256(domain_tag || F(tenant_uuid) || F(document_id) || F(type_key) || F(legal_entity_id-or-sentinel) || F(number) || F(version_no) || F(canonical_content))`, where `F(x)` is the field's UTF-8 bytes preceded by its length as an 8-byte big-endian unsigned integer (length-prefixed, fixed field order; no separator character is used, so no field value can shift a boundary). Output is lowercase hex as audit does (`lib/letflow/audit.ex:79`). The tenant is identified by its immutable tenant UUID, NOT by the schema prefix, so a restore or rename into a different schema name does not break recompute or `verify_binding`, while a row copied into another tenant still hashes differently (**Ruling. Ruled by the advisor (letflow-ec) under the user's delegation, recorded by the supervisor, 2026-10-15.** `tenants.id` (`binary_id`) is stable across a logical dump and restore of the same install, but NOT across a re-provision or an import into another install. REQUIREMENT: the tenant export MUST carry the tenant uuid, and an import MUST restore the document hash domain from it (or recompute under a recorded mapping); otherwise `content_hash` verification of the documents breaks after a move. This requirement is binding on the export/import work and on slice 1's verification tooling.). `document_id`, `type_key`, `legal_entity_id`, `number` and `version_no` make identical content in two documents hash differently (anti-transplant).
- PRIMARY RULE: the STORED BYTES ARE AUTHORITATIVE and are NEVER REGENERATED. `content` (structured JSON) plus `content_hash` is the authoritative record of what was issued; the PDF bytes stored at issue are the authoritative human form. A later re-render (library upgrade, template change) must never replace, overwrite or be compared against the stored artefact as truth. Whether the `pdf` library is byte-deterministic is therefore not a correctness requirement but an optimisation (open point 4, a spike). Not verified: the library writes fixed Creator/Producer strings (`deps/pdf/lib/pdf/document.ex:41`) and a date only if one is set, which the exam renderer does not set; byte-determinism is NOT VERIFIED.
- `content_hash` is written into the `document.issued` audit event and `artefact_hash` (slice 2) into `document.artefact_attached` (D9, D5). Integrity is re-checked: the service recomputes `content_hash` from stored `content` on read paths that feed a decision (`verify_binding`, signing, download) and by a periodic job; a mismatch is refused and audited as `document.integrity_failed` (T1).

### D4. Versioning rules and immutability (BINDING)

- A new version is created from the current `issued` version as a new `draft` (copy of content). Issuing it atomically (one transaction): sets the previous version `superseded`, records `superseded_by_version`, issues the new one, updates `documents.current_version`. At most one `issued` version per document (partial unique index).
- Immutability is enforced by a DATABASE TRIGGER, not by privilege. A privilege (`REVOKE UPDATE`) cannot work: tenant tables are owned by the application role and migrations run as the same role, so the owner cannot meaningfully revoke from itself. The trigger is modelled on `repository_artifacts_immutable` (`priv/repo/migrations/20260830030001_create_repository_artifacts.exs:142-171`: a `plpgsql` function raising an exception, attached with `BEFORE UPDATE` / `BEFORE DELETE` row triggers, schema name quoted as in that migration). Where it differs from the precedent, it is column-aware rather than all-or-nothing. Concretely:
  - `document_versions`: UPDATE is refused on every row whose `status` is not `draft`, EXCEPT these allowed transitions and only these columns: `issued -> superseded` (sets `status` and `superseded_by_version`); `issued -> cancelled` (sets `status`, `cancelled_at`, `cancelled_by`, `cancel_reason`). `content`, `content_hash`, `issued_at`, `issued_by` and `version_no` never change after issue; `artefact_hash` is write-once (NULL to a value, once) in the slice-2 attach transaction (D5) and never changes after that. The `draft -> issued` transition sets the issue columns once; the `draft -> discarded` transition sets `status`, `discarded_at`, `discarded_by` once. Rows in `discarded` are frozen.
  - `documents`: `number` and `period` are write-once (NULL to value once, never changed again); `type_key`, `legal_entity_id`, `issuing_org_unit_id` and `document_id` never change; `source_ref` may change only while no version of the document has left `draft` and is frozen from the first issue; `current_version` may be written only to a version that exists, belongs to the SAME document (composite foreign key `(document_id, current_version)` to `document_versions`) and has status `issued` at the moment of the write (trigger check; the supersede transaction issues the new version first and then moves the pointer). A version that is current and is later cancelled keeps the pointer; reads show its `cancelled` status. `hold` is the only other mutable column.
  - `document_types`: UPDATE is refused on every column once at least one `documents` row of that type exists (trigger looks up the type key), so `numbering_scope`, `signature_policy`, `retention_class`, `template_ref`, `legal_entity_required`, `restricted_fields_allowed` and `declared_fields` cannot change under existing documents; a policy change is a new type key. DELETE and TRUNCATE are refused.
  - `document_signatures` and `document_external_registrations` are append-only: UPDATE refused. (Slice-2 tables `document_signature_nonces` and `purge_requests` have their own column-aware rules, D6 and D7.)
  - `document_sequences`: UPDATE allowed only if the new counter is strictly greater than the old one.
  - DELETE is refused on all of these tables for every row including drafts (drafts are discarded by transition, above), and a statement-level `BEFORE TRUNCATE` trigger refuses TRUNCATE on them (the precedent has no TRUNCATE trigger, verified: this is new here). The only exception is the purge path (D7, direction), which is gated by a guarded session setting and an approved purge request (D7), not a general delete.
  - All triggers are created `ENABLE ALWAYS`, so `session_replication_role = replica` does not skip them. The application role must not be a superuser nor hold the privilege to set `session_replication_role` (production role attributes: NOT VERIFIED).
- Residual risk, stated: a role with DDL rights (the table owner) can drop or disable the trigger (`ALTER TABLE ... DISABLE TRIGGER`), and a superuser can bypass anything; `ENABLE ALWAYS` closes only the `session_replication_role` route. The detective control is the audit event holding both hashes (D9) plus the integrity check on read and periodically (D3), with `document.integrity_failed`.
- Post-issue facts are carved OUT of the immutable row: the external registration (id, system, time) goes to the append-only `document_external_registrations` table, not onto `document_versions`; `superseded_by_version` and `cancelled_*` change only through the trigger's allowed transitions above; the legal-hold flag lives on `documents`, not on the version row.
- Approval binds a version hash: the approval/process variable stores `{document_id, version_no, content_hash}`. The API `documents.verify_binding(document_id, version_no, content_hash)` returns true only if that version exists, is `issued` and the hash matches; consumers (procurement) call it at approval completion and at every later consuming step. A later version does NOT inherit the approval: the process route decides whether a new approval task is required (PR-06 wording, `:51`). The document service does not decide that routing. `verify_binding` is an INTERNAL function; if it is ever routed, the route is scope-checked and 404-equivalent (a true/false result is an existence oracle otherwise).
- Cancelling an issued version that others consumed is allowed but emits `document.cancelled`; consumers re-verify bindings and see `not issued`. Cancel of an issued version that other documents or processes consumed requires a second principal (SoD) or a mandatory reason at minimum; open point 12.

### D5. Rendering and templates (DIRECTION, non-binding)

- Module-provided templates only for now: a template is code shipped with the module (like `lib/letflow/modules/exam/certificate_document.ex:149`), versioned by `template_version`, recorded on the version row. A template change never alters an issued version (its artefact is stored).
- Ruled by the advisor (letflow-ec) under the user's delegation, recorded by the supervisor, 2026-10-15. The PDF is NOT rendered inside the numbering transaction (D2). Transaction 1 allocates the number, computes `content_hash` (the number is an input to the hash), flips the version to `issued` and writes `document.issued`; it commits with `artefact_hash` NULL and holds no render or file I/O. The render then runs with no lock held, and transaction 2 stores the bytes in the content-addressed store, sets `artefact_hash` once and writes `document.artefact_attached`. A type whose template does not print the number may instead render BEFORE transaction 1 and attach in it. A render failure returns `{:error, _}` (no raise through the caller), does not release the already committed number (gap-free is preserved; the version stays `issued` with the artefact pending and is retried by a bounded job), and puts no field values into the error or logs (INV-4 shape). A version with the artefact pending is not downloadable (the same 404-equivalent as D8).
- Per-tenant print-template overrides are a later customization candidate (`docs/migration/decisions/0053-tenant-scripted-rules.md:197,219`) and are NOT decided here. This record only reserves `template_ref`.
- Language: `content` carries ids and values; labels come from the template (RU and KK are a template concern, open point 6).
- Template output is PDF text only, no active content or embedded scripts (T10).
- Restricted data cannot reach the renderer by construction (D8): the renderer is called with ONLY the projection of `content` onto the type's `declared_fields`, never the full `content` or the entity record. A template that prints a field outside the projection gets nothing for it and fails the render (fail closed); the template cannot read restricted fields because they are not passed.

### D6. Signatures (DIRECTION, non-binding)

- A `document_signatures` row: `document_id`, `version_no` (foreign key to `document_versions (document_id, version_no)`), `signer_user_id` (and external signer label for counterparties), `method` (`internal_ack | ecp_ncalayer | external_registered`), `certificate_ref` (subject, serial, issuer; no private material), `signed_hash`, `signature_blob_ref` (content-addressed bytes of the detached signature, if any), `signed_at` (server clock) and `client_signed_at` (claimed, informational only, never used for ordering or validity).
- `signed_hash` is ONE defined value per method, not "content_hash or artefact_hash": it is `content_hash` for every method (it covers tenant, document, number, version and type, and does not depend on PDF bytes). The server RECOMPUTES `content_hash` from the stored `content` at signing time and compares; a client-supplied hash is never trusted. A signature is only valid if `signed_hash` equals that recomputed value AND the version is `issued`. A signature never replaces the hash: a stored signature without the hash is rejected (invariant, not a convention).
- Signer identity: for `internal_ack` the signer is the authenticated principal, never a request field. For `ecp_ncalayer` the mapping from certificate subject (IIN) to a platform user is NOT designed here and belongs to the ECP integration record.
- Sign only on `issued` versions; a signature on a `superseded` or `cancelled` version stays but is shown as such.
- `internal_ack` (platform user confirms) works now and is a record of an in-platform act, NOT a legal ЭЦП. ЭЦП via NCALayer is an OPEN external dependency: browser-side signing with the user's key, returning a CMS signature over the supplied hash. Verification of the CMS, certificate chain (NUC RK), and revocation checks are NOT designed here and need a separate integration record. Until then a type may require `ecp_ncalayer` and the document stays `issued`-unsigned; the service never fakes it.
- Replay and the nonce table (slice 2): each signature request first obtains a server nonce, stored in `document_signature_nonces` as a HASH (never the secret) with `(document_id, version_no, signer, method, signed_hash)`, `expires_at` (short TTL, minutes), and `consumed_at` (null until used), with a UNIQUE index on the nonce hash. "Unexpired" is judged by the database transaction clock (`transaction_timestamp() < expires_at`), never the app clock. The nonce is CONSUMED in the SAME transaction as the signature insert; the consume is a conditional update (`consumed_at IS NULL AND expires_at > now`), so two concurrent submissions cannot both succeed. The nonce table is in the trigger list with a column-aware rule: UPDATE is allowed only to set `consumed_at` from NULL to a value (nothing else changes); DELETE is refused. Expiry is a time comparison, not a deletion, so no sweep exception to the DELETE rule exists; expired and consumed rows are kept (table growth is small rows, accepted; open point 18). `document_signatures` carries a NULL-safe unique constraint: the signer is `signer_user_id` OR a counterparty label (a CHECK requires exactly one), and the unique index is on `(document_id, version_no, signer_user_id, counterparty_label, method)` declared `NULLS NOT DISTINCT`, so a counterparty signer (null `signer_user_id`) cannot sign the same version twice by method. A signature copied to another document or version is refused because the nonce and the foreign key bind it to exactly one `(document_id, version_no)` (T3, T14).

### D7. Storage, retention, legal hold (DIRECTION, non-binding)

- Rendered artefacts and detached signatures use the existing content-addressed store (`repository_artifacts`, reached as attachments do, `lib/letflow/repository/attachment.ex:16-19`); no new byte store. Document rows and their bytes are never deleted by the API: there is NO `delete` route.
- The byte store is SHARED with attachments (identical bytes are one row). Purge therefore must not destroy bytes that anything else references (T16).
- Retention: `retention_class` per type, minimum from the accounting rules (the figure is a legal input, open point 5). Event-store retention (`lib/letflow/event_store/retention_policy.ex`) is for events, not documents; this record does not reuse it.
- Purge after expiry is a TENANT-scope operation (it acts on tenant data; INV-10), with its own permission `DocumentsPurge`, NOT a platform-admin operation unless a later record places it on the platform tenant explicitly. A mandatory reason. Concretely (direction until the slice-2 record):
  - `purge_requests` table: `id`, `document_id`, `version_no`, `content_hash` of the target, `reason`, `requested_by`, `created_at`, `expires_at` (TTL from the database clock), `approved_by`, `approved_at`, `consumed_at`. A purge targets one version; a whole document is one request per version.
  - Two-principal SoD is enforced in the database: `CHECK (approved_by IS NULL OR approved_by <> requested_by)`; a trigger lets `approved_by`/`approved_at` be set once and `consumed_at` be set once, nothing else; DELETE refused. That the approver holds `DocumentsPurge` cannot be a DB check; module code checks it (stated residual).
  - The approval is BOUND to the request id and therefore to document, version and hash; the purge function takes the request id, refuses if it is unapproved, expired, consumed or its target hash no longer matches, runs the retention and hold checks ATOMICALLY with the delete in one transaction under a row lock on the `documents` row, performs the shared-bytes reference check in the same transaction, and consumes the request.
  - Trigger exceptions (stated, not hidden): the D4 triggers on the document tables AND the `repository_artifacts` BEFORE DELETE trigger (`repository_artifacts_immutable()`, `priv/repo/migrations/20260830030001_create_repository_artifacts.exs:142-171`; a new migration must replace that function) each allow a DELETE only when a guarded session setting (`letflow.purge_request_id`, set with transaction-local `set_config(name, value, true)` and set only inside the purge function) equals the id of a purge request that is approved, unexpired, unconsumed and targets exactly that row or hash. The artifact exception is SHARED with attachments (same byte table): it also makes attachment bytes deletable on this path, so the reference check must cover other document versions AND attachments, and bytes are deleted only when zero references remain (the attachment foreign key restriction is the second line, exact FK shape NOT VERIFIED).
  - Residual: code running as the application role can call `set_config` itself; the setting alone grants nothing without an approved request row, but a role that can also insert and approve rows could forge one. The detective control is the audit chain: `document.purge_requested`, `document.purge_approved` and `document.purged` (hashes and reason code only).
- Legal hold: a flag on `documents`, set by a `DocumentHold` permission with a mandatory reason, cleared in a SEPARATE step with its own reason, audited (`document.hold_set` / `document.hold_cleared`); blocks purge and tenant offboarding export deletion. What a deactivated tenant keeps is a sentence for the offboarding record (open point 13).

### D8. Access (BINDING)

- Permissions (additive core permissions, same additive-permission shape as `:AttachmentLinksIssue`, `lib/letflow/api/authorization.ex:933`): BINDING for slice 1: `DocumentsRead`, `DocumentsDraft`, `DocumentsIssue`, `DocumentsCancel`, and the single tenant-scope atom of the sequence-change route (D2; held only by TENANT_ADMIN, no separate `DocumentSequenceAdmin`, per the open point 10 ruling; the atom name is the implementing requirement's). RESERVED names with direction-only semantics: `DocumentsSign` (D6), `DocumentsPurge` and `DocumentHold` (D7, slice 2). Each is classified TENANT-scope under INV-10 and 0046 (`docs/migration/decisions/0046-admin-scopes-and-role-charter.md`); a permission without a classification fails the build. `AuditRead` is not widened: the audit view of document events stays on `GET /audit` (`lib/letflow/api/authorization.ex:776`).
- Why core and not an `org`-style foundation module (0039 D8): numbering, immutability and hashing are platform integrity guarantees that every domain relies on, not domain data; foundation modules (0050) hold reference data. Modules register types; they do not own numbering.
- Scopes (0051): scope is declared per route (D5), list queries carry a scope filter (D6) and out-of-scope reads are 404 (D7). Mapping of `legal_entity_id` onto 0051 scope nodes: 0051 scopes are over `org_unit` nodes, while a legal entity is an `org_legal_entity` ENTITY RECORD, not an `org_unit` node (0050). The mapping is therefore explicit and `issuing_org_unit_id` is a column of `documents` (D1) and immutable (D4). Rules:
  - Who sets it: the issuer NAMES one `org_unit` at draft creation, and it must be a unit on which the issuer holds the `DocumentsIssue` grant (inside the scope of a grant they hold, 0051 inheritance applies). A principal with several grants chooses one of them. A tenant-wide principal (nullable scope node, 0051) MUST name one unit; the field is never defaulted and never NULL.
  - Validation: the unit must belong to the document's `legal_entity_id`, resolved through the 0050 org structure, and a type with `legal_entity_required` additionally requires it to resolve to the declared legal entity. Checked at draft creation and re-checked at issue. A legal entity with no org unit under it cannot have documents issued (fail closed). The unit-to-legal-entity lookup is NOT designed here and is a DEPENDENCY: slice 1 cannot ship issuance of legal-entity-bound documents until open point 14 is resolved.
  - After issue: the issued document keeps its `issuing_org_unit_id` and its legal entity as of issue (both frozen). Scope reads resolve the CURRENT path of that unit, so a re-parented unit moves its documents with it. Retiring a unit that has issued documents is allowed and does NOT hide those documents from the unit's ancestors (the unit stays resolvable as a retired node; whether 0050/0051 keep retired units resolvable is NOT VERIFIED and part of open point 14). Re-parenting a unit to a different legal entity does not change `legal_entity_id` on documents already issued.
  - A principal with only a tenant-wide grant sees all documents of the tenant, as everywhere in 0051.
- Download and read routes (INV-5, INV-6): every document route states its scope proof. Download resolves `(document_id, version_no)` under the caller's scope in ONE scoped query; absent, out-of-scope and other-tenant all return the same 404, with the same headers and body. No route takes an artefact hash or a `content_hash` as an address, and no route fetches bytes by hash. Responses carry NO `ETag` and NO `Last-Modified`, no `Content-Disposition` difference between existing and missing, and add `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`, with `Content-Type: application/pdf`. There is no public or unauthenticated path (0028) and the attachment signed-link mechanism is not reused for issued PDFs. `document.downloaded` is audited only for a SUCCESSFUL download; refused, 403 and 404 requests are telemetry only (counters and logs without content), consistent with 0051 (no audit of scope 404s), so an unauthorized caller cannot grow the single serialized tenant audit chain (see D9 refusal rule).
- SoD: issuer != the draft's last editor is a type option, escalating by 0051 D10 rules; a document type that requires it fails closed.
- Field restrictions versus the PDF (INV-2). The PDF is one immutable byte string, so a reader without a field grant could read restricted fields by downloading it. The rule chosen: a document type MAY NOT include restricted fields in rendered content. It is enforced BY CONSTRUCTION, not by a one-time check:
  - The type declares `declared_fields` (the fields its template prints). The renderer receives ONLY the projection of `content` onto `declared_fields` (D5); nothing else is passed to it.
  - The restriction set is re-checked at EVERY issue, not only at registration, because restrictions are per-tenant runtime data (`entity_field_restrictions`) that a tenant admin or another module's `on_install` can add later. If any declared field is restricted for the source entity type at that moment, the issue fails closed with no number allocated. Registration performs the same check as an early failure (`restricted_fields_allowed` stays false).
  - **Ruling. Ruled by the advisor (letflow-ec) under the user's delegation, recorded by the supervisor, 2026-10-15.** (open point 15, resolved.) Restricted fields are FORBIDDEN in a type's declared rendering fields at template registration, AND checked again at every issue: a restriction added later makes issuance of that type refuse (no number allocated) until the template is revised (a new type key, since a type row is frozen once a document of it exists, D4). The alternative of a second redacted artefact is not adopted.
  - Non-entity-sourced documents (source is an `instance_id` or free JSON, so there is no source entity type to check): every declared field must be listed in the owning module's declared sensitivity list supplied at registration; a declared field with no sensitivity entry is refused, a field marked restricted in that list is refused, and such a type may not carry restricted data in the rendered projection at all. Whether instance variables have any sensitivity registry is NOT VERIFIED; until one exists the module's declared list is the only source.
  - Restricted fields may still appear in `content` for hashing and are redacted from the structured read view for readers without the grant; issuing requires a principal who can see all fields. Alternative, left as an open point (15): a second, redacted artefact that is NOT hashed as authoritative. Because the hash covers unredacted content, `content_hash` (and `artefact_hash`) is shown only to principals with the all-fields grant, since low-entropy fields can be guessed against a visible hash.
- Scripts: a tenant script (0053 hook 1) may NOT issue, sign or alter a document; the document service is not script-visible. Which capability gate enforces this is stated once the script host API exists (NOT VERIFIED; the host API does not exist yet).

### D9. Audit events (BINDING)

Hash-chain events, in the same transaction as the change (as 0051 D8). BINDING events: `document.type_registered`, `document.draft_created`, `document.draft_discarded`, `document.issued` (number, version, `content_hash`, `artefact_hash`, template version; this also records the number allocation), `document.superseded`, `document.cancelled` (reason), `document.downloaded` (version, principal; successful downloads only), `document.sequence_change_proposed`, `document.sequence_adjusted` (before, after, reason, proposer, approver), `document.integrity_failed`. RESERVED names with direction-only semantics (D5-D7, slice 2): `document.artefact_attached`, `document.hold_set`, `document.hold_cleared`, `document.signed` (method, certificate ref, `signed_hash`), `document.signature_refused` (reason code), `document.purge_requested`, `document.purge_approved`, `document.purged`. Refusal rule: only SUCCESSFUL sensitive actions are audited per event. Refusals (failed issue, cancel, verify, 403 authorization, signature refusals) are telemetry plus an AGGREGATED counter per `(principal, action, reason code, time window)`; at most one `document.refusals_summary` audit event (counts and reason codes only) is written per principal and window by a bounded job, in its own transaction, so a caller cannot flood the serialized tenant audit chain with refused attempts and the 0051 no-audit-of-404s stance holds. Nonce issuance is not audited by default (volume); open point 16. Payloads carry hashes, ids, counters and reason codes, NEVER content or PII, and render or exception messages must not carry field values either.

## Acceptance-criteria candidates

Criteria 1-4, 7-8, 11-19 and 22-24 belong to the BINDING part (D1-D4, D8, D9); 5, 6, 9, 10, 20 and 21 belong to the direction part and become binding only with their follow-up record.

1. Two issues racing on one scope yield consecutive numbers with no duplicate and no gap; a rolled-back issue releases its number; the first issue of a new scope succeeds (insert-if-absent).
2. An UPDATE of content, number, period, `source_ref` (after first issue), `issuing_org_unit_id` or hash on a non-draft version or its document fails at the database; so does a DELETE (including of a draft) or TRUNCATE on any document table, an UPDATE of `documents.number` once set, and a LOWERING of a sequence counter.
3. Issuing version N+1 atomically supersedes version N; never two `issued` versions; only the allowed status transitions and columns are accepted by the trigger.
4. `verify_binding` returns false for a changed hash, a superseded or cancelled version, another document's hash, and another tenant's id.
5. A signature with `signed_hash` not equal to the server-recomputed version hash, or on a draft, is refused and audited.
6. A reused or expired signature nonce is refused; a signature copied to another version is refused; two concurrent submissions of one nonce yield one signature.
7. Cross-tenant and out-of-scope document/version downloads and reads return 404 indistinguishable from not-found, including headers (no ETag, no Last-Modified), and there is no route addressed by artefact hash.
8. Audit payloads for all `document.*` events contain no field values; chain verification passes after every event.
9. No route deletes a document or version; purge is refused under legal hold, before retention expiry, when the bytes are referenced elsewhere, and without a second principal.
10. Rendered PDF for an issued version, re-downloaded, hashes to the stored `artefact_hash` (the stored bytes are served, never regenerated).
11. Two documents with NULL `legal_entity_id` and the same type, period and number are rejected by the unique index.
12. A document type whose declared fields include a restricted field is refused at registration; and a restriction added AFTER registration makes the next issue of that type fail closed with no number allocated; the renderer is called with only the declared-field projection (a test renderer that asks for another field gets nothing).
13. A forged `content_hash` supplied by a client at signing time is ignored (server recompute); identical content in two tenants yields different `content_hash`.
14. `legal_entity_id` to scope: a principal scoped to org unit A cannot read a document issued under org unit B of the same legal entity (404).
15. D3 pre-checks: a document `content` containing a float, a non-finite number or a duplicate object key is refused; strings in two Unicode forms (NFC and NFD) of the same text yield the same `content_hash`.
16. Trigger coverage: an UPDATE of any `document_types` column once a document of the type exists fails; `documents.current_version` set to a draft, cancelled, superseded or other document's version fails; `documents.period` and `source_ref` changes after issue fail; a draft is discarded only by the `draft -> discarded` transition and a DELETE of a draft fails.
17. `issuing_org_unit_id`: a tenant-wide issuer who names no unit is refused; an issuer cannot name a unit outside their `DocumentsIssue` grant; after a unit is re-parented the document is readable by the new ancestors and no longer by the old ones; after a unit with issued documents is retired its ancestors still see them.
18. Triggers are `ENABLE ALWAYS`: with `session_replication_role = replica` (where a test role may set it) the immutability triggers still refuse.
19. Refusals do not flood the chain: N refused attempts by one principal in one window produce telemetry counters and at most one `document.refusals_summary` audit event, and no per-attempt audit rows.
20. (Slice 2) Purge: a request with `approved_by = requested_by` is rejected by the database; an approval for request A cannot purge request B's target; an expired or consumed request is refused; the purge function succeeds only with the guarded setting and an approved request, and without them a DELETE on the document tables and on `repository_artifacts` fails.
21. (Slice 2) A counterparty signer (null `signer_user_id`) cannot sign the same version twice by the same method; a consumed nonce cannot be reused and UPDATE of any nonce column other than `consumed_at`, and DELETE of a nonce, fail.
22. Sequence change (open point 10): a change by one admin with no second approval is refused when the tenant has two or more distinct active owning tenant-wide TENANT_ADMIN users; the proposer cannot approve their own change; with fewer than two such admins a single admin succeeds with reason and audit; every change without a reason is refused; there is no `DocumentSequenceAdmin` permission.
23. Boot precondition (open point 1 and Postgres ruling): the application refuses to start when `server_version_num < 150000`; the numbering transaction contains no render and no byte-store call (asserted by a test with a renderer that fails the test if invoked inside it).
24. Tenant export carries the tenant uuid and an import restores the hash domain: a document's `content_hash` recomputes identically after an export/import into another install.

## Threats for SECURITY-REVIEWER

T1 Forged or edited issued document: content or number changed after issue; DB trigger immutability (D4), integrity recomputed on read and periodically (D3), audit event holds hashes; residual DDL-role risk stated. T2 Number reuse or skip: concurrent issue, rollback, manual reset lowering the counter (trigger-enforced upward only). T3 Signature replay or transplant: a valid signature attached to another document, version or tenant; nonce and hash binding. T4 Cross-tenant and out-of-scope access, including guessing document ids, content-addressed artefact hashes (no hash-addressed route), and the reuse of attachment signed links for PDFs. T5 PII in rendered PDFs and in logs/audit: PDFs contain personal and BIN/IIN data; restricted fields excluded from rendered content by type registration, no content in audit, telemetry or error messages. T6 Approval bypass: approving version N then consuming N+1, or consuming a cancelled version. T7 Hash ambiguity: non-canonical JSON, number formatting, Unicode forms, duplicate keys; two contents with one hash; the in-tree second canonicaliser must not be mixed in. T8 Forged `internal_ack` presented as legal ЭЦП; type policy must state which method counts. T9 Purge or legal-hold abuse by an admin. T10 Template injection: module template output from untrusted field values (PDF text only; no active content).

T11 Lock/DoS: a user holding the sequence row lock or a long render inside the transaction; mitigation: validation before lock, late allocation, statement and lock timeouts, an issue-rate limit (0040 defers per-actor limits). T12 Time manipulation: number period and `issued_at` come from the server clock only; `client_signed_at` is informational. T13 Mutable satellites: `external_registration`, `superseded_by_version`, `cancelled_*` and the hold flag are written after issue; carved out explicitly (D4 side table and trigger-allowed transitions). T14 Signature nonce storage and expiry: hashed storage, TTL, single use, consumed in the signature transaction. T15 Legal-entity NULL in the unique index: `NULLS NOT DISTINCT` plus NOT NULL for entity-required types. T16 Orphan or misdirected bytes: the byte store is shared with attachments, so purge could destroy another row's bytes; purge refuses on any other reference. T17 Audit read amplification: `document.downloaded` written only for successful downloads, not for 404s or refusals. T18 Cancel abuse: `DocumentsCancel` without SoD on a version others consumed. T19 Restricted field added after type registration, or a non-entity-sourced document with no restriction source: renderer gets only the declared projection and the restriction set is re-checked at every issue (D8). T20 Audit-chain flooding by refused requests: refusals are telemetry plus aggregated counters, not per-attempt audit rows (D9). T21 Trigger bypass by `session_replication_role` or the purge exception: `ENABLE ALWAYS`, role attributes, and the purge exception tied to an approved purge request (D4, D7). T22 Document visibility changed retroactively by retiring or re-parenting an org unit: frozen `issuing_org_unit_id`, current-path reads, retired units stay resolvable (D8).
