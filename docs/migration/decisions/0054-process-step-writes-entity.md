## Options

### Who declares the write

A. **Declared on the node as `entity_writes`** (a list of commands, interpreted by the engine, validated at definition activation). Pros: reviewable and auditable without running code; works for HUMAN_TASK and SERVICE_TASK identically; the activation check can enforce `managed_by`, append-only, scope columns and field lists before anything runs; no module dependency. Cons: limited expressiveness (values come from variables / constants, no logic).
B. **Module callback**. Pros: arbitrary logic. Cons: core would call into a module (0039 D3 allows only the Catalog edge), a code deploy per process change, and the callback runs inside the locked transaction (unbounded time under row locks).
C. **Script outputs as commands** (0053 hook 1). Pros: tenant logic. Cons: not built (#2534 7c open); the script principal is tenant-wide-only (0051 D1); scripts must stay pure (0053 D4).

**Recommendation: A, with C and B mapped onto the same command list.** The write itself is one engine-owned data structure, the `entity_write command` (D1). A script (C) later PRODUCES the same list as validated output through the identical path with the identical checks. A module (B) needs no callback: a module that must write a managed type ships the process definition that declares the write and is recognised as the owner by D6.

## Decisions

### D1. The command shape and where it is declared

An `entity_writes` attribute on a HUMAN_TASK node (applied on completion) and on a SERVICE_TASK node (applied with the result, in the existing second transaction, `engine.ex:3653`). Each line: `op` (`create | update | delete`), `entity_type`, `record` (update/delete: a server-side variable reference, D1a), `fields` (map field name -> server-side variable reference or constant; whole-document replacement as in `update_record`, `records.ex:294`), `expected` (D5), optional `output_record_id_var` (create: the engine stores the minted record id in an instance variable; the name MUST be `_sys.`-prefixed (D1a) and is written ONLY by the engine-internal writer after the create line, in the same transaction; it MUST NOT be pre-seeded, and a create line never accepts a client-chosen record id, `records.ex:239` mints it). The engine also writes `<output_record_id_var>.seq` (the `event_global_seq` of that create) so a LATER line of the same instance can use it as `expected` (D5). Values come ONLY from the allowed sources of D1a and constants; no expressions beyond what `Letflow.Engine.Expr` offers for gateways.

Activation REFUSES a definition whose lines reference an unknown / non-active entity type, an unknown field, a type for which the designer is not authorised (D4a), any declarative line on a `managed_by` type (D4 open-point-2 correction; managed types are written only through a module-registered handler, D6), an update/delete on an append-only type (D7), a line that maps any value onto a scope column (D4b), more than 20 lines on a node, or an input that violates D1a. The 20-line cap is ALSO enforced at runtime on the pinned snapshot (a hand-edited snapshot must not bypass it).

### D1a. Where `record`, `fields` and `expected` may come from (closes the completer-controls-input hole)

`:merge` writes the COMPLETER's submitted output variables. A variable that feeds `record` or `expected`, or a `fields` entry, from a form output lets the completer pick the target record, defeat the version check (submit the current seq) or choose values. Rules:

1. `record` and `expected` may reference ONLY variables in the **engine-owned namespace** `_sys.`. Definition of the namespace (flat, once): instance variables are a flat string-keyed map (`variable_merge.ex:216`, `merge/3` iterates `Map.keys(incoming_variables)`); the reserved keys are exactly the key `_sys` (even when its value is a map) and every key beginning `_sys.`; a reference names the flat key `_sys.<name>`, never a nested path, so no map under another key can reach it.
2. **Central closure (N1).** `VariableMerge.merge/3` is the one choke point and REFUSES any reserved key in `incoming_variables` before it validates or applies anything, returning the same `{:rejected, current_variables, [execution_error event]}` shape as a schema rejection, with a new reason `:reserved_variable_key`. It is applied from EVERY external source that already goes through `merge/3`: form outputs (`:merge`, `engine.ex:4306`), the service-task result body (`engine.ex:3691`; the response is attacker-influenceable data, so a body carrying a reserved key is rejected like a schema-rejected body is today; the handling of the `{:rejected, ...}` branch after `:3691` is NOT re-read here, the requirement must confirm it fails the advance), sub-process output mapping (`sub_process.ex:847`; a child's `_sys.` values never propagate to the parent), and replay (`reconstruction.ex:594,678`, see item 3). Advisor answers to the former NOT VERIFIED list (advisor session, against origin/main 1465df2a1; Ruled by the advisor (letflow-ec) under the user's delegation, recorded by the supervisor, 2026-10-15.) replace it. `VariableMerge.merge/3` is called by: task completion (`engine.ex:4306`, with validations), sub-process (`sub_process.ex:847`, with validations), the service-task result (`engine.ex:3691`, validations `nil`), replay (`reconstruction.ex:594`/`:678`, `nil`) and a no-op (`transition.ex:1367`). Process START variables do NOT go through `merge/3`: `PinResolver.validate_initial_variables` validates them against the pinned JSON schema, so the `_sys` / `_sys.` refusal MUST be added there too (same reason code, same rejection shape as a schema rejection). No message node type exists (`correlation_key` only dedups starts), so there is no message-variable source; timers carry no variable payload; scripts are not built yet (0053 D2 requires a merge with real validations, which then inherits the refusal; hook 1 outputs map to variables and cannot write `_sys.`; option C may only influence `_sys.` by producing `entity_writes` lines through D2). Still NOT VERIFIED: any admin variable-patch endpoint (the requirement routes it through `merge/3` or gives it the same check). Activation checks of the node's own form schema are insufficient alone (variables written by EARLIER tasks' forms are not covered); the central runtime refusal is what protects.
3. **Engine-internal writer.** Reserved keys are written only by a SEPARATE function (e.g. `VariableMerge.put_sys/3`) that takes engine-computed values, is not reachable from any path carrying an external map, and is the only way to bypass the refusal; a test asserts no call site of it receives data derived from a request, form, HTTP response, start input, message or script. Because replay and projection rebuild merge recorded events through `merge/3` (`reconstruction.ex:594,678`), engine-written `_sys.` values are recorded as their own event kind (registered like `TASK_ENTITY_WRITES_APPLIED`, D10) which reconstruction applies through the same internal writer; the event name and payload are the requirement's design. Replay never re-executes `entity_writes` (D11).
4. **`bind_at_activation` is DROPPED.** It had no defined source and would add an engine -> entities read edge at activation (the TOCTOU of open point 3). The only legitimate `_sys.` sources in this record are (a) `output_record_id_var` and its `.seq`, written after a `create` line of the same instance (D1, D5), and (b) engine-held state copied by the engine itself (instance scope node, once 0051 exists). `update`/`delete` lines on records the same instance did not create therefore have no legitimate `record`/`expected` source and are out of scope of this record until a read edge exists (open point 3, resolved below; open point 8, resolved in D2).

   **Ruling. Ruled by the advisor (letflow-ec) under the user's delegation, recorded by the supervisor, 2026-10-15.** (open point 3, option (b), MVP.) Steps may only CREATE records on append-only types; an update or delete of a record the instance did not create is refused (at activation and at run time). The re-activation scheme (a) of the former open point 3 is not built; a conflicting `expected` on the same-instance path (D5) returns `record_version_conflict` as specified in D8 and is not an MVP surface. WMS slice 5 needs only create lines.
5. `fields` entries MAY reference form outputs (that is the point of a worker entering a quantity) but the VALUE then passes the type's own field validation (`validate_field_values`) AND the write-side field check of D4c; a `fields` entry never names a scope column (D4b).
6. A line whose `record` or `expected` input would be a form output is REFUSED at activation. (A completer can therefore never choose which record is written and never skip the version check. This closes the S9 bypass.)

### D2. Layering: a behaviour defined in the engine, implemented in Entities

The engine names no `Letflow.Entities` module. It defines a behaviour `Letflow.Engine.EntityWrites` with callbacks `multi(multi, lines, ctx)` (appends the steps for the lines to the caller's `Multi` and returns it) and `validate_lines(lines, definition_ctx)` for activation. `Letflow.Entities.StepWrites` implements it, injected by configuration (same mechanism and same REVIEWER sign-off as 0053 F10: one new engine -> entities dependency edge, via behaviour). Whether `mix letflow.check_boundaries` allows a core->core behaviour impl injected via `Application.get_env`: NOT VERIFIED (not run in rework 2); the implementing requirement MUST run it.

`Records` gains a public `command_multi/3` returning `{:ok, Multi.t()} | {:error, term()}` (building can fail: definition missing, validation). It is NOT a thin export of today's private Multi; it MUST satisfy:

1. **Namespaced step names (composability).** `command_multi/3` takes a `line_key` (the declared line index) and prefixes every step it adds, including those added by `EventStore.append_multi/3`: `{:line, index, :assign_sequence}`, `{:line, index, :idempotency}`, `{:line, index, :insert_event}`, `{:line, index, :check_record_version}`, `{:line, index, :upsert_record_latest}`, etc. `EventStore.append_multi/3` therefore gains a step-name prefix option (it hard-codes the names at `event_store.ex:535-545` today). The existing single-command path passes no prefix and keeps the current names and `interpret_result/3` unchanged (D12).
2. **Error decoding.** A new `interpret_in_multi/1` decodes `{:error, {:line, index, step}, reason, _changes}` into `{:entity_write_refused, index, code}`. It has NO duplicate-as-success clause: the single-command `interpret_result` treats `{:duplicate_idempotency_key, event}` as success (`records.ex:727-735`); inside a completion a duplicate is an integrity error (D9) and MUST NOT be mapped that way.
3. **No eager work inside the transaction.** `EntityTypeInstance.get_or_create/2` for EVERY line's type runs BEFORE the transaction opens (types are known from the node, so the engine calls a `StepWrites.prepare/2` before `Repo.transaction`); it is an insert that would otherwise add an unlisted lock edge (unique-index wait) under the instance locks. Everything that depends on the existing record (existing row, carry-over of unseen fields, old scope value, the version value) is computed lazily in a `Multi.run` AFTER the type sequence lock and the record row `FOR UPDATE`, never from a pre-lock read. Pure validation that needs no row (definition lookup, field-name check) may run before.

Script outputs (option C) call the same behaviour; modules (B) never call it.

**Ruling. Ruled by the advisor (letflow-ec) under the user's delegation, recorded by the supervisor, 2026-10-15.** (open point 8, resolved.) There is ONE engine -> entities port, `Letflow.Engine.EntityPort`, a single behaviour carrying both the read callbacks (0053's read port) and the write callbacks (`multi/3`, `validate_lines/2`, `prepare/2` of this record). The name `Letflow.Engine.EntityWrites` used above is the write half of that behaviour, not a second behaviour; there is one injected implementation, one config key and one `check_boundaries` allowance, and one REVIEWER sign-off for the edge (F10).

### D3. One Multi, one execution order, lock order

All lines of one node run as additional `Multi` steps of the SAME `Repo.transaction()` as the completion (new step `:entity_writes` placed after `:merge` and before `:transition`). A refusal of any line aborts the whole Multi: the task stays `pending`, no event, no record, no idempotency claim commits.

**Execution order (normative, numbered; identical to the declared steps):**

0. BEFORE the transaction: `get_or_create` for every line's type (D2.3), in its OWN short transaction with `SET LOCAL lock_timeout` / `statement_timeout` (open point 4, a smaller value) so a concurrent create of the same type's row cannot hold the completion unbounded; a timeout there maps to `entity_write_contention` before the main transaction opens. It is safe to commit independently: `get_or_create` is idempotent and leaves only an empty per-type synthetic instance, never a record or event (N6).
1. `tasks` row `FOR UPDATE`.
2. `instance_projections` row `FOR UPDATE` (1-2 are the existing instance mutex, `engine.ex:348`).
3. The instance's own `instance_sequences` row (any instance-stream append, e.g. in `:merge`).
3a. ONLY when a line's type feeds `scope_node_paths` (org-tree types, owned by the org module per D6) OR is a scoped type whose ceiling check (D4b) reads `scope_node_paths` (N5): the `scope_node_paths` SHARE ROW EXCLUSIVE table lock via `Letflow.ScopeNodePaths.lock!(prefix)`, taken by the engine immediately AFTER step 3 and BEFORE step 4. (Rule order is therefore 1, 2, 3, 3a, 4, 5; the first draft's text put 3a before 3 in prose; this is corrected: 3a follows 3 and precedes every entity-type lock.) The `lock!` implementation MUST NOT interpolate the tenant schema name into SQL; it uses a validated/quoted identifier (INV-7).
4. Lines are EXECUTED sorted by `(entity_type, declared index)`. For each line in that order the sequence is: (4a) the type's `instance_sequences` row `FOR UPDATE` (taken by the first command of that type via `lock_and_increment_sequence`, held to commit); (4b) idempotency claim; (4c) for update/delete, the record row `FOR UPDATE` (`:check_record_version`); (4d) read-dependent computations (D2.3); (4e) event insert and `entity_record_latest` upsert.
5. `:transition` and the tail.

Lock order is therefore lexicographic over `(type, sequence-row < record-row)`: for each type, sequence row first, then that type's record rows, types in ascending `entity_type` byte order. Idempotency keys and error indexes keep the DECLARED index.

**Record-row order, resolved.** Two lines on the SAME type touching records (r1, r2) and (r2, r1) in two completions: both completions take the type's sequence row first (4a), and it is held to commit, so the second completion waits there and never reaches the record rows while the first holds them. Record-row order is therefore moot for every writer that goes through the event-store sequence protocol (all `Records` and engine writers take sequence-then-record). The first draft's "ascending record_id" sentence is DELETED because the execution order sorts by `(entity_type, declared index)` and the sentence was not implemented. Whether any other path locks `entity_record_latest` rows `FOR UPDATE` outside `records.ex:496-516`: NOT VERIFIED exhaustively (a grep of `lib` outside `engine.ex` showed no other locker on that table among the first 20 hits; not complete). The implementing requirement re-greps; if another locker exists, lines are sorted by `(entity_type, record_id, index)` for update/delete.

**Deadlock check, three scenarios.**
- Completion with lines vs concurrent `Records.update` of the same type: both take the type sequence row first (`event_store.ex:606-640`, then `records.ex:496-516`); the completion also holds 1-3, which `Records.update` never requests. No cycle.
- Completion vs an org move (REQ-496 rev 3: table lock, then per-type sequence, then record): a completion with org types takes 3a before 4, same order; a completion without org or scoped types never takes 3a and holds nothing the org move needs before 4 except the org types' sequence rows, which it takes only if it writes org types (then it took 3a first). SAFE under rev 3; NOT VERIFIED against merged code.
- Two completions of different instances with line sets (A,B) and (B,A): both execute (A then B). The instance's own `instance_sequences` row (step 3) may in fact first be taken only in `:transition` (after step 4) if `:merge` appends no instance event; that is harmless because every writer of that instance stream holds the projection mutex (steps 1-2, or the dispatch-then-projection locks of the service path), so that row is never contended in the opposite order. SAFE, provided no step before 4 (`:merge`, any hop chain in `:transition`, which runs AFTER 4 in this order) touches an entity-type sequence row; that is true for `:merge` (instance stream only) by construction; NOT VERIFIED for the `:transition` hop chain emitting entity events (none known).

**SERVICE_TASK path (N2).** `advance_after_service_task_outcome/4` is an imperative `repo.transaction(fn -> ... repo.rollback(reason) ... end)` (`engine.ex:3654-3659`), but it is NOT Multi-free: `do_persist_service_task_advance/10` (`engine.ex:3914`) builds the real `Multi` (hop chain, timer arms, dispatches, `:service_task_completed_event`, `:projection`) and runs it with a nested `repo.transaction(multi)` (`:4043`). `StepWrites.multi(multi, lines, ctx)` therefore appends `:entity_writes` to THAT Multi, after the hop-chain / timer / dispatch steps and before `:service_task_completed_event` and `:projection`; no imperative twin of the steps is needed, and the same composed steps and checks run on both paths. Lock order there: dispatch row (`:3680`), projection row (`:3682`), then the Multi steps, so rules 3-5 hold unchanged after those two locks; entity-type locks are requested only inside `:entity_writes`. ### D4. Principal, privilege and field rules

**D4a. Privilege delegation (stated, not implied).** A task completer needs `:TasksComplete` plus assignment; `:EntitiesRecordsWrite` is held only by admin-class roles. A completion with `entity_writes` therefore writes records the worker's own role could not write: the write is a DELEGATED privilege of the **activator**. Rules:
1. At definition activation the engine records, on the definition version, `activated_by` (principal id), the permissions evaluated (`:DefinitionsActivate` and `:EntitiesRecordsWrite`) and the set of `(entity_type, op)` pairs authorised. The authority is evaluated and RECORDED at activation and is not re-evaluated per run.
2. **Per-type designer authorisation (N4)**: coarse `:EntitiesRecordsWrite` is NOT enough. Declaring `entity_writes` on a type requires an explicit per-type allow: a `writable_by_process` flag on the entity type definition. (a) **Who may set it**: only a principal holding `:EntitiesDefinitionsWrite` (`authorization.ex:310`), through the existing type-definition write path; an `:EntitiesRecordsWrite`-only or `:DefinitionsWrite`-only principal cannot. (b) **Where it is refused**: setting `writable_by_process` is refused outright on `managed_by` types, org types (the `org_*` family and any type feeding `scope_node_paths`), user/role-adjacent types and attachment-metadata types; the refusal lives in the type-definition write path, not in the UI. (c) **Re-checked at RUN time**: the flag is read from the CURRENT active type definition, which D2.3 already reads under lock, on every execution of a line; if it is absent the line is refused (`write_not_permitted`), so removing the allow stops a running definition. Activation checks it too (fail early). (Closes first-draft open point 1: per-type, not coarse.)
3. At run time the write never exceeds BOTH the activator's grants as recorded at activation AND the completer's scope: a line is refused if the completer's role scope (existing completion authorization) does not cover the instance, and the field/scope ceilings of D4b/D4c use the recorded activator grants for the field check and the INSTANCE scope for the scope check.
4. If the activator is later deactivated (#2557) the definition keeps running with the recorded authority; this is flagged as a known weakness: deactivating a principal MUST mark its definitions `needs_reactivation` (open point 9) rather than silently continuing; until built, the weakness is accepted and documented.

5. **Amendment (2026-10-15, supervisor ruling under delegation, advisor FYI; from letflow-4's B1 review of GH #2587): the activator is a principal of the TARGET tenant.** D4a was silent on whose schema the activator lives in. The activator recorded in `activated_by` is always a principal of the tenant the definition is activated in. **Cross-tenant promotion of a graph that carries entity-write lines is REFUSED at promotion** with the distinct code `entity_write_activator_not_in_target_tenant`; this is documented as a PILOT LIMIT. Promotion has NO draft mode (the target row is inserted as `:draft` and activated inside the same swap, `lib/letflow/definitions/promotion.ex`), so such a graph cannot be promoted at all; both promotion routes answer 422. Recovery: the graph is created as a DRAFT directly in the target tenant and ACTIVATED there by a target-tenant user, who then becomes the recorded activator. (Corrected 2026-10-15 from letflow-4's B1 implementation: the first wording of this note said "promoted as a draft".) The activator of a promotion's apply step is the APPLYING principal (`apply_review/4`'s `actor_id`), never `review.requested_by`. The platform operator never activates a definition in another tenant.

**D4b. Scope ceiling (0051 T12/T13/T14).** The write is authorized against the INSTANCE `scope_node`, never re-derived from the caller. (1) Activation REFUSES any line that maps a variable or constant onto a scope column (scope is never taken from a mutable field). (2) On create, the scope column is set by the engine to the instance `scope_node`. (3) On update/delete, the OLD scope value is read from the row UNDER the row lock (D2.3), and both OLD and NEW values must lie inside the instance subtree. (5) **Until `scope_node` exists in code (0051 landed), ALL lines on scoped types are refused (fail closed)**; this is an explicit `depends_on` of the implementing requirement. (5a) **Once it exists (N5)**, the ceiling check for ANY scoped type, org or not, reads `scope_node_paths` only AFTER the rule-3a lock of D3 is held (a mode that conflicts with a concurrent org move; SHARE for a read-only ceiling check vs SHARE ROW EXCLUSIVE for org writers is decided against 0050 D8 when #2530 merges, NOT VERIFIED), so an org move cannot commit between the check and the write; the contention cost (3a now covers all scoped types) is listed in Consequences. Reading the scope paths without that lock is not allowed. SERVICE_TASK: `EventStore.platform_actor_id()` (`service_task_dispatcher.ex:675`), with the activator id carried in `source` (D10). ### D5. Version expectations on updates and deletes

`expected` is REQUIRED on `update`/`delete` lines (fail closed), and per D1a it comes from the engine-owned `_sys.` namespace (D1a): the `<output_record_id_var>.seq` the engine wrote after a `create` line of the same instance, never from a completer-writable variable, a service-task response or any other external source (`bind_at_activation` is dropped, D1a.4). The value is validated as a non-negative integer BEFORE `expected_seq/1` is reached; invalid -> `validation_failed`. A mismatch returns `record_version_conflict` (`records.ex:515`) and rejects the completion (D8). The version is never read from client request fields of the completion call. There is no literal `"any"` and no `last_writer_wins` (removed as scope creep); a type's guarantee is never relaxable by the process designer.

### D6. managed_by types and the ownership stamp (AMENDS 0050 D7)

0050 D7 says a process step that writes an entity and hook 2 "must also refuse managed types, with the owning module path identified by caller, not by request data". 0050 D7 (`0050` lines ~150-195) says `managed_by` is declared by module code/manifest, immutable, and that the owning module's own path writes it. It does NOT say a PROCESS DEFINITION can be an owner. This record introduces that concept and is therefore an **amendment to 0050 D7**. ACKNOWLEDGED by the advisor (open point 1 resolved; see the ruling after the list; the amendment is recorded here and in 0050's consistency list by the implementing requirement).

The mechanism is an `owner_module` stamp on a process-definition VERSION, with these properties:
1. **Set only by the module install step**, in code unreachable from `POST/PUT/PATCH /definitions`, import, rollback and `DefinitionsActivate`. The definitions API refuses the field outright.
2. **Per version, never inherited**: a tenant-created, edited, imported or rolled-back version of a module-owned definition (same key) NEVER carries the stamp; a module-owned version is immutable to tenant edits.
3. **Hash-pinned**: the stamp stores the hash of the module manifest/definition body; verified at activation AND at run from the pinned snapshot. A hash mismatch refuses the write.
4. **PinRebind**: an instance pinned to a module-owned version MUST NOT be rebindable to a tenant version that keeps its managed writes; `pin_rebind.ex` (`:140-150`) refuses a rebind whose target lacks the same stamp when the source has lines on managed types.
5. **Runtime recheck reads BOTH**: the `managed_by` of the CURRENT type definition (so a type that became managed after activation is refused) AND the stamp of the instance's PINNED definition snapshot.
6. Same-name supersession (0050 D7 tamper rule) cannot transfer the stamp (follows from 2).

**Ruling. Ruled by the advisor (letflow-ec) under the user's delegation, recorded by the supervisor, 2026-10-15.** (open point 1, resolved.) The 0050 D7 amendment is ACKNOWLEDGED. The module manifest hash lives on the process-definition VERSION row, beside `owner_module` and `owner_module_version`. It is written only by `Installs` and by the module-upgrade path (0055), never by the definitions API (which refuses the field, property 1). At activation the stamp MUST equal the hash of the module version recorded in `tenant_modules`; otherwise activation is refused. Property 3 (verification at run time from the pinned snapshot) is unchanged.

**Since the open-point-2 correction (D4, option A), the stamp never authorises a declarative `entity_write` on a managed type; it only decides which module's registered write handlers a definition version may invoke.** **Until the stamp exists (it does not; `owner_module` NOT FOUND), managed_by types cannot be written by a step: REFUSE.** Because `managed_by` is today just a JSON key a tenant could set or omit, a flag-presence stub protects nothing and is documented as non-protection: the WMS ledger MUST NOT rely on it. The only protection before 0050 D7 is the per-type authorisation of D4a.2. The test with a fake flag covers the refusal path only.

### D7. Append-only types

`create` lines are allowed; `update` and `delete` lines on a type whose CURRENT active definition has `"append_only" => true` are refused at activation and again at runtime with `entity_append_only` (`records.ex:993-1000`), ordered before the claim as today (`records.ex:42-54`). Stock ledger corrections are new compensating `create` lines. A create line can never target an existing record id (D1: ids are minted). MVP scope per the ruling in D1a.4: steps create records on append-only types only; update and delete lines are not an MVP surface.

### D8. Failure semantics (stable codes; nothing commits)

Any line failure rejects the completion; the task stays `pending`, no instance event, no record, no idempotency claim. New public members of `complete_error`: `{:error, {:entity_write_refused, index, code}}` with `code` one of:

- `record_version_conflict` (409, not retryable with the same input)
- `entity_append_only` (422, no)
- `write_not_permitted` (403, no): one code for managed type, unauthorised type, field restriction, and scope denial (see INV-5 below)
- `validation_failed` (422, no field names for restricted fields)
- `idempotency_conflict` (422, no; D9)
- `entity_write_contention` (503/409, retryable after backoff; D3)
- `entity_type_inactive` (422, no)

**INV-5 (no existence leak).** `record_not_found`, out-of-scope record and `field_restricted`-on-an-unseen-record all return the SAME `write_not_permitted`/uniform not-found-shaped response to the completer; `record_version_conflict` is evaluated only AFTER the scope and permission checks so it never reveals a record in another scope; `field_restricted` carries no field names. The detailed reason (managed, scope, restriction, missing) is written to the tenant audit log and the log, not the response. `managed_entity_type` can fire at runtime only from a tampered definition: logged, generic response.

`index` is the declared line index (never the sorted execution index). `{:output_refused,...}` and `:separation_of_duties` are unchanged and checked BEFORE the entity lines.

**`:merge` execution error.** `:merge` may return `{:ok, {:execution_error, _}}` (a successful Multi step recording an instance error; `engine.ex:2478`). The `:entity_writes` step MUST pattern-match on the `:merge` result and SKIP (write nothing) when it is an execution error; otherwise records would be written for a failed completion.

### D9. Idempotency key (hard prerequisite: #2550)

Each line's key is SERVER-DERIVED and never supplied by a client: `"sys:step:" <> dispatch_or_task_id <> ":" <> index`. HUMAN_TASK: the locked task row id. SERVICE_TASK: the DISPATCH row id (one per `(instance, node)` dispatch; a retried attempt reuses the same dispatch id and MUST NOT re-apply; the key is not keyed on attempt). Bound by #2543 to command, actor, entity type, target and field values.

**Squatting.** The key is derivable by any assignee (task ids are visible); a client can pre-claim it through `POST /entities/records` and wedge the task. Required, as a hard `depends_on` that lands BEFORE or in the same PR as `entity_writes`:
1. The `sys:` refusal lives INSIDE `Records.*` (every caller: HTTP create/update/delete, bulk import in `routers/entities.ex`, module code, scripts), NOT only in the router. An internal-only bypass is reachable only from `StepWrites`.
2. The check is on exact bytes after no normalisation. The closed charset (ASCII letters, digits and `:_-.` only) applies ONLY to the `sys:`-namespaced SERVER keys that `StepWrites` builds (the ids it appends are validated against it, so a lookalike cannot be minted). It is NOT a new global validator on client keys (N7): client keys are namespaced per #2550 (assumed form `client:<route>:<actor>:<K>`; text NOT FOUND, final scheme is open point 7), so they cannot collide with `sys:` by construction and existing clients are not broken (D12). The `Records.*` boundary refuses an INCOMING client key that, as exact bytes before #2550 namespacing, begins `sys:`; case or Unicode-lookalike variants are harmless only because of the namespacing, not because of a charset rule.
3. The #2550 final scheme must not re-allow `sys:`.

**Amendment (2026-10-15, #2550 REVIEWER finding 3; supersedes the "refuses an INCOMING client key" sentence of item 2 and Test 7's "is refused").** #2550 does not refuse a client key that begins `sys:`. It NAMESPACES it at the entry points: the entity body (POST, PUT and import), the instances idempotency-key header, and Lua `platform.emit_event`. Such a key is stored as `client:rec:<actor>:sys:step:...`, and the call succeeds with 201 (`client_key_namespace_test.exs`). So a client can never claim a server `sys:step:` key. `sys:` is held in `Letflow.Idempotency.reserved_prefixes/0`, not `server_prefixes/0`, because no server writer produces it yet. In-process `Records.*` callers still pass raw keys unchanged, because server writers such as `Certificate` rely on that. The item-1 boundary is therefore narrowed: an in-process caller other than `StepWrites` cannot store a raw `sys:step:` key. That is new enforcement in REQ-499 (GH #2587) PR A.

A duplicate key found inside a completion is NOT success: the task was pending, so a prior claim is an integrity error -> `idempotency_conflict`, rolling back (D2.2). The completion's own client `idempotency_key` is unrelated.

### D10. Audit and event shape

Each line appends the existing entity events on the entity-type stream (`ENTITY_RECORD_CREATED/UPDATED/DELETED`) with metadata `source: {kind: "process_step", instance_id, task_id, node_id, definition_id, definition_version, line_index, activator_id}`. **`source` is set by the engine only**: `Records.*` public entry points REFUSE any client-supplied `source` (reserved key) so a direct write cannot impersonate a process write; the reserved-key check lives inside `Records.*` like the `sys:` check. The reserved-key refusal and `validate_metadata` (`event_store.ex:494-502`) behaviour for client metadata: NOT VERIFIED in rework 2.

The instance stream gets ONE `TASK_ENTITY_WRITES_APPLIED` event in the completion tail carrying `(entity_type, record_id, event_global_seq)` per line and a hash of the declared lines. **The event type MUST be registered** (`Registry.validate_payload` returns `:unknown_event_type` otherwise; VERIFIED above); registration is part of the implementing requirement's migration. Tenant `Audit.append_multi/4` (`audit.ex:189`) is called UNCONDITIONALLY for every line (hash-chain trail), not only for managed or ledger types. No field values are copied into the instance event (INV-2).

### D11. Replay and reconstruction

The instance event records ids and global sequences, not a command to re-run. Rebuilding instance state from events never re-executes `entity_writes`; rebuilding `entity_record_latest` replays the entity-type stream as today. New record ids are minted ONCE inside the transaction and recorded in the event (`records.ex:239`). A test proves no replay path calls `StepWrites`. Timer, escalation and cancellation paths never call it (D12). A service-task retry cannot double-apply because the whole apply is one transaction keyed by the dispatch row (0053 D2 compare-and-set).

### D12. What does NOT change

`Records.create/update/delete` semantics and HTTP routes (the refactor to `command_multi/3` is behaviour-preserving for the single-command path, which passes no prefix and keeps `interpret_result/3`, proven by the existing suite); the exam `Certificate` path; the REQ-045 decision (no process per instance); variable merge and form validation (except the `_sys.` refusal of D1a, which also covers start variables via `PinResolver.validate_initial_variables`); gateways stay `Expr`; scripts stay pure (0053 D4); the instance lock mutex; `managed_by` / `scope` declarations by modules (0050/0051). No entity write from timers, escalations or cancellation.

## Consequences

- One new engine -> entities edge (behaviour), used twice: at run time (`multi/3`) and at definition activation (`validate_lines/2`); one new public Records function with prefixed step names and a changed `EventStore.append_multi/3` signature (additive option).
- EE-12 becomes a cross-instance lock inventory for completions with `entity_writes`: entity-type sequence rows are PER TYPE, so a long completion blocks every other writer of those types in the tenant (DoS hazard, mitigated by the 20-line cap, `lock_timeout`, `statement_timeout` and a wall-clock guard) and the `scope_node_paths` table lock (rule 3a, now also taken by completions that write scoped non-org types, N5) blocks org-tree writes, and concurrent completions of scoped types, while held.
- Process designers gain delegated write power: the per-type allow-list (D4a.2) is the new administrative surface; deactivated-activator definitions keep running until open point 9 is built.
- Service-task writes are atomic with the RESULT apply, not with the external call. Ruled (open point 6): that is enough for stock posting provided posting happens only in the result-apply transaction (or a HUMAN_TASK step), is keyed by `(instance, node, attempt)`, never depends on a side effect of the HTTP call (a lost response is an incident, never a second posting), and external systems (1C/SAP) are told AFTER posting through the outbound mirror (D3).
- New prerequisites that must land first: #2550 `sys:` and `source` refusal inside `Records.*`; the `owner_module` stamp plus the module write-handler registration mechanism (REQ-501, GH #2590) before any managed or ledger type is written by a step; 0051 `scope_node` before any scoped type; write-side field restrictions.

## Amendment (GH #2590 / REQ-501 PR R2): D6 stamp STORAGE

The module ownership stamp of a process definition version is four nullable columns on
`process_definitions` (`owner_module`, `owner_module_version`, `owner_manifest_hash`,
`owner_body_hash`; all-or-none CHECK) written ONLY by the INSERT of
`Letflow.Definitions.create_owned/3` from a module install, never by a cast list and never by
an UPDATE; a database trigger refuses any later change of an `owner_*` column and, on a stamped
row, of `graph`. `tenant_modules.manifest_hash` records the install-time manifest hash (NULL for
modules installed before R2; no backfill). The hashes are never serialised; `owner_module` and
`owner_module_version` are read-only on the definitions API. The manifest hash covers the
declared surface only (not handler code, permissions or settings) and is not proof of behaviour.
Nothing consumes the stamp until R3 (activation) and R4 (run time).
