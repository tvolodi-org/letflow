## Options

**U1. Re-install over the top (drop `already_installed`, re-run pack and `on_install`).** Rejected: `on_install` is not idempotent, `activate_and_promote` would hit `entity_name_conflict` against the module's own previous rows (`entity_activation.ex:96-102`), tenant additions are lost.

**U2. Code-only migrations (each version ships Elixir `up`/`down` steps, core runs them).** Full power, reviewed code, but every trivial change needs bespoke code and review, and nothing is diffable or previewable.

**U3. Declarative diff only (core computes old->new diff and transforms).** Previewable and safe, but cannot express real backfills; modules would route around it.

**U4 (recommended). Plan-then-apply with a computed diff, declarative steps for the common cases, reviewed code steps for the rest behind a runtime fence, one journal per tenant upgrade.** Additive changes are automatic; destructive or data-shaping changes need a declared step plus an explicit acknowledgement; anything not covered is refused. Recommendation: U4.

## Decision

### D1. What is versioned

* The unit of upgrade is the **module version**: manifest `:version` becomes a strict semver string (a new `Catalog.validate/1` rule; core change). `tenant_modules.version` is the version the tenant has APPLIED, changed only by a successful upgrade or rollback (D9), and no longer "immutable" (amends the `tenant_module.ex:58-62` text).
* **Per-artefact versions stay as they are** (entity definition `logical_shape_version`/`artifact_version_id`, process definition `version`) and remain the unit of activation and pinning. A module version is a bundle that names which artefact versions it ships.
* New table `tenant_module_upgrades` (tenant schema, **no `tenant_id` column**; tenancy is the schema prefix): `id, module_id, from_version, to_version, kind (upgrade|rollback), state (planned|running|failed|done|abandoned), plan_hash, actor_id, rationale, step_id, step_cursor (last primary key), steps_done (set of finished step ids), touches (the plan's allow-list of entity types and tables, D3), `catchup_from_seq` (D5), `runner_id`, `epoch` (integer fencing token, starts at 1, incremented on every takeover, D5), `heartbeat_at`, started_at, finished_at, error_code`. `kind`/`state` are `Ecto.Enum`. The journal is the audit anchor (D10). A status read, if one is added, returns state, step ids, counts and the stable `error_code` only: never `step_cursor` values, `runner_id` or lease internals (INV-2; N-S9). `kind` values `uninstall|reactivate` are added by the uninstall record, not here. The migration creating it, and the `status` column when it arrives, MUST be added to the tenant-provisioning migration list (`tenant_provisioning.ex`, the list around :482-532 and :642) so new tenants get it (INV-1(b)).
* A module declares, in the NEW version, an ordered `migrations/0` list of `%Step{}` structs (`@enforce_keys`, a `@type` union for declarative variants): `id, from, to, kind: :declarative | :code, up, down: spec | :irreversible, lossy: boolean`. Skipping versions is allowed only if the chain of steps from the tenant's version to the target is contiguous; otherwise `{:error, {:no_upgrade_path, from, to}}`.
* **Support window:** the manifest declares `min_upgradable_from` (semver). The new version's `migrations/0` must contain every step from `min_upgradable_from` onward, forever; a tenant below it gets `{:error, {:no_upgrade_path, ...}}`. `min_upgradable_from` is never above `min_data_version` of any release still deployable (D5).

### D2. The upgrade algorithm (diff, then classify)

`POST /tenant/modules/:module_id/upgrade/plan` (read-only, computes and stores `plan_hash`) then `POST .../upgrade` with the `plan_hash` and a non-blank rationale (reuse `Installs.fetch_rationale/1`, `installs.ex:267-278`; the router never synthesises one, 0052 D3). Both need `:ModulesManage`; tenant comes from the auth context only (INV-1). Plan cost is bounded (N-S7): one plan in flight per tenant and module, preflight queries run under a configured `statement_timeout` (a timeout answers the stable code `plan_too_expensive`, never a partial count), and the plan route is rate limited (limit: open point 10). The plan lists, per artefact class, old->new and a class:

| Class | Change | Rule |
|---|---|---|
| A. additive, automatic | new entity type; new optional field (nullable/default); new non-unique index; new optional constraint on a NEW field; widened enum; relaxed min/max; new process definition version; new `settings_schema` key with default; new permission atom; new route | applied without a step; new definition rows are inserted `:inactive`, activated at cutover (D5) |
| B. step required | new required field or default-less NOT NULL; type change; constraint tightening on an existing field (unique, min/max, required, enum narrowing); field removal; `settings_schema` change that stored settings no longer satisfy | refused unless the new version declares a covering step AND the apply carries `ack_destructive: [step ids]` whose set equals the plan's Class B step ids (a bare boolean is not accepted; a different set answers `ack_mismatch` 409) |
| C. forbidden | entity-type rename or removal in place; changing or removing `managed_by` (0050 D7, `0050:192`); a module-owned field/validation key starting `x_` (D4); touching a type with `managed_by` of ANOTHER module | `{:error, {:upgrade_forbidden, reason, subject}}`, no override. The `managed_by` clauses here and in D3/D8 are dormant until #2530 builds `managed_by`; until then they are enforced by `Catalog.validate/1` and CI on the manifest only |

* **Removed permission atoms and removed grants are INFORMATIONAL.** A removed compiled grant takes effect for every tenant at deploy (fact 3); a per-tenant acknowledgement for it would be fiction. The plan lists them as "effective at deploy" and they neither block nor need `ack_destructive`. The earlier Class C wording on removing an atom a tenant role holds is deleted: roles are core roles (0029 section 2) and tenants cannot hold module atoms (NOT VERIFIED beyond that reading of 0029).
* **Field removal** means "retire": the field leaves the definition, stored values stay in the record blob and in any promoted column (no column is ever dropped, fact 4). Physical removal of data is not an upgrade operation (D8).
* **Type change** only along a declared lossless widening list (integer->decimal, string->longer string, enum widening) as a Class B step with `lossy: false`; any other change is "add a new field, copy step, retire old".
* **Constraint tightening** runs a PREFLIGHT inside the plan: count of existing records violating the new constraint. The plan returns counts only: no record ids, no samples, and **no count for a field under `entity_field_restrictions`** (INV-2; a count over a restricted field leaks value equality to a `ModulesManage` holder), and any per-field count requires the caller to hold read on the type. Non-zero blocks apply until a step fixes the data; the constraint is promoted (unique) only after the data step (D5).
* **Entity-type rename** is "new type + copy step + old type retired"; the old type's definition and records stay (0050 D3.3 covers record rename, not type rename).
* **Process definitions:** new versions are created as DRAFT through `Definitions.create` (as the pack does, fact 6), never activated by the upgrade (consistent with 0052 D4); activation stays a `:DefinitionsActivate` act. The 3-way pack-update machinery is NOT used for module packs.
  **Ruling. Ruled by the advisor (letflow-ec) under the user's delegation, recorded by the supervisor, 2026-10-15.** (open point 7, resolved.) Process-definition drafts created by an upgrade are activated MANUALLY; a module cannot declare auto-activation.
* **settings_schema:** stored settings are revalidated against the new schema in the plan (`JsonSchema.validate`, `installs.ex:175`); a failure is Class B and needs a `settings` step; keys are never silently dropped.
* **on_install side effects (e.g. seeds):** not re-run. A version that needs a new seed ships a step; seeds are upserts that add or fill only and never delete or overwrite a row a tenant created or edited (exam's `entity_field_restrictions` is the model, fact 7).
* **`plan_hash` covers (all of):** the target manifest version; the ordered step list and a `steps_digest` DERIVED AT RUNTIME by core from the compiled step modules (hash of each step module's `module_info(:md5)` plus the declarative step structs), never an author-declared literal (CI may compare a committed copy, but the runtime value is what binds); each step's `touches` allow-list (D3); the content hashes of every target entity/process definition; a fingerprint of the tenant's current state (active definition ids, applied version, settings hash); a digest of the EFFECTIVE permission matrix (D7.1) and of the module's compiled route policies at plan time; the promotion-threshold, `lock_timeout`, lease, batch-size and `statement_timeout` configuration values (they select in-cutover versus post-cutover promotion and bound batches); and the preflight violation counts. Apply and resume recompute it and refuse on any mismatch with the stable code `plan_mismatch` (409), requiring `abandon` and a new plan. **Apply re-runs the preflight** and compares its counts with the plan's (per-record data itself is not hashed; a changed count means the reviewed plan is stale). Only one module version exists per node (fact 2), so without this a resume after a deploy would execute a different step set than the one reviewed.

### D3. Data migration steps: declarative first, reviewed code second

All identifiers and values in steps are handled as follows (INV-7; precedent `lib/letflow/design/iss-0777-entity-type-identifier-validation.md`):

* **Declarative step vocabulary (closed, executed by core):** `set_default(type, field, value)`, `copy_field(type, from, to, transform)`, `rename_field` (= copy + retire), `backfill_from_constant`, `settings_map`. Every entity-type, field and column identifier is validated against the ISS-0777 format AND against the loaded definition, and quoted when it reaches SQL; `transform` is a closed-atom lookup (identity, to_decimal, trim, upcase), never a name resolved to a function dynamically; every value is a bound parameter. Core runs steps in bounded batches by primary-key cursor, idempotently ("only rows where target is unset"), under the tenant prefix.
* **Key-level atomic writes (x_ integrity).** A step MUST update specific `field_values` keys in one statement (`jsonb_set` or `||` on named keys, with the "only where unset" predicate in the same statement). Reading the blob and writing it back is forbidden. The runner asserts no step touches a key starting `x_`, and `Catalog.validate/1` rejects a step field name starting `x_`.
* **Migration writes APPEND EVENTS; they never update the projection directly (N-R1; binding).** Records are event-sourced (fact 5): a direct `jsonb_set` on `entity_record_latest` would be reverted by `rebuild_projection/2` / `replay_record/3`, would leave the promoted per-type tables out of step and would be invisible to event consumers. So a batch appends, through the event store inside the batch transaction, one `ENTITY_RECORD_MIGRATED` event per changed record: a NEW event type (schema_version 1) registered per tenant beside the existing three (extension of `EventTypes.seed!/1` AND a migration/backfill registering it for existing tenants, INV-1(b); the registration must be in the tenant-provisioning list). Payload: `entity_type`, `record_id`, `entity_def_version` (the record's existing value, unchanged; the next ordinary write stamps the new version, open point 13), `upgrade_id`, `step_id`, `plan_hash`, and `before` / `after` maps of ONLY the touched `field_values` keys. The projector gets a new fold clause that MERGES `after` into `field_values` at key level (not the wholesale replace of UPDATED, `projector.ex:479-488`); without it the fold would reject the event (`projector.ex:511-514`). The clause has a not-deleted guard, sets `last_event_global_seq`, sequence number and type like any event, and keeps `entity_def_version` as the payload value. **Two projection paths, one fold (R3-1).** The REBUILD path (`rebuild_projection/2`, `replay_record/3`) writes `entity_record_latest` and the promoted per-type row from the folded snapshot (`projector.ex:340-372`, `insert_entity_table_row`). The LIVE path is different code: the `records.ex` Multi (`records.ex:379-390`: event append, then `:upsert_record_latest`, then `:dual_write_promoted_columns`, with its own promoted-column cast). The Writer REUSES those live steps (`:upsert_record_latest` then `:dual_write_promoted_columns`, factored so the Writer and `records.ex` call the same code; no third implementation of the live projection) to apply a MIGRATED event, and both paths apply the same fold for `ENTITY_RECORD_MIGRATED`. A MIGRATED event for a record that is `deleted` is SKIPPED (no event appended, no resurrection; the fold would otherwise give an `event_after_delete` corrupt stream), on the live path and on the rebuild path alike. Side effect, accepted and documented: advancing `last_event_global_seq` invalidates a client's optimistic-concurrency token for that record (GH #2528) once. `last_event_global_seq` advances with each MIGRATED event like any event. A tenant whole-document UPDATED composed before the batch can overwrite migrated keys; that is what the cutover catch-up re-runs the idempotent step for (D5). The step's 'only where unset' predicate is evaluated against the row locked in the same transaction.
* **No new `entity_def_version` on MIGRATED (ruling).** Ruled by the advisor (letflow-ec) under the user's delegation, recorded by the supervisor, 2026-10-15. (open point 13, resolved.) An `ENTITY_RECORD_MIGRATED` event keeps the record's existing `entity_def_version`; stamping the new version would claim a validation under the new definition that has not run. The migration step is recorded separately: `upgrade_id` and `step_id` in the event payload (above) and the journal row, so the event shows which step touched the record without touching the version stamp. The next ordinary write stamps the new version.
* **Consumers of MIGRATED events.** Tenant script hooks (0053 point 2 pre-write validation / derived fields, point 4 after-commit) and entity-event / outbox / webhook triggers do NOT fire for `ENTITY_RECORD_MIGRATED` and cannot block it (the bypass rule). The event IS visible to replay / rebuild, to the event-store read side and to retention accounting, and the per-upgrade audit entry (D10) references the `upgrade_id`; the events are the per-record trail, so no per-record rows are written to the audit hash chain (a million-row backfill would contend on it). `append_only` (`definition.ex:20-33`) and `managed_by` are not consulted because the writer is the module's own path by construction (0050 D7: module path identified by caller, never by request data). Which components filter by event type today: NOT VERIFIED; the implementing requirement enumerates every consumer (grep of event-type names) and adds a test per consumer that a MIGRATED event is ignored or handled as stated.
* **Reachability of the internal write (hooks-bypass).** The writer lives in an internal namespace that is NOT under `lib/letflow/modules/<id>/` (R3-2): `Letflow.ModuleUpgrade.Writer` (and the runner) in `lib/letflow/module_upgrade/`. `check_boundaries` treats every subdirectory of `lib/letflow/modules/` as a module id (its rules 0-5 are keyed on that segment), so a `lib/letflow/modules/upgrade/` directory would be classified as a module and its calls from `routers/tenant_modules.ex` and `installs.ex` flagged. The writer is `@doc false` and requires an opaque capability struct that only the runner constructs; a code step is handed the capability only through the wrapper's own calls, never in its `ctx`. `mix letflow.check_boundaries` (`lib/mix/tasks/letflow.check_boundaries.ex`, wired at `mix.exs:167`) gains a DEDICATED rule, expressible as one new `classify_edge` clause: target file = the writer/capability files under `lib/letflow/module_upgrade/`, allowed sources = files under that path, any other edge a VIOLATION (the task ignores edges whose source is not under `lib/`, so tests are unaffected). Limit stated plainly: the xref graph is static, so `apply/3`, dynamic module names and `Code.eval` are invisible to it. The opaque capability struct, which only the runner can construct, is the real control; the boundary rule is the CI backstop. Tenant scripts are sandboxed with no Elixir access (0053). Code steps get the same property by construction: the wrapper `repo` (fence layer 1) refuses direct writes to the record, event-store and promoted per-type tables (table names: NOT VERIFIED), so a code step changes records only through this writer and therefore also appends MIGRATED events and also bypasses hooks.
* **Migration writes bypass tenant script hooks and webhooks** as a property of the writer above, tested (AC16).
* **Code steps** (`kind: :code`) are module code under normal review (the on_install contract, guide section 5 `:183-218`, is the model): `up(repo, ctx)` and `down(repo, ctx)` with `ctx = %{actor_id, rationale, upgrade_id, cursor, batch_limit}`, returning `{:ok, cursor | :done}` or `{:error, code}`; resumable from `cursor`, idempotent per batch. Steps are given NO HTTP client (INV-9). They run as the system actor with `ctx.actor_id` recorded, never as the installer's session.
* **The code-step fence (INV-1, INV-6; review alone is not enforcement).** The wrapper and the tripwire are the enforcement; the lint is advisory. All three layers are required:
  1. *Prefix-fixed Repo wrapper.* A code step receives a `repo` wrapper that fixes the tenant prefix on every call; the raw `Letflow.Repo`, `Repo.query`, `Ecto.Adapters.SQL` and a caller-chosen `prefix:` are not reachable from `ctx`. It refuses writes to any table outside the step's declared `touches` and always to the record, event-store and promoted per-type tables (those go through the writer).
  2. *CI lint on module code (advisory):* no `Repo.query`/`Ecto.Adapters.SQL`, no `prefix:` other than the passed one, no alias of the grant, token, group or audit modules. It is bypassable (`apply/3`, dynamic module names, `Code.eval`), so it is never the only layer.
  3. *Runtime tripwire: an ALLOW-list of tables, checked from this transaction's own writes, in the same transaction as each batch.* Each step declares `touches: [entity types and tables]` (hashed into `plan_hash`, stored in the journal). Just before commit the runner reads `pg_stat_xact_user_tables` (per-transaction tuple counters: `n_tup_ins + n_tup_upd + n_tup_del`, per schema and table) and aborts the batch if ANY table other than the declared `touches`, the journal row and the tables the writer legitimately writes (event store, `entity_record_latest`, promoted per-type tables of the touched types) has a non-zero count. Because the counters are this transaction's only, other users' concurrent writes to grants, tokens, `audit_entries` and so on cannot cause false positives, the batch stays in READ COMMITTED (REPEATABLE READ would make the batch UPDATEs fail on concurrent row changes; the retention summary uses it for a read-only snapshot, `lib/letflow/event_store/retention_operations.ex:448`), and the cost is O(number of tables), never a table scan or digest. It covers tenant tables, public/global tables (users, companies, memberships, `entity_column_promotions`, platform tables), the script registry (0053), webhook/outbox tables, `tenant_modules`, process definitions/instances/tokens, `entity_definitions` activation state, `audit_entries` and the extension rows of D4 once they exist, because anything not allow-listed aborts. Trigger-caused writes are counted too. Abort rolls the batch back and journals `failed` with `error_code` `protected_state_changed`. The cutover transaction uses the same check with its own fixed allow-list (journal, `tenant_modules`, `entity_definitions` and activation rows, `entity_column_promotions`, `audit_entries`). **Preconditions (S3-1), fail closed.** The counters are collected only when `track_counts` is on; with it off the view reads zeros and the tripwire would fail OPEN. The runner therefore asserts `SHOW track_counts` is `on` at boot and at the start of every upgrade, and refuses to run otherwise; and before trusting a zero it self-tests that a known write registers (the journal-row write in the same batch transaction, which is allow-listed, MUST show a non-zero count in `pg_stat_xact_user_tables`); a zero there aborts the batch with the distinct code `tripwire_unavailable` and journals `failed`. **Blind spots (S3-2), stated.** The tripwire does NOT see `TRUNCATE` (not counted as `n_tup_del`), DDL (CREATE/ALTER/DROP/GRANT, role changes, catalog tables), sequence advances, `pg_notify`, writes on a DIFFERENT connection (a `Task` or `Repo.checkout` outside the batch transaction), or non-database effects (files, ETS, `Application` env, message sends). Savepoint-rolled-back writes still count (conservative). Reading the view is O(all user tables in the database), not O(the tenant's tables): filter `WHERE n_tup_ins + n_tup_upd + n_tup_del > 0` and measure with many tenants (open point 14); partitioned tables count on the partitions, which the allow-list names. The tripwire is a BACKSTOP, not a sandbox: code steps are trusted, reviewed module code, and the wrapper (layer 1, which also forbids DDL and `TRUNCATE`) plus review remain the enforcement for everything outside tenant-table and public-table DML in the batch transaction. A DB role split without DDL/`TRUNCATE` on protected tables for the batch connection: NOT VERIFIED, a hardening option. Whether `pg_stat_xact_user_tables` reflects trigger and cross-schema writes as assumed: Postgres behaviour, NOT code-verified here; proven by a test that writes to a non-allow-listed table, to `audit_entries` and to a public table (AC14), with a concurrent writer to those tables proving no false positive (AC22).
* **Tenant scripts (0053) and pack-carried code are NOT a migration mechanism.** A step is never tenant-authored or pack-supplied.

### D5. Atomicity, exclusion, runner, cutover, skew

* **Exclusion = the journal.** `tenant_module_upgrades` has a partial unique index on `(module_id)` WHERE `state IN ('running','failed')` (so a `failed` row blocks a new upgrade until it is resumed or abandoned; `planned`, `done` and `abandoned` do not); a concurrent upgrade gets 409. `resume` on a `failed` row keeps `steps_done` and `step_cursor` and takes the fenced claim below. There is **no whole-upgrade advisory lock**: a session-level advisory lock cannot be held across many committed batches under pooled Ecto connections (the lock belongs to a connection). `pg_advisory_xact_lock` is taken ONLY inside the stage transaction and the cutover transaction, keyed on `(tenant prefix, module_id)`.
* **Runner (phase 2).** Phase 2 does NOT run in the HTTP request process (request timeouts, `Plugs.Admission`). It runs under a supervised, bounded `Task.Supervisor` child (a new named supervisor under the existing infrastructure supervision tree; the project pattern is `{Task.Supervisor, name: ...}`, e.g. `Letflow.Obs.Alerts.TaskSupervisor`, `design/iss0429-async-alert-hook-delivery.md:60`), at most N concurrent runners platform-wide (N configured, open point 11; over capacity apply/resume answers 503 `upgrade_capacity` and leaves the row `planned` / `failed`, no queue), one per `running` journal row. This is a bounded job runner, not a supervised process per workflow instance (the REQ-045 decision stands; `Letflow.InstanceSupervisor` stays empty). **Fencing (N-S1).** Every claim of a journal row (first start, `POST .../upgrade/resume`, and runner-restart pickup of stale rows: ONE code path, no second resumer) runs in a transaction that locks the row `FOR UPDATE`, sets `runner_id := self` and `epoch := epoch + 1`, and commits. EVERY batch transaction, the cutover transaction and the `failed` write begin with `SELECT ... FROM tenant_module_upgrades WHERE id = $1 FOR UPDATE` and proceed only if `runner_id` and `epoch` equal the runner's own; otherwise the runner aborts without writing anything, so a slow or partitioned runner that lost its claim can never advance the cursor, run a step or cut over. **Lease versus batch time:** the lease is greater than 2 x (batch `statement_timeout` + `lock_timeout` + one heartbeat interval); batch size and a per-batch `statement_timeout` are configured so one batch cannot exceed that bound (a statement over it fails the batch as `step_error`, it is not allowed to run on); a batch also has a WALL-CLOCK bound (a `Task` timeout, closed code `step_timeout`), because a CPU-bound code step is not stopped by `statement_timeout` and would hold the journal row lock; `heartbeat_at` is also written inside every batch transaction under the same row lock. A live batch therefore holds the row lock, a takeover's `FOR UPDATE` blocks until that batch commits or rolls back and only then bumps the epoch, and the old runner's next batch sees the new epoch and aborts; a miscalibrated lease can delay or hasten pickup but cannot produce two writers. After a node crash the row stays `running` with a stale `heartbeat_at`; a row older than the lease is resumable by `POST .../upgrade/resume` (same `plan_hash`, D2 recomputation) or by pickup, and the staleness decision is RE-EVALUATED inside the claim transaction under the `FOR UPDATE` row lock (never taken from an earlier read; a heartbeat that became fresh in between refuses the takeover); a row with a fresh heartbeat refuses resume with 409.
* **Three phases:** (1) *Stage* (one transaction, xact lock): insert new `:inactive` entity definitions, new process-definition drafts, journal `running`. (2) *Migrate*: steps in batches, each batch committing its effects and advancing `step_id`/`step_cursor`/`steps_done` in the same transaction; replay of a batch is harmless (idempotent). The OLD definitions stay active throughout; old-shape writes remain valid. (3) *Cutover* (below). A failure before the cutover commit leaves the tenant on the old version, fully working.
* **Failure handling (INV-8, INV-4).** The runner rescues/catches raise, exit and throw from code steps. The failing batch rolls back; then, in its OWN small transaction, the journal row is set `failed` with a stable `error_code` from a closed set (e.g. `step_error`, `step_raised`, `protected_state_changed`, `plan_mismatch`, `cutover_lock_timeout`, `step_timeout`). No exception text or stack trace is stored in a tenant-visible field or returned. Audit lists the `running -> failed` transition and the stage commit (D10).
* **Cutover.** One transaction, started with `SET LOCAL lock_timeout` (configured, seconds) so it fails fast instead of queueing every writer behind it, and a lock that **blocks record writes** on the affected record tables (`SHARE ROW EXCLUSIVE`) plus `pg_advisory_xact_lock`. Under READ COMMITTED a writer committing between the catch-up scan and the commit would otherwise be missed. Inside it: a catch-up pass of every data step over rows changed since the migrate phase began, using `last_event_global_seq` as the **change marker** (fact 5; the journal stores `catchup_from_seq`, the highest `global_seq` observed when phase 2 starts; the catch-up selects records with `last_event_global_seq > catchup_from_seq` and re-runs each data step's idempotent predicate, appending MIGRATED events like any batch). Whether `global_seq` allocation order equals commit order (a writer that took a lower number may commit after the marker was read): NOT VERIFIED; the implementing requirement must lower `catchup_from_seq` by the oldest in-flight writer's seq or prove the ordering, and test with a concurrent writer (open point 12). The cutover transaction begins with the fencing check, then `activate_definition/4` per changed entity type in FK-DAG order (`EntityActivation`-style, same own-row check), `tenant_modules.version := to`, journal `done`, audit entry (D10). Lock timeout means: journal stays resumable, tenant stays on the old version.
* **Column promotion at cutover is the exception, not the rule.** `ALTER TABLE` for promoted columns and `CREATE UNIQUE INDEX` take ACCESS EXCLUSIVE (and `CREATE INDEX CONCURRENTLY` cannot run in a transaction), so "short" is false for big tables. Therefore: **post-cutover promotion (type stays "constraint pending", `unique` not yet enforced, visible flag) is the DEFAULT above a configured row threshold** per affected type, and in-cutover promotion is allowed only at or below it. The 0052 D7 DDL-in-transaction test (unproven) decides whether in-cutover promotion exists at all; if it fails, post-cutover promotion is the only mode. The write-freeze for big tables is this lock plus lock_timeout, stated here, not an option. The threshold value is open point 2.
* **Deploy skew.** After deploy, code is at N+1 while a tenant is at N (fact 2). A module declares `min_data_version`; below it the module's HTTP routes answer 503 `module_upgrade_required` (the module IS installed, so not 404, 0039 D5), at or above it the routes serve and the new code must tolerate version-N data. Tenants above the code's version (platform code rolled back) get 503 `module_version_ahead`; fail closed. The gate is **a single query** (fetch the `tenant_modules` row, compare) so installed / disabled / not installed / upgrade-required stay indistinguishable by timing from today's 404 gate (req404 section 9); `installed?` must not become a richer multi-query lookup. **Enforcement scope: this gate guarantees HTTP only.** Engine and background entry points that run module code without the module router (service-task handlers, module task/form resolution, outbox/webhook delivery, scheduled/poller work) are NOT covered by it; the implementing requirement MUST either enumerate and gate each (and add an AC for each) or, as the default stated here, require module code to be N-data tolerant on every non-HTTP path. The record does not claim more than HTTP.
  **Ruling. Ruled by the advisor (letflow-ec) under the user's delegation, recorded by the supervisor, 2026-10-15.** (open point 8, resolved.) Non-HTTP entry points are NOT enumerated-and-gated. The rule is: module code must tolerate N data (data at the previous version) on every non-HTTP path, and EACH module version ships a compatibility test that runs the module's code over fixtures at the previous data version. A release that cannot pass that test cannot raise `min_data_version`.
* **Expand/contract rule.** A release may raise `min_data_version` only after every tenant that has the module installed has been upgraded at the previous release; otherwise the deploy is a module outage for every non-upgraded tenant. The fleet driver (fact 10, open point 5) is therefore a **prerequisite of the first release that raises `min_data_version`** and sits before that point in D12.
* A deploy never auto-upgrades a tenant. Fleet rollout is a loop of independent per-tenant upgrades by a platform operator, reusing the shape in fact 10 (global rollout row, per-tenant outcome rows, resume), with halt-on-first-N-failures (N configured). The driver is platform scope: it needs its own `platform`-classified permission, bound to the platform tenant, never a role-name check (INV-10); constraint on that follow-up requirement. Each tenant route here (plan, upgrade, resume, abandon, rollback) is tenant scope and needs a cross-tenant negative test.

### D6. Running instances and live records

* **Process instances** keep running on the process-definition version they started on; the upgrade creates new versions and never edits or deletes an existing definition row. Whether an in-flight instance of definition version V is pinned to V's row independent of any later activation: NOT VERIFIED here (pin kinds `:catalog_entry | :variable_schema | :module`, `pin_resolver.ex:190` as cited by 0053); the implementing requirement must prove with a test that activating V+1 leaves a started instance on V. Module tasks/forms of V stay available as long as V's row exists (never deleted, D8).
* **Entity records** are read and updated under the new active definition from cutover (fact 5). New required fields therefore need a backfill step (Class B) so existing records stay updatable; reads of a record that predates a retired field return the stored blob unchanged.
* **Variable schemas** shipped by the module follow the process rule (new rows, old ones kept).

* **Widening (a new atom granted to an existing role, or an existing atom granted to a role that did not have it) cannot be tenant-gated today** because grants are compiled code evaluated without a tenant (fact 3): it takes effect for every tenant at deploy. A new module-only atom is inert for tenants without the module, but not for tenants that have it installed at an old data version, and a widening of an EXISTING atom (core or another module's) is live everywhere immediately regardless of the install gate. Therefore, as an INTERIM fence until per-tenant grants exist (open point 1):

The golden file and the declaration are checked by CI against each other; the declaration is NOT trusted on its own because it is authored in the PR it guards. The role enumeration source is `Authorization.roles/0` (`authorization.ex:478`, over `@roles` at `:401-410`); an explicit clause `role_allows?(_, :MyModulesRead) -> true` precedes the fall-through, so that atom is `true` for every role in the matrix. **The golden file is computed under the PRODUCTION module list (S3-3):** `Catalog` reads the list with `Application.compile_env`; `config/config.exs:60` compiles `[Letflow.Modules.Exam]` while `config/test.exs:283` overrides it with Exam plus fixture modules, so a golden test run under `MIX_ENV=test` would compute the matrix over fixtures and never see a real new module. The golden is generated and checked by a mix task run in the production module configuration (dev/prod env) in CI, and the CI job proves which list it used by asserting Exam's atoms appear in the matrix and that no fixture-module atom does.
  2. **Forbidden until per-tenant grants exist:** granting an existing atom to a role that did not hold it, and granting ANY atom referenced by a core (non-module) route policy. The latter is made enumerable as the set of permissions that `required_permission/1` (`authorization.ex:1222`) returns for the `endpoint_policy_key/2` clauses (`authorization.ex:675-1124`); the clauses are function heads, not data, so whether that set is enumerable without a maintained table is NOT VERIFIED. Resolution for the implementing requirement: a maintained `core_policy_atoms/0` list asserted equal to the clause set by a test, or this clause is dropped and the golden diff alone guards. New atoms may widen only for module-gated routes.

  4. The plan shows grants "effective at deploy, before this tenant upgrades" (information, not a gate).

Ruled by the advisor (letflow-ec) under the user's delegation, recorded by the supervisor, 2026-10-15.** (open point 1, resolved.) The interim golden file is adopted NOW. A module version that WIDENS `role_grants` (a role gains an atom it does not hold in the golden file) is REFUSED until per-tenant snapshots exist; NARROWING is allowed (declared informationally, effective at deploy). The two implicit rows for a new module atom (PLATFORM_ADMIN and TENANT_ADMIN, D7.1) are not a `role_grants` widening and remain the pre-approved diff. Per-tenant grant snapshots are therefore a MUST before the first module version that needs to widen.

### D8. What an upgrade may NOT do

1. Delete, truncate or overwrite tenant data: no record delete, no column drop, no definition-row delete, no retired field value erase. **`lossy`** has ONE meaning in this record: *a step after which the original information is not recoverable from the record.* A `lossy: true` step is forbidden in an upgrade, except through the explicit admin purge act (open point 3, resolved below).
   **Ruling. Ruled by the advisor (letflow-ec) under the user's delegation, recorded by the supervisor, 2026-10-15.** (open point 3, resolved.) A lossy step exists ONLY as an explicit purge act with its own record (its own journal row and audit entry), performed by a tenant-wide TENANT_ADMIN, with a MANDATORY export first (the export must complete and be recorded before the purge starts), and audited. It is never part of an upgrade plan; the purge act's own decision record defines the route and its two-step flow. The "copy, keep original, retire" pattern is NOT lossy (the original stays in the blob); it is the allowed form of conversion.
2. Touch the `x_` layer (D4), tenant-created entity types, process definitions or scripts, or any `managed_by` type of another module.
3. Widen permissions without the D7 golden-file match, review, and visibility in the plan; grant any role in any org scope.
4. Activate process definitions, or change a tenant's `settings` values except through a declared `settings` step recorded in the journal.
5. Run without a non-blank installer-supplied rationale and `:ModulesManage`; run across tenants in one transaction; take a tenant or schema identifier from a request body (INV-1), including the `tenant_id` used for the global `entity_column_promotions` table.
6. Change `managed_by`, a scope-column declaration (0051 D6) or `append_only` on a type in a way the owning module did not declare in this version's manifest.
7. **Tenant id derivation.** Wherever the cutover or a promotion reads or writes `entity_column_promotions` (global table scoped by a `tenant_id` column, `entity_activation.ex:163-171`), `tenant_id` MUST come from `TenantProvisioning.tenant_id_for_schema_name(prefix)` with `prefix` from the auth-derived context (the `entity_activation.ex:70` pattern), never from the plan, the journal row, a step, or the request. New tenant-schema tables carry no caller-supplied tenant id (INV-1(c)).

### D9. Rollback

* **Before cutover:** `abandon` (journal `abandoned`); staged `:inactive` rows stay as inert history (never deleted), migrated data of idempotent steps stays and is harmless (steps write only new/blank targets).
* **After cutover:** rollback is a new journal row of `kind: rollback` from the applied version to the PREVIOUS applied version (not to an arbitrary one), requiring `:ModulesManage` plus rationale. Allowed only if every step in between declares `down` and none is `:irreversible` (or, by D8.1, `lossy`); otherwise `{:error, {:rollback_forbidden, step_id}}`, and the plan states the **point of no return** at upgrade-plan time. Entity definitions roll back by re-activating the previous row (`activate_definition/4` is reversible, `definitions.ex:376-393`); promoted columns and constraints stay (no drop, fact 4), so a constraint added by the failed version remains while the old definition may not mention it: the rollback plan REPORTS such constraints and the validations/restrictions the target version lacks (a rollback can loosen something tightened for security); it does not remove them. Rollback chain: each rollback targets `from_version` of the latest `done` upgrade row not yet reversed (a rollback row marks it reversed); with no such row it answers `{:error, :no_previous_version}`, so a second consecutive rollback walks one more step back only if that step also declares `down`. A rollback is refused (`rollback_below_min_data_version`) when its target is below the running code's `min_data_version` (it would put the module in permanent 503 `module_upgrade_required`), and never targets a version above the code (`module_version_ahead`). A rollback MUST NOT re-activate a definition older than the last version carrying a `security_floor` marker in its manifest/steps (SHOULD-level marker, optional until a module uses it).
* **Cannot be rolled back, by design:** code steps without a tested `down`; `:irreversible` steps; declarative `set_default`/`copy_field` onto a column that already holds mixed old+new rows is reversible only for rows the journal marks as touched; process-definition drafts activated since (a tenant act). A step with no `down` is `:irreversible`; the default for a missing `down` is irreversible (fail closed). A present-but-wrong `down` is caught by a required per-step fixture test: up-then-down restores byte-identical data.
* Platform code rollback is separate from tenant rollback (D5 skew rule).

### D10. Audit

Every plan-apply, resume, abandon and rollback, the phase-1 stage commit, and the `running -> failed` transition write a hash-chain audit entry in the same transaction as their state change (`Audit.append_multi/4`, `lib/letflow/audit.ex:189`; verify the module path when implementing) with module, from/to, plan_hash, step ids, actor, rationale (verbatim), and counts only, never record content. Settings steps record a before/after hash. Per-step `done` is a journal field, not an audit entry. The Class B acknowledgement list is part of the audited payload. Rationale is mandatory (the 0052 D3 rule extended). `audit_entries` is outside every step's allow-list (D3 tripwire) so a code step cannot forge chain entries.

### D11. Uninstall -- split out; constraints upgrade imposes

Soft uninstall, reactivate and hard purge are NOT decided here; they are the follow-up record "module uninstall" (roadmap wave 3, `core-roadmap-20261014.md:73`). That record is **gated on `managed_by` being built** (0050 D7, #2530): without it, "generic writes stay refused (403)" is vapour (fact 9). Constraints the follow-up must satisfy, recorded so upgrade is written against them:

* Block starting NEW instances of the module's process definitions (otherwise any user with start permission still runs module logic, and after the wave-2 "process step writes entity" the engine can write module-managed types).
* Define and test who can read orphaned module data once the module router (and its ownership filters, e.g. exam_sessions `:not_owner`) is gone: either keep exactly the pre-uninstall `TypeAccess`/`entity_field_restrictions` and ownership filters, or restrict reads to named permissions; exam answer keys (`exam.ex:96-120`) must be proven preserved (INV-2).
* `GET /me` and `list_installed` (fact 12) must hide `disabled` modules, or they leak.
* Define whether a `disabled` module satisfies another module's `depends_on` at install (`module_installed?` is shared, `installs.ex:213-218`).
* Preconditions (dependents, running instances), a second approver for uninstall of a module with live data (open point 6), and the `status` column are that record's.
* `kind` values `uninstall|reactivate` in the journal and `tenant_modules.status` belong to that record's migration (also registered in the tenant provisioning list, D1).

### D12. Build order

(1) manifest semver rule, `min_upgradable_from`, `migrations/0`, `tenant_module_upgrades` (+ tenant-provisioning registration), plan endpoint (read-only, Class A/B/C classification, preflights, `plan_hash`); (2a) golden effective-permission-matrix file + CI diff (D7) as its OWN PR (independently shippable, protects against widening today, before upgrade exists); (2b) the `ENTITY_RECORD_MIGRATED` event type, projector fold clause, registration and writer (D3) as its own PR; (2c) the code-step fence and allow-list tripwire (D3), the supervised runner with fencing (D5), apply for Class A + declarative steps incl. entity definitions, journal/resume/cutover; (3) rollback and `down`; (4) **fleet driver** (platform-scope permission, reuse of the fact-10 shape); (5) deploy-skew gate (`min_data_version`, 503s): the first release that raises `min_data_version` is allowed only after step 4. Process-instance pinning proof (D6) and the 0052 D7 DDL test gate step 2. The `x_` layer (record for candidate (b)) and uninstall (own record, after `managed_by`) are separate, later.

## Acceptance-criteria candidates

AC1 plan is read-only and tenant-from-auth only. AC2 Class A applies with no step; Class B without step or ack is refused; Class C never applies. ## Consequences

* Every non-trivial module change now carries a plan, steps, a journal and an audit trail; reviews of module PRs gain the golden-file diff and the step digest.
* Ruled (open point 1): a module version that widens `role_grants` is refused until per-tenant grant snapshots exist; narrowing is allowed. Modules needing a widening wait for the snapshot work.
* A new bounded supervised runner and a heartbeat/lease concept enter the platform; they are a job runner, not per-instance processes.
* The first release that raises `min_data_version` is blocked on the fleet driver; until then `min_data_version` stays at its initial value.
* Large tables get "constraint pending" (post-cutover promotion) rather than an enforced unique constraint at cutover; tenants see a flag until the promotion finishes.
* The `x_` layer and uninstall are not delivered by this record; modules cannot rely on tenant extensions or soft uninstall yet.
* Migration writes are events: backfill volume is one event per changed record (bounded by batch size), and the event store, projector and event-type registry gain a new type (D3).
* Cost of the code-step fence: module authors cannot use raw `Repo`; steps that need something outside the wrapper must be declarative steps or a new vocabulary entry (a core change).
