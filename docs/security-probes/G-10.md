# G-10 — the config/env/flag registry with default/fail-closed and secret/URL probes

Class: TOOL (D-184/D-186). The probe is a mechanical test (no model): it derives every setting the
sources read from the tree and compares it with a machine-readable registry, and it exercises the
shared address validator and the secret redaction with hostile values. It runs under the
`:security_probe` tag and is a mandatory test in the bounded standard backend selection. Declared
cost: **13 seconds** (`probe_cost_s: 13`).

The gap it closes (team repository, `docs/security-coverage.md`, G-10): the product had no
machine-readable answer to "which configuration does this product have, who owns it, why does it
exist, how is it read and must its absence fail closed". The T-2588 check of the compile-time
platform-function catalogue was a manual reading of the tree; nothing made it a gate, and a new
environment variable, flag, secret or URL could arrive without a registered reason.

## What is derived

- The registry is `priv/config_registry.txt`: one line per setting, ten pipe-separated columns
  (`source | name | owner | scope | read | kind | default | fail_closed | validator | reason`).
  Every environment variable and every application environment key the tree names has a line
  there, and a line says why the setting exists. The file holds 101 environment variables and 151
  application environment keys.
- `Letflow.Support.ConfigRegistryScan` (`test/support/config_registry_scan.ex`) derives the other
  half **from the tree**: it parses `lib/**.ex`, `config/*.exs`, `priv/repo/migrations/*.exs` and
  `mix.exs` with `Code.string_to_quoted!/2` and reads every `System.get_env/1,2`,
  `System.fetch_env/1`, `System.fetch_env!/1`, `Application.get_env/2,3`,
  `Application.fetch_env/2`, `Application.compile_env/2,3` and the `config :app, :key, value` and
  `config :app, key: value` directives, with the form of the read (a default or not,
  compile-time or runtime, a `||` fallback or not). It starts nothing, opens no socket and reads
  no clock.
- An **environment variable** is named in six ways in the tree, and the derivation sees all six:
  1. a literal: `System.get_env("LETFLOW_SIGNUP_ENABLED")`;
  2. a name a module attribute holds: `@token_env "LETFLOW_SIGNUP_PROVISIONER_TOKEN"` read with
     `System.get_env(@token_env)`;
  3. a name a local variable holds: `name = "LETFLOW_SMTP_HOST"` read with
     `System.get_env(name)`;
  4. a list of names the boot reads: `~w(LETFLOW_MAIL_ADAPTER LETFLOW_SMTP_HOST)` piped into
     `Map.new(fn name -> {name, System.get_env(name)} end)`;
  5. a list of names a module attribute holds: `@env_unset_names ~w(GIT_EXTERNAL_DIFF
     GIT_DIFF_OPTS GIT_CONFIG_COUNT GIT_CONFIG_PARAMETERS)`, read by `git_env/1`, which hands a
     hardened environment to every git child process;
  6. a module that parses the operating system environment: it takes a map of variable names to
     raw values (`env`) and reads it with `Map.get/2`, so every upper-case literal of that module
     names a variable of the operating system. `Letflow.TenantProvisioner.Config` and
     `Letflow.LoginDiscovery.Notifier.Smtp.Config` are the two such modules of the tree, and the
     20 variables they name are registered.
- A name that is only named by an **attribute** is a variable too when the attribute says so in
  its own name (`@suffixes_var`, `@token_env`): the attribute holds a name in the shape of an
  environment variable and ends in `_env` or `_var`.
- A **list** is a list of variables when the code that consumes it reads the environment. The
  three ways the tree consumes such a list are seen: a list piped into a read of the environment
  (form 4), a list that is an argument of such a read, and a list a module attribute holds whose
  consuming code reads the environment (form 5). The four names `@env_unset_names` holds are
  variables of the operating system: the product neutralises them for every git child process, so
  a git config key cannot change a verdict, and the registry names them with that reason. A list
  of something else (the roles, the statuses, the formats) is not a list of variables.
- A read in the **default argument of a function head** is a read like any other:
  `def git_env(current_env \\ System.get_env())` is the one such read of the tree, it reads the
  whole operating system environment, and it is reported as a dynamic place.
- The **rules** the probe enforces, each of them a finding:
  - **coverage** — a setting the tree reads and the registry does not name, and a registry entry
    nobody reads, are both reported. A new setting cannot arrive without a registered reason.
    The finding of an unregistered setting names the places the tree reads it.
  - **shape** — every entry has its ten columns, a closed `kind` and `scope`, a read mode that
    matches the tree, and a reason that is neither empty nor a placeholder.
  - **read mode** — a key read with `Application.compile_env/2` is registered as `compile_time`
    and a key registered as `compile_time` is read that way.
  - **default off** — a feature flag defaults off, is never read with a default that turns it on,
    and is never switched on by a release configuration (`config/config.exs`, `config/prod.exs`,
    `config/runtime.exs`), in the directive form (`config :app, :key, true`) or in the keyword
    form (`config :app, key: true`).
  - **default on** — a guard (the switch of an address validation) defaults on and is never read
    with a default that turns it off.
  - **fail closed** — a setting marked `fail_closed` is never read with a default that takes
    effect when it is absent.
  - **secret by reference** — a secret carries no default in the registry, is never read with a
    literal default outside a test configuration, and has no literal value in the tree.
  - **URL validated** — a URL says how it is validated: a module of the tree (the file of that
    module has to exist) or `none` for an address the server never fetches. A sentinel that names
    no validation is reported: the registry's reason says which of the two it is.
- The seeded failing variants are `test/fixtures/security_probes/g10/broken_tree`: a tree that
  breaks one rule per setting (an unregistered variable in each of the seven ways the fixture
  names a variable, a flag read with a default that turns it on, a flag a release configuration
  switches on in the directive form and in the keyword form, a secret read with a literal
  default, a key read at compile time but registered as a runtime read, a registry entry nobody
  reads, a URL whose validator is not a module and a URL whose validator names no validation).
  The probe has to report every one of them, and it has to leave the one list of something else
  (`G10_STATUS_PENDING`, `G10_STATUS_DONE`) alone.
- The probe is pure: no database, no network, no clock, no model. One scan of the tree reads
  1 113 sources and finds 239 environment reads, 302 application reads and 28 dynamic reads; the
  whole probe takes about thirteen seconds.

## What the probe does not cover

- A read whose key is computed at run time cannot be resolved statically. There are 28 such
  places in the tree: 10 environment reads (8 in `config/runtime.exs`, where a helper reads the
  name it is given, 1 in `lib/letflow/signup/provisioning.ex` and 1 in
  `lib/letflow/risk_tier.ex`, where the default argument of `git_env/1` reads the whole
  environment) and 18 application reads (16 keyed by the module's own settings and 2 that
  compute the key, `lib/letflow/engine/script_task_dispatcher.ex` and
  `lib/letflow/scope_enforcement/shadow_window.ex`). They are reported as dynamic and need no
  registry entry; the settings they read are registered through the places that read them by
  name.
- These four forms are **not** seen, and a variable that hides in one of them is not covered:
  1. an attribute that holds a name in the shape of an environment variable but is named
     neither `*_env` nor `*_var` and is never read through a `System` call;
  2. a list of names that no code that reads the environment consumes (a list of roles, of
     statuses or of formats is not a list of variables). The three ways the tree consumes such a
     list are seen: piped into a read of the environment, an argument of such a read, and held by
     a module attribute whose consuming code reads the environment;
  3. a module that parses the environment but names its parameter something else than `env`,
     `envs`, `env_map`, `os_env`, `environ` or `environment`;
  4. a variable read through a helper the tree computes at run time (the dynamic places above).
  A variable in one of these forms has to be registered by hand; the probe says so in the class
  table rather than pretending the tree is fully covered.
- The rule that reads a list a module attribute holds takes the whole list for variables when
  the code that consumes the attribute reads the environment. A list of something else held by an
  attribute that an environment-reading code consumes is therefore reported as variables, and a
  reviewer decides what it is. The tree holds no such list: the only attribute-held lists whose
  consumer reads the environment are `@env_unset_names` (four variables) and
  `@env_unset_prefixes` (prefixes, which are not names and are not reported).
- A default that is an expression (`System.get_env("X") || raise "..."`) is not judged: the probe
  only judges a default it can read. The registry's reason names the case, and a reviewer reads
  it.
- The registry says how a URL is validated; it does not prove that the validation happens at the
  dispatch point. The runtime cases prove that the shared validator refuses a hostile value, and
  the product's own tests prove that each caller uses it.
- The secret probe proves that a value under a secret key is redacted out of the log **metadata**.
  A secret interpolated into the log **message** is not redacted, which is a limit of the product
  and not of the probe; the case states it so it is not forgotten.
- A test configuration may carry a literal where a release configuration must not: the master key
  of the test build is a literal in `config/test.exs`. The probe skips test configurations for the
  secret rules.
- The rule that looks for a literal value of a secret in the tree matches the name and a literal
  next to it. A secret written with `System.put_env/2` (the way the test build injects its master
  key) is therefore not reported; the registry entry and the reason of that setting are what the
  reviewer reads.
- A setting the shipped configuration opens on purpose is not a feature flag: the registry
  describes it as a plain setting and its reason names the flip. `:letflow:exam_snapshot_complete`
  is such a setting (REQ-511 PR b opens it in `config/config.exs` and a source test pins the
  value), and the probe reports it as a flag that a release configuration switches on.

## Running and refreshing

```sh
mix test test/letflow/security_probe/g10_config_registry_test.exs
```

The probe alone, without the suite (the derivation lives in `test/support`, which is compiled
only under `MIX_ENV=test`, and the boot of a development build refuses to start without the
master key):

```sh
MIX_ENV=test mix run --no-start -e 'IO.inspect(Letflow.Support.ConfigRegistryScan.findings("."))'
```

After a reviewed change of the settings, add or change the line of the setting in
`priv/config_registry.txt` and run the probe. A refresh is not a way to bypass a finding: the
reviewer must account for every added, removed or changed line. A setting the tree reads and the
registry does not name is reported with its name and its places, so the missing line is named by
the probe itself.
