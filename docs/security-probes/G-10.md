# G-10 — the config/env/flag registry with default/fail-closed and secret/URL probes

Class: TOOL (D-184/D-186). The probe is a mechanical test (no model): it derives every setting the
sources read from the tree and compares it with a machine-readable registry, and it exercises the
shared address validator and the secret redaction with hostile values. It runs under the
`:security_probe` tag and is a mandatory test in the bounded standard backend selection. Declared
cost: **10 seconds** (`probe_cost_s: 10`).

The gap it closes (team repository, `docs/security-coverage.md`, G-10): the product had no
machine-readable answer to "which configuration does this product have, who owns it, why does it
exist, how is it read and must its absence fail closed". The T-2588 check of the compile-time
platform-function catalogue was a manual reading of the tree; nothing made it a gate, and a new
environment variable, flag, secret or URL could arrive without a registered reason.

## What is derived

- The registry is `priv/config_registry.txt`: one line per setting, ten pipe-separated columns
  (`source | name | owner | scope | read | kind | default | fail_closed | validator | reason`).
  Every environment variable and every application environment key the product reads has a line
  there, and a line says why the setting exists.
- `Letflow.Support.ConfigRegistryScan` (`test/support/config_registry_scan.ex`) derives the other
  half **from the tree**: it parses `lib/**.ex`, `config/*.exs`, `priv/repo/migrations/*.exs` and
  `mix.exs` with `Code.string_to_quoted!/2` and reads every `System.get_env/1,2`,
  `System.fetch_env/1`, `System.fetch_env!/1`, `Application.get_env/2,3`,
  `Application.fetch_env/2`, `Application.compile_env/2,3` and `config :app, :key, value`
  directive, with the form of the read (a default or not, compile-time or runtime, a `||`
  fallback or not). It starts nothing, opens no socket and reads no clock.
- A configuration file names its variables in three ways — `System.get_env("X")`, a helper called
  with the name and a `~w(...)` list — so the names of a configuration file are also read from its
  text. The shape (an upper-case word with an underscore in it) leaves no other word in a
  configuration file.
- The rules the probe enforces, each of them a finding:
  - **coverage** — a setting the tree reads and the registry does not name, and a registry entry
    nobody reads, are both reported. A new setting cannot arrive without a registered reason.
  - **shape** — every entry has its ten columns, a closed `kind` and `scope`, a read mode that
    matches the tree, and a reason that is neither empty nor a placeholder.
  - **default off** — a feature flag defaults off, is never read with a default that turns it on,
    and is never switched on by a release configuration (`config/config.exs`, `config/prod.exs`,
    `config/runtime.exs`).
  - **default on** — a guard (the switch of an address validation) defaults on and is never read
    with a default that turns it off.
  - **fail closed** — a setting marked `fail_closed` is never read with a default that takes
    effect when it is absent.
  - **secret by reference** — a secret carries no default in the registry, is never read with a
    literal default outside a test configuration, and has no literal value in the tree.
  - **URL validated** — a URL says how it is validated: a module of the tree, `startup` for a
    value checked while the application boots, or `none` for an address the server never fetches.
    The registry's reason says which of the three it is.
- The seeded failing variants are `test/fixtures/security_probes/g10/broken_tree`: a tree that
  breaks one rule per setting (an unregistered variable, a flag read with a default that turns it
  on, a flag a release configuration switches on, a secret read with a literal default, a key read
  at compile time but registered as a runtime read, a registry entry nobody reads and a URL whose
  validator is not a module). The probe has to report every one of them.
- The probe is pure: no database, no network, no clock, no model. One scan of the tree reads
  about 1 100 sources and takes about two seconds; the whole probe takes about eight.

## What the probe does not cover

- A read whose key is computed at run time (five places in the tree) cannot be resolved
  statically. It is reported as dynamic and needs no registry entry; the settings those places
  read are registered through the other places that read them by name.
- A default that is an expression (`System.get_env("X") || raise "..."`) is not judged: the probe
  only judges a default it can read. The registry's reason names the case, and a reviewer reads
  it.
- The registry says how a URL is validated; it does not prove that the validation happens at the
  dispatch point. The runtime cases prove that the shared validator refuses a hostile value, and
  the product's own tests prove that each caller uses it.
- The secret probe proves that a value under a secret key is redacted out of the log **metadata**.
  A secret interpolated into the log **message** is not redacted, which is a limit of the product
  and not of the probe; the case states it so it is not forgotten.
- A test configuration may carry a literal where a release configuration must not: the master key
  of the test build is a literal in `config/test.exs`. The probe skips test configurations for the
  secret rules.
- The rule that looks for a literal value of a secret in the tree matches the name and a literal
  next to it. A secret written with `System.put_env/2` (the way the test build injects its master
  key) is therefore not reported; the registry entry and the reason of that setting are what the
  reviewer reads.

## Running and refreshing

```sh
mix test test/letflow/security_probe/g10_config_registry_test.exs
```

The probe alone, without the suite:

```sh
mix run --no-start -e 'IO.inspect(Letflow.Support.ConfigRegistryScan.findings("."))'
```

After a reviewed change of the settings, add or change the line of the setting in
`priv/config_registry.txt` and run the probe. A refresh is not a way to bypass a finding: the
reviewer must account for every added, removed or changed line. A setting the tree reads and the
registry does not name is reported with its name and its places, so the missing line is named by
the probe itself.
