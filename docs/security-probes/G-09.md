# G-09 — migration impact runner and schema matrix

Class: TOOL (D-184/D-186). The probe is a mechanical test (no model): it derives the tenant
migration manifest, the manifest-position pins of the test corpus and the test files a migration
change must run, and it proves that those pins are current and that the changed-path test mapping
runs them. It runs under the `:security_probe` tag and is a mandatory test in the bounded standard
backend selection. Declared cost: **15 seconds** (`probe_cost_s: 15`).

The gap it closes (team repository, `docs/security-coverage.md`, G-09): T-2588's deep gate found two
migration-position pin files that the mapped local tests never selected. The product CI would have
run them; the local selection did not, so the breakage of the class was invisible until a heavy
migration suite ran. The class is a *positional* pin: a tenant-scoped migration is appended to
`Letflow.TenantProvisioning`'s manifest and every test that pins a **position** of that manifest
(`Enum.at(manifest, -12)`, `List.last(manifest)`) then names another migration.

## What is derived

- **The manifest.** `Letflow.TenantProvisioning.tenant_scoped_migrations/0` (the public API) gives
  the version and the module of every tenant-scoped migration; the migration file follows from the
  migration directory, matched by module name.
- **The manifest-position pins.** Every `assert {version, module} = Enum.at(manifest, -N)` and
  `assert {version, module} = List.last(manifest)` of the test corpus, read from the AST (not from
  a text match): the file, the line, the index and the version the pin expects. A pin whose
  expected version the scanner cannot read is reported as `:unresolved`, never skipped.
- **The required test set** — the files a tenant-migration change must run:
  - `:position_pins` — the files that pin a position of the manifest (16 files);
  - `:table_oracle` — the files that compare a tenant's table set with the tenant table oracle
    `TenantFixture.expected_tenant_tables/0` (6 files);
  - `:manifest_replay` — the files that replay the tenant manifest into a tenant, the case that
    proves the existing rows survive a migration (20 files).
  The union is the reviewed list `test/fixtures/security_probes/g09_migration_impact_tests.txt`
  (33 files). The probe re-derives it from the tree and fails when the list and the tree disagree.
- **The changed-path test mapping.** `scripts/ci_select_tests.py` reads the list and makes every
  file **mandatory** when a migration path changes: a file that does not fit the CI budget fails the
  run closed instead of being deferred to the nightly.

The probe is pure: no database, no network, no clock, no model, no order dependence. The only
external program it runs is the changed-path selector of the product CI, on the real tree.

The seeded failing case is `test/fixtures/security_probes/g09/stale_position_pin.exs`: a pin that
names a migration the manifest does not hold at that position, with a version that can never be in
the manifest. It is a fixture, not a test (it is not named `*_test.exs`), so `mix test` never runs
it; the probe reads it with the runner and requires the runner to report it as stale.

## What the probe does not cover

- The **team's** local changed-path mapping (`project/scripts/lf.sh` of the team repository) is a
  file of the operator's repository, not of the product. The probe checks the product's own mapping
  (`scripts/ci_select_tests.py`), which is the one the product CI and the merge queue use; the
  operator's script needs the same rule to select the required list for a local run.
- The probe judges the **positions** of the manifest. A pin that names a migration by name (a
  membership pin, `assert {version, module} in manifest`) does not move when a migration is
  appended; it is not part of this class.
- The probe does not read the schema of a tenant. The table oracle comparison (the tenant table
  set) stays with the tests that own it: the probe makes sure they run.
- The heavy cases (a real replay of the manifest into a provisioned tenant, the backfill of
  existing rows) are the tests of the required list, not the probe: the probe proves they are
  selected and that the positional pins are current, in milliseconds.

## Running and refreshing

```sh
mix test test/letflow/security_probe/g09_migration_impact_test.exs
```

After a reviewed change of the manifest or of the test corpus, regenerate the required list from
the final tree:

```sh
MIX_ENV=test mix run --no-start -e 'IO.puts(Enum.join(Letflow.Support.MigrationImpact.required_test_file_list(), "\n"))'
```

and compare it with `test/fixtures/security_probes/g09_migration_impact_tests.txt`. A refresh is not
a way to bypass a finding: the reviewer must account for every added, removed or changed line, and
the pins themselves stay as they are — a stale pin is a finding, not a list to regenerate.
