# G-04 — Canary-secret/taint harness

Gap **G-04** of the team repository's `docs/security-coverage.md` §4. The design
is `G-04-design.md` (the intent); this file describes the code that exists, the
case table, the non-vacuity and mutation runs, the findings and what is not covered.

Class: **TOOL**. Mechanical: no model, no network beyond 127.0.0.1, no clock, fixed
seeds. Every file carries `@moduletag :security_probe` and `@moduletag probe_cost_s: N`;
the team runner's tagged set runs the files whose cost is within its share in `checks`
for every backend change, and `scripts/ci_select_tests.py`
(`STANDARD_SECURITY_PROBE_TESTS`) runs all of them in every bounded CI run.

## What is built, and what is not (read this first)

Built: the detector (every needle form, normalisation, zip and PDF steps, bounds that
fail closed), the exceptions list with its ratchet, the collectors S1, S2, S3, S4
(including the production formatter bytes), S5 (audit rows per column), S6 (DLQ, through
the catch-all), S7, S8, S9, S12, S14 and the S* catch-all over the tenant AND `public`
schema, a seeded failing case per surface, and the real cases in the table below.

**Not built** (each is stated, none is hidden):

| not built | why |
|---|---|
| C-01 (registration start, B-01/L4) | `start_register_tenant/2` needs the seeded platform definitions and a running instance; not driven from a probe file yet. B-01 is therefore not recorded (see Findings: S4 already scans Ecto SQL parameters on every case, and no leak was found on the cases that exist) |
| C-02 (`POST /instances` with `initial_variables`), S10, S13 | needs an active definition in the tenant; the S10/S13 collectors are not written |
| C-04 (user import by CSV/XLSX) | not written |
| C-20, S11 (data export) | a bare tenant offers no export dataset (`GET /api/v1/data-export/datasets` answers an empty list), so the case would be vacuous; it needs a tenant with a module installed |
| C-15 (`deliver_to_file` bytes) | only `deliver_to_address` is driven (C-14) |
| C-32 token env var | the fake token command's value is fixed; only the name and email canaries are planted |
| `body_2xx_authorised` for C-03/E-01 | built and tested (`authorised: true` on a case's responses, both parts proven by the seeded S5 test); C-21 and C-22 use the other part on purpose |

The task's acceptance criteria are met for the built surfaces; the table above is the
remaining work, in the order C-01, C-02/S10/S13, C-04, C-20/S11, C-15.

Bounds (SF-01, the scan fails closed instead of skipping): g04_detector `SF-01 bounds…`:
input over 4 MiB, a zip of 201 members, a zip declaring 16 MiB+, nesting deeper than 3, a PDF
stream inflating past 16 MiB each raise `G04Canary.TooLarge`. Residual limit: a zip whose
central directory understates its sizes is caught only after `:zip.unzip` (the post-check on
the real total), which OTP bounds by the input size cap.

Ratchet: a `baseline` row that matches no hit fails the run (`verdict/3`); a per-case verdict
judges only the rows that name its case, pooled over all canaries of that case
(`verdict_cases/3`): g04_http::`a case-scoped baseline row is not stale in another case`.

## Findings (real leaks found on the first run on main; recorded as baseline rows, not fixed here)

- **B-02** (S6, C-10): a webhook delivery that exhausts into the DLQ stores the target URL
  with its userinfo and query token in `dlq_entries`. Same class as T-2606. Fix: store the
  origin only. Remove the row when fixed (the ratchet fails until then).
- **B-03..B-07** (S14, C-33, L3 class): `scripts/qoimeks_qa2_fixture_count.sh`,
  `scripts/qoimeks_qa2_fixture_ledger3.sh`, `scripts/seed_meridian_definition.sh`,
  `scripts/seed_swiftroute_definition.sh` and `scripts/seed_swiftroute_incident_definition.sh`
  print the URL they were given (`QA_URL`, with userinfo and query token) on stdout. Fix:
  print the origin only (as the T-2606 scripts do).
- No leak was found in: HTTP bodies, headers and error answers of the built HTTP cases, all log
  levels (Ecto SQL included) of those cases, every table of the tenant and `public` schema after
  C-03/C-05/C-21..C-28, the notifier message and rows of C-14, the UAT run artifacts of C-30..C-32.
- The C-33 run reached the `curl` stub in a subset of scripts only; the others stop earlier
  (missing argument or env); they stay classified `run` so a later change that reaches `curl` is
  scanned.

## Decisions taken in the build (design silent or contradicted by the code)

- The signup route answers 404 unless `Letflow.Signup` is enabled; the case switches it on for the
  test and restores it.
- `POST /me/problem-reports` needs a platform tenant: the test pins its own tenant as the platform
  tenant (`PlatformTenantFixture.pin!`, restored on exit).
- Two canaries of one case share a core, so a case that plants two kinds that must be told apart
  (C-32 name vs email; C-33 URL vs token) gives the second `salt:`.
- C-33 canary case ids are `C-33/<script>` so each baseline row names its script.
- C-10/C-11 sit in their own file because the delivery's backoff makes it cost 28 s; it declares
  `probe_cost_s: 30` and so runs in CI and nightly, as design §7 provides.
