# G-13 — Generated malformed-input / no-5xx route and parser matrix

Gap **G-13** of the team repository's `docs/security-coverage.md` §4:

> Generated malformed input/no-5xx route and parser matrix (body shapes,
> content types, caps, child/start errors, codec fallback).

Class: **TOOL** (D-184/D-186 ratchet: mechanise the security gates). The probe
is mechanical — no model, no network, no clock — and it runs in the `checks`
step for every backend change. The enforcement is NOT "the probe files are
ordinary test files" (that only runs them when they change): it is the
`@moduletag :unit` in the parser-level file, which puts it in the team
runner's unit tier (`mix test --only unit`, run on every non-rework backend
change), plus the product's own bounded-CI safety set
(`scripts/ci_select_tests.py`, `STANDARD_SECURITY_PROBE_TESTS`), which makes
them mandatory on every bounded run. The tag `:security_probe` and the per-file
cost `@moduletag probe_cost_s: N` say so; the operator's `lf.sh` hook can
select the tagged set once it exists.

Measured cost: the parser-level file 0.7 s, the route-level file 5.8 s (both
on this host, warm, with the team's PostgreSQL on port 5492). The declared
costs are 20 s and 60 s — headroom for a cold database. The whole tagged
security-probe set (G-06 + G-08 + G-13) stays inside the five-minute budget of
the `checks` step.

## What is delivered

- `test/support/g13_matrix.ex` — the shared machinery: the route inventory, the
  generated shape list, the dispatcher, the verdict (`violations/1`) and the
  aggregate entry point (`run/3`).
- `test/support/g13_rogue_router.ex` — the seeded failing case (a router
  shaped exactly like the API pipeline **before** T-2658; never mounted, only
  probed).
- `test/letflow/security_probe/g13_malformed_input_matrix_test.exs` — the
  parser-level matrix: every mutating route × every body shape and content
  type, without a database.
- `test/letflow/security_probe/g13_route_no_5xx_test.exs` — the route-level
  matrix (a body that reaches a handler, with a real tenant and a real token)
  and the three targeted cases: the SUB_PROCESS child refusal, the start
  refusal and the cursor codec fallback.
- `lib/letflow/routers/instances.ex` — the one product change the probe found
  (a SUB_PROCESS child refusal answered a detail-free 500; see the class
  table, cases C10 and C11).
- This class table.

## The inventory the matrix is generated from

The route list is **derived**, never written down: `Letflow.Support.RouteInventory.routes/0`
returns the compiled route table (`__authz_routes__/0`) of every router mounted
under `lib/letflow/plugs/api_pipeline.ex` and every module router mounted at
`/modules/<manifest id>`, with the FULL mounted path. On the revision this
probe was written against that is **453 mounted routes, of which 256 are
mutating** (`POST`, `PUT`, `PATCH`) and 26 are `DELETE`. The numbers move with
the tree — that is the point: a route mounted after this probe was written is
covered by the next run, and the completeness case (C2) fails if the two ever
disagree.

The shape list is generated in `Letflow.Support.G13Matrix.shapes/0`: twelve
shapes, each with a body, a content type and (where the shape can carry one)
a canary token that must not survive into the answer.

## The verdict

One function decides every cell: `Letflow.Support.G13Matrix.violations/1`. It
returns the list of rules the cell breaks; an empty list means the cell is
fine. The rules:

| rule | meaning |
|---|---|
| `:no_answer` | the request produced no answer at all — the caller is left without a status and without a body |
| `:server_error` | the answer is a 5xx — a caller's own mistake answered as a server fault |
| `:untyped_refusal` | the refusal was signalled but the answer is not a typed problem document (`application/problem+json` with `status`, `title`, `type`, `detail`), or its status does not match the status the parser's own exception carries (`Plug.Exception.status/1`) |
| `:unexpected_error` | an error escaped that the pipeline does not own (anything but the four exceptions `Plug.Parsers` raises) |
| `:echoed_request` | the answer carries the canary from the request |

## The product change the probe found

`lib/letflow/routers/instances.ex`, `render_create/2`: a SUB_PROCESS child
refusal was mapped only for the module-only child (T-2515). Every other cause
fell through to the catch-all and answered the **detail-free 500**
(`{"status":500, …, "detail":"an unexpected error occurred"}`) — a caller's own
mistake answered as a server fault. Two clauses were added:

- a child definition that does not exist (or a node that names none) → the
  typed 404 a direct start gives (C10);
- a child definition that needs reactivation → the typed 409 a direct start
  gives (C11).

**Red proof.** On the unmodified `instances.ex` both child-refusal tests fail:

```
test "a parent naming a child definition that does not exist answers 404, not a 500"
  left: 500
  right: 404
  body: {"status":500,…,"detail":"an unexpected error occurred",…}

test "a parent naming a child definition that needs reactivation answers 409, not a 500"
  left: 500
  right: 409
```

Command: `MIX_TEST_PARTITION=2633 mix test test/letflow/security_probe/g13_route_no_5xx_test.exs`
(2 failed, 2 passed) on the unmodified code; 4 passed with the fix.

## Residual limits

Stated so the next reader does not mistake the coverage for more than it is.

1. **A SUB_PROCESS child refusal with a cause other than "the child definition
   does not exist" or "the child definition needs reactivation" still answers
   the detail-free 500.** That is: a missing required interface input, an
   input schema violation, a missing required output, an output schema
   violation, an invalid child graph and a pin resolution failure. These are
   configuration gaps of a different shape — the parent's interface demands
   something the child does not declare — and not a malformed request, so they
   are left as they are and named here rather than silently remapped. Mapping
   them needs its own decision (a 422 that names the interface field, or an
   error document that carries the interface's own detail), which is outside
   this probe's class.
2. **The matrix covers the mutating routes only** (`POST`, `PUT`, `PATCH`).
   A `DELETE` that carries a body (26 such routes) and a `GET` that carries a
   query string are not in the matrix; the cursor case (C12) is the one query
   string that is probed, and only for its fallback.
3. **The matrix judges the STATUS and the SHAPE of the answer, not the
   semantics of a business refusal.** A 422 with a well-formed problem
   document but the wrong field is not this probe's business — that is the
   route's own test's business.
4. **The route set is the compiled route table.** A route declared with a
   plain verb macro would not be in it; the product's `Letflow.Api.AuthorizedRouter`
   forbids that (ISS-0993 G0), so every route of every mounted router is in
   the table.
5. **Every path parameter is a placeholder** (a fixed UUID), so a route that
   validates the FORMAT of its path parameter answers a 4xx for that reason.
   The probe still sees "no 5xx", but it does not prove the route's own path
   validation — that is the route's own test's business.
6. **A route-specific parser changes the expectation, not the rule.** The
   pipeline's `LogoBodyParser` claims any content type on `PUT /tenant/logo`,
   `CsvBodyParser` claims `text/csv` on the record import route and
   `XlsxBodyParser` claims the workbook media type on the user import route.
   On those routes the body is NOT refused by the parser, so the probe asserts
   only "no 5xx, no missing answer" — the refusal itself is the route's own
   business. The probe does not pin which routes claim which media type.
7. **The over-cap case uses the JSON cap (2 MB).** The multipart cap
   (25 MiB) and the logo cap (512 KiB) are larger and smaller respectively;
   a body over the multipart cap is not probed (it would need a 25 MiB
   allocation per cell).

## The non-vacuity argument

The probe can fail. Three independent ways, all proved by the test suite:

1. **The seeded failing case (C13).** `Letflow.Support.G13RogueRouter` is the
   API pipeline as it was **before** T-2658: the same parser list, the same
   2 MB cap, and a `handle_errors/2` that returns the connection unchanged. It
   is driven through the SAME aggregate entry point (`G13Matrix.run/3`) and
   the SAME verdict (`G13Matrix.violations/1`) as the real tree, with the SAME
   shape list. The test asserts that the rogue IS flagged — on the malformed
   JSON shape and on the unsupported-media-type shape — and that the flags are
   `:no_answer` and `:untyped_refusal`. If the verdict were neutered, this
   test would fail; if the real tree were broken, C3..C9 would fail.
2. **The verdict is checked against synthetic outcomes (C14).** A synthetic
   500, a missing answer, a bodiless 400 and an unexpected exception are each
   fed to `violations/1` and must be flagged by the rule that names them.
3. **The inventory is checked against the tree (C2).** A matrix built from a
   hand-written list, or one that stopped seeing routes, fails the comparison
   with `Letflow.Support.RouteInventory.routes/0`.

There is no silent rerun and no retry anywhere in the probe: fixed shapes, a
fixed canary, a fixed placeholder id, no clock, no network, no ordering
dependence.
