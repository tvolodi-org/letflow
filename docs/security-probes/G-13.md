# G-13 — Generated malformed-input / no-5xx route and parser matrix

Gap **G-13** of the team repository's `docs/security-coverage.md` §4:

> Generated malformed input/no-5xx route and parser matrix (body shapes,
> content types, caps, child/start errors, codec fallback).

Class: **TOOL** (D-184/D-186 ratchet: mechanise the security gates). The probe
is mechanical — no model, no network, no clock — and it runs in the `checks`
step for every backend change. The enforcement is NOT "the probe files are
ordinary test files" (that only runs them when they change): it is the
`@moduletag :unit` in the parser-level file, which puts it in the team
runner's unit tier (`mix test --only unit`, run on every non-rework backend
change), plus the product's own bounded-CI safety set
(`scripts/ci_select_tests.py`, `STANDARD_SECURITY_PROBE_TESTS`), which makes
them mandatory on every bounded run.

**Where the tagged set runs.** The operator's runner has the hook, and it works
today: the team repository's `project/scripts/lf.sh` reads the tag
(`PROBE_TAG="${LF_PROBE_TAG:-security_probe}"`, line 68), finds the tagged test
files in the product worktree it runs in (`tagged_probe_files/0`, line 230) and
plans them for every backend change, whatever the changed paths are
(`plan_probe_chunk/0`, line 506). The tagged set on the merged tree is **16
files**:

- `test/letflow/platform_functions/failure_vocabulary_test.exs`;
- G-01: `g01_matrix_shard_0_test.exs`, `g01_matrix_shard_1_test.exs`,
  `g01_matrix_shard_2_test.exs`, `g01_matrix_shard_3_test.exs`,
  `g01_route_role_matrix_test.exs`;
- G-03: `g03_source_provenance_test.exs`;
- G-05: `g05_audit_row_schema_test.exs`, `g05_audit_writer_matrix_test.exs`;
- G-06: `g06_outbound_dispatch_probes_test.exs`,
  `g06_outbound_http_inventory_test.exs`;
- G-07: `g07_cursor_codec_probe_test.exs`,
  `g07_cursor_traversal_probe_test.exs`;
- G-08: `g08_uat_safety_equivalence_test.exs`;
- G-13 (this probe): `g13_malformed_input_matrix_test.exs`,
  `g13_route_no_5xx_test.exs`.

**The share rule and its outcome.** The hook does not run the whole set: it
divides the five-minute budget (`PROBE_BUDGET_S=300`, line 71) by the number of
tagged files — `share = $((PROBE_BUDGET_S / n))`, line 515 — and a probe whose
declared cost is **above** that share is deferred to CI and the nightly job
instead of the `checks` step (lines 525-526 and the message at line 540). On
the merged tree `n = 16`, so `share = 300 / 16 = 18 s`, and the outcome for the
two G-13 files is:

- the **parser-level** file declares `probe_cost_s: 10` — 10 s is not above the
  18 s share, so it is **KEPT**: it runs in the `checks` step. It carries the
  seeded failing case, the non-vacuity proof and the verdict test, so the
  acceptance criterion rests here;
- the **route-level** file declares `probe_cost_s: 60` — 60 s is above the
  18 s share, so it is **DEFERRED**: it runs in the product's required
  `Backend gate` and in the nightly job (via `scripts/ci_select_tests.py` and
  `test/shard_manifest.txt`, shards 2 and 8), not in the team's `checks` step.

The declared costs are honest upper bounds of the measured ones (below), and
the two files need different bounds: the parser-level file touches **no
database** (plain `ExUnit.Case`, no tenant fixture), so its bound is a 14x
margin over 0.7 s, while the route-level file provisions a real tenant schema
and therefore keeps a cold-database bound of 60 s.

The margin is now **8 s** (10 s declared against an 18 s share), and the
share moves with every probe that lands: the parser-level file is deferred
when the tagged set reaches 31 files (`300 / 31 = 9 s < 10 s`). Re-derive the
share when a sibling probe lands — the acceptance criterion depends on it.

Measured cost: the parser-level file 0.7 s, the route-level file 5.8 s (both
on this host, warm, with the team's PostgreSQL on port 5492). The declared
costs are 10 s and 60 s.

## The inventory the matrix is generated from

The route list is **derived**, never written down: `Letflow.Support.RouteInventory.routes/0`
returns the compiled route table (`__authz_routes__/0`) of every router mounted
under `lib/letflow/plugs/api_pipeline.ex` and every module router mounted at
`/modules/<manifest id>`, with the FULL mounted path. On the merged tree this
probe was last re-derived against (branch `team/T-2633` with `origin/main`
merged, commit 9dcc1c407) that is **453 mounted routes, of which 256 are
mutating** (`POST`, `PUT`, `PATCH` — 204 POST, 36 PUT, 16 PATCH) and 26 are
`DELETE`, over 61 routers. The numbers move with the tree — that is the point:
a route mounted after this probe was written is covered by the next run, and
the completeness case (C2) fails if the two ever disagree.

The shape list is generated in `Letflow.Support.G13Matrix.shapes/0`: twelve
shapes, each with a body, a content type and (where the shape can carry one)
a canary token that must not survive into the answer.

## The verdict

One function decides every cell: `Letflow.Support.G13Matrix.violations/1`. It
returns the list of rules the cell breaks; an empty list means the cell is
fine. The rules:

- `:no_answer` — the request produced no answer at all: the caller is left
  without a status and without a body.
- `:server_error` — the answer is a 5xx: a caller's own mistake answered as a
  server fault.
- `:untyped_refusal` — the refusal was signalled but the answer is not a typed
  problem document (`application/problem+json` with `status`, `title`, `type`,
  `detail`), or its status does not match the status the parser's own
  exception carries (`Plug.Exception.status/1`).
- `:unexpected_error` — an error escaped that the pipeline does not own
  (anything but the four exceptions `Plug.Parsers` raises).
- `:wrong_refusal` — the refusal is not the one the shape demands: the
  exception kind or the status it carries is not the one the shape's own
  `refusal:` pins. This is the CAPS dimension: a body over the cap must be
  answered 413, not 400; a media type no parser claims must be answered 415,
  not 400.
- `:echoed_request` — the answer carries the canary from the request.

The expected refusal of every shape is pinned in one place,
`Letflow.Support.G13Matrix.expected_refusal/1`:

- `:parse` — refused with `Plug.Parsers.ParseError` or
  `Plug.Parsers.BadEncodingError`, answered 400.
- `:unsupported_media_type` — refused with
  `Plug.Parsers.UnsupportedMediaTypeError`, answered 415.
- `:too_large` — refused with `Plug.Parsers.RequestTooLargeError`, answered
  413.

A shape whose `refusal:` is `:none` or `:handler` expects no refusal at all:
on a route with its own parser (the logo, CSV and XLSX parsers) the body is
not refused there, and the rule does not fire.

## The product change the probe found

`lib/letflow/routers/instances.ex`, `render_create/2`: a SUB_PROCESS child
refusal was mapped only for the module-only child (T-2515). Every other cause
fell through to the catch-all and answered the **detail-free 500**
(`{"status":500, …, "detail":"an unexpected error occurred"}`) — a caller's own
mistake answered as a server fault. Two clauses were added:

- a child definition that does not exist (or a node that names none) → the
  typed 404 a direct start gives (C10);
- a child definition that needs reactivation → the typed 409 a direct start
  gives (C11).

**Red proof.** On the unmodified `instances.ex` both child-refusal tests fail:

```
test "a parent naming a child definition that does not exist answers 404, not a 500"
  left: 500
  right: 404
  body: {"status":500,…,"detail":"an unexpected error occurred",…}

test "a parent naming a child definition that needs reactivation answers 409, not a 500"
  left: 500
  right: 409
```

Command: `MIX_TEST_PARTITION=2633 mix test test/letflow/security_probe/g13_route_no_5xx_test.exs`
(2 failed, 2 passed) on the unmodified code; 4 passed with the fix.

## Residual limits

Stated so the next reader does not mistake the coverage for more than it is.

1. **A SUB_PROCESS child refusal with a cause other than "the child definition
   does not exist" or "the child definition needs reactivation" still answers
   the detail-free 500.** That is: a missing required interface input, an
   input schema violation, a missing required output, an output schema
   violation, an invalid child graph and a pin resolution failure. These are
   configuration gaps of a different shape — the parent's interface demands
   something the child does not declare — and not a malformed request, so they
   are left as they are and named here rather than silently remapped. Mapping
   them needs its own decision (a 422 that names the interface field, or an
   error document that carries the interface's own detail), which is outside
   this probe's class.
2. **The matrix covers the mutating routes only** (`POST`, `PUT`, `PATCH`).
   A `DELETE` that carries a body (26 such routes) and a `GET` that carries a
   query string are not in the matrix; the cursor case (C12) is the one query
   string that is probed, and only for its fallback.
3. **The matrix judges the STATUS and the SHAPE of the answer, not the
   semantics of a business refusal.** A 422 with a well-formed problem
   document but the wrong field is not this probe's business — that is the
   route's own test's business.
4. **The route set is the compiled route table.** A route declared with a
   plain verb macro would not be in it; the product's `Letflow.Api.AuthorizedRouter`
   forbids that (ISS-0993 G0), so every route of every mounted router is in
   the table.
5. **Every path parameter is a placeholder** (a fixed UUID), so a route that
   validates the FORMAT of its path parameter answers a 4xx for that reason.
   The probe still sees "no 5xx", but it does not prove the route's own path
   validation — that is the route's own test's business.
6. **A route-specific parser changes the expectation, not the rule.** The
   pipeline's `LogoBodyParser` claims any content type on `PUT /tenant/logo`,
   `CsvBodyParser` claims `text/csv` on the record import route and
   `XlsxBodyParser` claims the workbook media type on the user import route.
   On those routes the body is NOT refused by the parser, so the probe asserts
   only "no 5xx, no missing answer" — the refusal itself is the route's own
   business. The probe does not pin which routes claim which media type. The
   `:wrong_refusal` rule follows the same line: it judges the refusal only
   where the parser raised one, so a route that accepts the body is not
   judged on a status it never owed.
7. **The over-cap case uses the JSON cap (2 MB), and that cap is now
   ENFORCED by the probe** (C6 and C15: the over-cap cell must be refused
   with `RequestTooLargeError` and answered 413 — raise the cap and the probe
   fails). The multipart cap (25 MiB) and the logo cap (512 KiB) are larger
   and smaller respectively; a body over the multipart cap is not probed (it
   would need a 25 MiB allocation per cell). The logo cap is not probed
   either — the over-cap body is already over it, so that route's own parser
   refuses it with the same 413, but the limit in the answer is the logo's
   own and the probe does not check it.
8. **The echo rule (C9, C16) checks the answer's BODY for a BODY-borne canary
   only.** Every shape that carries a canary carries it in the body;
   `concrete_path/1` replaces every path parameter with a fixed UUID and
   `build_conn/2` sets only the content-type header, so no canary ever travels
   in a path, a query string or a header. The probe captures no log, no audit
   payload, no DLQ entry and no run artifact, so the rule does not look at
   those either — it reads the answer's body and asks whether the shape's own
   canary is in it. The full sweep of the coverage map's canary MUST (every
   input encoding to every response, log, crash error, audit payload, DLQ
   entry, webhook and UAT artifact) is gap **G-04**'s own scope, not this
   probe's.

## The non-vacuity argument

The probe can fail. Five independent ways, all proved by the test suite:

1. **The seeded failing case (C13).** `Letflow.Support.G13RogueRouter` is the
   API pipeline as it was **before** T-2658: the same parser list, the same
   2 MB cap, and a `handle_errors/2` that returns the connection unchanged. It
   is driven through the SAME aggregate entry point (`G13Matrix.run/3`) and
   the SAME verdict (`G13Matrix.violations/1`) as the real tree, with the SAME
   shape list. The test asserts that the rogue IS flagged — on the malformed
   JSON shape and on the unsupported-media-type shape — and that the flags are
   `:no_answer` and `:untyped_refusal`. If the verdict were neutered, this
   test would fail; if the real tree were broken, C3..C9 would fail.
2. **The seeded failing case of the echo rule (C16).**
   `Letflow.Support.G13RogueEchoRouter` answers 200 with the request body
   echoed straight back. It is driven through the SAME aggregate entry point
   (`G13Matrix.run/3`) and the SAME verdict, and the probe MUST flag it with
   `:echoed_request`. The real tree never echoes, so an absence-only
   assertion over it holds even when the rule is dead — the seeded case is
   what proves the rule still detects. A synthetic twin (a driver whose
   answer carries the shape's own canary) covers the same rule a second way.
3. **The verdict is checked against synthetic outcomes (C14, C15).** A
   synthetic 500, a missing answer, a bodiless 400, an unexpected exception
   and a wrong refusal (a body over the cap refused with a parse error) are
   each fed to `violations/1` and must be flagged by the rule that names
   them.
4. **The inventory is checked against the tree (C2).** A matrix built from a
   hand-written list, or one that stopped seeing routes, fails the comparison
   with `Letflow.Support.RouteInventory.routes/0`.
5. **The caps are pinned, not derived (C6).** The status a refusing shape
   must be answered with is written down per shape, not read off the
   exception that happened to be raised. Raise the pipeline's 2 MB cap and
   the over-cap cell answers 400 instead of 413 — the wrong refusal, and the
   probe fails.

### The rules are checked against MUTANTS of the probe

Every rule of the verdict has a negative fixture, so neutering a rule turns
the suite RED. Each mutant below is a one-line change to the probe itself,
run against the probe's own suite
(`MIX_TEST_PARTITION=2633 mix test test/letflow/security_probe/g13_malformed_input_matrix_test.exs`):

- the body of `echoed_request/2` neutered → **7 of 9 pass** — the echo rule's
  two fixtures fail;
- `|> echoed_request(outcome)` dropped from the accumulator → **7 of 9 pass** —
  the same two fixtures fail;
- the body of `wrong_refusal/2` neutered → **8 of 9 pass** — the verdict's
  wrong-refusal case fails;
- the body of `untyped_refusal/2` neutered (the control) → **7 of 9 pass** —
  the rogue case and the verdict case fail;
- the pipeline's JSON cap raised from 2 MiB to 10 MiB → **7 of 9 pass** — the
  refusal case and the whole-matrix case fail.

There is no silent rerun and no retry anywhere in the probe: fixed shapes, a
fixed canary, a fixed placeholder id, no clock, no network, no ordering
dependence.
