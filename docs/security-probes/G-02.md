# G-02 — writer and start-path AST inventory

Class: TOOL (D-184/D-186). The probe is pure Elixir AST analysis: no model, database, clock, network,
process ordering or random input. It runs under the `:security_probe` tag and is a mandatory test in
the bounded standard backend selection. Declared cost: **20 seconds** (`probe_cost_s: 20`).

## What is derived

- `test/support/security_probe/g02.ex` parses every `.ex`/`.exs` below `lib/` and `priv/`. It
  normalises pipes; resolves full, grouped and renamed aliases, with or without the `Elixir.`
  prefix, whether they are written in the module or at file scope; resolves imported functions to
  the module they came from; sees calls, captures and literal/dynamic `apply/3`; and includes the
  repository variables used by transaction and Multi callbacks, plus any other receiver whose
  method name is a Repo mutation verb (`insert`, `insert!`, `insert_all`, `update`, `update!`,
  `update_all`, `upsert`, `delete`, `delete!`, `delete_all`). Documentation and type attributes are
  excluded, so prose and `Repo.t()` do not become inventory entries.
- There is NO checked-in snapshot of the tree. Every Repo call, every `Ecto.Multi` call and every
  repository-variable call (a `$name` target) is derived from the tree on each run and only used
  for derivations: the completeness check (W2), the definition writers (D1), the callers of those
  writers (W1) and the start paths (S1). An unrelated Repo call that lands on `main` can therefore
  never turn the probe red; a new writer or start path can.
- A module body is scanned in every form it can have: a `defmodule`, and a protocol implementation
  or protocol at FILE scope (which is a module of its own, under the name Elixir gives it, such as
  `String.Chars.Fake`). An implementation nested inside a `defmodule` is covered by that module's
  own functions.
- A module attribute that holds a capture of a function (`@ins &Repo.insert/2`), a module
  (`@repo Letflow.Repo`) or a function (`@writer fn changeset -> Repo.insert(changeset) end`) is a
  pointer the module keeps. The capture is inventoried where it is defined, a function held by an
  attribute is inventoried under the attribute name and its arity, and a call through the attribute
  (`@ins.(x)`, `@repo.insert(x)`, `@writer.(x)`) resolves to what the attribute holds, so neither a
  write nor a start can hide behind the attribute. The local call graph follows the pointer, so a
  definition writer behind an attribute is derived as a writer.
- A `defdelegate` is a call of the module it delegates to. The delegated call is inventoried under
  the delegating function with the form `delegate` (`as:` names the delegated function), and the
  local call graph follows the delegation, so a delegated write cannot hide behind it.
- A local transitive call graph derives every public function in the `Letflow.Definitions` namespace
  whose closure reaches a repository write: direct Repo writes, Multi writes, callback-repo writes and
  dynamic applies. The module set comes from the namespace, not from a hand-written list, so a
  definition writer outside the first three reviewed modules is still classified. D1's classes are
  `graph_write`, `switch_on`, `status_only`, `supporting_write`, `activation_write`, `review_write`,
  `reactivation`, `snapshot_write`, `pack_write` and `override_write`; an unclassified new path fails.
- S1 is the closed start inventory: HTTP `Engine.create/2`, the three module starts, the platform
  process start (`Letflow.PlatformProcesses.start_register_tenant/2`, a root instance in the platform
  tenant that carries the caller's `auth_context`, so the engine's own start-permission gate judges
  it), the scheduled-job
  `Engine.create/2` capture (repeated for the three arities generated by `run/3`'s two defaults), both
  `SubProcess.append_start_multi/7` call sites (initial start and continuation) and both
  `SubProcess.prepare_child_activation/4` call sites (the child activation that creates the child
  instance snapshot). The root start is inventoried by the NAME of the function, so a start through
  another arity of `Letflow.Engine.create` is a start path as well. S2 separately inventories every
  syntactic write of `:module_start`: the
  `Keyword` verbs (`put`, `put_new`, `replace`, `replace!`, `delete`), the `Map` verbs (`put`,
  `put_new`, `replace`, `replace!`, `delete`), `List.keystore/4` and a literal keyword pair, through a
  renamed module (`alias Keyword, as: KW`), an alias written at file scope, an `Elixir.`-prefixed
  alias or an imported function (`import Keyword, only: [put: 3]`) as well. A write through
  `apply/3`, `Kernel.apply/3` or `:erlang.apply/3` is the same write: it is seen when the module is
  written as an alias (`apply(Keyword, ...)`, `apply(Elixir.Keyword, ...)`, an aliased
  `apply(KW, ...)`) or as the module atom (`apply(:"Elixir.Keyword", ...)`), and is reported under an
  `apply_`-prefixed form (`apply_put`, `apply_map_put`, `apply_keyword_delete`, …) so the reviewer
  sees where it came from. Only stock, assets and
  maintenance module code may supply it, and only as literal `true`. Dynamic `apply/3` to Repo, Multi
  or a start target is retained as `:dynamic`, never treated as a harmless unknown call.
- S3 states where the two module-start gates live and judges every Engine start entry by the gate of
  the kind of start it performs. A root instance is started by `Letflow.Engine.create/2`, whose
  definition lookup passes `Letflow.Engine.gate_module_only_start/2`; an entry that can start a root
  instance must reach that gate. A SUB_PROCESS child is activated by
  `Letflow.Engine.SubProcess.prepare_child_activation/4` and
  `Letflow.Engine.SubProcess.append_start_multi/7`; an entry that reaches that activation must reach
  `Letflow.Engine.SubProcess.refuse_module_only_child/4`. The two gates are judged separately, so
  neither can stand in for the other: removing the root gate (T-2444) and removing the child gate
  (T-2588) are each reported on their own. An Engine entry that can start an instance without the
  module-only refusal of its kind is reported.

This is an inventory/ratchet, not a claim that every listed writer is tenant-safe. Existing semantic
and route probes retain their own verdicts.

### Limits, stated rather than hidden

- Non-literal dynamic modules/functions and macros defined elsewhere cannot be resolved without
  executing code. A computed `module_start` value fails closed (`:computed`) rather than being guessed.
- A `module_start` merged from a **computed** keyword list (`Keyword.merge(opts, other)`) cannot be
  resolved without executing code; a merge of a literal list that carries `:module_start` is seen.
- An option written through `apply/3` is seen when the module is written as an alias or as the module
  atom. A **computed** module or function (`apply(mod, fun, args)` with a variable in either
  position) is not resolved, for the same reason a dynamic Repo or Multi call is not: it cannot be
  resolved without executing code. A module that is not `Keyword`, `Map` or `List` cannot write the
  option, so it produces no row.
- An alias or an import written at file scope applies to every module of the file, as in Elixir; a
  module's own alias or import of the same name wins over the file's. The probe applies the file's
  aliases and imports to every module of the file, while Elixir applies them only from their
  position on; the probe therefore sees more, never less.
- An imported function is attributed to the module it was imported from. The probe does not load
  that module, so a function the imported module does not export is attributed to it as well (an
  unqualified call that Elixir would resolve to `Kernel`); such a row is not a database write and
  the reviewer confirms every added row. A function the module defines itself is the module's own,
  not the imported one — its body is scanned on its own.
- A write made inside a helper of another file is reported against that file, not against the call
  site; the call site is not a write of its own.
- A receiver whose method name is a Repo mutation verb is retained conservatively as a possible
  repository write, so the inventory can contain a row that is not a database write. The reviewer
  confirms every added row.
- The call graph is a fixpoint over local and remote calls. A call through a variable (an
  indirection) and a call into a module outside the scanned tree are not resolved.
- S3 judges the Engine start entries of the local call graph. A start call site outside
  `Letflow.Engine` (the HTTP route, the three module starts, the platform process start, the
  scheduled job) is covered by S1's
  closed inventory rather than by the gate reachability; it reaches `Letflow.Engine.create/2`, which
  the rule judges. The root start is inventoried by its name, so a start through another arity of
  `Letflow.Engine.create` is seen as well; a rename of the public root start is a probe change
  rather than a silent gap. A gate moved out of the scanned tree, or reached through an
  indirection, is not resolved.
- The arguments of a call are not part of any derived row, so re-argumenting a call does not change
  a verdict.
- A module attribute is resolved when it holds a capture of a REMOTE function (`&Module.fun/arity`
  or `&Module.fun(arg, ...)`), a module or a function. A capture of a function of the same module is
  not held as a pointer (the function's own body is scanned), and an attribute whose value is
  computed at runtime cannot be resolved without executing code. A function held by an attribute is
  inventoried under the attribute name and the arity of its clause; a call through the attribute
  follows it.
- A `defdelegate` is inventoried when the module it delegates to is written as an alias; a bare
  module atom (`to: :"Elixir.Mod"`) or a computed target is NOT resolved, and neither is a Repo
  call through `apply/3` with a module atom. No such form exists in the tree today. The delegated call is
  reported under the delegating function with the form `delegate`.
- The dot node inside a capture (`&Module.fun/arity`) names the captured function; it is not a call
  of its own, so it is not inventoried as a zero-arity call. The capture itself is inventoried with
  the form `capture`.
- The inventory is a static inventory: it says which writers and starts exist, not that each of them
  carries the right tenant scope or authorisation.
- D1's classification covers the `Letflow.Definitions` namespace only. A module that writes
  tenant-scoped rows outside that namespace is not a D1 writer, and is judged by its own gates. The platform-step dispatcher is the
  current example: it writes the `platform_step_dispatches` table, not a definition row, and starts
  no run, so it is neither a definition writer (D1) nor a start path (S1).

## Definition entry-point classes pinned by D1

A module is written in the short form: an entry that names a module (`Definitions.create/2`,
`Promotion.promote_definition/3`) starts a new module under `Letflow.Definitions`, and a bare entry
(`create_owned/3`) continues the module named before it in the same row. T2 compares this table
with the map the probe uses, so the two cannot drift apart.

## Running and refreshing

```sh
mix test --only security_probe test/letflow/security_probe/g02_writer_start_inventory_test.exs
```

There is no snapshot to refresh. The exception lists (`@definition_callers` for W1, `@definition_classes`
for D1, `@expected_starts` for S1) change only when a writer or start path is added, moved or
removed, and each such change is a reviewed decision.

A writer's class is a reviewer's judgement and not a mechanical derivation. After a change to the definition namespace,
run the probe and read the drift it reports: every `{:unclassified, {module, name, arity}}` entry is
a writer the map does not classify, and every `{:no_longer_a_writer, ...}` entry is one that stopped
writing. Add the new writer to `@definition_classes` in the probe test with its class, add it to the
table below, and remove the one that stopped writing. A merge of `origin/main` that renames or adds a
definition writer needs the same treatment, or the probe is red on the tree the merge queue builds.

An exception row is added only with the reviewer's reading of the new entry path: a new caller of a definition writer must be an authorised route, seed or activation, and the decision is recorded in this table's W1 row.
