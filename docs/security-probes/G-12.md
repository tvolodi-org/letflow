# G-12 — PR-blocking dependency advisory gate and the SAST scan of the Elixir tree

Class: **TOOL** (D-184/D-186 ratchet: mechanise the security gates). The probe is mechanical: no
model, no network, no clock, no database. It carries `@moduletag :security_probe` and
`@moduletag probe_cost_s: 10`, and it is listed in `STANDARD_SECURITY_PROBE_TESTS`
(`scripts/ci_select_tests.py`), so the operator's `lf.sh` runs it for **every** backend change.

The gap it closes (team repository, `docs/security-coverage.md` §4):

> **G-12** — PR-blocking dependency advisory gate plus Sobelow (or justified equivalent) and a
> real Dart advisory source. … None of the five named findings was a dependency advisory/SAST
> finding; this is unmeasured coverage, not a demonstrated regression.

What the coverage map found (§2): the dependency audit was **report only** —
`.github/workflows/dependency-audit.yml` runs `mix hex.audit`, `npm audit` and
`flutter pub outdated` weekly, every step `continue-on-error`, with no `pull_request` trigger;
`flutter pub outdated` is version freshness, not an advisory check; and no Sobelow, Semgrep or
`mix_audit` was configured anywhere.

## What is delivered

- `lib/mix/tasks/letflow.advisory_gate.ex` — the gate. `mix letflow.advisory_gate` reads the
  three real advisory sources, decides, prints a report and exits 1 on a blocking finding.
  The same file holds the SAST rules over `lib/`.
- `priv/security/advisory-allow.json` — the allow-list of accepted advisories. Every entry carries
  `id`, `package`, `reason`, `owner` and `expires`.
- `priv/security/sast-allow.json` — the allow-list of accepted SAST findings, same shape.
- `test/letflow/security_probe/g12_advisory_gate_test.exs` — the probe (29 tests).
- `test/fixtures/security_probes/g12/` — the seeded failing cases (a vulnerable dependency tree
  with a Hex, an npm and a Dart lock file, two recorded advisory feeds, an allow-list with a
  live, an expired and a stale entry, and a file with one violation of every SAST rule) and the
  **recorded answers of the three real sources** (the SARIF report of `mix hex.audit`, the JSON
  of `npm audit --omit=dev`, the batch answer and the query answer of OSV). Every one of those
  four answers was captured from the real tool, not written by hand.
- `.github/workflows/ci.yml` — the step **Dependency advisory gate (mix letflow.advisory_gate)**
  in the `backend_static` job. That job feeds the required check *Backend gate (mix
  letflow.check)*, so the gate **blocks the pull request**: the step is not `continue-on-error`.

## The decision

The gate is two halves over one decision function.

**The advisory half** collects the advisories of the locked versions from three sources:

- **Hex** — source `mix hex.audit --format sarif`, the Hex registry's own advisory list; the tool the coverage map names ("MUST run a blocking advisory check on PR/merge"). The **SARIF report** is read, not the human report: the human report is prose, and a parser of prose silently finds nothing when the prose changes. The SARIF result names the advisory in the `ruleId`, the package and the id in the `hexAudit/v1` fingerprint, the version and the aliases in the message arguments, and the severity in the rule's `security-severity` (the CVSS score, mapped onto the CVSS bands). The seeded case that proves it: `test/letflow/security_probe/g12_advisory_gate_test.exs::G12: the hex collector reads the advisory out of the recorded hex audit report`
- **npm** — source `npm audit --omit=dev`, the npm registry; `--omit=dev` keeps the tree to production dependencies ("with a stated severity policy"). The id of an npm advisory is the **GHSA id its URL carries**, not npm's numeric `source` (a database row number an operator cannot look up, and one no allow-list entry can name). The seeded case that proves it: `test/letflow/security_probe/g12_advisory_gate_test.exs::G12: the npm collector reads the advisory out of the recorded npm audit report`
- **Dart (pub)** — source the OSV `Pub` ecosystem (`https://api.osv.dev/v1/querybatch`): pub has no audit tool of its own; OSV is the real machine-readable advisory source for Dart packages (the GitHub Advisory Database and the Dart team publish into it) ("Add a real Dart/OSV advisory check"). OSV answers an **empty map** for a package that has no advisory — that is an answer, not a missing result, and a parser that expects a list of advisories in every result crashes on the answer of a clean tree. The batch answer carries the id of an advisory and nothing else, so the severity and the summary are read from the second query OSV answers for the package and the version. The seeded case that proves it: `test/letflow/security_probe/g12_advisory_gate_test.exs::G12: the pub collector survives the OSV answer of a package without an advisory`

The OSV request is an outbound request of the platform, so it goes through `:httpc` with
`autoredirect: false` — the one client this repository uses — and it is registered in the
**G-06** probe (`test/letflow/security_probe/g06_outbound_http_inventory_test.exs`) as the eighth
outbound call site, with the URL source `:platform_config`: the URL is the fixed service of the
platform operator, never tenant-controlled.

An advisory is **blocking** when all three hold: it hits a **production** dependency, its
severity is **medium or above**, and no allow-list entry covers it. The production set is derived
from the tree, not from a hand list: for Hex the closure of the direct dependencies that `mix.exs`
does not restrict to `:dev`/`:test` (the `only:` option is the authority), for npm the packages
the lock file does not mark `dev`, for pub the packages the lock file does not mark `direct dev`.

**The SAST half** scans `lib/**/*.ex` with the AST rules below and fails on a finding that
`priv/security/sast-allow.json` does not accept.

Both lists behave the same way:

- a **live** entry (expiry in the future) accepts the finding. The entry names the advisory by
  its id **or by one of its aliases** (the CVE or the GHSA id of the same advisory), and the
  comparison is between strings: an id that was a list or a number could never be matched by an
  entry, so no exception could ever have been accepted for the Hex or the npm ecosystem;
- an **expired** entry **fails the gate** — an exception nobody re-reviewed must not sit in the
  tree forever, and the expiry date is what makes that visible;
- an entry for an advisory that **no longer exists** is **reported** (a stale entry is noise,
  not a hole): it does not fail the gate.

### The id of a SAST finding

The id of a SAST finding is the **rule, the file and a hash of the offending call** — never the
line number. An id that carries the line moves whenever anything is inserted above the site, and
an accepted site that changes its line would become a NEW finding and block every pull request
that touches the file for an unrelated reason. The hash is over the canonical text of the call
(`Macro.to_string/1`), so:

- a change **of** the call is a new site: it has to be read again, and it gets a new entry (or
  a fix), never a widened reason on an old one;
- a change **around** the call (a line above it, a new function next to it) changes nothing: the
  accepted entries stay valid and the gate does not block unrelated pull requests.

Two sites with the **same call text** in one file would share one id, and a third site with that
text would then be accepted by the entry of the first two without being read. They are told
apart by an ordinal: the first carries the bare id, the second `:2`, the third `:3`.

The file of a finding is relative to the **scanned root**, never to the working directory: the
same tree scanned from any directory produces the same findings and the same ids.

## The SAST rules, and why this is not Sobelow

Sobelow is a Hex dependency. Adding one changes the lock file of **every** worktree, while the
operator's setup step only fetches dependencies when `deps/` is missing (`project/scripts/lf.sh`,
`setup`): a tree whose `deps/` already exists would fail to compile with "sobelow is not
available" until someone re-ran `mix deps.get` by hand — a landmine under every other task in
flight. The gap list allows "Sobelow (or justified equivalent)", and the equivalent is the rule
set below, implemented over this repository's own source with the same AST approach the
repository's other scans already use (`test/letflow/entities/handler_writes_callers_test.exs`,
`test/letflow/modules/write_target_sources_scan_test.exs`).

- **`unsafe_atom`** — flags `String.to_atom/1`, `List.to_atom/1`, `:erlang.binary_to_atom/2` with an argument that is not a literal, and a dynamic atom literal `:"...#{...}"`; it replaces the Sobelow check `unsafe_atom` (the coverage map: "make findings blocking at an agreed severity"). The case that proves it: `test/letflow/security_probe/g12_advisory_gate_test.exs::G12: the SAST rules flag every violation of the seeded rogue file`
- **`command_injection`** — flags `System.shell/1` with a non-literal argument, and `System.cmd/2,3` that calls a shell (`sh`, `bash`, `cmd`, `powershell`, …) with a non-literal argument; it replaces the Sobelow check `command_injection` (the coverage map: "make findings blocking at an agreed severity"). The case that proves it: `test/letflow/security_probe/g12_advisory_gate_test.exs::G12: the SAST rules flag every violation of the seeded rogue file`
- **`sql_interpolation`** — flags `Repo.query/1,2`, `Repo.query!/1,2` and `Ecto.Adapters.SQL.query/3,4` whose SQL string is built by interpolation (`"#{...}"` or `~s\|...\|`); it replaces the Sobelow check `sql_injection` (the coverage map: "make findings blocking at an agreed severity"). The case that proves it: `test/letflow/security_probe/g12_advisory_gate_test.exs::G12: the SAST rules flag every violation of the seeded rogue file`
- **`unsafe_deserialization`** — flags `:erlang.binary_to_term/1` without the `:safe` option; it replaces the Sobelow check `unsafe_deserialization` (the coverage map: "make findings blocking at an agreed severity"). The case that proves it: `test/letflow/security_probe/g12_advisory_gate_test.exs::G12: the SAST rules flag every violation of the seeded rogue file`
- **`weak_hash`** — flags `:crypto.hash/2` with `:md5` or `:sha`; it replaces the Sobelow check `crypto` (weak algorithm) (the coverage map: "make findings blocking at an agreed severity"). The case that proves it: `test/letflow/security_probe/g12_advisory_gate_test.exs::G12: the SAST rules flag every violation of the seeded rogue file`

Sobelow checks that do **not** apply to this codebase and are therefore not implemented: the
Erlang-specific ones (`:os.cmd`, `:erlang.open_port`), the Phoenix/Rails-specific ones (this is
not a Phoenix application), the GitHub Actions ones (the workflow is read by the probe, not
scanned), and the ones for runtimes this product does not use (Sobelow's Node and Lua rules; the
product's Lua runtime is sandboxed by its own capability gate, `test/letflow/engine/lua/`).

Two Sobelow rules are deliberately **not** implemented, and the reason is stated: `insecure_random`
(the product draws randomness from `:crypto.strong_rand_bytes/1`, and a rule that cannot tell a
security draw from a jitter draw produces noise) and `rogue_marshaller` (the product derives no
marshaller from request data).

## Non-vacuity

The probe ships its own failing cases, all under `test/fixtures/security_probes/g12/` (TEXT, never
compiled, never run):

- `seeded_tree/mix.lock` — a lock file that pins a package version with a known advisory, and
  `seeded_tree/mix.exs`, whose `only: :test` dependency makes the production scope testable;
- `seeded_tree/web/package-lock.json` — an npm lock with one production package and one
  dev-only package, the npm half of the production scope;
- `seeded_tree/apps/mobile/pubspec.lock` — a Dart lock with one production package and one
  dev-only package, the Dart half of it;
- `seeded_tree/advisories.json` — the recorded feed of the Hex advisory (plus a low one and one
  on the test-only dependency);
- `seeded_tree/advisories_npm_pub.json` — the recorded feed of an npm advisory on a production
  package, a Dart advisory on a production package, and an npm advisory on a dev-only package;
- `allow_list.json` — one live entry, one expired entry and one stale entry;
- `seeded_tree/lib/rogue_sast.ex` — one violation of every SAST rule.

The inventory the gate decides on is checked for emptiness (the three production sets are
non-empty), and the rules are checked against the seeded rogue file: a scan that finds nothing,
or that finds only some of the rules, fails.

the same call text in one file are told apart by an ordinal and never share an entry.

## Cost

**The share rule and its outcome.** The hook does not run the whole tagged set: it divides the
five-minute budget (`PROBE_BUDGET_S=300`, `project/scripts/lf.sh` line 71) by the number of
tagged files — `share = $((PROBE_BUDGET_S / n))`, line 515 — and a probe whose declared cost is
**above** that share is deferred to CI and the nightly job instead of the `checks` step (lines
525-526 and the message at line 540). On the merged tree `n = 21`, so `share = 300 / 21 = 14 s`,
and the outcome for this file is:

- the file declares `probe_cost_s: 10` — 10 s is not above the 14 s share, so it is **KEPT**: it
  runs in the `checks` step of every backend change. It carries the seeded failing case, the
  non-vacuity proof and the verdict tests, so the acceptance criterion rests here. The checks
  set is then 9 probes with a declared cost of 61 s of the 300 s budget.

The declared cost is an honest upper bound of the measured one (below). The margin is now **4 s**
(10 s declared against a 14 s share), and the share moves with every probe that lands: the file
is deferred when the tagged set reaches 31 files (`300 / 31 = 9 s < 10 s`). Re-derive the share
when a sibling probe lands — the acceptance criterion depends on it.

Measured cost: the file 1.6 s — `mix test test/letflow/security_probe/g12_advisory_gate_test.exs`
-> "Finished in 1.6 seconds (1.6s async, 0.00s sync)", "Result: 29 passed", on this host, warm:
one AST pass over `lib/` and over the migrations, one read of the three lock files of the real
tree, two scans of the seeded tree, no database, no network. The declared cost is 10 s.

Before this correction the file declared `probe_cost_s: 30` against a measured 1.5 s, which is
above the 14 s share: the checks step deferred it ("it runs in CI and in the nightly job, not in
checks"), so the acceptance criterion did not hold even though the probe passed everywhere else.

## How to run and refresh

```sh
# the probe (offline, deterministic)
mix test test/letflow/security_probe/g12_advisory_gate_test.exs

# the live gate (network: hex.pm, the npm registry, osv.dev)
mix letflow.advisory_gate

# the SAST half alone
mix letflow.advisory_gate --sast-only
```

After a reviewed change of the tree, re-run the SAST scan, read the diff of the findings and
refresh `priv/security/sast-allow.json` **in the same change**. A refresh is not a way to bypass a
finding: the reviewer must account for every added, removed or changed line, and a new finding
gets a new entry (or a fix), never a widened reason on an old one.

An edit that does **not** touch an accepted site needs no refresh: the id of a site is the hash
of its call, not its line, so a file that grows above an accepted site keeps its entries. A
site whose call text changed has a new id and blocks until it is read again — that is the
ratchet, and it is the only case that asks for a human.

## Residual limits

- The gate reads the advisories of the **locked** versions only. A dependency that is vulnerable
  in a version the project does not use is not a finding, and a version that is *not* locked but
  would be fetched later is out of scope too.
- The Hex source is read in the **SARIF** format (`mix hex.audit --format sarif`), which Hex 2.x
  writes. The toolchain of this repository does not pin a Hex version (`.tool-versions` names
  Elixir, Erlang and Rust only), so CI installs the current Hex; on a Hex that does not know the
  format the command fails, the collector cannot read the source, and the gate fails closed with
  "the hex advisory source could not be read" rather than passing a tree it could not audit.
- The severity of a Hex advisory is the CVSS score of its SARIF rule, mapped onto the CVSS v3
  bands (below 4 low, 4 to 6.9 medium, 7 to 8.9 high, 9 and above critical); a rule without a
  score is treated as **high** (the gate fails closed on a finding it could not classify). The
  severity of a Dart advisory is the band OSV publishes; an advisory OSV answers without a band
  is **high** as well.
- The gate reads the advisories of the **locked** versions. `mix hex.audit` reports the
  advisories of the whole lock file, npm only the production ones; the production scope of the
  Hex half is applied by the gate itself, over the same inventory it decides on.
- The SAST rules see literal module names and literal argument shapes. A call reached through a
  variable receiver, an `import`, a macro or a capture is not seen; a value built at runtime is
  treated as non-literal (the rules fail closed).
- The SAST rules see the SQL string **where it is written**. A SQL string that another function
  assembles is invisible to them: `lib/letflow/modules/locations/tree.ex` calls
  `Repo.query!(subtree_sql(prefix, ""), [bin])`, and the interpolation happens inside
  `subtree_sql/2`, so the rule never sees it. The interpolated values of that call are checked by
  the module's own `@prefix_re`, not by this scan.
- The rules do not decide whether an interpolated value is *tenant data* — that judgement is the
  reason an accepted finding carries a reason and an expiry date, and it is the security
  review's work, not the scanner's.
- The Dart production set is the packages the lock file does not mark **direct dev**. A
  transitive package that only a dev dependency reaches is counted as production, because
  `pubspec.lock` does not say so: the Dart scope is therefore wider than the npm one, and an
  advisory on such a package blocks the pull request. That is the safe direction to err in.
