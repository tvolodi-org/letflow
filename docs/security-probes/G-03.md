# G-03 — generated source-provenance matrix of the platform-call authority rule

Class: TOOL (D-184/D-186). The probe is a mechanical test (no model): it generates the
source-class cross-product of the platform-call authority rule (T-2588, gap G2 of the
"Register a tenant" pilot) and of the write-target rule it carries over from T-2430, and
compares the shipped code with a reviewed expectation file. It runs under the
`:security_probe` tag and is a mandatory test in the bounded standard backend selection.
Declared cost: **5 seconds** (`probe_cost_s: 5`).

The gap it closes (team repository, `docs/security-coverage.md`, G-03): the source classes
were checked by hand-written examples and by a pack scan, so a new source class, a new
side-effect class, a new route attribute or a new catalogue entry reached `main`
unchecked. It would have caught the T-2588 source-class findings and the node carrying
both `platform_call` and `endpoint`, the T-2430 completer-controlled write targets and
unknown source shapes, and the T-2444 foreign-source classes in module-write definitions.

## What is derived

Nothing in the matrix is written by hand except the reviewed expectation file
`test/fixtures/security_probes/g03_source_provenance.txt`:

- the closed set of **source classes** is read from the shipped catalogue entry module
  (`@type source_class :: ...`);
- the closed set of **side-effect classes** is read from the same module (`@type class :: ...`);
- the **route attributes** a platform-call node may not carry beside its call come from the
  shipped rule module (`@conflicting_route_attributes`);
- the **node types** that merge a value from outside the graph's own trusted inputs come from
  the same module (`@foreign_source_types`);
- the **entries** are the compiled catalogue (`Letflow.PlatformFunctions.Catalog`).

A new source class, a new side-effect class, a new route attribute or a new catalogue entry
therefore **grows** the matrix, and the expectation file has no line for the new cell: the
probe fails until a human reviewed it. That is the difference between this probe and the
hand-written examples it replaces — an example test covers its example.

The families of the matrix:

- `catalogue` — a synthetic catalogue entry per source class and side-effect class, through
  the shipped `Letflow.PlatformFunctions.Entry.validate!/1`. The deliberately broken cells (a
  write-like entry with a `person` input) are the seeded failing case: the shipped catalogue
  is benign, so only the validator itself can refuse them.
- `malformed` — the entries the shipped validator must refuse: no name, no permission, no
  platform flag, an unknown source class, a duplicate name.
- `arg_shape` — every shipped entry and every declared input, with the argument's source
  shaped as `var`, `const`, a blank, a dotted or a reserved variable, a malformed map and an
  unknown key.
- `foreign_source` — every shipped side-effect class beside every foreign source the shipped
  rule knows (an inline HTTP service task, a catalogue service task, a script-bound service
  task, a sub-process), at activation **and** at dispatch.
- `dual_route` — every route attribute beside the platform call, at activation **and** at
  dispatch. The activation answers with the conflicting-route code even for a write-like
  entry, whose graph also carries a foreign source (the T-2588 finding).
- `write_target` — the variable a catalogue call reads is refused in a completion body (the
  T-2430 rule carried over by source class), and the reviewed exception that lets a human
  task keep it.

## What the probe does not cover

- The **argument-shape alphabet** is the probe's own list (ten shapes). The closed sets of
  classes and the route attributes are derived from the shipped source, but a new *legal*
  source key in the shipped rule would not join the matrix on its own: the probe would
  report it as an unknown shape until a human adds the shape and the reviewed line.
- The activation path resolves the function in the **compiled catalogue**, so a synthetic
  entry cannot reach it: the synthetic entries are exercised through the catalogue validator
  (the path the coverage map names), and the activation and dispatch paths are exercised
  with the shipped entries.
- The dispatch-time **permission and tenant** checks (`Letflow.PlatformFunctions.Guard`)
  need the database, so the probe checks the two pure dispatch rules
  (`foreign_source_graph?/1`, `conflicting_route_graph?/1`) instead. The permission and the
  tenant of a dispatch are covered by T-2588's own tests.
- The catalogue validator does **not** refuse an entry that declares no side effect at all,
  and it does not classify an unknown permission atom. Such an entry is read-like, so the
  write-like rule does not apply to it. The probe does not assert either (a finding for the
  owner, recorded with T-2630); the coverage map's §3.3 line about a missing side-effect
  declaration stays open.

## Running and refreshing

```sh
mix test test/letflow/security_probe/g03_source_provenance_test.exs
```

After a reviewed change of the catalogue or of the rule module, regenerate the expectation
file from the final tree, inspect its diff and rerun the probe. A refresh is not a way to
bypass a finding: the reviewer must account for every added, removed or changed line.
