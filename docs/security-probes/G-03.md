# G-03 — generated source-provenance matrix of the platform-call authority rule

Class: TOOL (D-184/D-186). The probe is a mechanical test (no model): it generates the
source-class cross-product of the platform-call authority rule (T-2588, gap G2 of the
"Register a tenant" pilot) and of the write-target rule it carries over from T-2430, and
compares the shipped code with a reviewed expectation file. It runs under the
`:security_probe` tag and is a mandatory test in the bounded standard backend selection.
Declared cost: **5 seconds** (`probe_cost_s: 5`).

The gap it closes (team repository, `docs/security-coverage.md`, G-03): the source classes
were checked by hand-written examples and by a pack scan, so a new source class, a new
side-effect class, a new route attribute or a new catalogue entry reached `main`
unchecked. It would have caught the T-2588 source-class findings and the node carrying
both `platform_call` and `endpoint`, the T-2430 completer-controlled write targets and
unknown source shapes, and the T-2444 foreign-source classes in module-write definitions.

## What is derived

The closed sets and the entries are DERIVED from the shipped source. Two parts of the
matrix are the probe's own fixed lists: the `malformed` family's checklist (each of its
cases is named by the coverage map, §3.3) and the argument-shape alphabet. The reviewed
expectation file `test/fixtures/security_probes/g03_source_provenance.txt` states what
each generated cell must be.

Derived:

- the closed set of **source classes** is read from the shipped catalogue entry module
  (`@type source_class :: ...`);
- the closed set of **side-effect classes** is read from the same module (`@type class :: ...`);
- the **route attributes** a platform-call node may not carry beside its call come from the
  shipped rule module (`@conflicting_route_attributes`), and the **line attributes** it may
  not carry either (`entity_writes`, `module_writes`: the platform route plans no lines, so
  they are refused before the function runs, T-2703) from the same module
  (`@platform_call_line_attributes`); both feed the `dual_route` family, only the route
  attributes feed the `foreign_source` family (a line attribute routes nothing by itself);
- the **node types** that merge a value from outside the graph's own trusted inputs come from
  the same module (`@foreign_source_types`);
- the **entries** are the compiled catalogue (`Letflow.PlatformFunctions.Catalog`).

A new source class, a new side-effect class, a new route attribute or a new catalogue entry
therefore **grows** the matrix, and the expectation file has no line for the new cell: the
probe fails until a human reviewed it. That is the difference between this probe and the
hand-written examples it replaces — an example test covers its example.

The families of the matrix:

- `catalogue` — a synthetic catalogue entry per source class and side-effect class, through
  the shipped `Letflow.PlatformFunctions.Entry.validate!/1`. The deliberately broken cells (a
  write-like entry with a `person` input) are the seeded failing case: the shipped catalogue
  is benign, so only the validator itself can refuse them.
- `malformed` — the entries the shipped validator must refuse: no name, no permission, no
  platform flag, an unknown source class, a duplicate name.
- `arg_shape` — every shipped entry and every declared input, with the argument's source
  shaped as `var`, `const`, a blank, a dotted or a reserved variable, a malformed map and an
  unknown key.
- `foreign_source` — every shipped side-effect class beside every foreign source the shipped
  rule knows (an inline HTTP service task, a catalogue service task, a script-bound service
  task, a sub-process), at activation **and** at dispatch.
- `dual_route` — every route and line attribute beside the platform call, at activation **and** at
  dispatch. The activation answers with the conflicting-route code even for a write-like
  entry, whose graph also carries a foreign source (the T-2588 finding).
- `write_target` — the variable a catalogue call reads is refused in a completion body (the
  T-2430 rule carried over by source class), and the reviewed exception that lets a human
  task keep it.

### Non-vacuity: one mutant per family

Every family of the matrix has an in-tree **mutant**: a variant of the subject that is ONE
RULE APART. Each mutant is built FROM the shipped rule (every other shipped refusal still
runs) and is driven through the SAME aggregate entry point (`matrix/2` → `cells/1` →
`violations/2`), so what catches it is the reviewed expectation file and nothing else.

| Family | The mutant | Cells it moves (measured, illustrative) |
|---|---|---|
| `catalogue` | the shipped catalogue validator without the write-like (`person` input) rule | 3 — the write-like `person` cells |
| `malformed` | the shipped catalogue validator without the duplicate-name rule | 1 — `duplicate_name` |
| `arg_shape` | the shipped activation without the argument-shape refusal | 7 — the invalid source shapes |
| `foreign_source` | the shipped activation without the foreign-source refusal, and its dispatch twin blind | 24 — 12 write-like cells, activation and dispatch |
| `dual_route` | the shipped activation without the conflicting-route refusal, and its dispatch twin blind | 40 — 20 cells (12 route + 8 line attribute cells), activation and dispatch |
| `write_target` | the shipped completion refusal without the catalogue call's contribution to the read set | 13 — the non-`:person` inputs of the catalogue |

Each mutant test asserts that the probe goes red **and** that only that family's cells
move, so one family cannot mask another. The counts are the measured ones at the time of
writing and they move with the catalogue: the assertion is the family confinement, not the
count.

## What the probe does not cover

- The **argument-shape alphabet** is the probe's own list (ten shapes), not a derived one:
  the shipped rule names its two legal source keys (`var`, `const`) in the private clause
  heads of `source_codes/1`, so there is no closed set to read. A new *legal* source key in
  the shipped rule is therefore **uncovered SILENTLY**: the probe never looks at it and stays
  green until a human adds the shape to `@arg_shapes` and the reviewed line to the
  expectation file. (The silent window opens when `source_codes/1` is amended to accept the
  new key; until then the shipped rule refuses it as an unknown key.) The closed sets of
  classes and the route attributes ARE derived, so a new class or route attribute does fail
  the probe.
- The activation path resolves the function in the **compiled catalogue**, so a synthetic
  entry cannot reach it: the synthetic entries are exercised through the catalogue validator
  (the path the coverage map names), and the activation and dispatch paths are exercised
  with the shipped entries.
- The probe runs **only in the platform tenant**: it pins the platform tenant in its setup
  (`Application.put_env(:letflow, Letflow.PlatformTenant, ...)`, restored in `on_exit`), so
  `Letflow.Definitions.PlatformCalls.violations/4` always takes the platform branch. The
  company-tenant branch — the ONE fixed code `:platform_call_not_allowed`, whatever the
  function is and whether or not it exists (INV-5, "one code, no existence oracle") — is
  therefore **not measured by the probe**. That branch is covered by T-2588's own test
  `test/letflow/definitions/platform_call_company_tenant_refused_test.exs`.
- The probe exercises the **activation** and **dispatch** points of the dual-route rule, not
  its **graph-validation** point: `Letflow.Definitions.Graph.validate_node_attributes/1`
  refuses the same node with the same code (`:conflicting_platform_call_routes`,
  `lib/letflow/definitions/graph.ex`), so the product enforces the rule at all three points
  the coverage map names, but the probe calls only two of them. The graph-validation point
  is covered by T-2588's own tests.
- The dispatch-time **permission and tenant** checks (`Letflow.PlatformFunctions.Guard`)
  need the database, so the probe checks the two pure dispatch rules
  (`foreign_source_graph?/1`, `conflicting_route_graph?/1`) instead. The permission and the
  tenant of a dispatch are covered by T-2588's own tests.
- The catalogue validator does **not** refuse an entry that declares no side effect at all,
  and it does not classify an unknown permission atom. Such an entry is read-like, so the
  write-like rule does not apply to it. The probe does not assert either (a finding for the
  owner, recorded with T-2630); the coverage map's §3.3 line about a missing side-effect
  declaration stays open.

## Running and refreshing

```sh
mix test test/letflow/security_probe/g03_source_provenance_test.exs
```

After a reviewed change of the catalogue or of the rule module, regenerate the expectation
file from the final tree, inspect its diff and rerun the probe. A refresh is not a way to
bypass a finding: the reviewer must account for every added, removed or changed line.

The probe's line in `test/shard_manifest.txt` carries a measured weight (170 ms, the
`--slowest-modules` figure of this file), not the median placeholder `scripts/test_shard_plan.sh
--append` hands a file with no CI timing; the next `scripts/test_shard_plan.sh --from-logs`
rebuild replaces it with the CI-derived figure.
