# G-14 — Refusal-mapping matrix of the activation switch-on surfaces

Gap **G-14** of the team repository's `docs/security-coverage.md` (row added 24 Nov on the PM's
order). Class: **TOOL** (D-184/D-186 ratchet). Mechanical: no model, no network, no clock, no
database.

> A new refusal tuple of an activation fence has no typed HTTP mapping on all switch-on surfaces.

The class cost two pilot tasks (G16 T-2604, G14 T-2597) and a 500 in between: a fence returned a new
`{:error, ...}` tuple, one surface had no clause for it, and the catch-all answered
`internal_error` for what is the tenant's own mistake.

## Files

- Probe: `test/letflow/security_probe/g14_refusal_mapping_matrix_test.exs`
  (`@moduletag :security_probe`, `@moduletag :unit`, `probe_cost_s: 30`).
- Derivation: `test/support/g14_refusal_matrix.ex` (`Letflow.Support.G14RefusalMatrix`).

## What is derived (nothing is a hand list)

| Input | Derived from |
|---|---|
| The switch-on surfaces | every `render_*` function of `lib/letflow/routers/*.ex` whose clauses map activation refusals (`render_activate`, `render_reactivate`, `render_rollback`, `render_apply`, `render_promote`, `render_override_activate_error`) |
| The refusal tuples | the fence functions of `lib/letflow/definitions.ex` (`check_notify_calls`, `check_step_mappings`, `check_test_cases`, `check_outbound_destinations`, and any later fence in the same `with` chains): their bodies and `@spec` error shapes |
| The Response helper of a tuple | `lib/letflow/api/response.ex`: the helper named like the tuple; its violation keys are read from its own head and body |
| Which surface can receive which tuple | the call graph of the surface's context path (a surface that does not run a fence cannot receive its refusal) |

For every reachable (surface x tuple) the probe copies the router with its renderers made public,
drives the renderer with a synthetic tuple built from the clause's own pattern, and asserts status
422, the stable `error` code and the violations list.

## Non-vacuity

`a refusal tuple without a mapping is caught` and `the seeded synthetic tuple makes the matrix
verdict fail` drive a synthetic fence tuple with no clause through the SAME verdict function the
real-tree test uses: it must fail. Mutation check: delete any clause added above and the real-tree
test goes red naming the surface and the tuple.

## Adding a fence

Add the fence to the `with` chain of its activation path and a clause on every surface that runs it
(the probe names the missing surface). A new fence without a mapping fails CI before review.
