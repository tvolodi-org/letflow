# G-11 — the route inventory and the secret scan on the real tree

Class: TOOL (D-184/D-186). The probe is a mechanical test (no model): it runs the two scanners the
repository already owns against the repository itself. It runs under the `:security_probe` tag and
is a mandatory test in the bounded standard backend selection.

**The probe is two files, because the two tools cost very different amounts.** The route inventory
takes about 1.5 s on the real tree; the secret scan of the tracked tree takes about 46 s on this
host (35 s on an idle one, 71 s on a loaded one). The operator's `lf.sh` hook gives every tagged
probe an equal share of the five-minute checks budget (`share = 300 s / (the number of tagged
probe files)`), so one file for both would put the cheap tool out of the checks step as well. The
split keeps the cheap half in the checks step and the expensive half in CI:

| file | declared cost | measured | where it runs |
|---|---|---|---|
| `test/letflow/security_probe/g11_route_inventory_probe_test.exs` | `probe_cost_s: 10` | 7.4 s for the module | the checks step of every backend change, the CI backend gate, the nightly run |
| `test/letflow/security_probe/g11_secret_scan_probe_test.exs` | `probe_cost_s: 90` | 48.9 s for the module (the scan alone: 46 s) | the CI backend gate of every backend change, the nightly run |

The gap it closes (team repository, `docs/security-coverage.md`, G-11): `scripts/uat/check_routes.py`
was exercised only on fake checkouts built by `test/scripts/check_routes_test.exs`, and
`scripts/oss_audit/` had no CI invocation at all. A tool that is only tested on fixtures proves
nothing about the tree it guards, and the coverage map records both tools as "not a real-tree CI
step".

## What is derived

- The **route inventory** (`scripts/uat/check_routes.py`) is the mechanical route inventory of
  D-170: every route must declare how it is authenticated, how it is tenant-scoped and which
  permission guards it, and every route must be referenced by a business-process task or an
  orphan row. The probe runs it on the real tree and fails when it reports a gap, an uncovered
  route, an error or a write-target violation.
- The **secret scan** (`scripts/oss_audit/oss_audit.sh`) is the read-only scanner of T-1597. The
  probe runs its tree scope on the tracked tree and fails when the scan is not COMPLETE or when it
  reports a secret-class finding the reviewed triage list does not carry.
- The **triage list** (`test/fixtures/security_probes/g11_secret_scan_triage.txt`) is the review
  record of the findings the scanner already reports: one line per finding (`rule`, `path`,
  `count`). It holds no secret material — a rule id, a path and a number — because the scanner's
  own output (its masked hints) must stay out of the repository (`scripts/oss_audit/README.md`).
  A finding that is not listed, or a listed finding that occurs more often than it did when it
  was reviewed, fails the probe: the tree then holds a secret nobody has triaged.
- The **gated rules** are the secret-class rules of the scanner: S01–S12 (private key, cloud
  provider keys, provider tokens, a JWT, a connection string with a password) over the whole
  tracked tree, plus S13 (a password-like assignment) outside `test/` and `handoffs/` — those two
  directories hold fixture values and agent run logs by design, and the credential-shaped rules
  still apply there. The PII, infrastructure and wording rules (P01, P02, I01, I02, I03, N01,
  N02) are not gated: a personal-data policy is an owner decision, not a secret leak.
- The probe is pure: no model, no database, no network, no clock. The fake values of the seeded
  cases are built by concatenation at run time, so no secret-shaped literal sits in the test file
  (the secret scan reads that file).
- The secret-scan file carries `@moduletag timeout: 300_000`: the scan of the tracked tree needs
  35–70 s on this host and more on a loaded one, and the ExUnit default of 60 s per test killed
  the probe once (a run of the tagged set on a loaded host). The route file carries
  `timeout: 120_000` for the same reason on a slower host.

## Where it runs

- `scripts/ci_select_tests.py` lists **both** files in `STANDARD_SECURITY_PROBE_TESTS`: they are
  mandatory tests of every bounded backend run, so the required `Backend gate (mix letflow.check)`
  runs them on every backend change. That is the enforcement the coverage map asks for ("in CI").
- The team's checks step runs them as changed test files.
- The operator's `lf.sh` hook runs the tagged set (`mix test --only security_probe`). It gives
  every tagged probe an equal share of the five-minute budget: on this tree there are 15 tagged
  probe files, so the share is `300 / 15 = 20 s`.
  - The route half declares 10 s and **runs in the checks step** of every backend change.
  - The secret-scan half declares 90 s, which is over its share, so the hook **defers it to CI
    and to the nightly job** (PM rule 2 of 2026-11-22: "a probe slower than its share runs in CI
    and a nightly job instead (not in checks)"). This is the rule of the budget, not a choice of
    this probe: a full-tree secret scan costs more than an equal share of five minutes as soon as
    the tagged set holds a dozen probes. (The four G-01 shards, 22 s each, are over the same
    share for the same reason.)
- The probe is a pure file scan, so it needs no database and no service: it runs in the shard, in
  the checks step and in the nightly run alike.

N1 builds its broken variant from the **real tree**: the probe copies the files the inventory
reads (the router sources, the pipeline that mounts them, the business-process documents and the
module packs), proves that the copy passes, and then adds one undeclared route to a copy of a
router. The failure is caused by the seeded route, not by the copy.

## What the probe does not cover

- The **history** of the repository. The probe runs the tree scope only, because the history scan
  of the whole repository is a scheduled job, not a per-change gate. The scanner can do it:
  `bash scripts/oss_audit/oss_audit.sh --history --budget-seconds 900` (a bounded history scan on
  a scheduled path is what the coverage map asks for in §3.7; it is not this probe).
- A **password-like assignment in `test/` or `handoffs/`**. Those directories hold fixture values
  and agent run logs by design; their S13 findings are not gated. A credential-shaped value there
  is still caught (S01–S12 apply to the whole tree).
- The **PII, infrastructure and wording rules** (P01, P02, I01, I02, I03, N01, N02). They are
  findings of a different kind, and gating them would be a policy decision of the owner.
- The **blind spot of a count-based triage list**: a secret added to a file that already carries a
  triaged finding of the same rule, together with the removal of another one of that rule in the
  same file, keeps the count and is not seen. The gate sees every new file, every new rule and
  every growth of a triaged count.
- The **route inventory is a text scan** of the router sources: a route that is declared in a way
  the scanner does not read is not in the inventory. The probe proves the inventory is not empty
  and that it holds at least one route per route declaration it can see.
- **A web-only or docs-only change**: the backend gate (and with it the probe) runs when a changed
  path matches `BACKEND_PATHS_RE` (`scripts/ci_changed_paths.sh`). The scan itself reads `web/`
  and `docs/`, so a secret in those trees is caught by the backend change that touches them, but
  a change that touches nothing under the backend paths does not start the backend gate at all.

## Running and refreshing

```sh
mix test test/letflow/security_probe/g11_route_inventory_probe_test.exs
mix test test/letflow/security_probe/g11_secret_scan_probe_test.exs
```

The two tools alone (from the repository root):

```sh
python3 -I -B scripts/uat/check_routes.py --json
bash scripts/oss_audit/oss_audit.sh --tree --format json
```

To refresh the triage list after a reviewed change of the tree, run the scanner, keep the gated
findings (S01–S12 everywhere, S13 outside `test/` and `handoffs/`) and write one
`rule<TAB>path<TAB>count` line each. Inspect the diff and account for every added, removed or
changed line in the review: a refresh is not a way to bypass a finding.
