# Test spec — ISS-0287: connection-pool headroom clamp fix

**Run:** WF03-ISS0287-20260823, branch `feature/WF03-ISS0287-20260823`.
**Implementation commit under test:** `39c7364` (fix), parent `cb2cdae` (pre-fix,
design-only) on this branch.
**Test file:** `test/scripts/test_parallel_pool_sizing_test.sh` (REMOVED by PR #2459, GH #2442, as red on main and never run by CI; history at a9af273a0). The coverage is restored in `test/scripts/test_parallel_pool_behaviour_test.exs` (GH #2460), a behavioural ExUnit test that runs the real script with a stub `mix` and a fake `psql`, with no `eval`. The sections below describe the removed file and are kept as history: the replacement drives the whole script instead of extracting and `eval`ing the Step 1.5 block, so the extraction guards below no longer apply.

## Why a standalone shell test, not ExUnit

`scripts/test_parallel.sh`'s Step 1.5 clamp formula is pure POSIX-shell arithmetic
that runs *before* any Elixir process starts (it computes `TEST_POOL_SIZE`, which
`mix test` later reads as an env var). There is no Elixir module wrapping this
logic to call from ExUnit. Searched the repo for a prior shell-script-testing
convention (`bats` anywhere under `test/` or `scripts/`, any existing `*_test.sh`,
any `System.cmd`-based ExUnit harness shelling out to `test_parallel.sh`) and found
none — this file establishes the pattern rather than following an existing one.

The test extracts Step 1.5's arithmetic block verbatim from the real
`scripts/test_parallel.sh` (via that script's own `# --- Step 1.5:` / `# --- Step
2:` comment markers) and `eval`s it in a controlled subshell with `N` and the
relevant env vars set, rather than hand-duplicating the formula. This means the
test always exercises whatever the script currently says, not a copy that can
silently drift out of sync with it.

## Acceptance criteria and test cases

The design doc (`lib/letflow/design/iss0287-connection-pool-headroom-fix.md`
§2.2/§3) requires: (a) the formula widened to
`usable_ceiling = TEST_MAX_CONNECTIONS - TEST_SUPERUSER_RESERVED`,
`budget = usable_ceiling - TEST_CONNECTION_HEADROOM - TEST_NONPOOL_CONNECTION_RESERVE`;
(b) the two new knobs validated the same way as the existing `TEST_MAX_CONNECTIONS`
knob (non-negative integer, hard `ERROR` + exit 1 on malformed input); (c) no
regression at N=16, decision 0009's own original verification host.

1. **N=4, all defaults → TEST_POOL_SIZE=21.** Proves the new formula is what
   actually runs at the documented ISS-0219 remedy value. Recomputed independently
   of the design doc: `usable_ceiling = 100 - 3 = 97`, `budget = 97 - 10 - 2 = 85`,
   `computed = 85 / 4 = 21` (integer division). This is the primary "does the fix
   do what it says" assertion, and it is the case that fails against the pre-fix
   script (which computes 22, not 21).

2. **N=16, all defaults → TEST_POOL_SIZE=5.** Proves no regression at the host
   decision 0009 was originally verified against. `usable_ceiling = 97`,
   `budget = 85`, `computed = 85 / 16 = 5` (int div) — the same result the
   pre-fix formula also produces at N=16 (`budget = 90`, `computed = 90 / 16 = 5`),
   so this case is expected to pass unchanged both pre-fix and post-fix; it exists
   to catch a fix that accidentally changes N=16 behavior, not to distinguish
   pre/post fix by itself.

3. **N=4, `TEST_SUPERUSER_RESERVED=0`, `TEST_NONPOOL_CONNECTION_RESERVE=0` →
   TEST_POOL_SIZE=22.** Neutralizing both new knobs to 0 must reproduce the exact
   OLD pre-fix value (22) under the NEW formula's code path — proving that the two
   new knobs, not some other unrelated change, are what shifted the N=4-defaults
   result from 22 to 21. Without this case, cases 1 and 2 alone couldn't rule out
   an unrelated arithmetic change happening to also land on 21.

4. **Malformed `TEST_SUPERUSER_RESERVED` (e.g. `abc`) → ERROR + exit 1.** Design
   doc §2.2 requires the two new knobs validated the same way the pre-existing
   `TEST_MAX_CONNECTIONS` knob already is. Asserts the exact error-message
   substring the script prints, and that eval exits non-zero.

5. **Malformed `TEST_NONPOOL_CONNECTION_RESERVE` (e.g. `xyz`) → ERROR + exit 1.**
   Same rule, other knob — validated independently since the script validates them
   in two separate `if` blocks (a bug in one block's regex wouldn't necessarily
   show up in the other's).

## Extraction-guard hardening (rework, TEST-DESIGN-VALIDATOR gate, attempt 2)

TEST-DESIGN-VALIDATOR FAILed the first version of this test on the extraction
mechanism, not the test cases: the original awk extraction (`/^# --- Step 1\.5:/` to
start, `/^# --- Step 2:/` to stop) only tracked "did the start marker ever fire" and
relied on a weak sanity check ("output non-empty and contains `computed_pool`"). The
validator demonstrated concretely that if `scripts/test_parallel.sh`'s `# --- Step 2:`
comment header is ever reworded, the awk program runs off EOF instead of stopping,
silently capturing the rest of the script (Step 2's partition-launch logic, Step 3's
`wait`, Step 4's aggregation, Step 5's exit) — and the weak check still passes,
because the substring `computed_pool` is still present near the top of the
over-captured block. `eval`ing that over-capture would actually spawn background
`mix test` partitions, turning a lightweight read-only arithmetic test into something
that runs the whole suite.

Two independent guards now close that gap, both in `test/scripts/test_parallel_pool_sizing_test.sh`:

1. **Explicit closed-vs-EOF tracking in the awk program itself.** The awk program
   sets `closed=1` and does `exit 0` only when it hits the end marker while still
   inside the captured region; an `END` block does `exit 1` if `closed` was never
   set (i.e. awk ran off EOF still "inside" the block). The shell checks awk's own
   process exit code (`awk_rc`) separately from the captured text — not inferred
   from a substring test on the text — and hard-fails with a clear message before
   ever touching `eval` if `awk_rc != 0`.
2. **Positive bound on the captured block**, as a second, independent line of
   defense even if (1) were somehow bypassed: the block must be `<= 90` lines (the
   real Step 1.5 block is 64 lines as of this writing; an EOF over-capture on the
   real script would be ~218 lines), and must not contain any token unique to Step 2
   or later (`mix test`, `wait "`, `mktemp -d`, `# --- Step 3`, `# --- Step 4`,
   `# --- Step 5`). Either check tripping is a loud failure, no eval attempted.

**Scratch-file negative test proving the guard works** (validator's own bar: "would
this catch a reworded end-marker"), run against a throwaway copy — the real
`scripts/test_parallel.sh` on this branch was never modified:

## Extension — ISS-0287 (reopened): N-scaling coverage gap (WF03-ISS0287-20260928)

**Run:** WF03-ISS0287-20260928, branch `fix/ISS0287-pool-headroom-n-scaling-20260928`.
**Implementation commit under test:** `b7d26898` ("instrumentation-first N-scaling
response for pool-headroom clamp").
**Design doc:** `lib/letflow/design/iss0287-pool-headroom-n-scaling.md` §5
("Test-designer notes") — read in full before writing these cases; this section
implements that §5 checklist item by item.

### Why this extension exists

The reopening's own root cause (design doc §3) is that the original fix's
regression test validated exactly two N values — 4 and 16 — and never N=8, the
value that actually reproduced the flake. §3 also proves algebraically that the
clamp's worst-case bound holds at *every* N (not just 4 and 16), so the coverage
gap, not a formula defect, is what let the issue through undetected. This
extension closes that gap directly: it does not change the production formula (see
`scripts/test_parallel.sh` Step 1.5, the `per_partition_headroom` term added at
default `0`, a no-op) — it changes only what the regression test proves about it.

### New acceptance criteria and test cases (cases 6-15)

**Case 6 (a-m): N-sweep, `TEST_PER_PARTITION_HEADROOM` unset (default 0), N ∈
{1,2,3,4,5,6,7,8,9,12,16,24,32}.** Each case asserts BOTH the computed
`TEST_POOL_SIZE` (independently hand-computed as `floor(82/N)`, clamped to
`TEST_MIN_POOL_SIZE=2`) and the intermediate `budget` value (must be exactly 82 at
every N, since `N*0=0`). The budget assertion is the direct proof of the design's
own no-op claim ("`TEST_PER_PARTITION_HEADROOM`'s default (0) produces
byte-identical output to what the PRE-fix formula would have computed") as a
permanent regression test, not a one-time manual `eval` check: any future edit
that makes the default term non-zero, or makes it depend on anything other than
`N * TEST_PER_PARTITION_HEADROOM`, changes `budget` away from 82 at every N
simultaneously and fails all 13 sub-cases at once (verified — see "Mutation-proof
result" below). Case 6h (N=8) is a dedicated, explicitly-named regression guard
tied to the reopening's own N, per the design's explicit instruction to add one
even though the algebra says it should already pass unmodified.

**Case 7 (a-m): same N-sweep, `TEST_PER_PARTITION_HEADROOM=1` (a nonzero test
value).** Proves the knob is live, not dead code: `budget` must shrink by exactly
`N*1` at every N (`budget = 82 - N`), and `computed_pool` shrinks by exactly `1`
at every N except N=32, where `floor(50/32)=1` falls below `TEST_MIN_POOL_SIZE=2`
and the WARN-clamp fires instead (`TEST_POOL_SIZE` clamped to 2, `budget` still
50) — this is the sweep's own edge case exercising the clamp path together with
the new knob for the first time, confirmed to still exit 0 (WARN, not fail).
Case 7h (N=8, 10→9) is the reopening's own N under the live knob.

**Case 8: dynamic host-derived N.** Reads `nproc` (falling back to `getconf
_NPROCESSORS_ONLN`) at test-run time and asserts the same invariant for whatever N
this host actually auto-derives, with the expected value computed independently
in bash arithmetic from that live N (not hardcoded) — this is the case the design
doc explicitly calls out as "the one that would have caught a formula that only
happens to work at the two values anyone had thought to hand-pick," since N=4 and
N=16 were checked historically only because nobody's dev host had 8 cores at the
time. On this checkout, `nproc` derives N=8, so this case is currently identical
in content to case 6h/7h, but on a different host it independently exercises
whatever N that host has.

**Cases 9-12: Step 1.4 host-ceiling verification (ISS-0287 §4.2), WARN-not-fail.**
Step 1.4 queries the live Postgres instance's `max_connections` and
`superuser_reserved_connections` and WARNs (never hard-fails) on a mismatch
against the assumed defaults. These cases don't run against a live Postgres — a
fake `psql` executable is placed on a controlled, restricted `PATH` (built from
symlinks to only the specific tools the block needs: `tr`, and `bash`/`env` so the
fake `psql`'s own `#!/usr/bin/env bash` shebang can resolve under a deliberately
narrowed `PATH` — see the "found during this work" note below), so the *script
logic* is what's under test, not a real database:
- **9**: no `psql` on `PATH` at all → WARN "psql not found ... skipping", exit 0.
- **10**: `psql` present, both values match assumed defaults (100/3) → "host
  ceiling verified" message, no mismatch WARN.
- **11**: `psql` present, `max_connections` mismatched (90 vs assumed 100) →
  exact mismatch-WARN substring, exit 0 (config-drift reported, never
  hard-failed).
- **12**: `psql` present but every query fails (simulating an unreachable server)
  → "could not reach Postgres" WARN, exit 0.

All four assert exit 0 unconditionally — this itself is the "WARN-not-fail"
property: Step 1.4 is never allowed to abort the run over a diagnostic query,
matching the design's explicit rationale that a config-drift gap is not an
arithmetic gap and must never gate the run.

**Cases 13-15: opt-in connection sampler (ISS-0287 §4.3), gating only.** The
sampler must be off by default (zero cost on an ordinary run) and must fail soft
if requested without `psql` available:
- **13**: `TEST_PARALLEL_SAMPLE_CONNECTIONS` unset (default) → sampler never
  starts, no "connection sampler enabled" message. Proves "opt-in" really means
  off unless explicitly requested.
- **14**: set, but `psql` missing → WARN "sampler not started", still no
  "enabled" message. Proves the missing-diagnostic-tool case fails soft instead
  of crashing the run.
- **15**: set AND `psql` present → the sampler genuinely starts (a real
  background polling loop, captured pid non-empty), proving the knob is
  actually live rather than a gate that always short-circuits to "not started."
  The captured pid is killed immediately after assertion so the test suite never
  leaves a runaway background process; confirmed via `ps aux | grep
  letflow_pool_sizing_test` showing nothing after a full test-file run (see
  "Mutation-proof result" section below for the full transcript check).

### A bug found and fixed while writing case 15 (worth recording, not just noting in passing)

The first version of case 15 hung indefinitely (killed by a 60s timeout). Root
cause: capturing the sampler block's output via ordinary `out=$(...)` command
substitution (a pipe) doesn't return until every process holding the pipe's write
end closes it — and the background polling loop the sampler starts
(`while true; do ...; sleep 1; done &`) inherits that same write end and never
closes it (by design, it runs until killed). Fix: redirect that subshell's
stdout/stderr to a real temp file instead of a pipe (`... >"$out_file" 2>&1`,
then `cat` the file afterward) — a regular file has no such "wait for last
writer to close" semantics, so the parent returns as soon as its own foreground
work (the `eval` plus one `echo`) finishes, leaving the backgrounded loop to
append to the file independently until the test kills it. This is recorded in an
inline comment in the test file itself (`run_sampler_case`), not just here, so a
future editor sees it at the point where a naive rewrite would reintroduce it.

A second, smaller bug in the same case: restricting `PATH` to just a `tr` symlink
(to keep the "psql not found" cases deterministic regardless of what's actually
installed on the host running this test) also broke the *fake psql itself* when
it WAS supposed to be present — the fake psql's own `#!/usr/bin/env bash` shebang
needs `env` and `bash` reachable via `PATH` to exec at all, and a `PATH` with
neither present made every invocation of the fake psql silently fail to exec,
which read from Step 1.4/the sampler's own perspective as "server unreachable" —
indistinguishable from the deliberate case 12 without this fix. Both `bash` and
`env` (and, for the sampler's real polling loop, `date`) are now included in the
restricted-`PATH` tool set for cases that need psql to actually run. Caught by
actually running the test file, not assumed correct because the individual
pieces looked right in isolation.

### Explicitly out of scope for this test file (per design §5, left to
whoever runs live verification)

Design doc §5 items 4-6 (running `scripts/test_parallel.sh` with
`TEST_PARALLEL_N=8` five times against a real Postgres, running with
`TEST_PARALLEL_SAMPLE_CONNECTIONS=1` and attaching the resulting time series, and
confirming the live host's actual `max_connections`/`superuser_reserved_connections`)
are empirical, live-environment verification steps, not something an automated
unit-style regression test can prove — they require a real running suite against
a real Postgres instance and are the responsibility of whoever executes that
verification (ELIXIR-DEV/REVIEWER's own verification pass, or a follow-up
TEST-RUNNER/UAT pass), not TEST-DESIGNER's test-file coverage. This is stated
explicitly per core-directives.md rather than silently dropped.
