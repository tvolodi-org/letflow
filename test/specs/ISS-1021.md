# Test Spec: ISS-1021 -- Top-level key allowlist for `serialised_plan` on `GET /promotions/:id/context`

**Issue:** ISS-1021 (`docs/issues/ISS-1021.yaml`; Q-1003 / GH #2291; the queue's own number for it is ISS-1003, which
clashes with the local numbering). Design: `lib/letflow/design/iss1021-context-plan-allowlist.md` (section 5 maps the
criteria, section 6 lists the tests). Workflow: WF-03 regression. **Tier:** integration (real Postgres, real tenant
schemas, router-level dispatch, the real `PromotionReviewStore.insert_review/2`; no mocks). All modules `async: false`
(VM-global platform pin; restored by the fixture's `on_exit`). No wall-clock or unseeded-random dependence.

Fail-first: against the old key-suffix walk (`shape_tenant_ids/2`) the rewritten T-8 tests fail (`source_definition_id`
and `meta` were kept) and the T-11 odd-key, unknown-key, non-map, legacy and definition-id cases fail. Measured
by mutant M1 below (allowlist ignored: the decoded plan passes through unshaped, which is a superset of what the old walk
let through for those inputs): 11 of the 22 tests fail.

Malformed and legacy plans cannot go through `Scope.seed_review!/4` (it merges overrides into the seven default keys, and
`insert_review/2` reads `plan.process_key` and verifies the digest). They use ONE recipe, `overwrite_plan!/3`: seed a
normal review, then `Repo.update_all` the `serialised_plan` column verbatim with `prefix: fixture.schema_name`.

## KNOWN residuals (accepted; NOT tested as failures)

* R1 (standing TRACKED exception, INV-10; Q-1005 / GH #2297 / ISS-1023): `entries` graph JSON is copied as stored, pinned as documentation by
  `entries_kept_exactly_as_stored` and T-8. It is NOT "the caller's own tenant data" in every case: for an operator-created review naming
  foreign tenants B and C, held in the platform tenant's schema, `entries` carries B's and C's definition graph content, readable by a
  non-operator holding `:PromotionsRead` there and by readers of legacy rows. No worse than before this change. The issue file of
  ISS-1023 ships with its own fix PR. Whether non-admin platform-tenant users hold `:PromotionsRead` is unverified and belongs to it.
* R2 (CLOSED by this change): the key-suffix limitation on `/context`.
* R3 (unchanged, other routes): the `teardown_error` text on the review routes.
* R4 (accepted): `process_key` and `base_version` are tenant-authored strings kept as plain scalars; a tenant author could place any text in them.
* R5 (accepted by SECURITY-REVIEWER): `requested_by` stays in the nine-key envelope; it is a user id of the review's own schema.
* R6 (accepted by SECURITY-REVIEWER): `plan_digest` is returned for every caller and covers the unshaped plan; a non-operator cannot verify it from the shaped plan (already so today).
* R7 (behaviour change, intended): a non-operator reader loses a definition id whose side's tenant is foreign, and any unknown top-level key of legacy plans.
* OQ-3 (not tested): SQL NULL or invalid JSON in the `serialised_plan` column still raises in `Jason.decode!/1` (HTTP 500) for both views; not producible through the application.

## Note (ISS-1029, Q-1011)

A non-party non-operator (neither stored `source_tenant_id` nor `target_tenant_id` is the caller's tenant, or the ids are
unreadable) gets the nonexistent-review 404 from `GET /promotions/:id/context`. A named PARTY (source OR target is the
caller's tenant) is unchanged: the foreign-id shaping in this spec stays LIVE for it (200, own-side ids only), as do the
operator branch and the pin-unset case. The T-8/T-11 tests in this spec that read a review with one own side pass as
written; only non-party and id-less cases moved to the 404. See `test/specs/ISS-1029.md`.
