# REQ-394 — Per-entity-type record authorization, with denial indistinguishable from a genuinely empty entity type

## Requirement text (acceptance criteria, `docs/requirements.yaml`)

1. a user without access to entity type X and a user with access to a
   genuinely empty entity type Y of the same shape receive byte-identical
   `POST /entities/query` response envelopes (status, body shape, headers)
   for their respective requests — a test asserts this directly, comparing
   the two responses
2. the same indistinguishability holds for
   `GET /entities/definitions/active/:name` (and its two sibling
   definition-read routes) — a test asserts a caller without per-type
   access cannot learn the restricted type's field list any more than they
   can learn a nonexistent type's
3. a query against a genuinely nonexistent entity type and a query against
   an existing-but-unauthorized entity type, by the same caller, are
   indistinguishable — a test asserts this for both the query and
   definition-read routes
4. an existing caller with only the coarse route-level permission and no
   per-type restriction at all is completely unaffected — the full existing
   test suite for `POST /entities/query`, definitions reads, and
   `FieldGrants` passes unmodified
5. a design doc precedes implementation, is validated by
   CODE-DESIGN-VALIDATOR, and is signed off by SECURITY-REVIEWER before
   merge, per this requirement's security-relevant status
6. `mix compile --warnings-as-errors` and `mix test` both pass, with real
   output quoted

See `lib/letflow/design/req394-per-entity-type-authorization.md` for the
full design. Design/security sign-off (AC5) already completed before this
turn — this spec covers AC1-AC4 and AC6.

## Acceptance criteria → test-case map

### AC1 — denied-type and genuinely-empty-authorized-type `POST /entities/query` responses are byte-identical

`test/letflow/routers/entities_test.exs`, describe `"REQ-394 AC1 --
denied-type and genuinely-empty-authorized-type POST /entities/query
responses are byte-identical"`:

- Two distinct users in the same tenant. User 1 queries `restricted_type`,
  a type restricted via an `entity_type_restrictions` row with no matching
  `user_entity_type_grants` row for user 1 — denied. User 2 queries
  `empty_type`, an unrestricted, genuinely zero-row type of the same field
  shape.
- `restricted_type` genuinely HAS one seeded record (`"should never
  surface"`) — this is the load-bearing part of the test design: it
  proves the denial actually filters a real record out, rather than
  merely happening to coincide with a type that would have been empty
  anyway (a test that skipped seeding a record here would still pass
  against code where `TypeAccess` never ran at all — see the mutation
  check below, which is exactly the scenario this seeded record catches).
- `x-trace-id` is pinned identically across both requests
  (`maybe_pin_trace_id/2`, this file's own established convention) so the
  final comparison is a genuine whole-response comparison, not one that
  incidentally differs only in per-request correlation data.
- One assertion compares `{status, resp_body, sorted resp_headers}` as a
  single tuple across both responses — not separate assertions that could
  each pass independently while the two envelopes actually differ.

### AC2 — same indistinguishability for the three definitions-read routes

`test/letflow/routers/entities_test.exs`, describe `"REQ-394 AC2 --
denied-type and nonexistent-type responses are byte-identical on all
three definitions-read routes"` — one test per route:

- `GET /entities/definitions/active/:name`, `GET
  /entities/definitions/by-name/:name`, `GET /entities/definitions/:id`.
- Each test restricts a real, active entity type (a distinct field name
  per test — `secret_field`/`secret_by_id_field` — so the `refute
  resp_body =~ "<field name>"` assertion cannot accidentally match an
  RFC 9457 problem-document member like `"title"`), denies the caller (no
  matching grant), and compares the denied response against a request for
  a name/id that does not exist at all — same pinned-trace, whole-tuple
  comparison as AC1.
- Each test also asserts the field name never appears in the denied
  response's raw bytes at all, which is the direct test of AC2's "cannot
  learn the restricted type's field list" wording — not merely implied by
  the byte-identity assertion.

### AC3 — nonexistent type and existing-but-unauthorized type are indistinguishable to the SAME caller, both route families

`test/letflow/routers/entities_test.exs`, describe `"REQ-394 AC3 --
nonexistent type and existing-but-unauthorized type are indistinguishable
to the same caller"`:

- This is a distinct scenario from AC1/AC2 (which each compare TWO
  different callers/types): here ONE caller queries a genuinely
  nonexistent type and a real-but-restricted type in turn, and the two
  responses must be indistinguishable to that same caller.
- `POST /entities/query` test: restricted type genuinely has a seeded
  record (same "should never surface" pattern as AC1); compares the
  unauthorized-existing-type response against a nonexistent-type response,
  pinned trace, whole-tuple.
- `GET /entities/definitions/active/:name` test: same shape, definitions
  route.

### AC4 — a coarse-permission-only caller with no per-type restriction is unaffected

`test/letflow/routers/entities_test.exs`, describe `"REQ-394 AC4 -- a
caller with only the coarse route-level permission and no per-type
restriction rows is completely unaffected"`:

- Explicit positive-path test: a tenant that never inserts a single
  `entity_type_restrictions` row. The caller queries `widget` and reads
  its active definition — both succeed exactly as before this requirement,
  with real field data visible (`item["field_values"]["title"] ==
  "unrestricted"`, `definition_map(...)["name"] == "widget"`).
- The stronger half of AC4 ("the full existing test suite ... passes
  unmodified") is verified by re-running the pre-existing test files this
  requirement's design named as affected —
  `test/letflow/routers/entities_test.exs` (2415 pre-existing lines,
  untouched except for the design's own two flagged, deliberate updates —
  see "Design-flagged pre-existing test updates" below),
  `test/letflow/entities/query_cursor_field_grants_test.exs`, and
  `test/letflow/support/tenant_fixture_test.exs` — all green together with
  the new REQ-394 coverage (see "Verification run" below).
- A companion test, describe `"REQ-394 -- a per-user grant restores full
  access to a restricted type, end to end through the real routes"`,
  additionally proves the grant-override half of the grant model actually
  works over the real HTTP routes (not just the `TypeAccess.authorized?/3`
  unit level, AC5) — a user WITH a matching `user_entity_type_grants` row
  queries and reads a restricted type normally. This also exercises
  `insert_type_grant!/3`, keeping that helper genuinely used rather than
  dead code (per `docs/anti-patterns.md`'s recurring "helper defined but
  never exercised" class of finding).

### AC5 — `TypeAccess.authorized?/3` unit coverage (not itself an acceptance criterion in the requirement's own numbering, but the requirement's brief names it explicitly)

New file `test/letflow/entities/type_access_test.exs` — unit tests for
`Letflow.Entities.TypeAccess.authorized?/3` directly, against a real
Postgres tenant schema, not through HTTP (the router-level tests above
already cover the HTTP integration):

- **Default-allow**: a type with zero `entity_type_restrictions` rows is
  `{:ok, :allowed}` for any user. A second test confirms a restriction on
  one type does not deny an unrelated type.
- **Explicit restriction, no per-user override**: `{:ok, :denied}`.
- **Explicit restriction WITH a per-user override**: `{:ok, :allowed}`. A
  companion test confirms the override is genuinely per-user — a second
  user with no grant row is still denied on the same restricted type.
- **Tenant-scoping**: two independent tenants, same entity-type STRING
  name. A restriction row in tenant A does not deny that name in tenant
  B (two tests: one for a restriction-only row, one specifically for a
  restriction+grant pair, reusing the same raw user UUID across both
  tenant schemas to make sure isolation comes from the schema `prefix`,
  not from the id namespace happening to differ).
- **Invalid schema**: an unresolvable `prefix` returns
  `{:error, :invalid_schema_name}` rather than raising.
- **Before/after toggle**: the same entity-type name resolves `:allowed`
  before a restriction row exists and `:denied` immediately after, isolating
  the restriction row itself as the causal factor.

## Mutation check (fail-then-pass), performed this turn — AC1/AC3

**This is the single most important check for this requirement**: it
proves the router-level indistinguishability tests actually depend on
`TypeAccess`'s real denial logic, not merely on the seeded fixtures
happening to look identical by construction.

Temporarily changed `Letflow.Entities.TypeAccess.authorized?/3`
(`lib/letflow/entities/type_access.ex`) to always return `{:ok, :allowed}`,
regardless of the `Repo.exists?/2` result — a bypass of the entire
denial check:

```elixir
if Repo.exists?(query, prefix: prefix) do
  {:ok, :allowed}   # mutant: was {:ok, :denied}
else
  {:ok, :allowed}
end
```

Re-ran `mix test test/letflow/routers/entities_test.exs`:
**6 of 89 tests failed** — every REQ-394 test that depends on an actual
denial (AC1's one test, all three AC2 tests, both AC3 tests). AC4's
positive-path and grant-restores-access tests correctly kept passing (they
never depend on denial firing). The AC1 failure's own diff is the clearest
proof of a real, non-vacuous test:

```
code:  assert body_of(denied) == %{"items" => [], "next_cursor" => nil}
left:  %{"items" => [%{... "field_values" => %{"title" => "should never surface"} ...}], ...}
```

— the seeded "should never surface" record genuinely surfaced once the
denial check was bypassed, which is exactly the failure mode a
`TypeAccess`-unaware regression would produce in production. Reverted the
mutation immediately after measuring; `git diff --stat
lib/letflow/entities/type_access.ex` showed no diff post-revert (clean
revert); `mix test test/letflow/routers/entities_test.exs` returned to
`89 passed`, 0 failures.

## Design-flagged pre-existing test updates (already present on this branch, not TEST-DESIGNER's own edits)

Confirmed by reading `lib/letflow/design/req394-per-entity-type-authorization.md`
§2.2/§5 and `git show bd77a129`: ELIXIR-DEV's own implementation commit
already updated the two pre-existing tests the design flagged as a
deliberate, required behavior change (REQ-311's old 404-on-nonexistent-type
assertion for `POST /entities/query`, now 200-empty per AC3) —
`test/letflow/routers/entities_test.exs`'s `"REQ-311 AC5"` and `"REQ-311
AC9 -- INV-5"` describe blocks. TEST-DESIGNER re-verified both still pass
and did not re-author them (they are not new coverage this turn, and
re-editing already-correct, already-reviewed test code would not add
anything).

The design's own §5 also flagged
`test/letflow/entities/query_cursor_field_grants_test.exs`'s chain-order
assertion as needing an update from "four steps" to "five". Read that
test directly (`describe "AC4 -- query internals have exactly one router
consumer"`, `run_query_chain!/1` + `index_of!/2`): it asserts only the
RELATIVE order of three markers (`Compiler.compile(` <
`Cursor.paginate(` < `redact(`) inside the `with` chain, not a literal
step count — (GH #2700: the TypeAccess step is now `RequestAccess.check/4`, ahead of `Compiler.compile`; the chain-order test asserts that) inserting `TypeAccess.authorized?/3` as a fourth clause
between `compile` and `Allowlist.load` does not disturb that relative
order, so the test needed no code change and was confirmed still passing
as-is (see "Verification run" below). The design's flag was itself
correct to raise (a five-vs-four count assertion, had one existed, WOULD
have needed updating) — it just turned out the actual test doesn't encode
a count, only an order.
