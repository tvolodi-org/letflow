## Judgement calls, and what is NOT covered (be explicit)

1. **N6 on the create route.** The create handler's own comparison of the platform prefix with the caller's schema runs
   before its first database read, so no request seam sits between the authorization plug and it; it is reachable only
   by a race (design 3.2 "Defence in depth", PR 1's 403 test and mutant M12). The N6 test therefore drives the two
   operator routes that read the onboarding record first (list and revoke) through a telemetry seam that moves the pin
   mid-request. `PendingAdminGrants.create/3` itself is covered by the forced-failure test (a prefix that names no
   schema). The create route's own 500 branch has no HTTP-level test.
2. **"two users presenting the same verified e-mail: exactly one binds"** is the sequential case (the first binds, the
   second finds the grant consumed). The concurrent case is a separate test and shows the designed fail-closed result:
   with both accounts committed before either bind runs, step 5b sees the other as a holder of the address and BOTH
   binds are abandoned (zero binds, grant open). That is the design's behaviour (7 step 5b), not "exactly one" under
   concurrency; the design text of section 8 ("first commit wins") describes only the case where the second account
   does not exist yet.
3. **F6 (the consume update must change exactly one row)** is exercised by running a revoke INSIDE the bind's own
   transaction (same process and connection, through a telemetry hook on the row-locking select), because a second
   connection cannot revoke a row the bind holds locked. The injected revoke rolls back with the rest, so the assertion
   is that nothing the bind had done (the membership above all) survives; a bind that did not assert the row count
   commits that membership and fails the test (mutant M2).
4. **The empty e-mail claim** case is at the `bind_on_login/5` level with a row inserted directly: JIT refuses an empty
   `email` (`validate_required`), so no token with an empty e-mail ever reaches the bind through the pipeline.
5. **The default `JitProvisioningConfig`** is the only config the login helper uses; the pipeline tests swap `config :letflow, :oidc`'s `:token_verifier` for `PendingAdminTokenVerifierDouble` (restored in `on_exit`).
6. `LETFLOW_OIDC_ADMIN_BIND_UNVERIFIED_REALMS` boot validation is tested by evaluating the real `config/runtime.exs`
   with `Config.Reader.read!/2` under a temporary environment value (restored in `try/after`), not by booting a node.
7. Not covered: a real Keycloak token (the verifier is a test double, as everywhere in this suite), the SPA, load or
   timing of the login path (the design states the indexed probe; no latency assertion is made), and a multi-node
   interleaving (the concurrency tests hold a row lock on one node, which is the guarantee the design relies on).
