## 1. What is being proven, and what is not

The issue's acceptance criterion 3 is "a test leaving data behind does not leak into the
next test (mutation test)". The implementation makes that claim for a **pooled** tenant that
is reused by every test of a module, so the proof has to cover every way a test can leave
the shared schema different from a fresh clone, not just "rows". Each such way is a design
class (M1..M22). A class is covered only if some test **fails when the guarantee is
violated**; section 4 records the mutants that show it.

Not tested here, and why:

| Acceptance criterion | Where it is met instead |
|---|---|
| 1. Instrumented measurement (clone ms, tables per clone, share of test time) | Measured numbers, not behaviour: ISSUE-FIXER's diagnosis (`docs/issues/ISS-1042.yaml` `measurements`) and the permanent `LETFLOW_TENANT_FIXTURE phase=pool_*` marker lines. One test here asserts those marker lines (`outcome=reset`, `outcome=rebuilt`, `closure_added=2`) so they cannot silently disappear. |
| 2. One lever with before/after wall time, 5 runs each | A measurement protocol (design 11.2), executed by TEST-RUNNER. A unit test cannot assert a wall-clock ratio without becoming flaky; the suite deliberately has no timing assertion. |
| 4. No change to required check names, no paid runners | No executable surface: `git diff main -- .github` is empty (checked by RELEASE-VALIDATOR). |

## 2. Why the tests are shaped the way they are

* **No ordering assumption (design 9.1).** Every test starts by asserting the slot is
  pristine, by the pool's own report **and** by independent direct reads
  (`assert_pristine!/1`: row counts of every table via `query_to_xml`, called sequences,
  seed md5 against the live template, keyed public rows, the tenants row), then leaves data
  behind. Whichever test runs next catches a leak from whichever ran before.
* **Deterministic boundary proof (design 9.2).** `recycle_pool!/0` simulates the test
  boundary inside ONE test, so the leak proof does not depend on ExUnit's random order.
  The cross-test pairs (`for n <- 1..3, via <- [:test, :task]`) are in addition.
* **Teeth.** After every mutation the test asserts the pool's report *sees* the mutation
  (exact `dirty_tables`, `dirty_sequences`, `seeds_diverged`, `definition_drift`,
  `public_keyed_rows`, `tenant_row_diverged`), so "pristine next" cannot pass vacuously.
* **Independent oracle.** After every rebuild and several resets the test calls
  `TenantTemplate.assert_clone_parity!/3` (all 13 dimensions, the ISS-0427 oracle) against
  the live template, instead of trusting the pool's own digest.
* **Hooks are driven through `:persistent_term`** (they run in the pool worker, per the
  implementer note), module-keyed and erased in `on_exit`.
* **No wall-clock dependence.** The lock test releases its holder when `pg_stat_activity`
  shows the rebuild's `DROP SCHEMA` waiting on the lock (event-driven; the deadline is only
  an upper bound). The straggler is a transaction that blocks in `receive`.
* **Reviewer R3.** `Letflow.Support.TenantFixturePoolMisorderTest` is a pooled module with
  no attach; it asserts the misorder rejection still FIRES (the `owning_module/0` /
  `test_process?/0` rescues would otherwise silently disable it).

## 4. Fail-first proof (WF-03 "code under test does not exist")

Pre-fix, the pool API does not exist, so every test fails with `UndefinedFunctionError`
(`start_pool!/2` is undefined). That proves the module is new and says nothing about whether
the tests discriminate a correct implementation from a wrong one. Per
`docs/agents/workflows/WF-03_issue_resolving.md` the requirement is satisfied by mutating
the shipped logic. Each mutant below was applied in a throwaway `git worktree` of the
branch (never in the working checkout), the whole file was run, and the file was reverted
with `git checkout --` and verified (`git status --porcelain lib/ test/` empty).

Result: **35 mutants, 35 killed, 0 survivors, 0 compile errors.** The totals are against the
final 57-test file (56 tests + 1 property), every run `--seed 0`, tree verified clean after
each (`git status --porcelain lib/ test/` empty). The runner is
`scratchpad/mutate.py` (mutant list is its `M` table; each mix call takes the machine-wide
`mixlock`).

A first pass against a 55-test version found four survivors, each fixed by a test and then
re-proven killed in the pass above: X07 (reset verify pass: the reset path can only fail
verify when the baseline cannot be reproduced, so a test now corrupts the slot's baseline
seed digest via `:sys.replace_state`, simulating a mid-module template rebuild), X14
(constraint definition: a same-name FK recreate was also caught by the RI trigger function
class G, so `m18b` uses `MATCH FULL`, which only `pg_get_constraintdef` shows), X20 (M9
passed without `lock_timeout` because the client timed out 15 s later; the test now asserts
the logged cause is `lock timeout`) and X27 (the teardown test called `pool_stats/1`, which
itself sets `:auto`; it no longer calls any worker API).

## 5. Residual limits (honest)

* The pool's isolation claim is "proven clean at the final guard"; a foreign writer after
  that instant is only detected and bounded to the owning test (RR-1, M13c). That is asserted
  as documented behaviour, not hidden.
* Fence/straggler detection matches `pg_stat_activity.query` text, which Postgres truncates;
  a wide read whose schema name falls past the cut is invisible (documented in
  `pool_end_fence!/0`). The M14 straggler uses an `INSERT` so the schema is in the first bytes.
* `DISABLE TRIGGER ALL` (M15b) needs a superuser, as the CI and local Docker `letflow` role is.
