Ruling: hypothesis (b') of `lib/letflow/design/gh2630-ci-pg-connection-ceiling.md`, fixes F2 and F4, using the facts measured in hosted CI run 38764249729. Code: `test/support/nested_mix.ex` (new), `.github/workflows/ci.yml` ("Run test shard" env), `scripts/test_parallel.sh` (comments only), `docs/migration/decisions/0009-test-parallel-pool-sizing.md` (GH #2630 addendum).

## What is and is not established
- (b') is a hypothesis consistent with the measurement, NOT a proven cause. Which test spawned the shard-1 fifth process (pid 27329, 19 idle connections) is not proven; its size only fits an inherited pool of 20. F2 caps the two known app-starting spawn sites (login_directory tasks, migrate_tenant_admins).
- The shard-2 process holding 30 connections against a pool of 20 is UNEXPLAINED and NOT addressed by F2. The 86-of-97 worst case excludes it. The spare of 11 absorbs one such partition (92 of 97) but not two (98 of 97 usable), so the fix is safe against it by margin, not by construction.
- No run yet shows the cause gone. Acceptance is 3 consecutive hosted runs with zero strict FATAL matches (`FATAL 53300 \(too_many_connections\)|sorry, too many clients already`).
- A second measurement run (PR #2639, process snapshots) is pending; decision 0009's addendum will get its owner section, or a follow-up is filed.

## Behaviour under test
A `mix` child that a test spawns and that starts the app opens its own `Letflow.Repo` pool sized from `TEST_POOL_SIZE`. Such children get `TEST_POOL_SIZE=4` regardless of the partition's value (`Letflow.Test.NestedMix`, which `executor_test.exs`'s nested `mix test` now also uses). The CI shard step sets `TEST_NONPOOL_CONNECTION_RESERVE=16`, so the clamp gives `TEST_POOL_SIZE=17` at N=4 and a worst case of 4*17 + 4*4 + 2 = 86 of 97 usable. Children that do not start the app (`mix run --no-start`, `mix compile`, `check_boundaries`) are unchanged and are on an explicit allowlist.

Files: `N` = `test/letflow/nested_mix_test.exs`, `K` = `test/scripts/test_parallel_pool_clamp_test.exs`.

## Tests
### F2 (N)
- `the cap is 4`: `NestedMix.pool_size/0 == 4` (the 16 in the reserve is 4 partitions x this).
- `a child does not inherit the ambient partition pool size`: ambient `TEST_POOL_SIZE=20`; a real bash child prints `4`.
- `a caller-supplied TEST_POOL_SIZE is replaced, other env is kept`: `{"TEST_POOL_SIZE","99"}` becomes 4, `KEEP_ME` survives; `env/1` keeps `{name, nil}` unset pairs.
- `every mix-spawning call in test/ is allowlisted or goes through NestedMix.cmd`: scans the whole `test/` tree (code only: heredocs and comment lines dropped) for `System.cmd`/`NestedMix.cmd` of `mix`, `find_executable("mix")`, and `System.shell`/`Port.open` with mix. Allowlisted files (each with a reason: `mix compile`/`run --no-start`/static check, no app start) must have no capped calls; every other hit must have zero bare `System.cmd(mix)`, zero shell/port spawns, and a `NestedMix.cmd(` count equal to its spawn count. Sanity asserts the scan sees the known sites (login_directory, migrate_tenant_admins, executor, mail), and a stale allowlist entry fails. The scan is LEXICAL: TEST-DESIGN-VALIDATOR probes showed it catches a bare `System.cmd("mix", ...)`, `find_executable("mix")` and `System.shell`/`Port.open` with mix in a new file, but it does NOT catch a mix path built elsewhere (`Path.join(...)`), `System.cmd("bash", ["-c", "mix ..."])`, `:os.cmd` or `:erlang.open_port({:spawn, ...})`. It guards against drift, not against a determined bypass.

### F4 (K; hand-computed oracles, the script's clamp block run under bash with `N=4`)
- default reserve 5 -> pool 20 (the pre-fix value); reserve 16 -> pool 17; reserve 0 -> 21.
- worst case: `4*17 + 4*NestedMix.pool_size() + 2 == 86 <= 97`.
- a caller-set `TEST_POOL_SIZE=9` is never overridden.
- `ci.yml` parsed with YamlElixir: `TEST_NONPOOL_CONNECTION_RESERVE` is `"16"` in exactly one place, the `backend_shard` job's `Run test shard` step env, and absent from every other job's job-level and step env.

Zero `53300` in three consecutive hosted runs and the post-change connection peak need CI runs; the spawn sites' children were run locally only.
