# GH #2564: deactivation revokes all the user's API tokens; 0051 N1 zero-tenant-wide-admin guard

Ruling: issue #2564 comment 6174049298 (option 3). Design: `lib/letflow/design/gh2564-deactivation-revokes-tokens.md`. Code: `lib/letflow/identity.ex` (`update_user_profile/3`, `update_user_status/3`, `update_locked_user/6`, `revoke_owner_tokens/3`, `revoke_token_row/5`, `record_guard_refused/2`), `lib/letflow/routers/identity.ex` (`do_patch/3`, `do_status_update/3`).

## Behaviour under test
A status write (`POST /users/:id/status`, or `PATCH /users/:id` carrying `status`, either value) runs in one transaction: `lock_tenant_admins!/1` first, the user row `FOR UPDATE`, the admin count before, the user update, the login-directory step, then (when the user is or becomes inactive) every non-revoked token of the user `FOR UPDATE` in id order, each revoked by a per-row changeset at one shared second-truncated `revoked_at` with one `token.revoke` (`token_audit_state/1` before/after, `cause: "owner_deactivated"` in after), then the user audit entry (actor and trace from the request, plus `revoked_token_count`), then, for a deactivation, the count after. `before > 0 and after == 0` rolls everything back, answers `409 last_tenant_wide_admin`, and writes `tenant_admin.guard_refused` in its own transaction. A failed token revocation rolls back and answers 500. A PATCH without `status` takes no lock and touches no token. Reactivation restores nothing. `DELETE /tokens/:id` is unchanged (`cause` absent).

Files: `N` = `test/letflow/routers/gh2564_deactivation_revokes_tokens_test.exs` (router dispatch with a hand-assigned `auth_context` whose caller is a real user holding no admin source, so the guard sees only the admins a test sets up; old plaintexts through the full `Letflow.Router`). `P` = `test/letflow/api_token_auth_pipeline_test.exs`, `O` = `test/letflow/plugs/iss0736_oidc_live_revocation_test.exs`, `L` = `test/letflow/identity_login_directory_test.exs` (rewritten, see below).

## Acceptance criteria -> tests

### AC1: revoke every non-revoked token in the same transaction; forced failure rolls back both
N, describe "deactivation revokes all the user's tokens":
- `post:` / `patch: status inactive revokes all unrevoked tokens (TA, plain, expired); an already-revoked revoked_at is unchanged`: all three share one `revoked_at`; the earlier-revoked token keeps its own; another user's token is untouched; `revoked_token_count == 3`.
- `post:` / `patch: audit table dropped -> 500, user still active, every token revoked_at nil`: `DROP TABLE audit_entries` inside the test's own sandbox transaction (`sandboxed_tenant!/0`, the `audit_dispositions_test.exs` pattern).
- `revoke step returns {:error, r}: {:error, {:token_revocation_failed, :invalid_schema_name}}, all rolled back`: `ALTER SCHEMA ... RENAME` inside the test's sandbox transaction; every step before the revoke runs on the renamed schema and the first token's `Audit.insert_entry/3` returns `{:error, :invalid_schema_name}`. User stays `:active`, every token `revoked_at` nil. The router's 500 clause for this tag has no HTTP trigger; REVIEWER checks it.

### AC2: one `token.revoke` per token with the metadata, never value/hash/prefix
N, `N tokens -> N token.revoke with cause owner_deactivated, actor, user_id, id, roles, trace_id; no hash, name or lf_tok_; user entry counts N`: 3 tokens -> 3 entries whose `resource_id`s are the 3 token ids; per entry `actor_id` = caller, `trace_id` = request trace, before keys = `token_audit_state/1` keys, after keys = those plus `cause`; `user_id`, `id`, `roles` match; the encoded states contain no `lf_tok_`, `token_hash`, hash, 8-char hash prefix, name or plaintext; the `user.update_status` entry has `revoked_token_count == 3`, actor and trace set.

### AC3: reactivation resurrects nothing
N, describe "reactivation restores no token":
- `deactivate via {post,patch}, reactivate via {post,patch}: TA token stays revoked, old plaintext 401` (4 tests): 200 before, `revoked_at` unchanged by the reactivation, 401 after, one `token.revoke` in total.
- `legacy: inactive user (Repo.update!) with a live token; POST active -> token revoked, 401`: one `token.revoke` with `cause: "owner_deactivated"`, `revoked_token_count == 1`.
- `POST inactive on an already-inactive user with a leftover live token -> token revoked, one token.revoke`.
P (rewritten per the ruling): `reactivating the owner does not resurrect the token: still 401, revoked_at set`.

### AC4: the token list shows `revoked`
N, `GET /tokens after deactivation: status revoked, not owner_inactive; after reactivation still revoked` (`active` before).

### AC5: 0051 N1 counts correctly across deactivation and reactivation
N, describe "zero-tenant-wide-admin guard":
- `{post,patch}: the last tenant-wide admin ({group,token}-held) -> 409, nothing changed, one guard_refused` (4 tests): body `detail == "last_tenant_wide_admin"` naming neither user; user `:active`; the user's other token unrevoked; count still 1; no `token.revoke` and no user entry; exactly one `tenant_admin.guard_refused` with `resource_id` = target, `actor_id` = caller, `trace_id` = request trace, `before_state` nil and `after_state` exactly `{action: "deactivate_user", actor, target_id, reason_code: "last_tenant_wide_admin", counted_admins: 0, trace_id}`.
- `two group-held admins: first deactivation 200, second 409; reactivate the first -> second 200`.
- `token-only admin T plus group admin G: deactivate T 200, reactivate T not counted, deactivate G 409`: T's TA token revoked; after reactivation `tenant_wide_admin_user_ids == [G]`.
- `a tenant with no tenant-wide admin: deactivating a plain user is 200` (transition rule, not `== 0`).
- `the guard_refused write fails -> still 409, logged with error_kind, no value logged`: a sandbox-local trigger raises only on the `tenant_admin.guard_refused` insert; one `:error` log line carrying `error_kind` `Postgrex.Error`, the target id and `deactivate_user`, and not the exception message.
- `record_guard_refused/2 inside Repo.transaction raises ArgumentError, no row written` (and the same call outside a transaction writes it).

### Lock order
N, describe "lock order" (committed tenant, a separate task holds `lock_tenant_admins!/1`):
- `POST status inactive, PATCH status inactive and PATCH status active each wait for the tenant admin lock`: each request is still running after 500 ms, completes 200 after release.
- `PATCH display_name only does not wait for the lock; its entry has no revoked_token_count`: completes while the lock is held; actor set.
- `concurrent deactivation of U and DELETE /tokens of U's token: both complete, one token.revoke`.
