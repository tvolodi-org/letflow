# GH #2557: an inactive owner's API token is refused like a revoked one

Design: `lib/letflow/design/gh2557-inactive-user-api-token.md`. Code: `lib/letflow/identity.ex` (`verify_api_token/2`, `active_user?/1`, `active_user_condition/1`), `lib/letflow/plugs/auth_pipeline.ex` (moduledoc prose only; rendering unchanged).

## Behaviour under test
`Identity.verify_api_token/2` runs one `Repo.one/2` (`prefix:` the server-resolved tenant schema): `ApiToken as: :token` inner-joined to `User as: :owner` on `user_id`, filtered by `token_hash`, selecting the top-level interpolated map `%{token: t, owner_active: active_user_condition(:owner)}`. Decision order: no row -> `:invalid`; `revoked_at` set -> `:revoked`; owner not active -> `:revoked` with no `last_used_at` write; `expires_at` reached -> `:expired`; otherwise the unchanged `last_used_at` touch and `{:ok, ...}`. "Active" means `users.status == :active` in the token's tenant schema, defined once by `active_user_condition/1` (query side) and `active_user?/1` (in memory). Deactivating a user (either path) changes no token row and writes no token audit; reactivating the owner makes a non-revoked, non-expired token work again on the next request. The plug renders every `{:error, {:api_token, _}}` as the same 401, so an inactive owner is indistinguishable from a revoked token.

Files: `P` = `test/letflow/api_token_auth_pipeline_test.exs` (HTTP, full `Letflow.Router`), `I` = `test/letflow/identity_test.exs`. Routes: admin `GET /api/v1/identity/tokens` (`:TokensManage`), plain `GET /api/v1/me/memberships` (`:MembershipsRead`).

## Acceptance criteria -> tests

### AC1: refused with the revoked-token response
P, describe "GH-2557 AC1: an inactive owner's token is refused like a revoked one":
- `deactivated owner's TENANT_ADMIN token is refused 401 on GET /identity/tokens and GET /me/memberships`: positive control first (200 on both routes while active), then `update_user_status(:inactive)`, then 401 on both.
- `inactive-owner rejection is byte-identical to a revoked token`: on both routes, status, `resp_body` and `resp_headers` equal a freshly revoked token's response on the same route (`gh2557_assert_same_response!/2`). The only normalisation is the **value** of `x-trace-id`, a fresh UUID minted per request (two revoked-token requests differ in it too); the header must be present on both sides and both values must cast as UUIDs.

### AC2: in the same lookup, no extra or differing query
I, describe "verify_api_token/2 — inactive owner (GH-2557 AC2)":
- `inactive owner returns {:error, :revoked} and leaves last_used_at unchanged`: the persisted `last_used_at` stays `nil`.
- `inactive owner with an expired token returns {:error, :revoked}`: premise asserted first (active owner -> `:expired`), then deactivated -> `:revoked` (step 3 before step 4).
- `inactive owner and revoked token each issue exactly 1 query and no UPDATE on api_tokens`: a `[:letflow, :repo, :query]` handler that keeps only events from the test's own pid (captured before attach) and sends the SQL to the test; exactly 1 query per call for both cases, none an `UPDATE ... api_tokens`.
- The §3 select shape is proven at runtime by every request-path test above and in P, which execute the real query (no separate compile probe, per design §6).

### AC3: reactivation; revoked and expired unchanged
P, describe "GH-2557 AC3: reactivation, revoked and expired":
- `reactivating the owner makes the same token authenticate again (200)`: 401 while inactive, then 200 on both routes with `auth_context.user_id` and `roles == ["TENANT_ADMIN"]`.
- `reactivated owner with a revoked token stays 401` and `reactivated owner with an expired token stays 401`: both routes.
- Existing REQ-076 revoked/expired/invalid/cross-tenant tests in P and I (`verify_api_token/2 (REQ-076 AC4/AC5)`) stay green, unmodified.

### AC4: deactivation audit unchanged, no token revocation (design §4 choice: do not revoke)
P, describe "GH-2557 AC4: deactivation changes no token row and adds no token audit". Each test deactivates the target through the real HTTP route, authenticated by a second active TENANT_ADMIN token holder:
- `deactivate via POST /users/:id/status: ...`: 200; persisted status `:inactive`; the audit actions added are exactly `["user.update_status"]`; no `token.revoke`/`token.revoked` row; the target token's `revoked_at` stays `nil`; the target token then gets a 401 equal to a revoked token's (same comparison as AC1).
- `deactivate via PATCH /users/:id status=inactive: ...`: same assertions with exactly `["user.update_profile"]` added.
