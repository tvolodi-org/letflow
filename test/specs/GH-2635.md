# GH #2635: format validators end-anchored with `\z` (a trailing newline passed `$`)

Code: the eleven validators changed in `git diff 3a9ec210..HEAD`. Audit: GH #2635 audit table (scratchpad `audit2635.md`).

## Behaviour under test
PCRE `$` also matches just before ONE final `"\n"`, so `"name\n"` passed every `~r/^...$/` validator. Each now ends in `\z`. For every validator: (a) trailing `\n` refused, (b) leading / embedded `\n` refused, (c) a valid value still accepted, (d) the generated-as check refuses a trailing newline.

Files: `N` = `test/letflow/gh2635_trailing_newline_test.exs` (pure predicate / changeset / early-refusal calls), `C` = `test/letflow/tenant_provisioning/column_promotion_test.exs` (describe "GH #2635 -- execute_add_column ...", real DB).

## Why each case exists
- Trailing-newline cases are the regression: they fail on main (3a9ec210) because `$` accepted them.
- Leading / embedded newline cases pin that `^` is not multiline and the character classes exclude `\n`; they pass on main and are kept as guards so a future `m`-flag change or loosened class is caught.
- Valid-value cases prove the anchor change did not over-tighten.
- Valid-acceptance for `Secrets.put/2` and `FixtureLoader` needs real tenants / claimed sandbox schemas; the existing REQ-190 (`secrets_test.exs`) and REQ-039 (`fixture_loader_test.exs`) tests already cover it, so it is not duplicated.

## Known non-discriminating cases (pass on main; guards only)
- `tenant_id_for_schema_name/1`: on main a 33-byte hex part was already rejected by the fixed-size `<<... binary-size(12)>>` pattern after the regex. The regex fix is unobservable through the public function.
- `Solutions.load/1`: on main `"id\n"` fell through to `File.read` of the nonexistent `id\n.json` and returned the same `{:error, :not_found}`. The regex fix is unobservable through the public function.
- Leading / embedded newline cases everywhere (above).
