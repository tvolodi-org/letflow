# GH #2532: field `min`/`max`/`non_negative` on `:integer`/`:decimal` entity fields

Design: `lib/letflow/design/gh2532-field-min-max-non-negative.md`. Code: `lib/letflow/entities/definition/validator.ex` (Rule 12 `range_violations/1`, `valid_bound?/2`), `lib/letflow/entities/record/validator.ex` (`put_range/2`, `effective_minimum/2`, private), `lib/letflow/entities/definition.ex` (`field_def()`, moduledoc "Numeric ranges"), `lib/letflow/entities/records.ex` (`field_document/1`, `put_present/4`), `lib/letflow/routers/entities.ex` (`definition_field_document/1`), `lib/letflow/definitions/solution_pack.ex` (`@field_keys`).

## Behaviour under test
An `:integer` or `:decimal` field may carry optional `min`, `max` (inclusive; an integer on `:integer`) and `non_negative` (boolean). None is ever defaulted or inserted. `Definition.Validator` Rule 12 returns at most one `:invalid_range` violation per field at `[:fields, name]` with a fixed message: keys on another type, non-boolean `non_negative`, a non-integer bound on `:integer` or non-number bound on `:decimal`, `min > max`, or a negative bound with `non_negative: true`. `Record.Validator.build_record_schema/1` emits `"minimum"` (`max(min, 0)` under `non_negative: true`) and `"maximum"` only for number bounds, and a key-less subschema is exactly `%{"type" => "integer"}` / `%{"type" => "number"}`. Violations reach HTTP as the existing 422 `record_payload_invalid` entries with `code` `minimum`/`maximum`. Over HTTP a JSON `null` bound is dropped (absent); in a pack it is rejected. No DB CHECK.

Files: `V` = `test/letflow/entities/definition/validator_test.exs`, `RV` = `test/letflow/entities/record/validator_test.exs`, `R` = `test/letflow/entities/records_test.exs`, `H` = `test/letflow/routers/entities_test.exs`, `P` = `test/letflow/definitions/solution_pack_test.exs`, `S` = `test/letflow/entities/definition/shape_test.exs`, `D` = `test/letflow/entities/definition/ddl_test.exs`.

## Acceptance criteria -> tests

### AC1: definition validator
V, describe "GH #2532 :invalid_range" (each failure asserts exactly one `%Violation{rule: :invalid_range, path: [:fields, "qty"]}`):
- `{integer, min 0, max 10} is :ok`; `other well-formed range combinations are :ok` (`non_negative` alone, `non_negative: false` with `min: -5`, `min == max`, decimal float bounds, decimal integer/float mix).
- `min 5 max 1 is :invalid_range` (message "min must not exceed max").
- `min "a" is :invalid_range`.
- `min 1.5 (and 2.0) on an :integer field is :invalid_range`.
- `min on a :string field is :invalid_range`; `max or non_negative on other non-numeric types is :invalid_range` (`:boolean`, `:date`, `:datetime`, `:json`).
- `non_negative true with min -1 (or max -1) is :invalid_range` (also decimal `min: -0.5`).
- `non_negative "yes" is :invalid_range` (message "non_negative must be a boolean").
- `a present nil bound or non_negative is :invalid_range` (pack JSON null path).
- `malformed values never crash (INV-8)`: `"NaN"`, `"Infinity"`, a map, a list and an atom as `min` or `max`; `10^400` as `min` or `max` alone is `:ok`, and `min: 10^400, max: 1` is `:invalid_range`.
- `messages never echo the submitted value (INV-2)`: no message contains `987654`.
- `at most one :invalid_range violation per field`.
- `key-less numeric fields are still :ok`; every pre-existing V test runs unmodified.

### AC2: record subschema
RV, describe "GH #2532 range keywords":
- `{integer, min 1, max 5} yields "minimum" => 1, "maximum" => 5` (whole subschema compared).
- `non_negative yields "minimum" => 0` (integer, and decimal with `max: 9.5`).
- `key-less subschema is exactly the type map`: `%{"type" => "integer"}` and `%{"type" => "number"}`.
- `0 with min 1 gives minimum at /qty, 6 with max 5 gives maximum, 1 and 5 pass`.
- `decimal 0.5 with min 0.1 passes; 0.05 does not; 0.1 itself passes`.
- `effective_minimum/2 table, through build_record_schema/1` (OQ-2: the helper is private and tested only through the public function): `(number, true) -> max(m, 0)` (incl. the clamp: `min: -3, non_negative: true` -> 0), `(number, not true) -> m` (including `false` and `"yes"`), `(non-number, true) -> 0`, `(non-number or nil, not true) -> no "minimum"`.
- `a non-number stored bound is ignored, never a crash (INV-8)`.

### AC3: real DB records
R, describe "GH #2532 non_negative qty" (definitions created via `create_definition/2` + `activate_definition/4`):
- `the key is stored string-keyed and survives the round-trip`.
- `create with -1 is refused with zero events; 0 succeeds`: `{:error, {:record_payload_invalid, [_ | _]}}` with a `minimum` violation at `/qty`, zero events, no `Latest` row; then `0` creates one event.
- `update to -3 is refused and the row is unchanged`: `field_values` and `last_event_global_seq` unchanged, event count unchanged; an update to `0` then succeeds.

### AC4: round-trip guard
R, describe "GH #2532 read-back carries each key": `min only`, `max only`, `non_negative only` each refuse an out-of-range create on a definition read back from the DB (string keys), and `a key-less definition still accepts any integer`. Each key has its own test, so dropping any one key from `Records.field_document/1` fails that test (verified by mutant M1 below).

### AC5: HTTP
H, describe "GH #2532 ranges":
- `POST definition with bounds -> 201; GET active returns the keys` (`min`, `max`, `non_negative` on `quantity`).
- `min > max -> 422 invalid_range at [fields, quantity], nothing stored`: `min` is `987654`, and the body does not contain `987654`.
- `a JSON null bound is dropped (absent): 201 and no key stored`: stored `quantity` is exactly `%{"name" => "quantity", "type" => "integer"}`.
- `out-of-range record POST -> 422 code minimum, value not echoed; in-range -> 201`: `quantity: -987654` gives one error with `code "minimum"`, `path "/quantity"`, and `987654` is absent from the body; no record is written; `1001` gives `code "maximum"`; `1000` gives 201.

- `a JSON null bound in a pack is rejected (:invalid_range), nothing written`: `{:error, {:validation, violations}}` with `:invalid_range` at `[:fields, "qty"]`; zero rows.
