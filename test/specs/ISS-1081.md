# ISS-1081 (GH #2438): the register banner shows the server's detail for a 409

Issue record: GH #2438 (Q-1081, walk item B4, MINOR, web). The page is `web/src/pages/admin/onboarding/RegisterTenantPage.tsx`.

## Defect
The onboarding endpoint builds its 409s with `Letflow.Api.Error.conflict/1` (`lib/letflow/api/error.ex`), which sets `title` to the fixed string `"Conflict"` and puts the specific reason in `detail` (for example `"slug already exists"`, `"realm already bound"`, `"hostname already bound"`). The register page's 409 branch read `title` first, so every onboarding conflict showed `"Conflict"` and the server's reason never reached the banner.

## Acceptance criteria (from GH #2438)
1. The banner shows the server's detail for a conflict.
2. A test asserts the detail text in the banner.

## Decision: fallback order
In the 409 branch (`resolveApiErrorMessage`), after the `idempotency-conflict` check:
- `detail` if present (the server's reason, the primary text),
- else `title` (a body without a detail),
- else the generic text `"A conflict was detected. Please check your inputs."`.

Only the both-present case changes behaviour: it used to show `title`, and now shows `detail`. The detail-only, title-only and neither cases are unchanged.

The 422 and 502 branches and the `idempotency-conflict` branch are unchanged.

## Test cases (`web/src/pages/admin/onboarding/__tests__/RegisterTenantPage.conflictDetail.test.tsx`)
- `a duplicate-slug 409 shows the specific detail, not the generic title "Conflict"`: the client rejects with a 409 whose details carry `title: 'Conflict'` and `detail: 'slug already exists'`. The `role="alert"` banner must contain `slug already exists` and must not be `Conflict`. This is the case that fails on the defect.
- `fallback: a 409 with no detail shows its title`: details carry `title: 'Conflict'` and no detail. The banner shows `Conflict`.
- `fallback: a 409 with neither detail nor title shows the generic text`: no detail and no title. The banner shows the generic text.

The real onboarding module runs; only the HTTP client is mocked (the same harness as `RegisterTenantPage.iss1030.test.tsx`).
