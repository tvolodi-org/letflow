# ISS-0720 — `tenant_config.ex` stale `:issuer` config-key read / unscoped localhost IDP fallback

Design: `lib/letflow/design/iss0720-tenant-config-stale-issuer-key.md`
Fix commit: `dbcc89e2` (`fix(ISS-0720): tenant_config.ex reads :keycloak_base_url, scopes localhost IDP fallback to dev/test`)
Test: `test/letflow/routers/tenant_config_oidc_env_test.exs` (moved from tenant_config_test.exs, T-1938: async: false, VM-global env)

## Criterion

`GET /api/tenant-config`'s `oidc_authority` must be built from `:letflow, :oidc,
:keycloak_base_url` (REQ-370's live trust-resolution source) when
`BPM_IDP_BASE_URL`/`KEYCLOAK_BASE_URL` are both unset — not silently fall through to
the compiled `http://localhost:8082` default. Pre-fix, `oidc_issuer_base/0` read the
retired `:issuer` key (REQ-370 removed every writer of it), which is therefore always
`nil`, so `idp_base_url/0`'s `||` chain always bottomed out at the localhost literal
whenever the two env vars were unset — this is exactly ISS-0719's live-QA symptom
(browser gets redirected to a dead `localhost:8082` IDP instead of the real Keycloak).

## Test case

**"GET /api/tenant-config's oidc_authority is built from :letflow, :oidc,
:keycloak_base_url when BPM_IDP_BASE_URL/KEYCLOAK_BASE_URL are unset"**

- Confirms (via `refute System.get_env/1`) that the two env vars which take precedence
  over `:keycloak_base_url` are actually unset in this test run — without this check
  the test could pass for the wrong reason (an accidentally-set env var winning
  regardless of the bug).
- Sets `Application.put_env(:letflow, :oidc, ...)` with a distinctive,
  unmistakable `:keycloak_base_url` (`https://iss0720-regression-test-authority.example`)
  merged into the existing `:oidc` keyword list (preserves `:client_id` etc.), restored
  unconditionally via `on_exit/1`.
- Calls `GET /api/tenant-config` through the real `Letflow.Router` mount chain (same
  dispatch convention as every other test in this file).
- Asserts `oidc_authority` starts with `"https://iss0720-regression-test-authority.example/realms/"`
  and does not contain `"localhost"`.

This exists because none of the file's pre-existing (REQ-281) tests ever configure or
assert on the *host* portion of `oidc_authority` — they only check the `/realms/<slug>`
suffix and response shape — so none of them would have caught this regression. This
test is the first in the suite to discriminate the `:issuer` vs `:keycloak_base_url`
config-key bug directly.

## Compile-time raise-path testability (`default_idp_base_url!/0`'s `raise` branch)

**Not unit-tested here, and stated explicitly as an accepted gap, per the design doc's
own §5 item 3 and REVIEWER's step-03c `next_action`.** `@allow_localhost_idp_fallback?`
is resolved once at compile time via `Application.compile_env(:letflow,
:allow_localhost_idp_fallback, false)` — a module attribute baked into the compiled
BEAM bytecode at compile time, mirroring `Letflow.Repository.Activation`'s
`@activation_test_hooks_enabled?` pattern exactly. `Application.put_env/3` only changes
the *running* application environment; it has no effect on a value a module attribute
already captured at compile time, so there is no way, from inside this same
`test.exs`-compiled suite (where `config/test.exs` sets the flag `true`, making the
attribute permanently `true` for every test process in this run), to observe the
`false` branch and its `raise`. Exercising that branch would require compiling a
*separate* build with `config/test.exs`'s `allow_localhost_idp_fallback` line removed
(or a distinct `MIX_ENV`), which is outside what a single `mix test` run in this suite
can do. This is not a gap in effort: it is a direct, structural consequence of the
compile-time flag mechanism this fix deliberately adopted (for the same
release-safety reason `activation.ex` uses it — `Mix.env()` is unavailable in a
compiled release). The flag's own correctness (`false` in `prod`/`runtime.exs`, `true`
in `dev`/`test.exs`) was independently verified by direct config-file inspection by
both SECURITY-REVIEWER (step-03b) and REVIEWER (step-03c) already, which is the
practical substitute for a unit test here.
