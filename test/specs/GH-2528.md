# GH #2528: optimistic concurrency on entity record update/delete (`expected_last_event_global_seq`, 409 `record_version_conflict`)

Design: `lib/letflow/design/gh2528-record-version-conflict.md`. Code: `lib/letflow/entities/records.ex` (`expected_seq/1`, `maybe_check_record_version/2`, `check_record_version/3`), `lib/letflow/entities/record/latest.ex` (`get_for_update/4`), `lib/letflow/routers/entities.ex` (`@record_update_schema`, `parse_expected_seq_param/1`), `lib/letflow/api/error.ex` (`record_version_conflict/0`).

## Behaviour under test
`Records.update_record/2` and `delete_record/2` take an optional `:expected_last_event_global_seq`. Absent or `nil` adds no Multi step (today's last-writer-wins). Otherwise a `:check_record_version` step, after the per-type sequence lock and the idempotency check, re-reads the row `FOR UPDATE` and returns `{:error, :record_version_conflict}` on mismatch, rolling back the event and the idempotency claim. PUT takes the value in the body (422 on a bad type or range), DELETE as a query param (400 on a bad value). The 409 body is constant.

Files: `R` = `test/letflow/entities/records_test.exs`, `H` = `test/letflow/routers/entities_test.exs`, `E` = `test/letflow/api/output_refused_test.exs`, `V` = `test/letflow/api/validation_test.exs`.

## Acceptance criteria -> tests

### AC1: absent expected keeps today's behaviour
- R, describe "expected_last_event_global_seq", `absent expected keeps last-writer-wins: two updates both succeed, the second value is stored`. Fails if the check becomes mandatory (the second update would conflict or raise).
- R, `an explicit nil expected behaves exactly like an absent one`. `nil` is the router's value for a missing body key, so it must not be treated as a seq.
- All pre-existing update/delete tests in R and H run unmodified (no line of them changed by the GH #2528 commits; both files pass in full).

### AC2: match
- R, `matching expected updates and advances last_event_global_seq`: `{:ok, %{record: r}}` with `r.last_event_global_seq > S1`; the stored row agrees.

### AC3: mismatch is refused and atomic, key not claimed
- R, `stale expected is refused atomically and does not claim the idempotency key`: `{:error, :record_version_conflict}`; stored `field_values` and `last_event_global_seq` unchanged; event count unchanged; a retry with the same key and the correct expected gives `is_duplicate: false` and one new event. Proves the rollback covers the idempotency claim, not just the projection.

### AC4: delete match/mismatch
- R, `delete with matching expected deletes`.
- R, `delete with stale expected is refused atomically and leaves deleted: false` (also seq, values and event count unchanged).
- R, `delete of an already-deleted record stays a no-op success regardless of the expected value (D7)`: design D7, guards the early return against a check being added before it.

### AC5: race (real concurrency)
R, describe "expected_last_event_global_seq -- concurrency". The tenant is provisioned with the sandbox in `:auto` mode so each Task has its own connection and every write commits (a shared sandbox connection would serialise the writers and prove nothing).
- `barrier race, same expected, different values: exactly one wins, the other conflicts (20 iterations)`: `{:ready, pid}`/`:go` barrier, fresh record each iteration, exactly one `{:ok, _}` and one `{:error, :record_version_conflict}`, stored values and seq equal the winner's, exactly one new event.
- `control: the same race without expected gives two {:ok, _} (20 iterations)`: shows the race test's harness really runs both writers, so the single winner above comes from the check and not from the harness.
- `deterministic lock-holder: both writers pre-read S1, only the locked re-read decides` (mandatory, design §8.1 Test 3): a holder Task locks the entity type's `instance_sequence` row; both writers are started and the test polls `pg_stat_activity` until both are blocked on that lock, so both have already done their pre-transaction read of S1. Then the holder releases. Exactly one wins. This fails deterministically if the check compares against `ctx.existing_record` (the pre-read) instead of the row re-read `FOR UPDATE`, which the 20-iteration race can only catch probabilistically.

### AC6: replay precedence
- R, `identical replay returns the original, not a conflict`: same key K and same expected S1 twice gives `is_duplicate: true` with the original record, even though S1 is stale at the time of the second call.
- R, `same values, different stale expected -> is_duplicate: true` (split from the former "different stale expected and different values" test by GH #2543): key K reused by the same actor with the same `field_values` but a different stale expected (`S1 - 1`) returns `{:ok, %{is_duplicate: true}}` with the original record; the stored row and the event count are unchanged. Shows the idempotency short-circuit runs before the version check, and that the expected value is not part of the key binding.
- R, `different values, same key -> idempotency_key_reuse, nothing written` (GH #2543): the same key with different `field_values` (and a stale expected) returns `{:error, :idempotency_key_reuse}`; the stored row and the event count are unchanged. Before GH #2543 this returned the original as `is_duplicate: true`, which was the defect GH #2543 fixes.

### AC7: HTTP surface
H, describe "GH-2528 -- record version conflict".
- `PUT with a stale expected_last_event_global_seq -> 409 problem+json, no record data, nothing written`: status 409, `application/problem+json`, `code == "record_version_conflict"`, fixed detail, no `field_values`/`last_event_global_seq` member and no body member equal to either seq; stored row unchanged.
- `PUT with the current expected_last_event_global_seq -> 200`.
- `PUT with a non-integer expected_last_event_global_seq -> 422, nothing written`: `"abc"`, `1.5`, `true`, `-1`.
- `PUT with expected_last_event_global_seq: null -> 200 (treated as absent, last-writer-wins)`: JSON null with a stale-free write still succeeds, so null is not mistaken for a seq or rejected.
- `PUT with expected_last_event_global_seq one above max int8 -> 422, nothing written`: `9_223_372_036_854_775_808`; the `max_value` constraint keeps a bignum away from the int8 comparison (INV-8). Without it the request reaches the domain (measured: 409).
- `PUT with a stale If-Match header only -> 200 (If-Match stays ignored)`.
- `DELETE ?expected_last_event_global_seq=<stale> -> 409, record not deleted` (same body assertions as PUT).
- `DELETE ?expected_last_event_global_seq=<current> -> 200, record deleted`.
- `DELETE with a non-integer expected_last_event_global_seq query value -> 400, record not deleted`: `abc`, empty, `-1`, `1.5`, `1x`, `9223372036854775808`.
- `DELETE with an array or map expected_last_event_global_seq query param -> 400, record not deleted`: `expected_last_event_global_seq[]=N` and `expected_last_event_global_seq[a]=N`. Plug decodes these to a list and a map; the test checks they are refused rather than crashing (500) or being read as absent (an unconditional delete).

### AC8: INV-5
- H, `INV-5: PUT with an expected value on a cross-tenant or absent record_id -> the same zero-detail 404`.
- H, `INV-5: DELETE with an expected value on a cross-tenant or absent record_id -> the same zero-detail 404`.
Both send tenant B's real current seq from tenant A, compare the cross-tenant response byte-for-byte with an absent-id response (pinned trace id), check it equals the plain `Error.not_found/0` body, and then re-read tenant B's record: `field_values`, `last_event_global_seq` and `deleted` unchanged. The last part fails if a cross-tenant write ever lands even though the response is a 404.

### AC9: EventTypes unchanged
- R, `EventTypes unchanged: an opted-in update's stored UPDATED payload has exactly the four keys`: `entity_def_version`, `entity_type`, `field_values`, `record_id`.

### AC10: error value and mixed-version safety
- E, describe "Error.record_version_conflict/0": status 409, code, fixed detail; serialised keys are exactly `code detail status title trace_id type`; sent through `Response.send_problem/2` as 409 problem+json with the conn's trace id.
- V, `GH #2528: an unknown body key does not break validate/2 and is dropped from the result`: an old server's POST schema receiving the new key still validates.

### Extra (design D1 guard)
- R, `a non-nil expected that is not a non-negative integer raises ArgumentError, live or deleted`: internal-caller programmer error raises on both paths, including delete's already-deleted early return.
