# GH #2543: bind an entity-record `idempotency_key` to its request (422 `idempotency_key_reuse`)

Design: `lib/letflow/design/gh2543-idempotency-key-binding.md`. Code: `lib/letflow/entities/records.ex` (`idempotency_match/1`, `request_fingerprint/2`, `interpret_result/3`, `match_original/3`, `resolve_original_payload/2`, `same_request?/2`, `json_equal?/2`, `same_uuid?/2`), `lib/letflow/api/error.ex` (`idempotency_key_reuse/0`), `lib/letflow/routers/entities.ex` (`render_record_command/3`, `import_reason_json/1`, route table and comments), `lib/letflow/modules/exam/certificate.ex` (`idempotency_match: :target`), `lib/mix/tasks/letflow.seed.exam_fixtures.ex` (moduledoc only).

## Behaviour under test
On a duplicate `idempotency_key`, `Letflow.Entities.Records` compares the new request with the **original event**: its `event_type` column (the command), its `actor_id` column, then (after reading an oversized `%{"$ref" => id}` payload back from `event_payload_store`) the payload's `entity_type`, `record_id` (update, delete) and `field_values` (create, update). `field_values` are compared as JSON values (`json_equal?/2`: key order irrelevant, `1` matches `1.0`, an integer read back from jsonb matches the float it came from via `:erlang.binary_to_float/1`; a string never matches a number). UUIDs are compared after `Ecto.UUID.cast/1`. The same request returns the original as `is_duplicate: true`; anything else returns `{:error, :idempotency_key_reuse}` with no event appended. `expected_last_event_global_seq`, `entity_def_version` and the minted create `record_id` are not bound. HTTP maps the error to a constant 422 problem with `code "idempotency_key_reuse"`; the import route reports it per entry. `create_record/2` takes the internal-only `idempotency_match: :target`, which skips the `field_values` compare (Certificate's fetch-or-create); any value other than `:request`/`:target` raises `ArgumentError`. Step order is unchanged (GH #2529 append-only check first, GH #2528 version check after the claim).

Files: `R` = `test/letflow/entities/records_test.exs`, `H` = `test/letflow/routers/entities_test.exs`, `E` = `test/letflow/api/error_test.exs`.

## Acceptance criteria -> tests

### AC1: binding plus stable error
R, describe "GH #2543 -- idempotency key bound to the request":
- `update key reused for a different record_id -> idempotency_key_reuse, target unchanged, no event`: second record's `field_values` and `last_event_global_seq` unchanged; event count unchanged.
- `create key reused for update -> reuse` and `create key reused for delete -> reuse`: same actor, same values; the record is unchanged / not deleted; no event.
- `delete key reused against a different record_id -> reuse, second record not deleted, no event`.
- `oversized original reused with different field_values -> reuse, no event` (D3): the stored event payload is asserted to be `%{"$ref" => _}` first.
- `create key reused with different field_values -> reuse`; `update key reused with different field_values -> reuse`.
- `create key reused on another entity type with identical field_values -> reuse`: no `supplier` row.
- `same key and payload from another actor -> reuse` (D4).
- `key first used by a non-entity event -> reuse, no raise`: a permissive event type is registered and `EventStore.append/2` claims the key on the entity type's started synthetic instance; `create_record/2` then returns the error instead of raising `KeyError`; no entity row.
- `update replay of the same request with an upper-case record_id -> is_duplicate: true` (UUID normalisation, design section 3).
- R, describe "expected_last_event_global_seq": `different values, same key -> idempotency_key_reuse, nothing written` (split from the #2528 test, see below).

### AC2: no original data, fixed status
- H, describe "idempotency key binding (GH #2543)", `POST reuse -> 422, body is exactly the constant problem, contains neither the original record_id nor its field values`: status 422, `application/problem+json`, the body minus `trace_id` equals the serialised `Error.idempotency_key_reuse/0`; the body contains neither the original `record_id` nor its title; one record.
- H, `PUT reuse -> 422 idempotency_key_reuse`: same body check; the second record is unchanged; the first record's id is not in the body.
- E, `idempotency_key_reuse/0 builds the 422 document`: type `.../idempotency-key-reuse`, title, status 422, fixed detail, `code`, and exactly the keys `code detail status title trace_id type`.

### AC3: same-request replay stays idempotent
- Existing R AC3 tests (`submitting create_record/2 twice ...`, `a THIRD submission ...`) and `identical replay returns the original, not a conflict` stay green unchanged.
- R, `replay with reordered keys and 1 vs 1.0 -> is_duplicate: true, one event`: a `:json` field holding nested maps and lists; the replay swaps integers and floats; then the same key with `"1"` instead of `1` gives `idempotency_key_reuse`.
- R, `replay with a float >= 2^53 (1.0e23, 12345678901234567890.5 and 9.099724907720628e285) -> is_duplicate: true, one event`: premise asserted — the stored jsonb values come back as integers, `stored != data`, and `:erlang.float/1` of the third stored integer is not the original float (so a `:erlang.float/1` comparator would fail this test).
- R, `same values, different stale expected -> is_duplicate: true` (D5).
- R, `oversized (> 4096 B payload) create replay -> is_duplicate: true, full field_values` (D3; before the change this raised `KeyError`).
- H, `POST replay -> 201 with the same record_id`.

### AC4: backward compatibility
- R, `:target create with different values -> original, is_duplicate: true`.
- R, `:target create on another type -> reuse`: also another actor -> reuse.
- R, `invalid idempotency_match raises ArgumentError`: `:bogus` and `"target"`, also for an unknown entity type (raised before the definition lookup); zero events.
- H, `import: same record_id with different values -> per-entry idempotency_key_reuse`: first entry ok, second entry `%{"status" => "error", "source_record_id" => id, "reason" => %{"type" => "idempotency_key_reuse"}}`; one record. The existing intra-call dedup test (identical values) stays green unchanged.
- Unchanged suites green: certificate_test, session_test, anti_cheat_test, exam_sessions_test, record_deadline_sweep_test, `test/mix/tasks/letflow.seed.exam_fixtures_test.exs`.

### AC5: payload compared, choice named
Existing stored payload compared (no hash column, no migration, no `EventStore` change). Stated in the PR body.

### AC6: order unchanged (D8)
- R, `reused key on an append-only type -> entity_append_only`: a same-request update replay after an `append_only: true` version is activated returns `{:error, {:entity_append_only, "customer"}}`, not `is_duplicate: true`; no event.

## Intentional rewrite
The #2528 test `replay with the same key but a different stale expected and different values returns the original` asserted the defect. It is split into `same values, different stale expected -> is_duplicate: true` and `different values, same key -> idempotency_key_reuse, nothing written` (both pass an explicit shared `actor_id`, because `gh2528_update_attrs/3` mints a fresh actor per call). `test/specs/GH-2528.md` AC6 is reworded to match.
