# Test Spec: REQ-304 — SolutionPack `entity_definitions` export

**Requirement:** REQ-304 — `entity_definitions` export half of decision `0026-solution-pack-entity-definitions-section.md`,
built against `lib/letflow/design/req304-solution-pack-entity-definitions-export.md`.

Acceptance criteria (verbatim from `docs/requirements.yaml`, `id: REQ-304`):

1. `pack_document`'s `@type` declares `entity_definitions` with its own `@typedoc` distinct from `packed_definition`/`packed_variable_schema`.
2. `export/3` (or new arity) accepts a way to name entity definitions to include, returns them under `entity_definitions`, each entry has at minimum `name`, `display_name`, `definition_json`.
3. Every entity definition read runs under `opts[:prefix]`, no caller-suppliable tenant id anywhere in the new path.
4. Naming a nonexistent entity definition (wrong name, or another tenant's) produces the designed error shape (`{:error, {:entity_definition_not_found, name}}`).
5. `export/3` with no entity definitions named still returns `entity_definitions: []` and is otherwise byte-for-byte compatible with pre-change output — no regression.
6. `mix compile --warnings-as-errors` succeeds.
7. `git diff --name-only` shows no file under `lib/letflow/definitions/solution_pack_install.ex` or anything the requirement didn't name touched.

**Test tier:** unit+integration (real Postgres via `Letflow.DataCase`, context-module level — no route exists yet for `entity_definition_names`, per 0026/REQ-304's own scope fence leaving `lib/letflow/routers/solution_packs.ex` untouched).

**Test file:** `test/letflow/definitions/solution_pack_test.exs`

## Test cases

1. **`export/3` process-definitions-only call — full key-set + `entity_definitions: []` assertion** (AC5, and AC1 indirectly — the document produced necessarily has the real `entity_definitions` key with real values, so this exercises the type-level change without a separate type-only test). Why: proves the *existing* call path is untouched in both shape (`Map.keys` sorted comparison against the pre-change key list plus the one new key) and content (`definitions`/`service_catalog_entries`/`variable_schemas`/`manifest` values unchanged) — a test that only checked "still returns `{:ok, _}`" would miss a regression that silently dropped or renamed an existing key. — `solution_pack_test.exs:"process-definitions-only export/3 call still succeeds, with entity_definitions: [] and no other regression"`

2. **`export/3` with zero `definition_ids` still `{:error, :empty_definition_ids}`** (AC5). Why: the design requires `export/3`'s only permitted body change to be delegating to `export/4` with `entity_definition_names: []` — this proves that delegation didn't also change the empty-input error path. — `solution_pack_test.exs:"export/3 with zero definition_ids is still {:error, :empty_definition_ids} (unchanged)"`

3. **`export/4` naming one real entity definition — full `packed_entity_definition` key-set + value assertion** (AC1, AC2). Why: AC2 requires "at minimum `name`, `display_name`, `definition_json`" in each entry — this test asserts the *complete* five-field shape (`entity_definition_id`, `name`, `display_name`, `definition_json`, `logical_shape_version`) the design specifies, both to prove the required three fields are present with correct values AND that no storage-only field (`tenant_id`, `content_hash`, `artifact_version_id`, `status` — INV-2) leaked in. A test asserting only `Map.has_key?/2` on the three named fields would pass even with a wrong or leaking key set; this doesn't. — `solution_pack_test.exs:"naming one real entity definition returns it under entity_definitions with name/display_name/definition_json (+ id/logical_shape_version)"`

4. **`export/4` with `definition_ids: []` and a non-empty `entity_definition_names`** (AC2). Why: the design states this must be "a legitimate entity-definitions-only pack," not rejected as if it were the zero-both case — this proves the two lists are independent, not that naming one implicitly requires the other. — `solution_pack_test.exs:"naming zero definition_ids but a non-empty entity_definition_names list is a legitimate entity-only export"`

5. **`export/4` naming both a process definition and an entity definition** (AC2). Why: proves the two pack sections are built independently in one call (no cross-contamination, no accidental sharing of the `reduce_while` accumulator between `pack_each_definition/2` and `pack_each_entity_definition/2`). — `solution_pack_test.exs:"naming both a process definition and an entity definition populates both lists independently"`

6. **`export/4` with both lists empty — still `{:error, :empty_definition_ids}`** (design §2.1 point 1, direct consequence of AC2/AC5's mechanics). Why: the design specifies naming zero of *both* kinds must still reject, matching `export/3`'s pre-existing zero-`definition_ids` behavior extended to the new parameter — a pack with nothing to export is still nothing to export. — `solution_pack_test.exs:"zero definition_ids and zero entity_definition_names is still {:error, :empty_definition_ids}"`

7. **Two tenants, each with an entity definition of the identical name — export under tenant A's `opts` returns only A's row, and its own field values, never B's** (AC3, and the leak-prevention half of AC4). Why: this is the test that would actually fail if `pack_each_entity_definition/2` ever used a caller-suppliable tenant id instead of `opts[:prefix]`-derived scoping, or if `get_definition_by_name/2` were ever called without the prefix — a same-tenant-only fixture couldn't distinguish "correctly scoped" from "accidentally correct because there's only one tenant." Asserting the returned `display_name` equals A's value and explicitly `refute`s B's value closes that gap. — `solution_pack_test.exs:"two tenants each own an entity definition of the SAME name -- export under A's opts returns only A's row, never B's"`

8. **Naming a wholly nonexistent name — `{:error, :entity_definition_not_found}`, no name echoed** (AC4; GH #2746). Why: direct assertion of the designed error tuple shape (not just "returns an error") for the "wrong name" half of AC4. — `solution_pack_test.exs:"naming a wholly nonexistent name -- {:error, :entity_definition_not_found}, no name echo"`

9. **Naming another tenant's entity definition by name, called as tenant A (who has no definition of that name at all) — the SAME `{:error, :entity_definition_not_found}` shape, asserted twice for determinism, never a leaked `{:ok, doc}`** (AC4's "another tenant's" half, INV-1/INV-5 cross-tenant-invisibility reasoning from the moduledoc). Why: this is the test that would fail if a future change ever let a cross-tenant name resolve successfully (a leak) or produced a *different* error shape than the plain not-found case (which would itself leak the fact that the name exists somewhere) — asserting byte-identical equality to the genuine-miss tuple closes both failure modes. — `solution_pack_test.exs:"naming another tenant's entity definition (by name, no definition of that name in the caller's own schema) -- SAME not-found shape, no leak"`

10. **First offending name wins deterministically when multiple names are given, one missing before a real one** (design §2.2's ordering guarantee, mirrors `pack_each_definition/2`'s existing precedent). Why: proves `pack_each_entity_definition/2`'s `Enum.reduce_while` halts on the *first* problem in caller-given order rather than, e.g., an unordered `Enum.map` that could report a different name depending on internal traversal order. — `solution_pack_test.exs:"first offending name wins deterministically when multiple names are given"`

## AC1 / AC6 — not independently tested (by design)

- **AC1** (distinct `@typedoc`, new `pack_document` key): satisfied structurally by every `export/4` test above actually exercising the real `entity_definitions` key's shape and content — Elixir `@type`/`@typedoc` declarations are compile-time documentation with no runtime representation to assert on separately; a dedicated "type exists" test would be a tautology. Confirmed by direct read of `lib/letflow/definitions/solution_pack.ex:187-206`: `packed_entity_definition/0`'s `@typedoc` ("One entity definition inside a pack document (0026 §Consequences, REQ-303 doc §1).") is textually distinct from `packed_definition/0`'s ("One definition inside a pack document.") and `packed_variable_schema/0`'s.
- **AC6** (`mix compile --warnings-as-errors` succeeds): verified directly, not via a test — see "Verification run" below.
