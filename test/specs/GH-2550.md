## Behaviour under test
Every caller key is stored namespaced: `client:rec:<actor>:<K>` (record POST/PUT body), `client:inst_start:<actor>:<K>` (start header), `client:inst_cancel:<actor>:<instance>:<K>` and `client:inst_rebind:<actor>:<instance>:<K>` (cancel/rebind header), `script:<actor>:<K>` (Lua `emit_event`). No server writer produces a `client:`/`script:` key, so a caller can no longer pre-claim (squat) a server key. A raw key over 199 bytes (162 on cancel/rebind; counted in bytes) is refused with a constant 422 `max_length` field error (`idempotency_key` for the body, `idempotency-key` for the header, no `received` echo) and nothing is written; it is never truncated. A script key that is empty, non-string or over 199 bytes is `invalid_arguments`. An absent key (or an empty header) is a bare minted UUID, as before. For one release (removed by GH #2578), a record POST/PUT key that matches no server or caller family is also looked up bare: an `ENTITY_RECORD_CREATED`/`ENTITY_RECORD_UPDATED` row written before `legacy_cutoff/0` (pinned 2026-11-16) by the same actor is matched by `match_original/3` (same result or 422 reuse) with no append. Instance routes have no legacy path; the engine ignoring `is_duplicate` there is GH #2577 and out of scope.

Files: `U` = `test/letflow/idempotency_test.exs` (pure), `N` = `test/letflow/client_key_namespace_test.exs` (real Postgres, full `Letflow.Router` pipeline with an API token, real server writers).

## Acceptance criteria -> tests

### AC1: a squatted server key does not stop the server writer
Each test sends the server key as a caller key FIRST, then runs the real server writer.
- N `squat timer_fired: via a record POST -- the timer still fires and advances`: `Scheduler.fire_timer/2` returns `{:ok, :fired}`, exactly one event keyed `timer_fired:<id>`, a `TIMER_FIRED` on the timer's instance; the instance is `:completed`.
- N `... via the POST /instances header ...` and `... via Lua emit_event ...`: same assertions, squatting through C3 and C6.
- N `squat escalation_timer_fired: -- the escalation still runs`: squats `escalation_timer_fired:<id>` and `timer_fired:<id>`; after the fire the original task is `:cancelled`, an escalated task is `:pending`, and the `TIMER_FIRED` exists. The bare `escalation_timer_fired:<id>` key is never written as an event key by itself; it is only the base from which the escalation's sub-process keys are derived, so it cannot be squatted end-to-end. This test's teeth are its `timer_fired:` squat; the `escalation_timer_fired:` POST only shows that such a key does not get in the way.
- N `squat service_task_dispatch:<id> via a record POST -- the dispatch still completes and advances` (success path): the bare `service_task_dispatch:<dispatch id>` key is written only when a dispatch succeeds, as `SERVICE_TASK_COMPLETED` (`Engine` appends it after a 2xx). The test turns the SSRF gate off with `:service_task_ssrf_validation_enabled` (restored in `on_exit`) and points the SERVICE_TASK at a real local `Letflow.WebhookTestServer` (200 `{"ok":true}`). Order: the caller POSTs a record keyed `service_task_dispatch:<id>` (201); `poll_and_dispatch/1` gives `claimed: 1, advanced: 1, given_up: 0`; exactly one event exists under the bare key and it is the instance's `SERVICE_TASK_COMPLETED`; the instance is `:completed`.
- N `squat service_task: (attempt 0) -- the dispatcher still completes the give-up`: squats the `service_task:` give-up key (attempt 0) of a real SERVICE_TASK dispatch whose URL (`https://127.0.0.1/hook`) the SSRF gate blocks; `poll_and_dispatch/1` gives `claimed: 1, given_up: 1`, the instance is `:error`, and the give-up event exists under its key. (This test used to squat `service_task_dispatch:` as well, but the give-up path never writes that key, so that half was a no-op; it moved to the success-path test above.)
- N `another writer squats certificate:issue:<sid>, issuance still succeeds`: a PROCESS_OPERATOR POSTs a `widget` record keyed `certificate:issue:<sid>` (201); `Certificate.issue_or_get_for_user/3` for the candidate then returns `first_issuance: true` for that session with a different record id, and the one event under the key is the candidate's `ENTITY_RECORD_CREATED`. Called at the context level (the issuer), not over HTTP.
