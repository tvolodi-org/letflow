# GH #2529: append-only entity types (`append_only: true` refuses update/delete, 422 `entity_append_only`)

Design: `lib/letflow/design/gh2529-append-only-entity-types.md`. Code: `lib/letflow/entities/records.ex` (`ensure_mutable/2`), `lib/letflow/entities/definition/validator.ex` (`check_optional_boolean/3`), `lib/letflow/entities/definition.ex` (`t()`), `lib/letflow/definitions/solution_pack.ex` (`@top_level_keys`), `lib/letflow/routers/entities.ex` (`build_definition_document/1`, `render_record_command/3`), `lib/letflow/api/error.ex` (`entity_append_only/0`).

## Behaviour under test
An entity definition may carry an optional top-level boolean `append_only` (never defaulted). When the entity type's **current** active definition has `"append_only" => true`, `Records.update_record/2` and `delete_record/2` return `{:error, {:entity_append_only, entity_type}}` right after resolving the definition, before the record lookup, the already-deleted no-op, payload validation and idempotency. No event is appended. Create is unaffected. HTTP maps the refusal to a constant 422 problem body with `code "entity_append_only"`. A present non-boolean (including `nil` via a pack) is `:malformed` at `[:append_only]`.

Files: `R` = `test/letflow/entities/records_test.exs`, `H` = `test/letflow/routers/entities_test.exs`, `V` = `test/letflow/entities/definition/validator_test.exs`, `P` = `test/letflow/definitions/solution_pack_test.exs`, `S` = `test/letflow/entities/definition/shape_test.exs`.

## Acceptance criteria -> tests

### AC1: refusal, no state change
R, describe "append_only":
- `create succeeds on an append-only type`: `{:ok, _}`, one event for the type.
- `update refused, record and event count unchanged`: `{:error, {:entity_append_only, "customer"}}`; stored `field_values`, `deleted`, `last_event_global_seq` unchanged; the type's event count (events on its synthetic instance) and the schema's total event count unchanged.
- `delete refused, record and event count unchanged`: same assertions for delete; `deleted` stays false.

### AC2: existence independence (INV-5)
- R, `random non-existent record_id gets entity_append_only, not record_not_found`: both update and delete; zero events in the schema.
- H, `PUT and DELETE on a non-existent record id of an append-only type -> the same 422`.
- H, `PUT and DELETE give byte-identical 422s for random, pre-flag-deleted and cross-tenant ids` (SECURITY-REVIEWER finding 1): three ids against tenant A's append-only `ledger`: (a) a random UUID, (b) a record deleted while `ledger` was mutable, before a second version with `append_only: true` was activated, (c) a record of tenant B's own `ledger` type, which is mutable, so a request that crossed the tenant boundary would succeed and change it. All six responses (PUT and DELETE for each id, `x-trace-id` pinned to one value) have the same status, the same `content-type` header and the same `resp_body`, byte for byte. Why: any difference would tell the caller whether an id exists, was deleted, or belongs to another tenant (INV-5). Afterwards tenant B's record has the same `field_values`, `deleted == false` and `last_event_global_seq`; tenant A's deleted record is still deleted with the same `last_event_global_seq` (no event); tenant A has no row under the random or tenant-B id.
- R, `delete of an already-deleted record is refused once the flag is active`: pins the behaviour change documented in `delete_record/2`'s `@doc`. While the type is mutable, a second delete is the no-op `{:ok, _}` (premise asserted). After a version with `append_only: true` is activated, the same delete returns `{:error, {:entity_append_only, "customer"}}`; the record stays deleted, `last_event_global_seq` and the type's event count unchanged.

### AC3: default off
- All pre-existing update/delete tests in R and H run unmodified (no existing line changed); all files pass in full, including delete idempotency.
- R, `append_only: false behaves as mutable incl. delete idempotency`: update ok, delete ok, second delete is the no-op success with no new event.

### AC4: real round-trip
- Every append-only fixture in R, H and P is built through `Definitions.create_definition/2` + `activate_definition/4` (or the routes), never a hand-built struct.
- R, `the flag survives the real create/activate round-trip as string-keyed JSONB`: reloaded `definition_json["append_only"] == true`, no atom key.

### AC5: version flip
- R, `activating a version without the flag unlocks; re-adding it locks again`: v1 `true` refuses; v2 without the key allows the update; v3 `true` plus one extra optional field (distinct logical shape from v1) refuses update and delete again with no new event.

### AC6: HTTP surface
H, describe "append_only (GH #2529)":
- `PUT on an append-only type -> 422 entity_append_only, nothing written` and `DELETE on an append-only type -> 422 ...`: status 422, `application/problem+json`, `code == "entity_append_only"`, fixed detail, no `field_values` member, no record value in the body; stored row unchanged.
- `POST record on an append-only type -> 201`.
- `a normal type is unchanged: PUT 200 and DELETE 200`.
- `definition POST with append_only true -> 201; after activate, GET active echoes it`: activation via `POST /entities/definitions/:name/activate` with a non-blank `rationale`, then `GET /entities/definitions/active/widget` has `definition.append_only == true`.
- `definition POST with append_only null -> 201 and no key stored`: JSON null is dropped by the builder, so the stored document has no `append_only` key (hash unchanged).
- `definition POST with append_only "yes" -> 422 malformed at ["append_only"]`: an `errors` entry with `code "malformed"`, `path ["append_only"]`; nothing stored.

### AC7: validator
V, describe "append_only":
- `true, false and absent are all :ok`.
- `a present non-boolean (including nil) is malformed at [:append_only]`: `"true"`, `1`, `"x"`, `nil` each give exactly `[%Violation{rule: :malformed, path: [:append_only]}]`.

### AC8: pack
P, describe "append_only round-trip (GH #2529)":
- `export from tenant A, install into tenant B: definition_json["append_only"] == true`: also the whole `definition_json` and `logical_shape_version` equal the source.
- `any other unknown top-level key still gives {:error, :invalid_pack_document}`: `"frozen": true`; zero rows written.
