Extras (10): unknown `admin_*` listed in `ignored_fields` by name; an `idp_realm_id` validation error never
echoes the value; bind-realm validates the realm like onboarding and answers 503; the runbook exists and
references T-0150, T-0158, bind-realm and the automatic-activation statement (AC3); a create with a realm and a
taken hostname answers 409 and never binds the realm to the failed tenant (SECURITY-REVIEWER F1); a bind on a
tenant that became non-active answers 409 even for the realm already stored (design 3.2); a create whose realm
is claimed by another tenant before the bind answers 201 with `realm_request.status = not_bound` and keeps the
record (SECURITY-REVIEWER MAJOR-2); a create with a realm answers 403 before any write when the platform pin is
another tenant (the authorization plug answers first); the bind-realm request's `x-trace-id` reaches the
platform chain and never the tenant chain; a bind-realm request issues no tenant read after its commit
(SECURITY-REVIEWER BLOCKER-1, asserted by query order).

**Telemetry seams.** (a) Platform-prefix 500s on bind-realm: the platform gate and
`PlatformTenant.platform_prefix/0` read the same pin, and the bind route's gate runs after the authorization
plug, so the test attaches a `[:letflow, :repo, :query]` handler that, in the calling process only, changes the
pin on the first query whose SQL mentions `onboarding_registry`. (b) The create race: the handler claims the
requested realm for another tenant right after the onboarding-record INSERT, so the create's own bind loses
the race. (c) The bind's query order: a handler forwards each statement to the test process, and the test
asserts that no `FROM "tenants"` read follows the `UPDATE "tenants"`.

**Create-path platform gate: defence in depth (decision recorded).** `POST /onboarding` also runs
`verified_platform_prefix/1` before any write. That gate is defence in depth. The authorization plug
(`Letflow.Plugs.Authorize`) runs before the handler and answers 403 when the platform pin does not match the
caller, so the handler gate is reachable only by a race between the plug and the handler. It is pinned by two
tests: the plug-level test "POST /onboarding with a realm answers 403 before any write when the platform pin is
another tenant" (which proves the 403 comes first, with no write), and mutant M12 (the create gate removed:
the valid-realm create test fails). The equality itself is pinned by M5 on the bind route, which shares the
same function. Two earlier attempts to test the handler gate directly answered 403 from the plug and were
removed rather than weakened.

### Realm probe file

14 design names (one worded as the test is; the timeout case is in "no stray http message after cancel or
timeout") plus: delegation through the configured adapter; foreign request ids (messages with another ref
injected into the probe's Task from the server's responder) are ignored; upper-case `HTTPS` normalised and still
verified (match and mismatch); upper-case `HTTP`; a doubled slash of an unstripped base URL is not accepted;
unknown scheme / no scheme / unset base URL -> unreachable with no request (the live server's own port is used,
so an ignored scheme would reach it); the exact-64-KiB boundary (accepted) and one byte over (refused); a
trailing newline in the realm. The TLS tests use `:public_key.pkix_test_data/1` with explicit prime256v1 keys
(the same fixture rule as `smtp_sink.ex`), and `:public_key.cacerts_load/1` with a positive control (a
certificate for the right host from the SAME trusted CA is accepted), so the negative result is the host name
check, not an untrusted CA. The CA store is snapshotted and restored after each test (it is VM-global; the
restore is registered before the install). The cancel test asserts the server saw the connection close (no
wall-clock bound). One test waits for the 3 s probe deadline.

### Concurrency test

"two concurrent bind_tenant_realm calls with different realms ...": a Task holds `SELECT ... FOR UPDATE` on the
tenant row in an open transaction; two binders are started; the test polls `pg_stat_activity` (bounded attempts,
no sleep) until BOTH wait on a lock behind a `FOR UPDATE` read of `tenants`; only then the holder is released.
Expected: exactly one `{:ok, _}`, one `{:error, :realm_already_bound}`, one entry per chain.

## Lib findings (fixed in this PR)

1. The realm format regex used `$`, which PCRE also matches before a final newline, so `"realm\n"` was accepted.
   Fixed: `\z` in `Letflow.Oidc.RealmProbe` and `Letflow.Identity.Tenant`. Design amended to `\z`.
2. A same-realm re-bind on a non-active tenant returned 200. Fixed: the status check runs first, so the answer
   is 409 `tenant is not active` (design 3.2).
3. SECURITY-REVIEWER F1 (BLOCKER): the create path wrote the realm with the tenant, before provisioning and the
   onboarding record, so a taken hostname left an active tenant owning the realm. Fixed: the create path refuses
   a realm already bound (409, no write), creates the tenant without the realm, and binds it after provisioning
   and the onboarding record, through the same audited bind-once path.
4. SECURITY-REVIEWER BLOCKER-1: the bind route read the login state after the bind committed, so a failed read
   answered 500 with the realm bound. Fixed: the response is built from the bind's own result; the create path
   does the same. Pinned by the query-order test (M14).
5. SECURITY-REVIEWER MAJOR-2: a bind that fails after the tenant and record are committed (a lost race, or an
   audit fault) answered 409 or 500, which implies nothing was created. Fixed: the create answers 201 with
   `login.loginable = false` and `realm_request = {status: not_bound, reason: taken | unavailable}` (M13 and the
   race test).
6. SECURITY-REVIEWER F5: the platform-prefix gate runs before the outbound probe on create.
7. Hardening: the tenant-chain audit entry carries no operator-chosen trace id; the onboarding-record lookup in
   the audit path takes `limit: 1`.
