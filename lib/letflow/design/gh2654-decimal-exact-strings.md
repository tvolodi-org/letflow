## 1. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | New optional boolean field key **`decimal_strict`** on `:decimal` fields, default false, never defaulted by any layer (absent key = byte-identical JSON/hash). | Opt-in. A field without the flag keeps today's behaviour EXACTLY: accepts JSON numbers, stores/returns numbers, no scale or precision enforcement beyond today's, no rounding change. |
| D2 | Every new code path is guarded by `Decimals.strict_specs(definition_doc) == %{}` -> return the input untouched. | Makes "non-strict unchanged" structural, not a promise. |
| D3 | On a strict field a write accepts a **canonical decimal string** or a **JSON integer**; every JSON float (`2.5`, `3.0`, `1e3`) is refused (`type`). | Plug.Parsers/Jason decode a JSON number with a fraction/exponent to a float BEFORE our code runs, so a lossy float (e.g. 17 significant digits) is indistinguishable from an exact one; refusing all floats is the only exact rule. A JSON integer decodes to an exact bignum. A process variable holding a float therefore cannot feed a strict field: the author converts to a string (documented, section 8). |
| D4 | Strict value is validated, then **rewritten to its canonical scale-padded string**; that string is what is stored in `field_values`, put in the event payload, fingerprinted, and echoed in the create response. | `->>` of a JSON string is the exact text, so `(?->>?)::numeric` (compiler.ex:531) is exact; Jason cannot emit a `Decimal` as a bare number. |
| D5 | Strict scale: refuse (422, field path, constraint `scale`), never round. Value-based: exactly representable at `decimal_scale` fractional digits (section 3). Precision: integer digits `> precision - scale` -> `precision`. | Issue allows refuse-or-round; silent rounding of a ledger quantity is wrong. |
| D6 | Strict bounds `min`/`max`/`non_negative` are compared with `Decimal.compare/2` only. On a STRICT decimal field a bound may be a JSON number or a canonical string; on a non-strict field a bound must be a number exactly as today (a string bound there is a definition violation, 2.1). | Exactness (AC5). |
| D7 | Strict **reads** return strings, over HTTP and in process (one shared decoder, section 6). Non-strict reads are untouched. | AC3. |
| D8 | Per-unit-of-measure scale is not a core concern: field scale = maximum; narrowing per UoM is the module/handler's job via public `Decimals.parse/3` (section 9). | Scale is a property of the field. |
| D9 | No event schema bump (`field_values` is `{"type":"object"}`, event_types.ex:54-64). | Only the inner value type of a strict field differs for new events. |
| D10 | **The flag is immutable once the type has any record** (section 5): any change of `decimal_strict` on a `:decimal` field (either direction; also removing the field or changing its type) is refused at `activate_definition/4` with 409 when the entity type has any record row (any status, deleted or not); allowed on an empty type. WMS declares the flag from its first definition. | Legacy numbers can never coexist with a strict flag: no flip read path, no echo-write problem, no silent reinterpretation. |
| D11 | Decision record NEW `docs/migration/decisions/0060-decimal-strict-exact-string-fields.md` (written in this PR) plus the "Amended by 0060" line under 0057 D4. letflow-2 registers 0060 in the docs PR. | Condition 1/4. |

## 2. Where `:decimal` is handled today (evidence) and the change at each place

### 2.1 Definition validation (`lib/letflow/entities/definition/validator.ex`)
- 463-503 Rule 7 `:invalid_decimal`: precision+scale required together, `scale <= precision`, absent on other types. **Extend** with `decimal_strict`: present on a non-`:decimal` field -> violation "decimal_strict is only allowed on :decimal fields"; present and not a boolean -> "decimal_strict must be a boolean"; `true` with `decimal_precision > 1000` -> "decimal_precision must not exceed 1000 when decimal_strict is true" (Postgres max; the cap bounds all later arithmetic). Fixed strings, never echo values, one violation per field (existing `cond` style). Non-strict precision stays uncapped (unchanged).
- 505-578 Rule 12: `valid_bound?(:decimal, b)` is `is_number(b)` (578) and `min > max`/`min < 0`/`max < 0` compare raw terms. **Change** for `:decimal` fields (strict or not): a bound is valid if it is a number, OR (only when the field has `decimal_strict: true`) a binary accepted by `Decimals.bound/1`. A string bound on a NON-strict decimal field is a definition violation (`:invalid_range`; no ignore special case). This cannot break an existing definition: `valid_bound?(:decimal, b)` is `is_number(b)` today (578), so no stored definition can carry a string bound, and number bounds stay valid. For strict fields the three comparisons (`min > max`, `min < 0`, `max < 0`) use `Decimals.bound/1` + `Decimal.compare/2`; non-strict comparisons are unchanged. Message at 557/560: strict -> "a number or a decimal string"; non-strict unchanged.
- `Definition` typedoc (definition.ex:55-58, 95-96): add `optional(:decimal_strict) => boolean()`; `min`/`max` on `:decimal` -> `number() | String.t()`.
- **Carrier places for the new key** (ISS-0624 key-drop class; each needs the key AND a test):
  1. HTTP builder `routers/entities.ex:585-586` (`maybe_put_optional(:decimal_strict, field, "decimal_strict")`; `false` passes through, `null` is absent, non-boolean reaches the Validator).
  2. `Records.field_document/1` (records.ex:1511-1526): `decimal_strict: Map.get(field, "decimal_strict")` (treat nil/false the same downstream).
  3. `TenantProvisioning.field_from_persisted/1` (tenant_provisioning.ex:2895-2905): carry it (DDL-neutral: `DDL.decimal_pg_type/1`, ddl.ex:581-588, ignores it; `numeric(p,s)` is unchanged and a promoted column's pg_type is fixed at registration).
  4. `Query.Allowlist` (allowlist.ex:63, 273-291, 415): the allowlist holds only the entity's queried fields, so it is used ONLY for the filter and aggregate paths (the scale of the aggregated/filtered field): an allowlisted field gains `decimal_scale` and `decimal_strict` (nil for non-decimal). It is NOT the source of read-rendering specs (those come from the definition document, 2.6).
  5. Solution pack key map `definitions/solution_pack.ex:1134` (`"decimal_strict" => :decimal_strict`) and the exam pack generator `priv/modules/exam/generate_pack.exs:71`; pack `"definition" -> installer` path: a strict field in a pack JSON survives install (test with a fixture pack). `Definitions.PromotionDigest`/`Shape.content_hash` canonicalise the whole field map, so the key participates in `logical_shape_version` automatically (only definitions that carry it change hash).
  6. Definition export/import and the API definition representation return `definition_json` verbatim: nothing to change, but test a create -> GET -> export round-trip keeps `"decimal_strict": true`.
  7. `web/src/types/api.ts:343`: add `decimal_strict?: boolean` (type only; no UI).

### 2.3 Current behaviour (AC1 reproduction target; from code reading, to confirm by running on main BEFORE editing)
- Create `{"qty":"2.50"}`: `field_subschema(%{type: :decimal})` is `{"type":"number"}` (record/validator.ex:108); `matches_type?(_, "number")` is `is_number/1` (json_schema.ex:83) -> violation `{"/qty","type"}` -> `{:record_payload_invalid, _}` (records.ex:1451-1455) -> 422 `record_payload_invalid`, entry `{"code":"type","path":"/qty","message":"/qty violates type"}` (`violation_map/1`, routers/entities.ex ~2694, drops `actual`).
- Create `{"qty":2.5}`: passes; stored `2.5` (records.ex:1000 `Jason.encode!`), read back as JSON number `2.5` (Ecto `:map`, latest.ex:30); `2.50` vs `2.5` indistinguishable; 17+ digit numbers already lose digits in the body decode.
- Scale unchecked: `2.505` into scale 2 passes; JSONB keeps `2.505`; a promoted `numeric(10,2)` column rounds to `2.51`; promoted overflow raises Postgres 22003 (likely 500). **These stay true for non-strict fields.**

### 2.4 Write side -- the single choke point (strict fields only)
All writes pass `Records.validate_field_values/2` (records.ex:1451): `create_record` (338), `update_record` (419), `command_multi/3` (551; `HandlerWrites.create/3` and process `entity_writes` both use it), bulk import (via `create_record/2`, routers/entities.ex:1340-1350). **Change**:
1. `validate_field_values` calls `Decimals.normalize_field_values(definition_doc, field_values)` first (no-op when `strict_specs == %{}`, D2).
2. The NORMALISED map must replace the original in `ctx.field_values` at the three call sites (338-345, 419-424, 551-557): events, JSONB insert (records.ex:1000), fingerprint (1226), `to_append_attrs`, create response. This is the main trap (validating but storing the raw input defeats D4). **Test F8**: after a strict write, `entity_record_latest.field_values`, the per-type table `field_values`, the appended event payload and the HTTP response all contain the normalised map (same strings).
3. Idempotent retry compares normalised vs stored strings through `json_equal?` (records.ex:1292-1330), untouched.
4. `step_writes.ex` caps (65_536 B value, 262_144 B line; 514-520, 725) measure the JSON encoding; the 1100-byte input cap is below them. No change.
5. Process variables: variables are JSON terms (floats from `expr.ex`); a strict field accepts a string or integer variable and refuses a float variable (step fails with the normal `record_payload_invalid`). Non-strict mapping is unchanged.

### 2.5 Record validator (`record/validator.ex`)
- `field_subschema(%{type: :decimal})` (108) keeps returning `put_range(%{"type" => "number"}, field)` for a non-strict field (byte-identical). For a **strict** field it returns `%{"type" => "string"}` (no range keys; bounds are enforced in the pre-pass). `build_record_schema/1` therefore needs the strict flag: it already receives `decimal_*` through `field_document` (2.1 item 2).
- New `normalize_record_payload(definition, field_values) :: {:ok, map} | {:error, violations}`: strict-decimal pre-pass, then `validate_record_payload` on the normalised map. A field that failed the pre-pass is replaced by `""` only in the schema-pass input so no duplicate violation is emitted. `validate_record_payload/2` keeps its signature and behaviour.

### 2.7 Query: filters, sort, cursor
- Filters: values reach the compiler raw (routers/entities.ex:2079-2080; `build_one_filter_dynamic`, compiler.ex:980-988). **Strict decimal fields only**, ops `eq neq gt gte lt lte in not_in`: coerce the value (each element for `in`/`not_in`) via `Decimals.filter_value/1` (canonical-grammar string or integer -> `%Decimal{}`; float -> error) else `{:error, {:invalid_decimal_value, field}}` -> 422 next to `{:invalid_in_value, field}` (routers/entities.ex:2710). Filter scale is not enforced (`> "2.5555"` is legitimate). Non-strict decimal filters are untouched. Bound parameter; the fragment stays the compile-time `@decimal_fragment`.
- Sort/group: `json_cast_dynamic(:decimal, ...)` casts the stored text, exact for the stored text. No change.
- Cursor (cursor.ex:353-355): `decode_component(:decimal, v)` does `Decimal.new(to_string(v))`, which raises `Decimal.Error` on a tampered cursor. **Replace for ALL decimal fields** with strict `Decimal.parse/1` (`{d, ""}` else `:error`). ### 2.8 Aggregates (`compiler.ex:870-905`; router `aggregate_result_map`, routers/entities.ex:2309)

With exact strict storage there is no float step. **Non-strict fields: unchanged** (no padding, no new code path), so the existing assertions stay as they are (`entities_aggregate_test.exs:231` `sum_quantity == "7"`; `query_aggregate_test.exs` ~168-169; check both against the field type: if a fixture field is strict by accident none exists, the flag is new). **Strict fields**: pad `sum`, `min`, `max` and a decimal `group_by` key to the field scale (ten `"0.10"` sum to `"1.00"`; ten `"0.1"` into a scale-1 field sum to `"1.0"`); `avg` is returned as Postgres computes it, UNPADDED (a precision-bearing average is not a field-scale value); the module developer guide task documents this. ## 3. Strict-field grammar and limits (single definition: `Decimals.parse/3`)

Accepted for a strict WRITE:
- a **binary**, `byte_size <= 1100` checked BEFORE the regex or any `Decimal` call, matching `^-?(0|[1-9][0-9]*)(\.[0-9]+)?$`;
- an **integer**; magnitude pre-check WITHOUT `Integer.to_string`: refuse if `abs(n) >= Integer.pow(10, precision - scale)` (precision <= 1000 is guaranteed by the strict Rule 7 cap, so the power is bounded), and first refuse if `:erlang.bit_length(abs(n)) > 3400` (guards the pow comparison against a giant bignum).
Refused with `type`: any JSON float (D3), leading `+`, whitespace, `".5"`, `"5."`, exponent, commas, `"NaN"`, `"Infinity"`, empty string, leading zeros (`"007"`), boolean, map, list. (`null` follows the existing null handling, unchanged.)
Value-based digit counting (strings): parse with `Decimal.parse/1`, then `Decimal.reduce/1`; with coefficient `c` and exponent `e`: fractional digits = `max(-e, 0)` (so `e > 0` means 0), integer digits = `0` if `c == 0` else `max(digits(c) + e, 0)`. Refuse `scale` if fractional digits `> decimal_scale` (so `"2.500"` is accepted at scale 2, `"2.505"` refused); refuse `precision` if integer digits `> decimal_precision - decimal_scale` (`numeric(2,2)` accepts `"0.99"`, refuses `"1.00"`). Order: grammar/type -> scale -> precision -> `minimum`/`maximum`; one violation per field per write.
Normalisation: negative zero (`"-0"`, `"-0.00"`) -> unsigned zero; output rescaled to exactly `decimal_scale` fractional digits in plain notation (`"2.5"` -> `"2.50"`, `"3"` -> `"3.00"`; scale 0 -> no dot).
Filter literals (strict fields): same grammar and 1100-byte cap, no scale/precision check, integers allowed, floats refused.
Legacy JSON floats on non-strict fields are lossy by construction (Jason decodes them to floats); documented, not changed.
New `ValidationFailure.constraint` strings `"scale"`, `"precision"` (document in validation_failure.ex's closed list); `type`/`minimum`/`maximum` reused; response `{"code":"scale","path":"/qty","message":"/qty violates scale"}` (`actual` dropped by `violation_map/1`, INV-2).

## 5. Changing `decimal_strict` (immutable once the type has records; D10)

Precedent checked: a definition change creates a NEW immutable version (`Definitions.create_definition/3`; `Shape.logical_shape_of` hashes the whole definition), records keep their `entity_def_version`, and no definition change scans rows today. This design does not scan rows; it forbids the one change that would need a scan.
- **Rule.** `Definitions.activate_definition/4` (definitions.ex:469) refuses, with `{:error, {:decimal_strict_change, [field names]}}`, an activation whose target version differs from the currently active version (`get_active_definition_by_name/2`) in the strict-ness of any decimal field (`false->true`, `true->false`, a strict field removed, or its type changed) when the entity type has any record. "Any record" = at least one row in `entity_record_latest` with that `entity_type`, **regardless of `deleted`** (a soft delete only sets `deleted: true` and retains `field_values`, records.ex ~484; there is no separate archived status; per-type promoted tables are populated from the same rows and add nothing). One `Repo.exists?/2`, evaluated only when a strict-ness difference exists. An empty type may change freely; a first activation (no active version) is never refused. Creating (not activating) a differing version is allowed.
- **No legacy numbers under a strict flag, ever** (WMS declares `decimal_strict: true` from its first definition). The defensive decoder (2.6) is unreachable by contract.
- **Atomicity.** The check and the promotion must be one unit: run the `exists?` check inside the transaction of `promote_and_demote_siblings/2` (definitions.ex ~503-521), after taking the same per-entity-type sequence lock that record writes take (records.ex ~375, ~535, "per-type sequence lock"), so a record cannot be created between the check and the flip. If the implementer finds that lock cannot be taken from the activation path, the fallback is stated in the PR: the accepted window is one record committed under the old definition between the check and the promote on a type that was empty at check time; every later write is normalised by the strict path and the defensive decoder renders that record's numbers.
- **HTTP.** `render_activate_definition/2` (routers/entities.ex ~816-837) gets an explicit clause for `{:error, {:decimal_strict_change, fields}}` -> **409** with the fixed message "decimal_strict cannot change while records exist" and the field names (definition metadata, not values). Without it the tuple would hit the changeset catch-all or a function clause. Route test in PR-1 (this puts `routers/entities.ex` in PR-1).
- Managed types and module/pack upgrades use the same create/activate path, so the gate applies unchanged.

## 6. Managed types, stamp adoption and the manifest hash

**Manifest hash.** `ManifestHash.compute/1` (lib/letflow/modules/manifest_hash.ex) hashes only `id`, `version`, sorted `manages_entity_types` and per write handler `name`/module/function/`targets`/`args`; entity-definition content is not an input. So `decimal_strict` is NOT part of the hashed surface and a flag change in a pack does not change `manifest_hash`. A module that changes the flag in a shipped pack MUST bump its manifest `:version` (hashed) in the same release; the hash then changes and in-flight handler tasks refuse per the OQ-R3 pilot limit. Test M1 (pins the contract, not a tautology): `compute/1` of two manifests equal except for an extra definition-bearing key (e.g. `:entity_definitions` with a strict versus a non-strict field) returns the SAME hash, and bumping `:version` changes it. Adding strict-field names to the surface is a deferred follow-up (needs pack access, changes installed hashes); the stamp gap below is closed here.
**Stamp adoption.** `ManagedTypes.Stamp` (entities/managed_types/stamp.ex) adopts a tenant's existing unstamped rows when `compatible?/2` (~507) holds, which today checks only that every pack `(name, type)` pair exists on the row. A tenant row with a non-strict field could be adopted by a pack that declares it strict (or the reverse), bypassing the immutability rule (5). **Change**: `compatible?/2` additionally requires, for every pack `:decimal` field, `pack strict? == row strict?` (absent = false); a mismatch classifies the type as `:shape_not_compatible` (existing conflict reason, reported by type name and row count only). Add `:decimal_strict` to `@compared_keys` (stamp.ex:72) and to the per-field `differs?/4` clause beside `:required`/`:enum_values`, so the report names the key (for a stampable type it is equal by construction). Tests: strict pack vs non-strict row -> conflict; non-strict pack vs strict row -> conflict; matching -> stampable.
Installed definition migration: normal pack upgrade (new version + activation, section 5). The exam pack declares no strict field, so no exam version bump is needed.

## 8. Invariants
I1 No float arithmetic/comparison on a strict path (`Decimal.from_float` only inside `to_decimal/1`/decoder for legacy numbers). I2 After a successful write every strict decimal in stored/event/response `field_values` is a canonical scale-padded string. I3 A validated strict write cannot raise in `cast_promoted_value` or the numeric cast. I4 Reads, cursors, decoders never raise on stored data. I5 Values reach SQL only as bound parameters; fragment literals stay compile-time. I6 `strict_specs == %{}` => every function returns its input untouched (non-strict behaviour is byte-identical).

## 9. Per-unit-of-measure scale (D8) and out of scope
Core guarantees: stored strict value has exactly `decimal_scale` fractional digits, never more. A UoM with a smaller scale (kg 3, pcs 0 on one scale-3 field) is enforced by the module's write handler through public `Decimals.parse/3`, refusing in its own handler error. Out of scope: definition-level "scale depends on field X", conversion factors, per-item rounding (0057 D4 half-up is posting logic), SPA/mobile strict-field input widgets, a default flip of non-strict fields (a SEPARATE future decision), backfill of legacy numbers.
